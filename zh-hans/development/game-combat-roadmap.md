# Game Mode 战斗开发路线图

本文记录[混合地形 #6265](https://github.com/Pasta-Devs/Marinara-Engine/issues/6265)及后续战斗工作的约定方向，区分计划行为与当前游戏。实现从 `staging` 开始；这不表示以下所有能力都已发布。

## 分离参与方式与战场规则

目前 `combatStyle` 的值为 `classic` 和 `tactical`，应保留这些值。未来的召唤属于单独的参与设置，对旧配置和存档默认采用队伍战斗。创建预设可以同时设置这两个值，无需引入另一个持久化模式枚举：

| 预设 | 参与方式 | 战场 |
| --- | --- | --- |
| 队伍 | 玩家和同伴 | Classic 菜单 |
| 召唤（计划中） | 受控生物；训练师不参战 | Classic 菜单 |
| 战术 | 玩家和同伴 | Tactical 网格 |
| 战术召唤（后续） | 受控生物；训练师不参战 | Tactical 网格 |

不要开放尚未完成的组合。叙事同伴与战斗单位不同；队伍数组中第一个成员的位置不应成为控制者身份的永久约定。

## 当前实现重点：混合地形

GM 提供基于场景的小型结构化简述。引擎使用种子确定精确地形与初始位置，验证棋盘并保存结果。之后 GM 描述已接受的战场。常规移动和攻击不需要调用模型。

扩展现有环境与阵形处理流程，加入可选地图尺寸、场景地标、玩家地形指引和可复用种子。保持旧配置有效。保存接受的网格及生成来源，避免未来生成器变化重绘已有战斗。保存的种子能在简述和参战者相同时复现生成，但不能让任意模型输出变得确定。

可以修复生成地形以保证连通性，但不能让作者约束悄悄消失。限制模型输出、格子数量、单位数量和要素尺寸。对于无法满足约束的布局，应拒绝并给出可采取行动的原因，明确提供生成地形的替代方案。完整绘制与放置编辑器以及任意自制地图属于后续工作，必须遵循相同验证规则。

### 移动能力

步行、飞行和传送需要明确语义。飞行与传送可以跨越墙壁、水域和山地，绕过森林的额外移动消耗。地形防御与闪避加成独立于移动模式。

旧遭遇未填写移动模式时默认为步行。明确填写但不受支持的移动模式应报错拒绝，不能悄悄把请求的能力改成步行。该验证约定适用于生成蓝图和战术 API 输入。

分开处理途中通行、合法目的地和占用状态。能传送穿墙不代表允许停在实体地形内部。初始平面网格无法表示高度、天花板、法术特有视线条件或有限飞行时长；应记录这些限制，而非声称实现了完整桌面移动规则。预览、结算、路径动画和敌方 AI 应复用同一套移动合法性判定。

## 桌面规则：内置规则配置与 GM 参考工具

优先支持类似 5e 和 V20 的玩法，而非完整的生物收集游戏。后续再加入范围明确、有版本管理的规则配置。在将某个配置称为某套规则的实现前，先确定准确版本和支持子集。

引擎应负责实际掷骰、合法目标、移动、行动额度、资源消耗和数值结果。GM 负责解释故事、选择适用且受支持的操作、提供 NPC 意图并叙述真实结果。检索的世界书文本可以提供参考资料和战役规则，但不能绕过结算器或改写骰子结果。

[问题 #5955](https://github.com/Pasta-Devs/Marinara-Engine/issues/5955)涵盖世界书语义检索和可选择启用的工具路径。检索起补充作用：帮助 GM 找到相关信息，而明确的规则配置让常用机制一致且可测试。避免每次常规掷骰都单独查询。

从支持的检定、回合和资源基本操作开始。面向 d20 的配置与面向 d10 骰池的配置需要不同的结算规则，不能只是互相改名。未来应覆盖先攻、对抗检定、伤害及减伤、状态和资源使用。记录未支持的情况，并明确 GM 的裁定。

战术桌面玩法还需要共享的视线与掩体规则。当前网格阻止穿墙移动，但依据距离选择目标的远程攻击可以穿墙。结算器、AI、反击、预测和威胁叠层应一起更新。保留当前队伍与敌方阶段系统；个人先攻应是另一个可选规则配置。

## 召唤：保留设计，推迟大型系统

第一阶段可以很小：每方一只上场生物、拥有的替补、不参战的训练师、消耗命令的主动换位，以及生物失去战斗能力后可保存的替换暂停。没有可部署生物时判负。训练师道具不能给生物增加额外行动。

维护一个以稳定 ID 索引的名单，以及上场位置的 ID。根据名单推导替补和失去战斗能力状态，不维护相互竞争的数组。拥有生物的 HP、资源和状态应持久保存，遭遇生成不能每场战斗都重新编造数值。明确规定替补状态的推进时机。

捕获、进化、繁殖、双打、临时召唤持续时间和战术召唤是独立扩展。GM 的回顾必须区分失去战斗能力的生物与受伤的训练师。

## 持久化与验证

战斗开始时固定实际生效的遭遇规则。新增可选字段必须兼容旧 Classic 和 Tactical 存档。设置导入、不可变的创建快照和摘要必须保留新选择。刷新、重启、带入下个会话、切换回复、分支和检查点恢复都需要明确的独立覆盖。

未来由服务器管理的战斗状态，应使用遭遇 ID、修订号和幂等行动 ID，将战斗与名单变更一并应用。适当复用现有写入队列。复用 `game_engine_state` 前，审查回合游戏和 Experience 的命名空间；它并不会自动成为安全的战斗存储。

每条新规则都添加最小可运行的 `*.regression.ts` 验证，包含被拒绝的行动和旧输入。浏览器验证须涵盖设置、真实战术行动、刷新、小屏幕、主题对比度、焦点与键盘操作，以及有帮助的错误状态。本地化和用户文档应与实现同步。

## 既有工作与贡献入口

`feat/game-mode-combat-expansion` 上[已关闭但未合并的 PR #4391](https://github.com/Pasta-Devs/Marinara-Engine/pull/4391)包含更广泛的战斗会话、战术动作、目标和首领扩展。它是有用的先例，不是当前 staging 行为。重新开展前先核实负责人和状态，不要把合并整个扩展作为地形工作的前提。

主要 Engine 文件包括 `packages/shared/src/features/tactical-combat/`、`packages/server/src/routes/encounter.routes.ts`、`packages/server/src/routes/game.routes.ts`、`packages/client/src/components/game/GameSetupWizard.tsx`、`GameSurface.tsx` 和 `TacticalCombatUI.tsx`。如果后续工作影响可下载智能体或 Experience 的定义，以及包自身的提示词，这些改动属于 Marinara-Agents。
