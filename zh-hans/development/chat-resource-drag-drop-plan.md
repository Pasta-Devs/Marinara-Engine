# 聊天资源拖放方案

## 状态

阶段 1 到阶段 4 已经在 `drag-me-baby-one-more-time` 上实现，并已合并进 `staging`。后续的工作（#7362）让角色库里的行不用拖动手柄也能拖动，让触屏用户可以用第二根手指点按，把兼容的资源叠成一摞，并在重新排序时显示插入间隙。

解析器的自动化覆盖已经生效。角色分配和用户角色替换也补上了桌面端 Playwright 覆盖，但当前开发容器里跑不起来，因为 Chromium 加载不了 `libnspr4.so`。这些浏览器用例必须交给 CI，或者交给装好 Playwright 系统依赖的环境去跑。

剩下的阶段开工之前，先照仓库的协作规则来：

1. 查一下有没有已经在做聊天资源拖放的 Issue、关联 Issue 的分支、草稿 PR 或项目看板条目。
2. 在这个 Issue 上明确归属，让别人看得见。
3. 开始实现时，对着 `staging` 开一个草稿 PR。

## 目标

让用户把右侧面板里受支持的资源直接拖进当前聊天，不用再绕进聊天设置。

中央区域有两个可能的落点：

- **聊天区：**改动当前聊天的持久化配置。
- **消息输入框：**给当前草稿加一个受支持的附件。

这两个地方不是通用的放置目标。只有被拖的东西在那里确实有一个当前支持的操作，落点才会出现。

## 产品规则

拖动只负责选定资源和落点。应用执行的操作，一律限于聊天数据模型和生成管线里已经有的那些。

- 只有一个有效的追加操作：立即应用，并提供撤销。
- 只有一个有效的替换操作：会替换掉已有值时先确认。
- 确实支持多个操作：弹一个小的选择器，里面只列这几个操作。
- 没有有效操作：不要激活任何目标。
- 资源已经应用过：不接受重复放置。
- 不做臆测式的单回合上下文，不做隐藏的提示词注入，不凭空生成提及，也不加装饰性小标签。

## 现有契约

现有的 `Chat` 和 `ChatMetadata` 契约支持下面这些持久化操作：

- 角色：更新 `Chat.characterIds`。
- 用户角色：更新 `Chat.personaId`。
- 提示词预设：更新 `Chat.promptPresetId`。
- 连接：更新 `Chat.connectionId`。
- 世界书：更新 `ChatMetadata.activeLorebookIds`。
- 智能体：更新 `ChatMetadata.activeAgentIds`，用户同意的话还会更新 `ChatMetadata.enableAgents`。
- 聊天背景：走 `BackgroundPicker` 用的那条分配路径，更新现有的聊天背景元数据。

现有的消息输入框支持文件附件，但目前还不支持以消息为作用域的角色、世界书、智能体、用户角色、预设或连接引用。

## 支持的操作矩阵

能力解析器还必须落实当前聊天模式的限制和资源可用性。下表描述的是现有界面在当前模式下已经允许这个操作时的行为。

| 资源 | 聊天区 | 消息输入框 | 放下时的行为 |
| --- | --- | --- | --- |
| 角色 | 把 ID 加进 `characterIds` | 无 | 立即添加；toast 提示里带撤销 |
| 世界书 | 把 ID 加进 `activeLorebookIds` | 无 | 立即添加；toast 提示里带撤销 |
| 智能体 | 把 ID 加进 `activeAgentIds` | 无 | 智能体已启用时立即添加；否则先确认要启用智能体并添加它 |
| 用户角色 | 设置 `personaId` | 无 | 原来是空的就立即设置；要替换掉另一个用户角色时先确认 |
| 提示词预设 | 设置 `promptPresetId` | 无 | 遵守模式限制；原来是空的就立即设置；要替换掉另一个预设时先确认 |
| 连接 | 设置 `connectionId` | 无 | 要改动当前连接时先确认，并写出新旧两个连接的名称 |
| 聊天背景 | 设置现有的聊天背景元数据 | 无 | 沿用当前背景分配的语义；只有现有流程要求时才确认替换 |
| 图片或受支持的文件 | 无 | 加进草稿附件 | 复用现有的附件校验和准备管线 |
| 角色、世界书、智能体的文件夹 | 无 | 无 | 没有目标 |
| 设置控件 | 无 | 无 | 没有目标 |
| 正则脚本 | 无 | 无 | 在有以聊天为作用域的分配契约之前，没有目标 |
| 自定义函数或工具 | 无 | 无 | 在有以聊天为作用域的分配契约之前，没有目标 |
| 扩展贡献项 | 默认无 | 默认无 | 只能通过将来的类型化贡献 API 主动开启 |

### 模式规则

不要在拖动处理逻辑里重复一遍模式策略。放置能力解析器应当使用与现有聊天创建/设置界面相同的谓词。

至少要做到：

- 提示词预设在 Conversation 模式下依然不可用，与 `PresetsPanel` 保持一致。
- 放置智能体的前提是这个智能体已安装、可用，并且在当前模式下有效。
- 角色、用户角色、世界书、连接和背景的操作，只在各自现有的分配控件可用的地方才提供。
- 没有活动 ID 的聊天不暴露任何资源放置目标。
- 除非现有的变更路径本来就会拦，否则流式输出或智能体处理不应挡住安全的元数据更新。替换确认必须在应用之前重新读一遍当前聊天状态。

## 交互设计

### 拖动开始

每一个受支持的面板行都写入一份带版本号的资源载荷：

```ts
type ChatResourceDragPayload = {
  version: 1;
  kind: "character" | "lorebook" | "agent" | "persona" | "preset" | "connection" | "background";
  ids: string[];
  label: string;
};
```

用一个自定义 MIME 类型，例如 `application/x-marinara-chat-resource`。迁移期间保留现有的文件夹 MIME 载荷，因为对同一次拖动来说，调整文件夹顺序仍然是另一种有效解读。

资源拖动的效果应当声明为 `copyMove`：

- 文件夹目标把这次拖动理解成移动。
- 聊天目标把这次拖动理解成复制或分配。

内部资源操作不要依赖 `text/plain`。它有歧义，而且目前装的只是裸 ID。

### 目标的可见性

静止状态下，放置提示是隐藏的。

识别得出的资源拖动进入中央区域时：

1. 解析并校验这份类型化载荷。
2. 对着最新的当前聊天解析出有效操作。
3. 只显示有效的落点。
4. 用针对具体操作的文字，例如 `Add Maris to this chat`，不要用笼统的 `Drop here`。
5. 无效区域保持原样，不接受放置。

拖动受支持的文件时，只有消息输入框高亮。拖动角色、世界书、智能体、用户角色、预设、连接或背景时，首个版本里只有聊天区高亮。

### 放到聊天区

有效的放置区域就是当前的聊天区，与消息记录滚动到哪里无关。放在一条旧消息上面，不会插入历史，也不会追溯性地改动上下文。

放下时：

1. 重新读取当前聊天的 ID 和聊天数据。
2. 重新解析一次能力，避免出现过期或重复的操作。
3. 属于追加且没有歧义时，立即应用。
4. 遇到替换或需要启用智能体时，弹一个聚焦的确认框。
5. 成功后用本地化的 toast 提示反馈，并附上撤销操作。
6. 变更失败也要反馈，但不要改动消息记录。

不要为了记录配置改动去创建 user、assistant、narrator 或 system 消息。消息模型里没有专门的活动事件类型，配置事件也绝不能进入模型看得见的历史。

### 放到消息输入框

`ChatInput` 和 `ConversationInput` 里现有的文件行为都要保留：

- 校验受支持的类型和 20 MB 的体积上限。
- 图片走 `prepareImageAttachment` 做准备。
- 受支持的文本和 PDF 文件走现有的附件路径读取。
- 保留按聊天分开保存待发附件草稿的行为。

把消息输入框的拖动检测收紧，别让内部资源拖动点亮文件放置高亮之后什么都不做。

### 确认

只有操作会带来实际后果时才确认：

- 替换掉一个活动的用户角色。
- 替换掉一个活动的提示词预设。
- 切换一个活动的连接。
- 添加智能体的同时需要启用智能体。
- 现有背景分配路径里本来就要求做选择或确认替换的情况。

有相应的值时，确认框必须写清当前值和将要设成的值。里面不许夹带无关操作，比如新开一个聊天、单次调用某个智能体，或者在消息里引用这个资源。

### 撤销

撤销恢复的是放下之前那个一模一样的值，不是重新拼出来的猜测值。

- 角色：恢复此前完整的 `characterIds` 数组。
- 世界书：恢复此前完整的 `activeLorebookIds` 数组。
- 智能体：`activeAgentIds` 和 `enableAgents` 都要恢复。
- 用户角色、预设、连接和背景：恢复此前的值。

执行撤销之前，先确认当前聊天里还是那次放置产生的值。如果这中间另有改动动过同一个字段，就不要覆盖它，直接把这个过期的撤销收掉，并告知聊天已经变了。

## 架构

### 共享的客户端工具模块

新增一个职责单一的客户端模块，暂定 `packages/client/src/lib/chat-resource-drag.ts`，里面包含：

- MIME 常量。
- 载荷类型和运行时解析器。
- `writeChatResourceDragPayload(dataTransfer, payload)`。
- 文件拖动的检测。
- 资源类型的类型守卫。

首个版本里这份载荷只留在客户端本地，因为它属于浏览器交互状态，不是 API 契约。

### 能力解析器

新增一个纯函数解析器，暂定 `packages/client/src/lib/chat-resource-drop-capabilities.ts`：

```ts
type ChatResourceDropAction =
  | { type: "add-characters"; ids: string[] }
  | { type: "add-lorebooks"; ids: string[] }
  | { type: "add-agents"; ids: string[]; mustEnableAgents: boolean }
  | { type: "set-persona"; id: string; replacesId: string | null }
  | { type: "set-preset"; id: string; replacesId: string | null }
  | { type: "set-connection"; id: string; replacesId: string | null }
  | { type: "set-background"; id: string };
```

输入包括解析好的资源载荷、当前聊天、归一化后的元数据、当前模式，以及可用的资源 ID。输出要么是一个具体操作，要么是 `null`。

解析器负责这些事：

- 抑制重复。
- 模式限制。
- 多 ID 过滤。
- 已安装、可用与否的检查。
- 替换检测。
- 挑选面向用户的操作文案键。

解析器不执行变更，也不渲染界面。

### 变更协调器

在聊天区附近加一个 hook，暂定 `use-chat-resource-drop.ts`，它负责：

- 在放下的那一刻从 React Query 或 Zustand 里读取最新的当前聊天。
- 顶层聊天字段调用 `useUpdateChat`。
- 世界书和智能体调用 `useUpdateChatMetadata`。
- 复用现有的背景分配变更路径。
- 用现有的 app-dialog 辅助函数打开本地化的确认框。
- 生成成功和失败的 toast 提示，以及带保护的撤销操作。

不要把异步的变更逻辑塞进 Zustand store。

### 拖放浮层

在共用的中央聊天边界上加一个纯展示组件，而不是在每份消息记录里各写一套：

- 接收当前的拖动载荷和解析出来的操作。
- 盖住聊天区，但不挡住消息输入框。
- 用 `dragenter` 和 `dragleave` 的层级计数，避免鼠标经过子元素时闪烁。
- 显示图标、资源名称和本地化的操作文字。
- 适配不同指针类型和主题。

Conversation 和 Roleplay/Game 的界面都应当走同一个协调器。各界面自己的包装组件可以提供几何布局，但绝不能把能力策略再实现一遍。

### 面板接入

可拖动的行分批迁移：

1. 角色。
2. 世界书。
3. 智能体。
4. 用户角色。
5. 预设。
6. 连接。
7. 背景，前提是现有的分配契约能干净地复用。

每一行都保留原有的文件夹拖动载荷，再加上聊天资源载荷。文件夹移动的行为不要改。

## 交付阶段

### 阶段 1：拖动契约与中央浮层

- 加上类型化载荷的工具模块和解析器。
- 加上面向角色、世界书和智能体的纯函数能力解析器。
- 加上中央聊天区浮层和变更协调器。
- 接入 Character、Lorebook 和 Agent 面板的行。
- 加上操作、确认、成功、失败、重复和撤销的本地化文案。
- 确保内部资源拖动不会触发消息输入框的文件高亮。

这个阶段验证的是这个功能最主要的那条追加工作流。

### 阶段 2：可替换的资源

- 加上 Persona、Preset 和 Connection 的载荷。
- 加上替换检测和本地化的确认窗口。
- 复用现有的模式限制和变更 hook。
- 给替换操作加上带保护的撤销。

### 阶段 3：背景分配

- 确认现有的背景选择器流程能不能在不重复实现策略的前提下接收放下来的背景 ID。
- 只有能复用同一套以聊天为作用域的分配行为时，才加入背景拖动。
- 否则背景就先不支持，并把阻塞点记录到 Issue 或 PR 里。

### 阶段 4：触屏与非拖动方式的对等

桌面端的 HTML 拖放是第一条实现路线。移动端绝不能依赖跨面板的精确拖动。

- 在每一个受支持的行原有的操作入口里加上 `Add to active chat`。
- 能力解析器、确认框、变更和撤销行为全部复用同一套。
- 如果保留触屏拖动，就用现有的触屏拖动手柄，并用 `elementFromPoint` 解析中央目标。
- 不要给文件夹的长按行为叠太多含义，那会让整理操作变得不可靠。

移动端上这个功能能不能算做完，取决于这个阶段。

## 无障碍与输入要求

- 不要只靠颜色区分，同时显示资源图标和操作文字。
- 非拖动的等价入口不能非得靠悬停才发现得了。
- 确认框可以用键盘操作，关闭后焦点回到原处。
- 按 Escape 取消尚未完成的确认。
- 出现有效放置目标时，以及操作成功或失败时，屏幕阅读器都会收到一句简短播报。
- 没有识别得出的拖动正在进行时，拖动浮层绝不能拦截正常滚动。
- 触控目标沿用现有的移动端最小尺寸。
- 开启减少动态效果的用户看到的是不透明度和状态的变化，没有多余的位移。

## 本地化

所有新增的可见文案都用语义化的本地化键。只更新英文标准目录，社区语言可以回退到英文。

文案分为这几类：

- 每种资源类型的操作标签。
- 替换确认。
- 启用智能体的确认。
- 成功和失败的 toast 提示。
- 撤销和过期撤销的提示消息。
- 无障碍播报。
- 需要显示时，重复或已激活的反馈。
- 非拖动的 `Add to active chat` 操作。

## 测试

不要把临时的 `.test.ts` 文件留在仓库里。

### 纯函数回归覆盖

给能力解析器补的长期覆盖，只能放在现有受支持的回归测试位置、按现有格式来：

- 角色不在 -> 添加操作。
- 角色已在 -> 没有操作。
- 多角色混合载荷 -> 只添加缺失且有效的 ID。
- 世界书不在 -> 添加操作。
- 世界书已激活 -> 没有操作。
- 智能体不在、智能体功能已启用 -> 添加操作。
- 智能体不在、智能体功能已禁用 -> 添加操作，但需要先启用。
- 智能体不可用 -> 没有操作。
- 当前没有用户角色 -> 非替换的设置操作。
- 用户角色要替换掉另一个 -> 替换操作。
- 预设处在不支持的模式 -> 没有操作。
- 连接与当前连接相同 -> 没有操作。
- 版本无效、类型未知、ID 格式错误、载荷过大 -> 拒绝。

### 浏览器冒烟覆盖

在可行的地方扩展 `pnpm smoke:ui`：

- 把一个角色从面板拖到聊天区，确认分配成功。
- 执行撤销，确认恢复到之前的角色列表。
- 确认角色拖过消息输入框时不会出现文件放置反馈。
- 把一个受支持的文件拖到消息输入框上，确认附件行为没有被破坏。
- 确认已经激活的资源没有可用的放置落点。
- 确认取消替换确认框之后不会产生任何变更。
- 确认替换之后聊天确实被更新。
- 确认文件夹拖放仍然能在面板内移动资源。

### 手动验证

在桌面端支持这个功能的 Conversation、Roleplay 和 Game 模式下验证：

- 深色和浅色主题。
- 右侧面板打开，且消息记录很长、已经滚动过。
- 追加式放置、重复放置、替换、取消、失败、撤销和过期撤销。
- 拖动经过消息记录里层层嵌套的元素时，浮层不闪。
- 面板里原有的文件夹移动。
- 两个消息输入框里原有的文件和图片放置。

在移动端或粗指针视口下验证：

- 非拖动的 `Add to active chat` 是否对等。
- 现有的文件夹触屏拖动依然好用。
- 确认框放得下，也关得掉。
- 文字和控件没有重叠。

必须执行的命令：

```bash
pnpm localization:check
pnpm check
pnpm regression:prompt
pnpm smoke:ui
```

合并之前必须跑 `pnpm regression:prompt`：`LorebooksPanel.tsx` 的改动影响世界书的激活，而世界书激活会喂给提示词组装。

## 风险与应对

### 与现有文件夹拖动冲突

风险：这些行本来就在用拖放把条目移进文件夹。

应对：保留现有的文件夹 MIME 类型，另加一个类型化的聊天资源 MIME 类型，各个目标只解读属于自己的载荷。同时验证 `copyMove` 的行为和文件夹相关的回归。

### 消息输入框误高亮

风险：目前消息输入框的 `dragover` 处理逻辑对任何拖动都有反应，包括内部资源 ID。

应对：只有 `DataTransfer.types` 或 `DataTransfer.items` 表明是文件，或者是另一种明确受支持的附件载荷时，才启动消息输入框的反馈。

### 聊天状态过期

风险：从开始拖动、放下、确认到撤销，这中间当前聊天或已分配的资源都可能发生变化。

应对：放下时对着当前状态解析一次，变更和撤销之前再解析一次。还要防住撤销覆盖更新的改动。

### 模式策略走样

风险：拖放可能放行创建/设置界面本来禁止的分配。

应对：从现有的分配流程里抽出或复用共享谓词。不要在面板组件里硬编码第二套策略矩阵。

### 行为暗中膨胀

风险：消息输入框在视觉上接受了资源，会让人以为有单回合上下文，而服务器根本不认这回事。

应对：在单独设计出以消息为作用域的上下文契约之前，把资源放到消息输入框这条路一直关着。

### 一次放下大量选中项

风险：选择模式下的拖动可能一口气加进出乎意料的一大批角色、世界书或智能体。

应对：过滤掉无效和已激活的 ID，遵守服务器或模式已有的上限，多项放置越过现有阈值时要求确认。不要凭空发明一个新的上限。

## 明确的非目标

- 把资源放到某条历史消息上。
- 追溯性地改动提示词历史。
- 把配置改动写成消息记录里的消息。
- 单回合的角色、世界书、用户角色、预设、连接或智能体。
- 靠放到消息输入框上来调用智能体。
- 从中央区域的放置动作新开一个聊天。
- 把任意设置项拖进聊天。
- 首个版本里提供通用的插件放置 API。
- 从一个聊天的消息记录拖到另一个聊天。

## 验收标准

阶段 1 满足下面这些条件才算通过：

- 角色、世界书或智能体可以从右侧面板的行拖到有效的当前聊天区上。
- 更新的是正确的那个现有聊天字段，同时没有产生消息记录里的消息。
- 已经激活的资源和不可用的资源都不被接受。
- 智能体功能处于禁用状态时添加智能体，必须明确确认。
- 每一次成功的变更都提供带保护的撤销。
- 资源拖动不会触发消息输入框的附件反馈。
- 两个消息输入框里原有的文件附件放置依然可用。
- 现有的文件夹拖放行为没有变化。
- 所有新增的可见文案都做了本地化。
- 桌面端和移动端的操作是对等的，哪怕移动端用的是菜单操作而不是跨面板拖动。
- `pnpm localization:check`、`pnpm check` 以及相关的界面冒烟测试全部通过。

整个功能要等阶段 2 的可替换资源和必需的移动端对等也做完，才算通过。背景分配一直是可选项，直到阶段 3 确认它现有的语义能在不重复实现策略的前提下复用。

## 推迟的扩展

将来如果做以消息为作用域的上下文功能，角色、世界书、智能体、用户角色、预设或连接也许就能合法地放进消息输入框。那份工作需要一份单独的 shared/服务器契约，把持久化、提示词组装、Token 预算、服务商路由、显示、草稿恢复和消息历史的语义都定下来。它绝不能以纯客户端小标签的形式偷偷混进这个功能里。
