# Наборы правил Game Mode и листы персонажей: передача реализации

Статус: в работе. Написано 18 сентября 2026 года для `staging` на коммите `459f8b85` (v2.4.6). Реализованы этап 1 (общая схема, привязка, реестр и Capability API 1.20), этап 2 (вычислитель `dice-sum`, `who=` и замена напоминания Game Master), этап 3 (листы в карточках и персонах), этап 4 (выбор Rules, привязка при создании, копирование при настройке и обмен настройками), этап 5 (лист в игре, текущее состояние и команда `[sheet:]`), этап 7a (пути для сообщества), этап 8a (формат каталогов, маршрут и Capability API 1.21), мост к бою (блок `battle`, общие вспомогательные функции и Capability API 1.22), этап 8c (масштабируемые значения каталогов, команда `use`, Refresh from ruleset и Capability API 1.23), этап 7b (вид разрешения `dice-pool`, атрибуты тега `with=`, `threshold=` и `bonus=` и Capability API 1.24), слои L1 (варианты в собственном файле набора правил, переключатели слоев в мастере, слот `gm.worldGuidance` и Capability API 1.25), а также настоящий бой по набору правил C1 (блок `combat`, чистый вычислитель, дополнения механик и Capability API 1.26), C2 (бестиарии, действия существ и ограничение угрозы, Capability API 1.27), C3a (распорядитель боя, разрешающий сражение по собственному реестру состояния сервера), C3b (отображение такого сражения на экране в терминах набора правил), C4a (позиции, досягаемость и дальность, области, укрытия и атаки при выходе из зоны угрозы, Capability API 1.28), C4b (отображение сражения на поле боя) и C5a (возможности одного хода: вторая составляющая урона, несколько ударов за один лимит, способности, меняющие экономику действий, дополнительные эффекты, новые эффекты состояний и Capability API 1.29). Там, где предусмотрена клиентская часть, она тоже реализована; этапы после C5a пока остаются предложениями. Раздел "Решения по формату" объясняет отличия реализованного формата от первого черновика и их причины. Документ дополняет `game-combat-rulesets-implementation.md` (документ передачи реализации боя). При расхождениях раздел "Связь с документом передачи реализации боя" прямо отмечает их и запрашивает согласование, а не молча заменяет прежние решения.

Сопутствующий файл: [`ruleset-5e-2014.example.json`](ruleset-5e-2014.example.json), первая декларация набора правил, точное описание того, что означает "весь лист", и файл, который проверяет регрессионный тест этапа 1. Канонический источник формата – схема zod в `packages/shared/src/schemas/ruleset.schema.ts`.

## Зачем это нужно

Запрос функции поступил от автора [Marinara-RPG-Extension](https://github.com/Kenhito/Marinara-RPG-Extension), расширения с шестнадцатью настольными системами: проверки Game Mode ограничены d20 с модификаторами Engine, лист содержит шесть характеристик, а для другой системы сейчас нужны четыре или пять агентов на каждый ход для каждого набора правил. Автор предпочел бы встроенную поддержку. Его `docs/ENGINE-CONSTRAINTS.md` полезен как список требований; архитектура расширения не является целевой.

В собственную реализацию входит **5e с привязкой к SRD 5.1 (`5e-2014`)**. V20 и другие системы оставлены авторам сообщества через тот же формат данных (этап 7), поэтому формат не должен повторять устройство 5e.

## Контракт продукта

1. Набор правил выбирается при создании игры и закрепляется на весь срок ее существования. Он не зависит от Experience, представления боя, участия и контроллера.
2. Отсутствие привязки к набору правил означает `engine-legacy`: текущее поведение, байт в байт, включая промпты.
3. **Набор правил никогда не добавляет вызов модели.** Проверки используют существующие процессы бросков кубиков. Изменения листа передаются тегами в самом повествовании GM. Контекст промпта собирается из строк на основе листа и данных набора правил. Ни один набор правил не использует `api.registerTool` и не поставляет агента, запускаемого на каждом ходу.
4. Engine отвечает за броски, модификаторы, арифметику ресурсов и допустимость действий. GM выбирает предмет и сложность проверки и описывает фактический результат.
5. Лист в карточке персонажа или персоне – это **начальная сборка** персонажа для этого набора правил. Игра получает копию. Ничто в игре не записывает изменения обратно в библиотеку.
6. Набор правил объявляет область своей поддержки, а интерфейс показывает ее до начала игры. Пока для набора правил не существует адаптера из документа передачи реализации боя, его сражения используют бой `engine-legacy`, и интерфейс сообщает об этом простыми словами.

## Связь с документом передачи реализации боя

Документ передачи реализации боя говорит: "Начните с закрытого реестра встроенных чистых адаптеров TypeScript. Не добавляйте язык сценариев или произвольные исполняемые пакеты правил".

Предлагаемая трактовка. На ней построен этап 1, а в issue мейнтейнера просят согласовать ее и расширенный `RulesetRef`:

- **Закрытый реестр** – это набор _видов разрешения_ и _операций вычисления производных значений_ в TypeScript-коде Engine. Добавление вида требует PR в Engine с регрессионными тестами.
- **Декларация набора правил** – это проверенные данные, задающие параметры вида и описывающие лист. В ней нет строк с выражениями, она никогда не исполняется и не содержит кода пакета.
- **Боевые адаптеры остаются TypeScript-кодом Engine**, с ключом по той же ID набора правил, в точности как описывает документ передачи реализации боя. Данные не могут разумно выразить порядок объявления действий, экономику действий или окна реакций, и этот документ не пытается этого сделать.
- Оба документа используют один `RulesetRef`. Этот документ закрепляет его за игрой; документ передачи реализации боя сохраняет его снимок в каждой встрече.

Так базовая поставка остается свободной от необязательного содержимого правил, что соответствует цели пакетов агентов, без открытия пути для исполняемого кода.

**Мост к бою и эта граница.** Мост (§ Что определил мост к бою) находится внутри этой трактовки, а не рядом с ней. Он не добавляет разрешения действий: он в обе стороны переносит числа через границу между листом и существующей боевой моделью Engine для набора правил, который подключает его блоком `battle`. Он не применяет броски атаки, спасброски или концентрацию и не меняет арифметику урона, поэтому не заявляет о реализации боя какой-либо системы. Он универсален и с первого дня обслуживает систему сообщества на 2d6, а не только 5e. Для каждого набора правил также явно предусмотрена его замена: как только появляется настоящий боевой адаптер набора правил, тот получает управление сражением, а мост уступает ему место. В PR мейнтейнера просят согласовать это, поскольку ближайшая граница установлена документом передачи реализации боя, а не этим документом.

## Решения по формату

Формат должен поддерживать еще не написанные наборы правил, многие из которых будут созданы ИИ-агентом, читающим файл 5e как пример. Все, что понадобилось файлу 5e, оформлено как именованный универсальный примитив, чтобы автор никогда не заключал, что что-то "можно сделать только способом 5e".

- **Особых ID нет.** Engine никогда не ищет `level`, `dex`, `slots` или `hp`. Бонус мастерства берется из значения, на которое ссылается `resolution.proficiency.bonus`; его можно не задавать, и тогда уровни используют бонус `flat`. Таблицы уровней – обычное производное значение `stepTable`, читающее обычное поле.
- **Кубики задаются параметром** `dice-sum` (`{ count, sides }`), а натуральные результаты запрещены, если набор правил бросает не один кубик.
- **Модификаторы характеристик – закрытые операции**: `floorHalfMinusTen`, `identity` (значение и есть модификатор) или `stepTable`.
- **Спасброски – список, как и навыки**, а не "по одному на характеристику", поэтому можно выразить систему с тремя спасбросками. У навыков и спасбросков может не быть характеристики.
- **Каждый навык и спасбросок может иметь произвольный числовой бонус** в листе (`bonuses`), что покрывает системы с рангами и бонусы предметов без нового примитива.
- **Пассивные значения не являются операцией.** Это `sum` над `{ "const": 10 }` и `{ "skillMod": "perception" }`.
- **Список, строки которого являются ресурсами, объявляет `pools`** (столбцы имени, максимума и необязательной перезарядки), а отдых восстанавливает их через `listPools` с фильтром по `recharge`. Ничто не знает слово "counters".
- **Величины восстановления при отдыхе имеют закрытые формы**: `to` (`"max"`, `"min"` или число) либо `by` (константа или доля максимума с округлением и нижней границей). Правило 5e "половина кубиков здоровья, но не меньше одного" – это `{ "fractionOfMax": 0.5, "round": "down", "min": 1 }`.
- **Запасы могут начинаться пустыми** (`start: "empty"`) для стресса, порчи и подобных растущих шкал.
- **`gm.sheetSummary`** задает поля, производные значения и списки, отображаемые в компактном блоке промпта, поэтому Engine не фиксирует в коде "AC, пассивное Восприятие, подготовленные заклинания".
- **`$comment` разрешен в любом объекте**, а `$schema` – в корне; оба удаляются до проверки. Всё остальное строго: набор правил, который Engine понимает лишь частично, незаметно изменил бы арифметику игры, поэтому неизвестный ключ отклоняет весь файл. В отказе перечисляются строки `path: message`, по которым автор может исправить ошибки.
- **Раздел объявляется до того, как элемент ссылается на него**, поэтому у каждой группы в редакторе есть подпись.
- **Производные значения читают только значения, объявленные выше**, что делает циклы невыразимыми. Значение, питающее бонус мастерства, и всё выше него не могут читать модификатор навыка или спасброска.
- **Каждая подпись и строка указаний соблюдают гигиену промптов gm-verbs**: одна строка, без управляющих символов, квадратных скобок и скобок макросов.
- **Пакет объявляет вид `ruleset`**, не требует разрешений или точки входа и должен объявить Capability API 1.20, если перечисляет `ruleset.json`.

## Что определил этап 2

- **Вычислитель стоит за существующим контекстом.** В `SkillCheckModifierContext` добавляется необязательный `ruleset`. Все вызывающие стороны уже проходят через `resolveSkillCheckWithContext`, поэтому конечная точка, постобработка генерации, броски в одном запросе и видимый пул достигают набора правил без новых точек вызова.
- **Теги, выглядящие завершенными, сверяются с листом.** В `engine-legacy` полный тег с аккуратной арифметикой принимается как есть: для него не загружается контекст, он не сверяется ни с каким листом и не перебрасывается. В игре с набором правил маршрут генерации передает признак `rulesetPinned`, контекст загружается и для таких тегов, а модификатор, число кубиков или натуральный результат, которых набор правил не мог бы дать, возвращают тег на бросок. Признак нужен, чтобы прежняя игра по-прежнему никогда не загружала контекст для готового тега.
- **Привязка, которую установка не может выполнить, приводит к безопасному отказу.** Загрузка контекста выбрасывает исключение, а существующий путь ошибки обработчика тегов сохраняет проверки незавершенными, всё еще требующими броска.
- **`who=` передается вместе с результатом.** `SkillCheckResult.who` задается только вычислителем набора правил и записывается сериализатором, поэтому прежние записи сохраняют свои байты.
- **Посторонний бросает кубики без модификаторов.** `who=`, не соответствующий ни одной карточке отряда или общий для двух карточек, не получает модификатора вообще, поскольку значения набора правил по умолчанию нейтральны не в каждой системе. Участник отряда (или игрок) без листа бросает на основе пустой стандартной сборки набора правил, которую настройка копирует для него. Неизвестное набору правил имя навыка тоже ничего не добавляет. Возврата к угаданной характеристике нет. Собственная карточка игрока сохраняет приоритет при совпадении имени с участником отряда.
- **Внедренный d20 и заранее брошенный игроком d20 учитываются только там, где набор правил бросает один d20.** Остальные кубики берутся из честного генератора Engine.
- **Ограничение сложности конечной точки остается 40** (помечено `ponytail:`); постобработка генерации поддерживает более широкую шкалу.
- **Блок листа и команда листа относятся к этапу 5**, вместе с текущим состоянием. Этап 2 заменяет только строки проверок в напоминании и убирает строку, обучающую другим обозначениям кубиков, поскольку в игре с набором правил действует одна система правил.

## Что определил этап 3

- **На границе хранения проверяются ограничения, но не структура.** `rulesetSheets` объявлен в схемах расширений персонажа и характеристик персоны как словарь: ключи должны быть ID наборов правил, значения – объектами размером не более 64 КБ, всего не более 32. Структура листа там не проверяется, поскольку набор правил может быть не установлен. Обновление, нарушающее ограничение, отклоняется с сообщением.
- **Импортеры ограничивают, а не отклоняют импорт.** `capImportedRulesetSheets` убирает только тот лист, который не прошел бы границу, поэтому один плохой лист никогда не лишает импорт карточки. Функция работает в родном импортере персонажей, импортере SillyTavern и внутри `normalizePersonaStats`, который также является путем чтения персоны.
- **Редактор – один универсальный компонент** (`RulesetSheetEditor`), построенный из декларации и размещенный через `RulesetSheetsSection` в обеих вкладках **Stats** (характеристики). Установленные наборы правил берутся из `GET /api/capability-packages/rulesets` под ключами запросов пакетов возможностей, поэтому установка или удаление обновляет список.
- **Значения ограничиваются при редактировании, никогда при чтении**, а сохраненный уровень мастерства, которого набор правил больше не предлагает, всё еще отображается как есть.
- **Ничто не считается неактивным, пока не загружен список установленного**, поэтому медленный запрос не показывает рабочий лист как отсутствующий.

## Что определил этап 4

- **Сервер формирует привязку.** Мастер отправляет `ruleset` в `GameSetupConfig`, но доверяет только его `id`: `POST /game/create` заново создает `RulesetRef` из собственного реестра и записывает его в `gameSetupConfig.ruleset` и `chat.metadata.gameRuleset`. Неустановленный набор правил отклоняется с `ruleset_not_installed`, а не подменяется другими правилами.
- **Игра без набора правил не получает ключа.** `gameRuleset` записывается только при выборе набора правил, поэтому прежние метаданные сохраняют свои байты.
- **Копирование при настройке находится в одном месте.** `applyGameSetupPayload` самостоятельно загружает сохраненные листы отряда и персоны, поэтому обе точки настройки (`/game/setup` и `/game/setup/apply-json`) копируют одинаково. Карточки сопоставляются по нормализованному имени, как уже происходит с `rpgStats`, а персона имеет приоритет при совпадении имени с участником отряда. Участник без сохраненного листа получает пустую стандартную сборку.
- **Обмен настройками следует правилу Experience.** Общий набор правил восстанавливается для новой игры, если в этой установке есть указанная версия или более новая, и отбрасывается иначе; тогда мастер называет отсутствующий набор правил по подписи `rulesetName` из файла. Привязка внутри общего файла – недоверенные входные данные и читается через `rulesetRefSchema`.
- **Блок Rules – отдельный компонент** (`GameSetupRulesChooser`), расположенный рядом с Combat Preference и отображаемый только для новой игры при наличии хотя бы одного установленного набора правил.

## Что определил этап 5

- **Текущее состояние хранится в отдельном столбце снимка.** `game_state_snapshots.ruleset_live` содержит `RulesetLiveStates` с ключами по нормализованному имени карточки. Новый столбец в файловом хранилище не требует повышения `STORAGE_VERSION`: старая строка читает столбец как null, а null означает стандартные значения всех запасов. Это не ключ внутри `playerStats`, поскольку несколько трекеров пересоздают этот объект из известных им полей.
- **Текущее состояние разреженное.** Сохраняются только явно заданные значения; вернувшееся к стандарту значение снова удаляется. Поэтому нетронутый "полный" запас следует за своим максимумом, когда повышение уровня увеличивает его, а у персонажа без потраченных ресурсов записи вообще нет.
- **Ход считается относительно состояния на его начало.** Команды `[sheet:]` применяются после каждого переписывания ответа и до сохранения, поверх текущего состояния строки, предшествующей ходу (для продолжения – строки, уже принадлежащей продолжаемому сообщению). Перегенерированный ход получает базу из предыдущих сообщений, поэтому не может потратить ресурс дважды, а каждый свайп сохраняет состояние на свой конец.
- **Каждый сохраненный ход игры с набором правил записывает свою строку**, с изменениями или без, чтобы у следующего хода, свайпа и новой сессии всегда была исходная строка. Трекер, позже пересоздающий то же сообщение и свайп, сохраняет текущее состояние: `create` переносит его из заменяемой строки, если вызывающая сторона не передала свое.
- **Команда принадлежит Engine, имена – набору правил.** Грамматика (`spend`, `restore`, `damage`, `temp`, `track`, `condition`, `note`, `rest`, причем `heal` читается как `restore`) одинакова для всех наборов правил. `concentrate` из первого предложения стал общим `note`, поскольку "концентрация" – термин одной системы. Имена запасов, шкал, состояний, заметок и отдыха берутся из набора правил и сопоставляются по ID или подписи.
- **Сохраненный ответ служит записью результата.** Каждая команда переписывается на месте с `result="ok" now="…"` или `result="refused" reason="…"`. Результат, написанный самой моделью, игнорируется. Отклоненная команда ничего не меняет и записывается в журнал; клиент сообщает об этом один раз за ход.
- **Листы попадают к Game Master ближе к концу промпта.** Блоки листов и строки команд входят в напоминание о формате каждого хода, а не в системный промпт: текущее состояние меняется каждый ход, а провайдер кеширует именно системный промпт. Без набора правил напоминание побайтно совпадает с прежним.
- **Игрок редактирует через те же правила.** Лист в игре применяет `applyRulesetSheetOp` для каждой кнопки и сохраняет через `PATCH /chats/:id/game-state`, который ограничивает текущее состояние (`rulesetLiveStatesSchema`) и больше ничего не оценивает: это собственная игра пользователя.
- **`sheet` зарезервирован.** Глагол пакета с таким именем отклоняется, а проверка имен глаголов находит обучаемый тег в напоминании.
- **Здесь не сделано:** собственные ходы участников отряда (`/party-turn`) не применяют команды листа; это делает только ответ Game Master.

## Что определил этап 7a

- **Хранение.** Наборы правил сообщества находятся в новой файловой таблице `game_rulesets`: одна строка на ID с пространством имен и версию, с точным импортированным текстом и его sha256. Формат хранения не повышается. У таблицы нет владельца и каскадного удаления: удаление репозитория, поставившего набор правил, лишь очищает `repositoryId`.
- **ID.** Файл всегда содержит собственную ID без пространства имен. Engine сохраняет его как `local/<id>` для выбранного файла и `<owner>/<id>` (владелец GitHub в нижнем регистре) для репозитория, а реестр переписывает `definition.id` на ID с пространством имен, поэтому листы, привязки и мастер используют ее как ключ. Аккаунт GitHub с именем `local` отклоняется, чтобы никто не мог размещать наборы правил среди собственных наборов пользователя.
- **Версии.** Сохраненная версия никогда не переписывается. Те же байты ничего не меняют; другие байты под существующей версией отклоняются (`RulesetVersionConflictError`) с просьбой автору повысить версию. Привязка сообщества разрешает точно указанную версию (`version-missing`, если она отсутствует); официальные пакеты сохраняют правило "установленная версия не старее закрепленной".
- **Ограничение доступа.** Импорт отдельного файла требует привилегированного доступа и **Allow custom Agent imports**. Путь репозитория дополнительно сохраняет собственный флаг окружения. При выключенном импорте `/game/create` отклоняет набор правил сообщества (`ruleset_imports_disabled`), а мастер не показывает их, но разрешение никогда не проверяет политику, поэтому существующие игры продолжают работать. Удаление требует только привилегированного доступа и потому работает даже при выключенном импорте.
- **Удаление.** `DELETE /api/game-rulesets?rulesetId=` удаляет все сохраненные версии. Если игры привязаны к набору правил, он отвечает 409 `ruleset_in_use` с их количеством, а клиент повторно спрашивает перед повтором с `force=true`.
- **Проверка.** Флажков возможностей нет, поскольку у набора правил их нет. Проверка показывает идентификацию, лицензию, область поддержки, способ бросков и дословный текст Game Master и сообщает, что текст отправляется модели.
- **Путь репозитория.** `<top>/rulesets/*.json`, только непосредственные дочерние файлы, не более 32 файлов размером до `RULESET_MAX_BYTES`. Репозиторий может содержать агентов, наборы правил или и то и другое. Один непригодный файл становится строкой предпросмотра с причинами, а не ошибкой всего репозитория. Набор правил, отозванный в источнике, остается установленным.
- **Создание.** `docs/extending/writing-rulesets.md` начинается с ограничений. `docs/extending/ruleset.schema.json` генерируется из схемы zod командой `pnpm ruleset:schema`, а регрессионный тест падает, если схема устарела. Руководство содержит по примеру на каждый вид разрешения, и ни один не устроен вокруг d20: Ember Roads бросает 2d6, Gravewatch – пул десятигранных кубиков. Оба проверяются регрессионным тестом, который также проверяет наличие в опубликованной схеме элемента для каждого вида.

## Что определил этап 8a

- **Заголовок находится в наборе правил, записи могут быть отдельно.** В `ruleset.json` добавляется необязательный массив `catalogs` (не более 12). Каждый заголовок содержит `id`, `label`, списки листа, которые он заполняет через `feeds` (от 1 до 8), объявленные `filters`, необязательные `units` и ровно одно из `entries` (встроенные записи) или `asset`. Если набор правил не поставляет каталогов, ключ отсутствует, а не пуст, поэтому файл, написанный до появления каталогов, по-прежнему разбирается в те же байты.
- **Путь ресурса выводится, а не выбирается.** `asset` должен равняться `catalogs/<the catalog's id>.json`, поэтому маршрут находит файл только по набору правил, и ни один каталог не может назвать файл другого.
- **Одна функция определяет допустимое содержимое списка.** `rulesetListRowIssues(list, values)` экспортируется общим пакетом и служит единственным ответом на вопрос "можно ли сохранить эту строку": схема применяет ее к каждой встроенной записи, `parseRulesetCatalogFile` – к записям ресурса во время чтения, а клиент – еще раз к выбранным игроком строкам. Поэтому каталог не может записать то, что редактор затем отклонит. `rulesetCatalogEntryIssues(definition, catalog, entries)` – общая обертка, вызываемая обоими путями проверки.
- **Копирование при выборе, как при настройке.** `rowsFromCatalogEntry` возвращает строки с одним зарезервированным ключом `RULESET_CATALOG_ROW_KEY = "_catalog"`, содержащим `<catalogId>/<entryId>`. ID столбцов должны начинаться с буквы, поэтому конфликт невозможен. Строки являются копиями: игрок редактирует их, лист остается читаемым при удаленном наборе правил, а новая версия набора правил никогда не переписывает персонажа.
- **Ограничения.** 12 каталогов на набор правил, 8 списков назначения и 8 фильтров на каталог, 2 000 записей на каталог во встроенном виде или ресурсе, 6 строк на запись и `RULESET_CATALOG_MAX_BYTES = 1 MB` на ресурс, что сверяется с объявленным в манифесте `files[].bytes` до чтения файла.
- **Список остается небольшим.** `GET /api/capability-packages/rulesets` убирает встроенные `entries` и сообщает `entryCount`, поскольку список читается при каждом открытии редактора листа. Набор правил без каталогов перечисляется побайтно как прежде. `GET /api/capability-packages/rulesets/catalog?rulesetId=&catalogId=&version=` отдает один каталог: встроенные записи либо разобранный и проверенный ресурс. Привилегированного ограничения нет по той же причине, что и у `/rulesets`; маршрут зарегистрирован перед маршрутами `/:id/...`, чтобы ID пакета не мог его перекрыть. Неизвестный набор правил, версия или каталог дают 404 с кодом; ресурс, который Engine не будет читать, дает 422 со строками проблем для автора.
- **Capability API 1.21, две части.** Объявление ресурса `catalogs/<id>.json` требует 1.21 и соседнего `ruleset.json`. Каталоги также живут ВНУТРИ файла набора правил, чего манифест не показывает, поэтому установка читает проверенные байты и отклоняет ключ `catalogs` при более низкой объявленной версии. Неразбираемый набор правил не срывает установку: о нем по-прежнему сообщает реестр со строкой журнала.
- **`mechanics` проверяется и частично используется.** Необязательный блок (вид, дальность, область, цели, дружественный огонь, величина, тип урона, бросок атаки, спасбросок, стоимость, шаг на единицу стоимости, концентрация, реакция) – закрытый строгий словарь, поэтому опечатка обнаруживается сейчас, а не когда его наконец начнут читать. Этап 8a только проверял его и показывал одну компактную строку в окне выбора. Мост к бою использует вид, дальность, область, дружественный огонь, величину, тип урона, стоимость и реакцию (чтобы исключать записи реакций). Бросок атаки, спасбросок, концентрацию и шаг на единицу стоимости пока ничто не читает.
- **Известная граница: каталоги сообщества только встроенные.** Набор правил, импортированный одним файлом или полученный из репозитория GitHub, несет каталоги внутри одного файла, следовательно, внутри существующего ограничения 256 КБ. Отдельные файлы каталогов для наборов правил сообщества (`rulesets/<id>/catalogs/*.json`) намеренно исключены: путь репозитория читает только непосредственные дочерние файлы `rulesets/`, а путь отдельного файла по определению содержит один файл. Автор сообщества со списком, не помещающимся в 256 КБ, публикует пакет. Если это станет реальным ограничением, потребуется отдельный этап.
- **Доказательство – второй набор правил не на d20.** В `docs/examples/rulesets/ember-roads.json` появились список `knacks`, список `tricks` со строками-запасами и каталог, заполняющий оба: одна запись пишет две строки, другие несут `mechanics`. Ничто в формате не привязано к устройству 5e, а регрессионные тесты читают этот файл вместо файла 5e.

## Что определил мост к бою

- **Набор правил подключается явно; отсутствие блока ничего не меняет.** В `ruleset.json` добавляется необязательный блок `battle`: `health` (обязательный текущий запас очков здоровья), необязательный `energy` (запас, становящийся MP), необязательные `slots` (запасы с уровнем от 1 до 9) и необязательные `skills` (до восьми списков листа, каждый с необязательным логическим столбцом `onlyWhen` и необязательным исключением `alwaysWhen: { column, equals }`). Без блока бой побайтно остается прежним. Capability API 1.22 проверяется при установке как `catalogs`, поскольку блок находится внутри файла набора правил, а не манифеста.
- **Каждое имя указывает на объявленный текущий запас.** Список со строками-запасами не может быть очками здоровья: запас строки имеет ключ по имени строки и появляется или исчезает при редактировании листа. Здоровье и энергия различаются, запасы ячеек уникальны, уровни уникальны, списки существуют, `onlyWhen` является логическим столбцом, а `alwaysWhen.column` – столбцом того же списка.
- **Мост – три чистые общие функции** в `packages/shared/src/features/rulesets/combat-bridge.ts`: `seedCombatantFromSheet`, `combatSkillsFromSheet` и `sheetOpsFromCombatResult`, плюс `applyCombatResultToLive`, над одним преобразованием `carryHealthShare`, через которое здоровье проходит в обе стороны. Без ввода-вывода, исключений или серверного маршрута. Клиент вызывает их по обе стороны единой границы, общей для всех трех интерфейсов боя.
- **Очки здоровья переносятся как ДОЛЯ максимума в обе стороны.** Это обнаружил первый проход в браузере: Engine создает бойца 1-го уровня примерно с 60 очками здоровья и наносит 11–15 урона за удар, тогда как персонаж Ember Roads имеет 9 Grit, а волшебник 1-го уровня в 5e – 8 очков здоровья. Арифметика урона принадлежит и продолжает принадлежать Engine, поэтому перенос сырых чисел листа убивал персонажа через мост первым ударом в каждом бою. Боец сохраняет собственный `maxHp` Engine и начинает с той же долей максимума, что у запаса здоровья листа; обратная запись переводит итоговую долю обратно в шкалу листа и записывает разницу. Энергия и ячейки остаются абсолютными: это небольшие количества, их стоимость снимается с того же листа, а Engine тратит их по одной. Уведомление, `docs/game/combat.md` и руководство по наборам правил сообщают, что числа в бою принадлежат Marinara.
- **Доля сама по себе не меняет лист.** Сражение, не изменившее очки здоровья бойца, вообще не записывает операцию здоровья, поэтому два округления не могут сдвинуть лист на единицу. Значение выше нуля в обоих направлениях никогда не превращается в значение ниже единицы, поэтому округление никого не выводит из боя или с листа.
- **Нулевые очки здоровья – настоящее число.** Участник с пустым запасом здоровья начинает бой выведенным из строя – в том же состоянии, в котором уже находится участник, выведенный из строя в сражении. Ограничение минимумом 1 придумало бы здоровье, которого нет в листе. Полностью выведенный из строя отряд немедленно заканчивает бой поражением – честным исходом. В обратную сторону действует то же: боец с нулем записывает ноль в лист.
- **Только строки с отметкой каталога становятся навыками.** У введенной вручную строки нет стоящей за ней `mechanics`, поэтому нечего превращать в числа. Стоимость в запасе, который Engine не может потратить (очки здоровья, группа запасов, ресурс класса), убирает навык, а не делает его бесплатным. Записи `utility` и реакций исключены.
- **`power` калибруется, а не вычисляется.** Это множитель атаки бойца, поэтому мост делит среднюю величину на 7 и ограничивает результат от 0,5 до 3: базовое оружие оказывается примерно там, где собственные базовые навыки Engine (1,35 для атаки, 1,15 для лечения), а заклинание 3-го уровня по области достигает той же верхней границы, что уже ограничивает сгенерированный навык. Больший пул кубиков никогда не дает меньшего множителя.
- **Обратная запись проходит через собственные правила листа.** Каждая разница становится операцией `damage`, `restore` или `spend`, применяемой через `applyRulesetSheetOp`, поэтому бой никогда не может записать то, что лист отклонил бы от Game Master или игрока. Обратная запись не атомарна: отклоненная операция пропускается и возвращается вызывающей стороне, а принятые остаются примененными. Брошенное сражение ничего не записывает: боя не было.
- **Сводка несет то, что нужно листу.** `buildTacticalSummary` теперь сообщает `mp`, `maxMp` и `spellSlots`, как уже делала сводка распорядителя.
- **Что мост намеренно не читает.** `attackRoll`, `save`, `concentration` и `perCostStep` остаются проверяемыми, но неиспользуемыми, а `coverage.combat` сохраняет собственное значение. Их применение означало бы заявление о реализации боя системы, что относится к документу передачи реализации боя.

## Что определил этап 8c

Все три части готовы: масштабируемые значения каталогов, команда `use` и Refresh from ruleset.

- **Строка может содержать четыре числа, поддерживаемых набором правил.** У строки записи каталога появляется необязательный словарь `scaled`: до четырех собственных столбцов `number` этой строки, каждый в форме `{ from: <value reference>, table?: <step table> }`. Без `table` столбец берет значение ссылки (число применений трюка равно характеристике); с ней значение ищется по таблице (Rage по уровню). Более сложное выражается значением `derived`, объявленным набором правил и указанным записью, поэтому формат не учится новой арифметике. `values` по-прежнему содержит обычное число строки до появления конкретного листа.
- **Одна проверка для обеих форм каталога.** Перекрестные проверки находятся в `rulesetCatalogEntryIssues`, через которую проходят и встроенные записи, и записи ресурсов. Поэтому масштабируемая строка подчиняется одному правилу при любой поставке: ключ является столбцом `number` списка этой строки, `from` разрешается, а строка – ЕДИНСТВЕННАЯ строка записи для своего списка, чтобы отмеченная строка листа однозначно сопоставлялась со спецификацией. Замыкание `checkRef`, проверявшее все остальные ссылки на значения, стало общей `rulesetValueRefIssues`, поэтому допустимая в производном значении ссылка допустима и в масштабируемом столбце. Такой столбец может назвать любое объявленное производное значение, как `max` текущего запаса: он находится вне собственного порядка листа сверху вниз.
- **При редактировании, никогда при чтении.** `recomputeScaledRows(definition, build, catalogs)` в `packages/shared/src/features/rulesets/scaled-rows.ts` возвращает ТУ ЖЕ ссылку на сборку, если ничего не изменилось, поэтому просто открытый лист никогда не переписывается. Значение подгоняется к целевому столбцу (ограничивается `min` и `max`, округляется вниз для целочисленного столбца), поэтому функция никогда не записывает то, что редактор отклонил бы. Текущее состояние, блок промпта, мост к бою и сервер продолжают читать сохраненное число. `scaledRowColumns` сообщает редактору, какие ячейки заблокировать.
- **Из отсутствующего каталога ничего не угадывается.** Строка без отметки `_catalog`, каталог, который вызывающая сторона не загрузила, и исчезнувшая запись остаются в точности прежними, поскольку намерение набора правил для этой строки неизвестно.
- **`use` – помощник применения заклинаний без слова "заклинание".** `[sheet: who="Name" op="use" name="..."]`, с псевдонимами `op="cast"` и `spell=`, как `heal` является псевдонимом `restore`. Команда оплачивает каждое слагаемое `mechanics.cost` плюс одну единицу из каждого запаса строки списка, записанного той же записью. Слагаемое, называющее группу, оплачивается из первого способного заплатить запаса группы в порядке объявления; автоматического перехода к более высокому НЕТ: группа не всегда является лестницей. `pool=` задает применение с повышенным запасом и принимается только для стоимости из одного слагаемого внутри той же группы. Всё или ничего: шаги проходят через `applyRulesetSheetOp` на рабочей копии, и первый отказ отклоняет всю команду. Запись без стоимости получает `ok` и ничего не меняет. Новые отказы: `unknown-entry`, `ambiguous-entry`, `bad-pool`.
- **Имя – то, что показали Game Master.** Строка отвечает на свой столбец имени из `gm.sheetSummary`, затем `pools.nameColumn`, затем первый текстовый столбец списка, а также на собственную `label` записи, поэтому переименованная строка продолжает работать. Не загрузившийся каталог читается как `unknown-entry` с записью в журнале сервера: Engine не может знать цену и не будет ее придумывать.
- **Каталоги загружаются только тогда, когда нужны ходу.** `loadTurnRulesetCatalogs` ничего не читает, если в ответе нет команды `use` или `cast`, а затем читает только каталоги, на которые указывают собственные строки отряда. Часть маршрута, читающая ресурсы, перемещена в `services/game/ruleset-catalog.service.ts`, где открытие и чтение каталога разделены на два шага, чтобы маршрут по-прежнему мог ответить 304 до разбора мегабайта. Неудачная загрузка вызывает `logger.warn` и никогда не теряет ход.
- **Capability API 1.23 читается из байтов.** `scaled` – новый ключ в строгом файле, поэтому старая Engine отклоняет всё, что его содержит. Установка уже имеет проверенные байты `ruleset.json` И каждого объявленного `catalogs/<id>.json`, поэтому проверка читает оба: масштабируемая строка внутри файла или ресурса требует 1.23. Неразбираемый файл, как и прежде, пропускает проверку.
- **Refresh предлагает новый ТЕКСТ набора правил, только текст.** `planCatalogRefresh` и `applyCatalogRefresh` в `packages/client/src/lib/ruleset-catalog.ts` сравнивают только столбцы `text`, `longtext`, `dice` и `enum`, которые запись действительно задает, никогда не масштабируемый столбец и не значение, которое сам столбец отклонил бы. Число или логическое значение хранит собственное состояние игрока, а сохраненной базы для слияния нет, поэтому оно не меняется: эта граница описана в руководстве автора. Строка сопоставляется с исходной строкой записи по позиции среди строк с той же отметкой в этом списке, если количества совпадают; иначе – только если запись пишет одну строку для списка. Строка с исчезнувшей записью молча пропускается.
- **С проверкой, никогда за спиной игрока.** Если различий нет, ничего не рисуется. Список с отличающимися строками получает одну обычную строку (не live region, чтобы не объявлять ее заново при вводе в лист) и кнопку **Review** (проверить), открывающую `RulesetCatalogRefreshModal`. Там показаны отличающиеся столбцы каждой строки с текстом листа рядом с текстом набора правил и флажком для каждой строки, по умолчанию установленным. **Update selected** (обновить выбранное) применяет всё одним `commit`, записывая только отличающиеся столбцы и сохраняя все остальные ключи строки, включая отметку `_catalog`. Отмена ничего не меняет.
- **Редактор загружает только то, на что указывает лист.** `RulesetSheetEditor` получает каталоги, названные собственными отметками сборки, через `useQueries` над `rulesetCatalogQuery` окна выбора, поэтому окно выбора, предварительная загрузка боя и редактор делят одну запись кеша, а сборка без отметок ничего не загружает. Ожидающая или неудачная загрузка означает "каталогов пока нет": ничего не блокируется и не пересчитывается. `commit` остается единственным путем изменения и теперь вызывает `recomputeScaledRows` для измененной сборки; открытие листа никогда не вызывает `onChange`, а лист, отредактированный до загрузки каталогов, один раз приводится в соответствие при их поступлении.
- **Проверено на обоих примерах.** `docs/examples/rulesets/ember-roads.json` масштабирует число применений трюка по характеристике без таблицы в системе 2d6 вообще без уровня; пример 5e используется с тестовым каталогом, где ресурс класса следует за `level` через ступенчатую таблицу. `scripts/regressions/game-ruleset-scaled-rows.regression.ts`, случаи `use` в регрессионных тестах текущего состояния и каталогов и клиентский путь `scripts/regressions/ruleset-catalog-refresh.regression.ts` проверяют Refresh на обоих примерах.

## Что определил этап 7b

Второй вид разрешения – `dice-pool`. План предполагал согласовать его с автором сообщества, уже использующим системы пулов; никто не ответил, поэтому словарь взяли из того, что реально нужно существующим системам пулов, а PR приглашает к такой проверке.

- **Тот же лист, другое значение его числа.** Всё, что лист уже вычисляет для проверки (модификатор характеристики, бонус уровня мастерства, свободный бонус записи), при `dice-pool` означает ЧИСЛО КУБИКОВ. Нет новых терминов листа, нового редактора или второго способа объявить рейтинг. `formatRulesetCheckValue(definition, value)` – единственное место, определяющее, печатается число как "+5" или "5 кубиков"; через него проходят блок листа в промпте, редактор и лист в игре.
- **Виды изначально разделяют арифметику листа.** `abilityModifier`, `proficiency` и `proficiencyTiers` – один объект, развернутый в обоих членах объединения, поэтому перекрестные проверки, отклоняющие множитель без бонуса для умножения, работают для обоих, а правило только для dice-sum (натуральные результаты требуют одного кубика) остается внутри своей ветви.
- **Что выражает этот вид.** `die.sides`, `pool` (диапазон, которым ограничивается число листа; `min` равный 0 позволяет пустому пулу провалиться без броска), `target` (фиксированный или диапазон, внутри которого Game Master может его двигать), `double`, `explode` (цепочкой, с ограничением собственным максимумом пула), `cancel`, `botch`, `exceptional`, `situationalDice` и `difficultyLadder` требуемых успехов с необязательной целью каждого шага. Правило, которое никогда не может сработать, отклоняется при импорте: грань вне кубика, отменяющая грань, которая также успешна, ступень сложности с целью, которую Game Master не мог бы задать.
- **Критический провал определяется до отмены.** Правило звучит так: "Ни один кубик не дал успеха И выпала грань критического провала". Поэтому пул, чей единственный успех был отменен, дает обычный, а не критический провал. Критический провал принудительно проваливает проверку, так что он и успех никогда не сообщаются вместе.
- **Три атрибута проверки ограничиваются, а не отклоняются.** `threshold=` (только при регулируемой цели), `bonus=` (только с `situationalDice`) и `with=` (проверка навыка или спасбросок с другой характеристикой). Значение вне объявленного диапазона подтягивается к ближайшей границе, а отсутствующая в наборе правил характеристика игнорируется со строкой отладки. Разрешенная запись пишется из РЕЗУЛЬТАТА (`SkillCheckResult.threshold`, `bonusDice`, `withAbility`), поэтому показывает примененное броском, а не сырой запрос; только незавершенное переписывание без броска сохраняет запрос как написан. `with=` работает для обоих видов благодаря общей функции модификатора, поэтому набор правил 5e бесплатно получает "Сила (Запугивание)".
- **Результат пула всегда принадлежит Engine.** `rulesetVouchesFor` никогда не подтверждает пул: числа можно проверить, но у горсти кубиков столько внутренне согласованных исходов, что проверка ничего не ограничивает. Поэтому `isRulesetRollableSkillCheckTag` принимает любые `dice=` или `resolution=`, написанные моделью по привычке, и игнорирует `mode=`, поскольку пул берется из листа, а у вида нет преимущества. Кубик, брошенный игроком до хода, никогда не применяется.
- **Сложность – число успехов.** Ее потолок в `isResolvableSkillCheckRequest` – `rulesetPoolMaxSuccesses` (самый большой пул, еще столько же кубиков от взрывов, удвоение, если грани считаются дважды), то же число, которое схема разрешает запросить ступени сложности или `exceptional`, а не границы d20. Вычислитель ограничивает ее еще раз, поскольку видимый пул ограничивает написанный DC до загрузки любого набора правил.
- **Видимый пул для одного запроса остается в стороне.** Он содержит двадцатигранные кубики, поэтому игра `dice-pool` идет по слепой ветви, как уже делает набор правил `dice-sum` на 2d6: проверку бросает Engine, значение пула не тратится, и слот не записывается за броском, который оно не определило. Та же проверка теперь читает вид до кубиков, поскольку у набора правил пула вообще нет `dice`. Заполнители бросков (`[[roll: 1d8+NAME]]`) не разрешают имена листа при наборе правил пула, и промпт их не предлагает: число кубиков, прибавленное к броску урона, означало бы совсем другое.
- **В `SkillCheckResult` добавлен `threshold?`.** Его задают оба пути пула: набор правил `dice-pool`, знающий цель, выбранную его правилами, и прежний тег `resolution="successes"`, знающий переданную ему цель. Сериализатор пишет `threshold=` из результата, поэтому два представления не могут разойтись, а байты прежнего пути не меняются.
- **Capability API 1.24 читается из байтов.** Разрешение `dice-pool` имеет форму, которую строгая схема старой Engine полностью отклоняет, поэтому установка читает `ruleset.json` и отклоняет вид при более старой объявленной версии, как уже делает для `catalogs` ниже 1.21, `battle` ниже 1.22 и `scaled` ниже 1.23.
- **Что намеренно исключено и прямо названо в документации.** Выбор наибольшего кубика (требует степени частичного успеха, которой нет в типе результата), пулы стоек со сравнением с характеристикой, символьные кубики, встречные пулы, бросок ниже значения и открытые процентные броски, а также суммируемые пулы с диким кубиком. Для каждого нужен отдельный вид. Перебросы за ресурс и автоматические успехи – это команды Game Master `bonus=` и `[sheet:]`, а не правила вычислителя.
- **Доказательство.** `docs/examples/rulesets/gravewatch.json` – оригинальная система пулов десятигранных кубиков, поставляемая рядом с Ember Roads. `scripts/regressions/game-ruleset-dice-pool.regression.ts` фиксирует отказы схемы, каждое особое правило с внедренной последовательностью кубиков, ограничения, атрибуты тегов, строку промпта для каждого вида, формулировки блока листа, проверку установки 1.24, нетронутый прежний путь пула и возврат видимого пула к слепому режиму.

## Что определили слои L1

Этап L1 из пункта 5 раздела "Открытые решения": слой – вариант, который набор правил поставляет ВНУТРИ своего файла, поэтому он никогда не может пропасть у привязанной игры, не требует нового хранилища, нового пути поставки или проверки установки сверх номера API. L2 (слои, поставляемые кем-то другим) остается открытым.

- **Эффекты образуют закрытый набор, и каждый сужает либо дописывает.** Указания добавляются в конец `gm.checkGuidance` и нового `gm.worldGuidance`, значения УДАЛЯЮТСЯ из поля перечисления, шкала сложности заменяется шкалой того же вида разрешения, записи каталога скрываются в окне выбора редактора листа. Слой ничего не добавляет: добавленное значение было бы неизвестно всем остальным читателям листа и всем играм, отключившим слой. Он также не добавляет вызов модели, текущее состояние или число боя.
- **`gm.worldGuidance` – базовый слот, а не ключ слоя.** Базовые наборы правил не могли влиять на мир, в котором генерируется игра. `/game/setup` один раз разрешает привязку и передает `worldGuidance` со слоями в `buildSetupPrompt`, который выводит его как `<ruleset_world>`. Он читается один раз при настройке и никогда не попадает в ход; существующее отладочное журналирование промпта настройки печатает его вместе с остальным.
- **Выбор замораживается в словаре `options` привязки**, который существовал для этого и был пуст. `/game/create` проверяет его по декларации через `rulesetLayerSelectionIssues` и отвечает `ruleset_layer_unknown` или `ruleset_layer_conflict` с кодом 400, а не начинает игру по правилам, которых игрок не выбирал. Не принадлежащие Engine ключи проходят без изменений, а словарь ограничивается `RULESET_REF_MAX_OPTIONS` только на входе: сама привязка по-прежнему читается терпимо, поскольку существующая игра никогда не должна стать нечитаемой.
- **Применение ровно в одном месте.** `resolveGameRuleset` возвращает ЭФФЕКТИВНУЮ декларацию, поэтому промпт, вычислитель, блок листа, редактор и мост к бою видят набор правил со слоями без собственных изменений. Функция также предоставляет `baseDefinition` и активные `layers: {id,label}[]`. Ни одна вызывающая сторона не держала объект реестра по идентичности, поэтому больше ничего не изменилось.
- **Эффективная декларация проверяется заново с двумя описанными послаблениями.** `rulesetEffectiveDefinitionSchema` – схема файла с разрешенной ID с пространством имен (реестр меняет ключи наборов правил сообщества, а схема ФАЙЛА запрещает косую черту) и более мягким ограничением указаний, поскольку слой дописывает текст, ограниченный 1500 в каждом файле. Итог тоже ограничен: база плюс собственные 4000 каждого слоя. Перекрестная проверка слоя с полем – единственное правило, пропускаемое для эффективной декларации: удаляемых значений уже нет, в этом и смысл.
- **Слой никогда не лишает игру набора правил.** `applyRulesetLayers` никогда не выбрасывает исключение. Она проверяет все активные слои вместе и лишь при неудаче добавляет их по одному, сохраняя работающие. Выбранный слой, которого больше нет в файле, и более поздний из конфликтующей пары просто не применяются. Оба случая дают строки отладки, а не предупреждения, поскольку разрешение запускается каждый ход.
- **Указания соединяются пробелом, а не пустой строкой.** Каждая строка указаний в формате однострочная по собственному правилу `promptSafeText`, а напоминание Game Master выводит `checkGuidance` внутри одного пункта, где перенос строки читался бы как новая инструкция.
- **Конфликты симметричны, и убирается БОЛЕЕ ПОЗДНИЙ слой.** Достаточно назвать одну сторону пары, решает порядок объявления, поэтому те же два выбора всегда дают те же правила.
- **Ничто не переписывает персонажа.** Лист, уже содержащий удаленное значение перечисления, сохраняет и показывает его, а редактор просто перестает его предлагать. Скрытая слоем запись каталога не показывается в окне выбора, но ранее взятая игроком строка остается. `catalogEntryHiddenByLayers` – фильтр окна выбора; собственные записи набора правил никогда не меняются.
- **Клиентская часть построена на тех же двух функциях.** `GameSetupRulesChooser` рисует по флажку на слой под выбранным набором правил, отключает и называет слой, исключаемый выбранным. `packages/client/src/lib/ruleset-layers.ts` содержит чистую часть: переключение, словарь параметров и восстановление, отбрасывающее ID слоя, которого больше нет в установленной декларации. `useGameRuleset` применяет слои привязки один раз, поэтому все читатели внутри игры видят эффективную декларацию, а заголовок листа содержит имя набора правил и активные слои. Окно выбора фильтрует через `visibleCatalogEntries`, что только сужает предложение: Refresh from ruleset и масштабируемые столбцы читают каталог прямо из запроса, а редакторы персонажей и персон вообще не передают параметров и ничего не скрывают. `scripts/regressions/ruleset-layers-client.regression.ts` фиксирует всё это.
- **Capability API 1.25** читается из байтов, как `catalogs` ниже 1.21, `battle` ниже 1.22, `scaled` ниже 1.23 и `dice-pool` ниже 1.24: непустой массив `layers` или базовый `gm.worldGuidance` требуют объявления версии.
- **Проверено на всех трех примерах.** Ember Roads получает "Hard winter" (более жесткую шкалу, оба слота указаний и правило, скрывающее в окне выбора умения со стоимостью Grit), Gravewatch – "The long night" (шкала успехов с целями на каждом шаге, показывающая отсутствие привязки к d20), а черновик 5e – "Low magic" (два значения убраны из перечисления магических способностей) и конфликтующий "High magic". `scripts/regressions/game-ruleset-layers.regression.ts` фиксирует отказы схемы, применение всех сочетаний каждого примера, случай той же ссылки, запасной путь, отказы маршрута и замороженную привязку, напоминание, промпт мира и проверку 1.25.

## Настоящий бой по набору правил

**Решение.** На вопрос, должен ли бой быть TypeScript-адаптером для каждого набора правил или данными, пользователь решил в [#6361](https://github.com/Pasta-Devs/Marinara-Engine/issues/6361): "делайте всё необходимое, чтобы получить максимально точную версию боя 5e, которую мы можем реализовать, а порядок PR выбирайте сами". Поэтому блок `combat` присоединяется к `resolution` как проверенные данные, задающие параметры принадлежащего Engine вида, а зарезервированный в документе передачи реализации боя адаптер `5e-2014` становится собственными данными пакета 5e. При этом постоянное правило сохраняется: ФОРМАТ никогда не строится по образцу 5e. Точность обеспечивают богатый закрытый словарь и данные пакета, а не файл, способный называть термины одной системы.

**Архитектура.** Четыре границы, в таком порядке:

1. Чистый общий вычислитель `packages/shared/src/features/ruleset-combat/` без ввода-вывода, с внедренным генератором бросков и простым сериализуемым состоянием. Всё, что действует, выбирает ID из одного меню допустимых действий.
2. Одна серверная сессия в существующем реестре состояния распорядителя боя как третий `style` рядом с `classic` и `tactical`: та же строка хранения, ревизия, идемпотентность, мьютекс, окна и единственный вызов модели "выбери ID кандидата". Второго реестра нет.
3. Существующие оболочки, управляемые через уже принимаемый ими проп `directed`, с меню вариантов вместо жестко заданного и настоящим броском в журнале.
4. Мост уступает место отдельно для каждого набора правил: набор с `combat` никогда не идет по пути `battle`, а `coverage.combat` наконец получает смысл.

**Этапы.** C1 – схема и вычислитель. C2 – каталоги бестиариев, действия блоков характеристик, последовательности и перезарядка, ограничитель угрозы, а также собственные существа и дополненные заклинания пакета 5e. C3 – стиль `ruleset` распорядителя, разделенный на C3a (сессия, маршруты, сохранение, выбор врага по меню) и C3b (оболочка Classic на настоящих числах, `coverage.combat` true). C4 – поле, разделенное на C4a (формат, позиции, движение, досягаемость и дальности, области, укрытия, атаки при выходе из зоны угрозы, выбор и представление) и C4b (поле на экране на основе внешнего вида стиля Tactical). C5 – возможности хода и то, что его прерывает, разделенное на C5a (экономика хода, дополнительные эффекты и словарь состояний) и C5b (само окно: незавершенное перемещение и окно покупки особого действия). C5c и позже: другие причины открытия окна, легендарные действия, состязания и оставшиеся состояния.

### Что определил C1

- **Блок необязательный, отсутствующий вместо пустого и расположенный рядом с `battle`.** Набор правил может нести оба: мост – запасной путь Engine, слишком старой для `combat`, а сражение никогда не использует оба. Capability API 1.26 читается из собственных байтов набора правил точно так же, как `catalogs` ниже 1.21, `battle` ниже 1.22, `scaled` ниже 1.23, `dice-pool` ниже 1.24 и `layers` ниже 1.25.
- **Один вид, `attack-vs-defense`**, параметризованный как `dice-sum`: кубики инициативы и атаки объявляются, поэтому системе 2d6 не нужен отдельный вид. Спасброски в сражении используют кубики атаки, поскольку у набора правил `dice-pool` нет суммы для сравнения со сложностью; руководство автора прямо это сообщает.
- **Каждое имя принадлежит набору правил и проверяется перекрестно**: запас здоровья – объявленный текущий запас, не начинающийся пустым; защита и модификатор инициативы – ссылки на значения; столбцы атаки принадлежат названному списку и имеют правильный тип; список способностей фильтруется точно как `battle.skills`; состояния сопоставляют собственные ID листа с закрытым списком эффектов; концентрация называет текущий текст и спасбросок; умирание называет две разные шкалы; лимиты имеют уникальные ID; `attacks[].budget`, `abilities[].budget` и `mechanics.budget` называют объявленный лимит.
- **Экономика действий – список лимитов**, каждый с количеством и периодом `per` на ход или раунд. ПЕРВЫЙ объявленный лимит – основной, его тратит стандартное действие: это соглашение, а не ключ, поскольку стандартное действие принадлежит самой Engine, а альтернатива создала бы второй способ сказать "действие" в каждом файле.
- **В `mechanics` добавлены шесть необязательных совместимых ключей**: `targetCount`, `autoHit`, `applies` (состояние, длительность, необязательный прекращающий спасбросок), `temporary`, `scales` (дополнительные КУБИКИ из ступенчатой таблицы по ссылке на значение) и `budget`. Их проверяет `rulesetCatalogEntryIssues`, поэтому встроенный каталог и каталог-ресурс подчиняются одному правилу.
- **Бойцы на основе листов и блоков.** Участник отряда ЧИТАЕТ через `evaluateRulesetSheet`, `resolveRulesetValueRef`, `readRulesetLive` и `rulesetCheckModifier`, а ПИШЕТ через `applyRulesetSheetOp` в блок текущего состояния внутри встречи. Поэтому здоровье, ресурсы, состояния и концентрация принадлежат листу во время сражения и после, а перезагрузка посреди боя точна. Противник – простой блок характеристик, живущий только во встрече.
- **Допустимость существует только в меню.** `rulesetCombatOptions` предлагает то, что действующий может оплатить прямо сейчас, с ценой по пробному запуску собственной команды листа `use` (`planRulesetUse`, повторно используемой, а не реализованной заново), включая усиленное применение: более высокий запас того же семейства с добавлением кубиков `perCostStep` за каждый шаг между объявленным и оплачивающим запасом.
- **Декларация – параметр, а не часть состояния.** `rulesetCombatOptions`, `applyRulesetCombatChoice`, `advanceRulesetTurn` и `rulesetEncounterSummary` принимают декларацию, к которой разрешается привязка. Состояние несет `{ id, version }`, чтобы сохраненное сражение говорило, чем разрешалось, и остается достаточно небольшим для сохранения: каталоги участника отряда сужаются до записей, на которые указывают его собственные строки.
- **События несут арифметику**, а не заключение: выпавшие кубики, модификатор, сумму, встреченную защиту или сложность, влияние сопротивления и остаток. Журнал может напечатать "17 + 5 = 22 против 15: попадание, 9 рубящего урона", не выполняя собственной арифметики.
- **Ничто не выбрасывает исключение.** Недопустимый выбор возвращает то же по идентичности неизмененное состояние и одно событие `refused` с причиной из закрытого списка.
- **Чего C1 намеренно не делает**, с оставленными границами и прямым описанием в руководстве автора: позиции, расстояние, досягаемость, дальности, области на карте, укрытие и движение (`range`, `area`, `economy.movement` и четыре эффекта состояний, читающих расстояние, проверяются, но не читаются); реакции и их окна (`cannot-react`, а запись `reaction` отсутствует в меню); бестиарии, множественные атаки и перезарядка; выбор цели противником. Играть пока не во что: нет маршрута, сессии и экрана.
- **Проверено на обоих примерах с заданными кубиками.** `scripts/regressions/game-ruleset-combat-core.regression.ts` фиксирует отказы схемы, перекрестные проверки механик, инициативу и оба разрешения ничьих, меню, экономику действий, попадания, промахи, удачные грани, критические попадания, взаимную отмену преимущества и помехи, типизированный урон с сопротивлением, уязвимостью и иммунитетом, первоочередные временные очки, спасброски за половину и за отсутствие эффекта, общий бросок урона области, расход ячейки через лист и отказ при пустом запасе, усиленное применение, масштабируемый заговор, состояния с прекращающим спасброском и длительностью, концентрацию, прерываемую уроном и заменяемую второй способностью, умирание с возвращением при удачной грани и смертью после трех неудач, лечение с нуля, победу, поражение, сводку, проверку установки 1.26 и сражение, прошедшее через `JSON.parse(JSON.stringify(...))` посреди боя.

### Что определил C2

- **Каталог сообщает, что содержит.** `holds` равно `"rows"` (по умолчанию, поэтому каждый каталог до этого выпуска остается прежним) или `"creatures"`. Бестиарий не объявляет `feeds`, требует блока `combat` и шкалы `threat` и никогда не предлагается окном выбора редактора листа, которое ориентируется на `feeds` и потому его не видит. Запись содержит `rows` или `creature`, никогда оба и никогда ни одного, а существо не содержит `mechanics`: оно описывает свое поведение собственными действиями. Смешанный каталог отклоняется и во встроенном виде, и в ресурсе `catalogs/<id>.json`, поскольку оба проверяются в `rulesetCatalogEntryIssues`.
- **Существо записывается ключами, уже объявленными в `combat`**: здоровье как число или кубики, бросаемые при создании встречи, защита, модификатор инициативы, значения характеристик и модификаторы спасбросков под собственными ID листа, сопротивления по объявленным типам урона, иммунитеты по собственным состояниям листа, ступень собственной шкалы набора правил, безопасные для промпта особенности, которые Game Master видит, но никогда не разрешает, и действия. Capability API 1.27 читается из байтов набора правил точно как версии с 1.21 по 1.26.
- **Блок характеристик несет собственные сложности спасбросков.** `save.difficulty` или `saveDifficulty` для состояния, прекращаемого спасброском, когда само действие не требует своего; одно из двух обязательно везде, где нужен спасбросок. Правило C1 для строк каталогов (число дает источник способностей) здесь не имеет аналога, поскольку блок – не лист.
- **Четыре свойства только действия существа**: `uses` (на встречу или день), `recharge` (тратится при использовании, бросается в начале хода владельца, возвращается при `from` или выше, изначально доступно), `sequence` (другие действия того же блока по порядку, один лимит на все, у каждой части свои цель и бросок, без ссылки на другую последовательность) и `signature` (покупается за собственные `signaturePoints` блока, обновляемые в начале его хода, и никогда не находится в меню собственного хода). `rulesetSignatureOptions` определяет цену, а `applyRulesetCombatChoice` расходует их только в окне, которое C5b открывает между двумя ходами.
- **Последовательность получает цели всех своих частей.** Если передать меньше, каждая часть берет цели из начала списка, поэтому одна ID означает "всё в одну цель". Часть, для чьей цели сражение уже закончено, пропускается, и новая цель не выбирается: выбор – задача вызывающей стороны.
- **Ограничитель предназначен только для предложений.** Поставляемый бестиарий – данные автора, принимаемые как написано. Придуманное Game Master существо проходит через `clampRulesetStatBlock`, которая подтягивает здоровье в диапазон ступени, ограничивает защиту, попадание и сложности спасбросков двумя пунктами выше ступени, отбрасывает отсутствующие в наборе правил имена и всё после шести действий и уменьшает урон, пока лучший раунд не укладывается в верхнюю границу `damagePerRound` ступени. Сначала уменьшается число кубиков, затем плоская добавка, затем удар последовательности, затем размер кубика; ничто никогда не сводится к нулю. Необъявленная ступень заменяется самой низкой, а каждое изменение возвращается простой фразой для журнала.
- **`damagePerRound` понимается как весь раунд урона одной цели**, включая последовательность, а не одна атака, поскольку ограничитель должен ограничивать именно раунд.
- **Поиск сначала точный, затем обычный, затем пустой.** `findRulesetCreature` сопоставляет `<catalogId>/<entryId>`, затем подпись или ID без учета регистра и пунктуации, затем возвращает null. Ссылка, отсутствующая в переданных каталогах, исключает противника из сражения с одним событием `refused` и причиной `unknown-creature`, а не вводит существо без чисел.
- **Проверено на обоих примерах** в `scripts/regressions/game-ruleset-combat-creatures.regression.ts`: Ember Roads поставляет трех оригинальных существ и трехступенчатую шкалу угрозы, черновик 5e – четырех, и формат ни одного файла не знает терминов другого.

### Что определил C3a

C3 разделен на две части: C3a – серверная часть, C3b – экран. Capability API не повышается, поскольку формат не изменился.

- **Один реестр состояния, третий `style`.** В `DirectedCombatView.style` добавляется `"ruleset"`. Та же строка хранения, то же пространство имен, та же ревизия, идемпотентность экземпляра и ID запроса, та же очередь каждого чата и то же правило "модель только выбирает ID кандидата из меню, перечисленного Engine". `GameCombatStyle`, то есть предпочтение ИГРОКА, сохраняет два значения: стиль набора правил никогда не является предпочтением, его получает игра на наборе правил с блоком `combat`.
- **Собственная логика стиля находится в отдельном файле.** `ruleset-combat-director.service.ts` чист относительно `(definition, state)`, поэтому регрессионный тест проводит целое сражение без базы данных. Существующий `combat-director.service.ts` получил три точки диспетчеризации и больше ничего: расширенный `style`, поле `rulesetFight` в сохраняемом состоянии и ранний возврат в `advanceCombatDirector` и `commandCombatDirector`, чтобы очередь задач никогда не запускалась для сражения, которого не может разрешить.
- **Сервер решает, чем разрешается сражение.** `/start` самостоятельно разрешает привязку чата и отклоняет игру без набора правил или блока `combat`. Отряд читается из собственных листов чата через `rulesetSheetBuildsByName`, которая ПЕРЕМЕЩЕНА в общий мост к бою, чтобы мост `battle` и этот стиль сопоставляли бойца с листом по одному правилу. Присланный клиентом лист никогда не читается, а участник без листа отклоняется по имени.
- **Числа противника**, по порядку: `findRulesetCreature` по ссылке Game Master, затем по собственному имени противника, затем `clampRulesetStatBlock` над предложением в общей форме существа, затем простой блок из собственных чисел ступени (`rulesetTierStatBlock`: середина диапазона здоровья, защита и попадание ступени, одна атака с плоским нетипизированным уроном в середине `damagePerRound`). Каждый запасной путь и каждая строка ограничителя сохраняются в сессии как `adjustments` и один раз записываются в журнал.
- **Собственные `party` и `enemies` Engine синхронизируются** после каждого шага, поскольку их читают `handleCombatEnd`, пересказ и журнал, а при окончании боя из них заполняется `CombatSummary`. Победителя определяет `rulesetEncounterOutcome`; очки здоровья согласованы, потому что это одни и те же числа.
- **Текущее состояние листа записывается при ПРИНЯТИИ действия**, внутри собственного сохранения реестра состояния, а новый блок возвращается с ответом, поэтому клиентскому хранилищу не нужна повторная загрузка. Если запись не удается, шаг не удается, поэтому реестр и лист не могут разойтись; отдельной обратной записи в конце боя у этого стиля вообще нет.
- **Меню отправляется, а не вычисляется на клиенте.** `rulesetOptionTargets` – новая общая функция рядом с вычислителем; собственная проверка целей `applyRulesetCombatChoice` теперь проходит через нее, поэтому предлагаемый клиенту список и принимаемый правилами список – один и тот же.
- **`continue` разрешает ровно один ход** действующего, которым не играет человек: каждое его действие, конец хода и следующего действующего. Механизм выбора превращает меню в `CombatAiCandidate` и дает существующей `chooseCombatCandidate` выбрать, поэтому сражение по набору правил оценивается той же тактикой, что и два других стиля. Ограничение – двенадцать действий за ход; ход всегда заканчивается, а удар по области никогда не нацелен на свою сторону: союзность читается с ЦЕЛИ, а не со стороны, для которой написан вариант, что и нужно автору, разрешающему дружественный огонь.
- **Босс вместо этого открывает окно.** Один `CombatDecisionOption` на кандидата, совместимо расширенный полями `optionId`, `targetIds` и `label`, получает ответ существующей задачей `continue` через учитывающий набор правил построитель промпта рядом с `buildCombatBossPrompt`: тот же только JSON-ответ `{"candidateId"}`, те же строки отладки, тот же тайм-аут десять секунд, тот же лимит вызовов и тот же возврат к локальному выбору при мусоре или ID вне меню.
- **Отказ ничего не меняет**, не повышает ревизию, не расходует ID запроса и отвечает 400 с собственной причиной вычислителя в стабильном поле `code` (`ruleset_combat_<refusal>`).
- **Сражение с исчезнувшим набором правил** возвращается завершенным с исходом `flee` и одним событием распорядителя с причиной вместо 500 или разрешения по другим правилам. Ничто из этого не сохраняется, поэтому переустановка набора правил продолжает то же сражение с места остановки.
- **План встречи говорит терминами набора правил.** Если набор правил чата объявляет `combat`, `/encounter/init` перечисляет ступени угрозы и ограниченный индекс бестиария (первые шестьдесят имен в порядке объявления) и запрашивает блок `creature`, `tier` или `proposed` для каждого противника. Игра без набора правил или без `combat` получает сегодняшний промпт без изменений, а некорректный `proposed` отбрасывается, не ломая весь план встречи.
- **Проверено** в `scripts/regressions/ruleset-combat-director.regression.ts` (чистая логика, оба примера наборов правил) и `ruleset-combat-director-route.regression.ts` (настоящие маршруты, запись текущего состояния, неизмененное сражение Classic, окно босса с подставной моделью и промпт плана встречи).

### Что определил C3b

C3b – экран. Capability API всё еще не повышается: формат не изменился, а три общих дополнения ниже – поля, которые ничто вне Engine не записывает.

- **Одно решение определяет, принадлежит ли сражение набору правил**, и его читают все: `isRulesetCombatFight({ combatDirector, definition, anchor })` в `packages/client/src/lib/ruleset-combat-bridge.ts`. Все три условия должны выполняться. Решение читается из объявленных файлом БЛОКОВ, никогда из `coverage.combat`, отражающего заявление автора, а не содержимое файла. Мастер настройки и проверка импорта сообщают о поведении боя по той же проверке.
- **Сценой служит оболочка Classic.** Проп `directed` компонента `GameCombatUI` получает необязательную часть `ruleset`; без нее каждый путь Classic остается прежним, а с ней жестко заданное меню атаки/навыка/защиты, его подфазы и обработка клавиш со стрелками заменяются собственным меню набора правил. Портреты, полосы здоровья и их анимации уже читают `party` и `enemies`, синхронизируемые сервером, поэтому их вообще не трогали.
- **Ничто на экране не вычисляет допустимость или арифметику.** Меню, ID допустимых целей, цены, прогноз и все числа журнала приходят из представления сервера. Отклоняемый правилами вариант просто не отправляется, поэтому клиент ничего не делает серым, а отказ 400 становится локализованным предложением по `code` с собственным предложением сервера как запасным вариантом для кода, которого сборка не знает.
- **Слова принадлежат набору правил.** Лимиты, состояния, спасброски, шкалы, ступени, запасы и то, против чего бросается атака, печатают подписи из файла, поэтому 5e говорит "Armor Class", а Ember Roads – "Guard". Engine называет только собственный закрытый список стандартных действий вида и завершение хода.
- **Журнал – один чистый модуль**, `packages/client/src/lib/ruleset-combat-log.ts`, поэтому строку каждого типа события можно зафиксировать. Бросок без добавок печатается как один кубик; несколько кубиков, сумма которых равна сохраненному результату, печатаются как горсть; преимущество и помеха печатают оба кубика и выбранный, причем только когда событие указывает направление.
- **Мост уступает место ровно этому сражению.** `startBattleParty` не инициализирует из листа, а `handleCombatEnd` не вызывает `applyRulesetBattleResult`, поскольку сервер записывал каждый принятый шаг сразу. Набор правил с `battle` без `combat` и игра без распорядителя сохраняют мост в точности прежним.
- **Пересказ использует настоящую сводку.** `CombatSummary` получил необязательное поле `ruleset` с `RulesetEncounterSummary`. Вместо строк с процентами пересказ печатает здоровье как значение и максимум собственного запаса набора правил, кто выведен из строя, умирает или стабилен, состояния по подписям, собственное число раундов набора правил и одну строку о поддержании листов в актуальном состоянии.
- **Три небольших общих совместимых дополнения**: `RulesetEncounterSummary.party[].stable` (иначе пересказ не отличил бы переставшего ухудшаться от того, чье время еще идет), `CombatSummary.ruleset` и `creature`/`tier`/`proposed` в `CombatEnemy` и `Combatant`, чтобы собственные термины плана встречи доходили до `/start` через клиентский конвейер.
- **Одно небольшое серверное изменение:** `syncRulesetCombatants` теперь задает собственный `round` распорядителя из раунда сражения. Раньше он навсегда оставался единицей, что давало "Round 1" на протяжении всего боя и "после 1 раунда" в пересказе.
- **Проверено** в `scripts/regressions/ruleset-combat-screen-client.regression.ts` (строка каждого типа события на обоих примерах через настоящий английский каталог, группировка меню, выбор целей, решение выше для всех сочетаний и пересказ по настоящей сводке) и третьем режиме `e2e/game-combat-director.e2e.ts`, который импортирует Ember Roads через настоящий маршрут и проводит сражение.

### Что определил C5a

C5a – возможности одного ХОДА на общей и серверной стороне. Всё в нем совместимо и необязательно; набор правил, не объявляющий ничего из этого, разрешается побайтно как прежде.

- **Удар может состоять из нескольких величин.** `mechanics.plus` записи каталога и `damage.plus` действия существа содержат до трех составляющих, каждая со своими броском и типом, каждая отдельно встречает защитные свойства цели, отдельно удваивается критическим попаданием и может запросить у ЦЕЛИ собственный спасбросок (`onSuccess: "none"` убирает всю эту составляющую, `"half"` оставляет половину). Вместе они образуют ОДНУ проверку концентрации с суммарным уроном и одну проверку выхода из строя. Прогнозы, ограничитель угрозы и измеренный урон за раунд учитывают составляющие полностью, включая зависящую от спасброска: прогноз говорит, что сделал бы удар.
- **Несколько ударов за один лимит.** `combat.attacks[].strikes` – ссылка на значение. Первое применение тратит лимит и помещает остаток в `combatant.strikesLeft`; пока удары остались, каждая строка списка с `strikes` предлагается без расхода лимита, неся `option.strikes`, чтобы меню могло назвать остаток. Разные виды оружия, разные цели и перемещение между ними получаются из меню без особых случаев. Список, покупающий один удар за расход, ничего не оставляет в запасе и не создает события, поэтому сегодняшние журналы не меняются.
- **Способности, меняющие экономику действий.** `mechanics.free` не тратит лимит, `mechanics.gives` добавляет к лимитам в момент использования и ограничивает результат, а `mechanics.standard` предлагает именованные стандартные действия как `standard:<id>@<budget>` по цене давшей их способности. Запись `utility`, объявляющая `gives` или `standard`, создается как действие вместо отбрасывания; запись, у которой есть только `standard`, сама отсутствует в меню: разрешение не является действием, которое кто-то выполняет.
- **Дополнительные эффекты.** Новый вид записи каталога `rider` и собственные `riders[]` существа. Пассивные, никогда не появляются в меню и добавляют еще одну составляющую к первому подходящему попаданию периода. Подходящие атаки определяются один раз при начале сражения по названным спискам атак и одному истинному столбцу их строк, поэтому разрешение никогда не перечитывает лист. `oncePer: "turn"` очищается в начале КАЖДОГО хода, независимо от владельца, поэтому удар во время чужого действия может нести такой эффект.
- **Словарь состояний.** Пять новых эффектов, плюс `saves` (каких спасбросков касаются два эффекта спасбросков), `whileSourceInSight` (условие для всех эффектов этого состояния) и `endsWhenSourceDown`. Отслеживаемое состояние уже записывало применившего, поэтому для трех привязанных к источнику свойств не понадобилось нового хранения.
- **Проверено** блоком C5a в `scripts/regressions/game-ruleset-combat-core.regression.ts` (отказы, составляющие, удары, экономика действий, дополнительные эффекты, состояния, оба примера и пособытийное сравнение с тем же сражением на наборе правил без этих ключей) и случаями состояний только на поле в `game-ruleset-combat-grid.regression.ts`.
- **Оставлено для C5b и позже**: у `on` одно значение, `hit`, поэтому дополнительный эффект пока срабатывает сам. `combat.standard` остался закрытым списком обычных строк, поскольку каждый уже поставляемый набор правил пишет его так; то, что уклонение делает ПОМИМО снижения вероятности попадания, описано рядом, в `combat.standardEffects.dodge.saves`.

### Что определил C5b

C5b – ОКНО: сражение удерживается между одним шагом и следующим для того, кто не является текущим действующим.

- **Нет нового ключа и повышения версии возможностей.** Все части словаря, читаемые окном, уже существовали: `combat.opportunity.budget` говорит о стоимости удара по проходящему, `signature` и `signaturePoints` существа – о покупке за его очки. Изменилось то, что Engine спрашивает, а не решает: раньше атака при выходе из зоны угрозы выполнялась ЗА владельца, а особое действие можно было купить в любой момент вне собственного хода. Пакет, созданный до этапа, играет тот же бой по одному вопросу за раз.
- **Окно находится в состоянии.** `RulesetEncounterState.window` хранит вид, причину открытия, тех, кто еще должен ответить, и, если его открыло перемещение, остаток пути: пройденные клетки, оставшиеся клетки, оплаченное и всех уже спрошенных. Сражение, сохраненное посреди перемещения, возвращается с теми же ожидающими вопроса и теми же непройденными клетками; `windows` считает все когда-либо открытые окна, чтобы ответ для закрытого окна отклонялся, а не тратился на заменившее его.
- **Пока окно открыто, больше ничего не движется.** Любой другой выбор, включая конец хода, отклоняется с `window-open`, а ответ с другим окном – с `stale-window`. В обоих случаях одна точка входа: `applyRulesetCombatChoice` принимает ответ так же, как выбор хода, из `rulesetWindowOptions` или `RULESET_PASS_OPTION`.
- **По одному ответу.** Окно спрашивает каждого ожидающего бойца один раз – удар или пропуск – и убирает тех, кому больше нечем ответить, вместо удержания боя ради меню с одним пропуском. Один шанс каждому на всё перемещение, сколько бы раз путь ни покидал ту же досягаемость.
- **Перемещение завершается, даже если последний удар закончил бой**, поскольку именно его событие сообщает, где действительно остановился идущий.
- **Им управляет распорядитель.** Каждый участник окна, которым не играет человек, отвечает сразу из собственного меню окна и через ту же оценку, которая играет его ход; босс Game Master спрашивается через собственное решение Game Master с пропуском момента среди ответов. Окно остается только для собственного участника отряда пользователя, а `DirectedRulesetView.window` дает клиенту вопрос и Pass.
- **Проверено** блоком окон в `scripts/regressions/game-ruleset-combat-grid.regression.ts` (удержание, меню, удар, пропуск, отказы, один шанс на перемещение), окнами особых действий в `game-ruleset-combat-creatures.regression.ts` и собственным окном босса в `ruleset-combat-director-route.regression.ts`.
- **Оставлено для C5c и позже**: что ЕЩЕ открывает окно. Запись каталога с `reaction` пока не называет триггера и потому отсутствует во всех меню; словарь ответа реакции, а также вложенность, отмена и возвраты при противодействии относятся к следующему этапу.

### Что определил C5c

C5c – МОМЕНТ: какой именно ожидает реакция, чтобы запись с `reaction` наконец получила подходящее окно.

- **`mechanics.reaction` может быть объектом вместо `true`.** `on` называет момент, `at` говорит, на кого направляется выбранное, а `cancels` останавливает то, что удерживало окно. `true` по-прежнему означает лишь то, что нечто не используется на ходу; запись только с этим признаком всё еще отсутствует во всех меню. Capability API 1.33 читается из собственных байтов ресурса каталога точно как 1.23 и версии с 1.26 по 1.30.
- **Два момента, поскольку замечать их должна Engine.** `aimed` – до попадания чего-либо во владельца, `harmed` – после того, как что-то нанесло ему вред. Список закрыт по той же причине, что и список эффектов: момент, за которым никто не следит, не может открыть окно.
- **`aimed` открывается только для другой стороны; `harmed` – для любого.** Наведение связано с тем, что кто-то НАМЕРЕН сделать вам, а лечащий друг не является угрозой для ответа; иначе союзник под управлением Engine мог бы отменить лечение своего друга. Получение вреда – факт о вас независимо от источника, а направленная обратно на источник реакция по-прежнему не попадет в друга благодаря обычной допустимости целей.
- **Продолжение называет свой вид.** Для перемещения оно несет `kind: "walk"`, для действия – `kind: "action"`. Сохраненное C5b посреди перемещения сражение имеет продолжение без вида и читается как перемещение, которым только и может быть.
- **Engine может пропустить момент.** Меню окна содержит кандидата "пропустить момент", оцениваемого подобно завершению хода, поэтому наличие доступной реакции больше не означает ее обязательного расхода; это относится и к удару C5b по уходящему. Вариант, не запрашивающий никого, но действующий на кого-то (движущегося или источник момента), оценивается по воздействию на него (`rulesetWindowTargetOf`). Ответ механизма выбора, отклоненный правилами, пропускается и записывается в журнал: отказ никогда не сохраняется, и иначе пропуск выглядел бы как выбор.
- **Стоимость оплачивается до вопросов.** Окно `aimed` открывается после расхода лимита и запасов, поэтому отменяющий ответ останавливает СОВЕРШЕНИЕ действия, а не факт его покупки. Это собственный ответ боя на вопрос "тратит ли отмененное заклинание ячейку"; набору правил с другим ответом нужен отсутствующий здесь словарь возвратов.
- **`harmed` читается из урона, записанного самим действием**, после полного разрешения, поэтому ничему внутри вычислителя не нужно знать о существовании окна. Действие, ранившее троих, открывает одно окно со всеми тремя.
- **`at: "source"` подставляет цель, а не предлагает ее выбрать.** Причинивший момент – единственная цель большинства таких реакций, поэтому вариант вообще не несет целей, а клиент не показывает выбор. `at: "chosen"` сохраняет собственные цели записи.
- **Отменяющая запись `utility` что-то делает.** До этого запись `utility` без `gives` и `standard` отбрасывалась как не имеющая ничего для разрешения; отмена тоже является разрешением.
- **По-прежнему одно окно за раз.** Ничто внутри окна не открывает новое, поэтому противодействию нельзя противопоставить другое противодействие, а ранящая реакция не создает второго момента. В исходнике это отмечено как ограничение, с ограниченным стеком из документа передачи реализации боя в качестве пути расширения.
- **Проверено** блоком моментов в `scripts/regressions/game-ruleset-combat-core.regression.ts` (отсутствие в меню любого хода, окно и триггер, только ожидающие ЭТОТ момент варианты, отмена, расход лимита в любом случае, пропуск, пропускающий удержанное действие, второй момент после получения вреда, ответ обратно источнику и отсутствие третьего окна).
- **Оплата из большего запаса участником отряда под управлением Engine.** Включено из [issue #6528](https://github.com/Pasta-Devs/Marinara-Engine/issues/6528), поскольку это та же граница: игроку предлагались запасы оплаты способности, а собственный механизм выбора Engine видел только базовую стоимость, поэтому переданный Engine персонаж никогда не усиливал растущее заклинание. Построитель кандидатов теперь создает по кандидату на способ оплаты, каждый с `choice.payWith`, прогнозом реально покупаемых дополнительных ступеней, подписью запаса и ценой, учитывающей и пройденные ступени, и количество, чтобы усиленная версия не принималась за бесплатную. **Противники не затронуты, поскольку им некуда подниматься:** действия блока характеристик не тратят никакого запаса, поэтому ни противник под управлением Engine, ни босс Game Master не имеют более дорогого способа оплаты. Собственные запасы блоков потребовали бы изменения формата, не этого изменения. (Оно появилось следующим: существо в форме листа имеет запасы и получает усиленные способы оплаты, как любой другой. См. "Что определили листы существ".)
- **Оставлено на потом**: реакция, меняющая ЧИСЛО отвечаемого действия вместо остановки. Словарь состояний – закрытый список имен, а не модификаторов, поэтому набор правил пока не может сказать "сложнее попасть до вашего следующего хода", ни через реакцию, ни иначе. Это вопрос состояний, а не реакций.

### Что определили листы существ

[Issue #6610](https://github.com/Pasta-Devs/Marinara-Engine/issues/6610): существо бестиария, записанное в собственных терминах набора правил. Противники не каждого набора правил укладываются в один фиксированный набор простых чисел, а противник не мог оплачивать что-либо из отсутствующего запаса.

- **Существо может нести `sheet`** в форме самого листа персонажа, где каждая часть необязательна и нет части `live`; схема строгая, поскольку бестиарий – авторские данные. Capability API 1.34 читается из собственных байтов набора правил и файлов каталогов точно как 1.27.
- **Одно место для каждого числа.** При наличии листа рядом с ним запрещены `health`, `defense`, `initiativeModifier`, `speed`, `abilities` и `saves`, а действия блока можно не задавать; без листа первые три и действие обязательны как прежде. Опубликованная JSON Schema описывает обе половины (`oneSourceForCreature` в генераторе).
- **Один построитель.** `sheetCombatant` в `encounter.ts` одинаково строит участника отряда и противника на основе листа, поэтому они не могут разойтись. Добавления блока (собственные действия, очки особых действий, дополнительные эффекты и игнорируемый урон) накладываются сверху.
- **Проверка как авторских данных**: каждая ID по объявлениям листа, навыки и спасброски по предложенным для них уровням, значения характеристик и бонусы как целые числа в диапазонах, строки по `maxItems` каждого списка, поля и ячейки строк через общую `rulesetListRowIssues` (теперь применяемую и к полям), а `_catalog` – по каталогу, заполняющему список и, если он встроенный, содержащему запись.
- **Маршрут загружает то, что читают листы.** `rulesetBestiarySheetCatalogIds` называет каталоги, из которых листы бестиария выбирают строки; они загружаются после бестиариев только при ссылке листа.
- **Запасы и усиленная оплата получаются бесплатно.** Построитель кандидатов никогда не ограничивался стороной, только наличием у действия запаса для повышения, поэтому противник с листом получает усиленные способы оплаты и в механизме выбора Engine, и в решении Game Master, которое уже несло `payWith`.
- **Теперь противник может получать отметки на шкале ран.** Сначала читаются его защитные свойства, затем отмечается шкала, поэтому прежнее ограничение, при котором сопротивления не могли описать шкалу, снято для существа с листом; существо на простых числах по-прежнему теряет очки.
- **Это всё еще противник.** Поражение при нуле определяется стороной, как и шкала смерти. Обратная запись текущего состояния также учитывает сторону наряду с наличием листа: без этого противник с листом и именем участника отряда перезаписал бы сохраненный лист этого участника.
- **Придуманное Game Master существо тоже может иметь лист**, поскольку придуманному магу нужны ячейки и заклинания (решение пользователя в PR). `rulesetProposedCreatureSchema` принимает мягко проверяемый `sheet` (схему сборки персонажа) и отбрасывает написанные рядом числа вместо отклонения предложения. `hold.ts` ограничивает его в три шага: `readProposedRulesetSheet` убирает отсутствующее в наборе правил по имени, подгоняет значения и превращает строку с именем записи каталога в эту запись (маршрут загружает все каталоги, заполняющие список предложенного листа); `holdRulesetSheetHealth` переносит здоровье в диапазон ступени через единственное поле, из которого читается запас здоровья, или `sum` с одним полем, а остальное оставляет как написано со строкой пояснения; после построения сражения `holdRulesetCombatant` ограничивает защиту, попадание и сложности спасбросков и масштабирует лучший раунд на самом бойце, учитывая максимальную доступную оплату. Купленные одним расходом удары остаются в запасе и могут уйти на любую ударную строку, поэтому ударный раунд измеряется как оплаченная строка плюс остаток ударов по самой тяжелой ударной строке. Части блока рядом с листом по-прежнему проходят обычный ограничитель. Промпт плана встречи несет `EncounterSheetBrief`: ID, допустимое содержимое каждой, читаемые боем списки, поле открытия каталогов каждого списка и до 60 имен каталога на список.
- **Придуманный враг, не являющийся боссом, следует собственным классам набора правил** (решение пользователя: "чтобы Sorcerers не имели доступа ко всему списку заклинаний"). Изменение формата не понадобилось: `startFrom` фильтра каталога уже называет поле листа, по которому организованы записи, а `restrictRulesetSheetEntries` оставляет только записи с фильтром, соответствующим значению листа, сопоставленные через `sheetFieldMatchTexts` (перенесенную в общий код для согласованности окна выбора и боя). Число ячеек по уровню класса НЕ объявляется никаким набором правил (5e вводит их в поля), поэтому таблицы класса для ограничения нет; ограничитель ступени сдерживает то, что за них покупается.
- **Открытые выборы заполняются характером и компетентностью без вызова модели.** `fillRulesetSheetChoices` заполняет каждый список выбора существа (источник способностей с `onlyWhen`) доступными ему записями, оплачиваемыми из собственных запасов, до фиксированного числа на ступень запаса (1, 2, 2 и 3 от новичка до мастера) и без ограничений применения (2, 2, 3 и 3). Это ограничение Engine, пока набор правил не сможет объявлять число выборов класса. Вес зависит от природы записи (вред, поддержка, контроль или изменение хода) относительно характера боевого ИИ; компетентность повышает вес изменения хода. Маршрут дает врагу тактику до построения боя из той же единицы и начального значения генератора, что использовал бы механизм выбора, поэтому существо заполняется и сражается с одним характером. Босс освобожден от обоих ограничений: Game Master пишет его целиком.
- **Слой, сужающий поле перечисления, никогда не лишает существо.** Значение перечисления существа может быть удаленным слоем значением, прочитанным из собственных `layers` декларации, но не иным необъявленным: `refineRulesetDefinition` передает `layersApplied`, а загрузчик каталогов игры, который может иметь декларацию со слоями, передает `narrowedByLayers`. Поэтому слой никогда не отбрасывается молча, файл бестиария не отклоняется из-за удаленного слоем значения, а опечатка по-прежнему отклоняется. Установка пакета никогда не разбирает файлы каталогов, поэтому пути для настройки во время установки нет.
- **`no-health`.** Лист, дающий в сумме нулевое здоровье, исключается во время боя с отдельной причиной вместо появления неубиваемым. Бестиарий уже отклоняется при импорте за поле вне диапазона, поэтому сюда приводит формула с нулевой суммой или вручную созданный блок.
- **У каждого отказа есть слова с обеих сторон.** У `window-open` и `stale-window` из C5b не было предложений в английском каталоге или на сервере, у четырех позиционных причин C4a – на сервере. Теперь они есть у всех; клиентский тест экрана падает при добавлении причины без обоих текстов.
- **Проверено** `scripts/regressions/game-ruleset-combat-creature-sheets.regression.ts` (один источник, ID и ссылки, те же числа, что у участника отряда в черновике 5e и Ember Roads, сохранение блока рядом с листом, собственный Luck, более высокая ячейка у вычислителя, механизма выбора Engine и Game Master, шкала ран и иммунитет, поражение, проекция, обратная запись, отказы, предложение и проверка 1.34), тестом маршрута с заклинателем, чье заклинание живет в другом каталоге, и тестом JSON Schema.

### Что определил C4a

C4a – поле на общей и серверной стороне. C4b – экран, который его рисует.

- **Набор правил определяет размер клетки, и это делает позиции возможными.** Новое необязательное `combat.distance: { label, perCell }`. Каждое расстояние мира блока выражается в этой единице: `economy.movement`, `speed` существа, `reach` и `range` оружия, `reach` и `range` действия существа. Каталог с собственными `units.distance` преобразует свои `mechanics.range` и `area.size` через собственный `perCell`; без них используется значение блока. Capability API 1.28 читается из байтов набора правил, как каждая версия начиная с 1.21.
- **Ничто из работающего сегодня не изменилось.** Сражение без поля побайтно остается прежним: сравнивается весь журнал событий того же сценария на тех же наборах правил, теперь объявляющих размер клетки, и копиях без каждого нового ключа. Состояние осталось `v: 1`, поскольку каждое новое поле необязательно и отсутствует в сражении без него.
- **Либо все на поле, либо никто.** `createRulesetEncounter` принимает необязательный `board: { grid, placements }` и хранит его, только если набор правил объявляет `distance` И каждый боец имеет клетку внутри сетки. Одно отсутствующее размещение оставляет весь бой в воображении: сражение, где кто-то нигде не стоит, не может отвечать на вопросы о расстоянии.
- **Сетка принадлежит тактической Engine.** Сервер вызывает `generateTacticalBattlefield` и `placeSpawns` с теми же начальным значением генератора и курсором, что тактический стиль, используя подставные единицы только со стороной, признаком босса и клеткой. Для этого `placeSpawns` расширена до структурного `TacticalPlaceable`, которому `TacticalUnit` уже соответствует. Нет второго генератора, второй таблицы местности или особых размеров поля этого боя.
- **Восемь соседей по одной клетке, расстояние – большая разница по осям.** Так играют на предназначенных для этого настольных сетках. Это намеренно НЕ собственные четыре направления и манхэттенское расстояние тактической Engine, которые остаются прежними для ее боев. `moveCost` местности – цена ВХОДА в клетку; в твердые клетки входить нельзя, срезать угол между двумя твердыми клетками нельзя, мимо друга пройти можно, остановиться на ком-либо нельзя.
- **Один новый чистый модуль**, `packages/shared/src/features/ruleset-combat/grid.ts`: `rulesetInCells`, `rulesetCellDistance`, `rulesetReachableCells`, `rulesetLineOfSight`, `rulesetAreaCells` и `rulesetOpportunityAttack`. Настоящие формы всплеска, конуса и линии, а не один радиус прежнего моста.
- **Меню по-прежнему единственный источник допустимости.** Куда можно пройти, на кого направить вариант и куда нацелить форму – одно правило, по которому разрешение проверяет выбор. Цель, допустимая будь она ближе, отклоняется с `out-of-reach` или `no-line-of-sight`, а не просто `bad-target`.
- **Механизм выбора движется.** Он оценивает каждую достижимую клетку против каждого доступного оттуда варианта, вычитает за каждый провоцируемый перемещением удар, предпочитает оставаться на месте, если уже может сделать лучшее, и сближает дистанцию (сначала рывком, если набор правил перечисляет `dash`), когда ничего не достигает. Ограничен 48 клетками, а окно Game Master – 24 кандидатами.
- **Проверено** в `scripts/regressions/game-ruleset-combat-grid.regression.ts` (нарисованные вручную поля, заданные кубики, оба примера и побайтное сравнение), а также позиционными случаями в `ruleset-combat-director.regression.ts` и `ruleset-combat-director-route.regression.ts`.
- **Оставлено на потом**: укрытие на три четверти и полное укрытие, высота, полет над препятствиями, протискивание, скрытность и принудительное движение. Само окно реакции относится к C5b.

### Что определил C4b

C4b – поле на экране. Оно рисует разрешаемое C4a и не принимает собственных решений.

- **Экран следует ПРЕДСТАВЛЕНИЮ, а не предпочтению.** `DirectedCombatUI` размещает поле, когда представление набора правил несет `grid`, и сохраняет сцену Classic без него. Клиент отправляет `positioned: true` в `/start` ровно тогда, когда сражение принадлежит набору правил, предпочтение боя игры – Tactical, а разрешенный набор правил объявляет `combat.distance`; сервер всё еще решает, возможно ли вообще отобразить поле.
- **Один новый компонент представления**, `RulesetCombatBoard.tsx`. `TacticalCombatUI` не перестраивался: его палитры, текстуры, значки местности, тень клетки, ключевые кадры и функции жетонов без изменений переместились в `lib/tactical-board-look.ts`, импортируемый обоими полями. Поэтому они выглядят как один продукт, а новая тема местности не может разойтись между ними.
- **Клиент ничего не вычисляет.** Достижимые клетки и их стоимость, путь, провоцируемые шагом противники, допустимые цели и места наведения формы со всеми попадающими в нее берутся из представления. `lib/ruleset-combat-board.ts` индексирует их по клетке; единственное выводимое число – собственное расстояние набора правил, клетки на `perCell`, в котором выражен весь экран.
- **Один фокусируемый элемент на клетку.** Клетки – кнопки с перемещаемым tabindex и навигацией стрелками; жетоны нарисованы поверх с `pointer-events-none`, поэтому нажатие жетона означает нажатие клетки, а клавиатура имеет один смысл. Escape оставляет незавершенный выбор и возвращает клавиатуру меню, как требует правило C3: фокус возвращается только если окно закрыл ИГРОК.
- **Незавершенный выбор живет на поле**, которое передает его вниз в `RulesetCombatMenu` через необязательный управляемый `step`. Без этой пары меню сохраняет собственное состояние, а экран C3 побайтно остается прежним.
- **Поле сохраняет собственную минимальную высоту**, а меню, строка подсказки и журнал ограничивают себя отдельно. Измерено при 1366x850 и 375x812 во время сражения с журналом из 17 строк: нет горизонтальной прокрутки страницы и перекрывающихся жетонов, всё поле видно при обоих размерах.
- **Проверено** в `scripts/regressions/ruleset-combat-screen-client.regression.ts` (клетки, перемещение, путь, цель, наведения, предложения, правило "ничего не достать", форматировщик расстояния и четыре отказа на обоих примерах) и четвертом режиме `e2e/game-combat-director.e2e.ts`, проводящем позиционное сражение Ember Roads в настоящем браузере.

## Архитектура

### Привязка

```ts
type RulesetRef = {
  id: string; // bare for an official ruleset, "<owner>/<id>" or "local/<id>" for a community one
  version: number;
  packageId: string | null;
  source?: string; // where a community ruleset came from
  options: Record<string, boolean | number | string>;
};
// chat.metadata.gameRuleset?: RulesetRef   (absent means engine-legacy)
```

Записывается один раз при создании игры, как `gameExperienceId`. `gameRuleset` объявлен в интерфейсе `ChatMetadata`, поэтому определение пространства имен глаголов GM видит его как принадлежащий Engine. Неизвестная ID или закрепленная `version`, более новая, чем установленная декларация, переводит игру в доступный для восстановления режим только чтения с ясным сообщением, никогда не переинтерпретируя ее молча. Установленная декларация новее привязки принимается, поскольку листы читаются терпимо по текущей схеме. `RulesetRef` документа передачи реализации боя ограничивает `id` четырьмя встроенными именами; этот документ расширяет его до строки для существования наборов правил сообщества, что входит в запрошенное выше согласование.

### `ruleset.json` (Capability API 1.20)

Пакет перечисляет `ruleset.json` в `contributions.assets.paths`, закрепляя хеш в `files[]`. Обнаружение идет по зарезервированному имени файла, как у `gm-verbs.json`. Engine отклоняет файл при объявленном размере свыше 256 КБ до чтения, проверяет строгой общей схемой zod и отбрасывает с одной строкой журнала, если он непригоден. Пакет набора правил бесполезен без этой границы, поэтому объявляет 1.20, а более старые версии Engine корректно отклоняют установку.

Форма верхнего уровня (см. черновой файл): `id`, `version`, `name`, `edition`, `license`, `coverage`, `resolution`, `sheet`, `rests`, `gm`.

### Виды разрешения

`resolution.kind` – дискриминированное объединение. Реализованы два вида:

- **`dice-sum`** (этап 2): бросить кубики набора правил (по умолчанию 1d20), добавить модификатор характеристики, бонус уровня мастерства и свободный бонус листа и достичь либо превысить DC. Поддерживает преимущество и помеху, а также политику крайних граней одного кубика для каждого типа броска. У `5e-2014` эта политика для проверок и спасбросков – `none`, что намеренно отличается от `engine-legacy`. Первый черновик называл вид `d20-sum`; кубики стали параметром, чтобы системе 2d6 плюс характеристика не требовался собственный вид.
- **`dice-pool`** (этап 7b): бросить собственное число кубиков листа и посчитать достигшие цели, с необязательными удвоенными, взрывающимися и отменяющими гранями, критическими провалами, исключительными успехами и ситуативными кубиками. Тот же лист: то, что `dice-sum` прибавляет к броску, здесь является числом кубиков (§ Что определил этап 7b).

Общая арифметика листа обоих видов (`abilityModifier`, `proficiency`, `proficiencyTiers`) объявлена один раз и разворачивается в каждом члене, поэтому ее перекрестные проверки работают для каждого вида, а третий не может вырастить второе правило для того же числа.

Вычислитель сохраняет каждый инвариант, описанный текущим сервисом: никогда не выбрасывает исключение, невозможный бросок записывает тег незавершенным, придуманные GM числа заменяются, а запись в **Logs** (журналы) принадлежит Engine.

### Примитивы схемы листа

Закрытый набор: `abilities`, `skills` и `saves` (каждый может называть свою характеристику), типизированные `fields` (`number`, `text`, `longtext`, `boolean`, `enum`, `dice`), значения `derived` (закрытые операции `sum`, `stepTable`, `scale`, `min`, `max` над ссылками на значения), `lists` типизированных столбцов с `maxItems` и текущее состояние `live` (`pools`, `tracks`, `text`, `conditions`). Ссылка на значение – объект ровно с одним из `const`, `field`, `derived`, `abilityScore`, `abilityMod`, `abilityModFromField`, `skillMod`, `saveMod`; строк с выражениями нет. Редактор и лист в игре строятся универсально из этого. Не нужны ни клиентский код пакета, ни слот редактора.

Снаряжение намеренно не является списком: Game Mode уже владеет инвентарем. Лист несет `attacks` и введенное `ac`.

### Хранение: сборка и текущее состояние

| Часть | Содержимое | Место | Откатывается со свайпами |
| --- | --- | --- | --- |
| Начальная сборка | Всё, что вводит автор | Карточка: `data.extensions.rulesetSheets[rulesetId]`. Персона: `personaStats.rulesetSheets[rulesetId]` | неприменимо |
| Сборка игры | Копия при настройке; редактируется через Edit Sheet и повышение уровня | `chat.metadata.gameCharacterCards[].rulesetSheet` | Нет, как сегодня `rpgStats` |
| Текущее состояние | Текущие HP, временные HP, оставшиеся ячейки, кубики здоровья, счетчики класса, состояния, концентрация, истощение, спасброски от смерти | Снимок игрового состояния с ключом по имени карточки | Да |

Текущее состояние относится к снимку, поскольку команды листа относительны ("потратить одну ячейку 3-го уровня"), а перегенерированный ход не должен тратить дважды. У него отдельный столбец `game_state_snapshots.ruleset_live`, не потребовавший повышения `STORAGE_VERSION`. Чтение и запись ходом описаны в разделе "Что определил этап 5".

Каждый сохраненный лист имеет форму `{ v, build }` и отклоняется при сериализованном размере свыше 64 КБ.

### Интерфейс для GM

Когда набор правил игры разрешается, напоминание о формате каждого хода (`buildGmFormatReminder`, никогда не системный промпт):

1. заменяет встроенный абзац проверки навыка на `gm.checkGuidance` и шкалу сложности;
2. добавляет компактный блок листа каждого участника отряда внутри `<character_sheets>`: модификаторы характеристик, освоенные навыки и спасброски, поля `gm.sheetSummary`, оставшиеся ресурсы, отклоняющиеся от стандарта шкалы, заметки, активные состояния и списки сводки;
3. обучает одной принадлежащей Engine команде `[sheet: who="Name" op="…" …]` с закрытым набором операций: `spend`, `restore` (`heal` читается как `restore`), `damage`, `temp`, `track`, `condition`, `note`, `rest`. `concentrate` из первого предложения стал общим `note`.

Engine проверяет каждую операцию по текущему листу. Применение без оставшейся ячейки отклоняется, попадает в журнал, записывается обратно в ответ как отказ и показывается один раз за ход, никогда не применяется как отрицательный запас. `sheet` входит в набор зарезервированных тегов GM, а регрессионный тест имен глаголов находит обучаемый тег в напоминании. Без привязанного набора правил промпт побайтно совпадает с прежним; это фиксируют `game-ruleset-checks.regression.ts` и `one-request-dice-prompt.regression.ts`, а `pnpm regression:prompt` покрывает остальную часть промпта.

`[skill_check:]` получает необязательный `who=`. Без него проверяется игрок, как сегодня. Спасброски запрашиваются как `skill="Dexterity save"`, что существующий нормализатор уже распознает.

Заполнители кубиков одного запроса получают `PROF` (если у набора правил есть бонус мастерства), а также навыки, спасброски и характеристики набора правил по ID или подписи как разрешаемые имена, по существующему правилу: неразрешимое имя отклоняется, а не считается нулем.

### Настройка, редактор и интерфейс в игре

- **Мастер настройки**: локализованный выбор **Rules** (правила) рядом с представлением боя, не внутри него. По умолчанию используются собственные правила Marinara. Каждый установленный набор правил показывает `coverage.summary`. У участников отряда и персоны видно наличие листа для выбранного набора правил; при отсутствии предлагается редактор или пустая стандартная сборка. Генерация никогда не придумывает канонические значения.
- **Обмен настройками** (`game-setup-share.ts`): восстановить набор правил, если он установлен и совместим; иначе сообщить об этом и вернуться к стандартным правилам, как при импорте Experience.
- **Редакторы персонажей и персон**: под **Stats** по одному сворачиваемому подразделу на установленный набор правил, построенному из схемы. Сохраненные листы неустановленных наборов правил показаны одной строкой с кнопкой **Remove** (удалить).
- **Лист в игре** (`GameCharacterSheet.tsx`): при наличии набора правил отобразить его лист с текущими запасами, управлением отдыхом и расходом кубиков здоровья. Повышение уровня в v1 ручное: игрок редактирует сборку, производные значения пересчитываются.

### Импорт и экспорт

Чтобы листы передавались, ничего добавлять не нужно: `extensions` и характеристики персоны уже проходят через каждый импортер и схему. Правило – **сохранять неактивными, никогда не отбрасывать**: лист набора правил, которого нет у импортера, сохраняется под своим ключом, скрывается из промптов, показывается одной удаляемой строкой, ограничивается по размеру при импорте и проверяется по схеме набора правил лишь при первой установке и использовании этого набора. Отбрасывание незаметно уничтожило бы лист для того, кто установит набор правил позже, и для всех получателей после повторного экспорта.

Пока не проверено, сохраняют ли экспортеры Compatible JSON и PNG неизвестные ключи расширений. Проверить перед документированием поведения.

## Создание и распространение набора правил сообщества

**Создание.** Автор пишет один `ruleset.json` на основе файла 5e. Выбирает поддерживаемый Engine вид разрешения, объявляет лист, отдых и указания GM и проверяет по JSON Schema, сгенерированной из общей схемы zod и опубликованной с документацией, плюс небольшим скриптом проверки. Листа, введенного вручную через **Edit Spoilers** (редактировать спойлеры), достаточно для теста проверки до появления интерфейса редактора.

**Граница возможностей.** Данные могут только параметризовать существующий вид. Механика, не выражаемая ни одним видом (взрывающиеся кубики, процентный бросок ниже значения, степени успеха, лестница Fate), требует PR в Engine с новым видом и регрессионными тестами, а не файла набора правил. Это цена отсутствия языка сценариев, и авторская документация должна говорить о ней сначала, а не в конце. Авторы сообщества, уже реализующие эти механики, – подходящие участники для добавления видов, а их существующие случаи – готовые регрессии.

**Три пути распространения.**

| Путь | Как | Для чего подходит |
| --- | --- | --- |
| Официальный каталог | Добавить пакет в Marinara-Agents через PR; установка одним нажатием через **Download Agents** (скачать агентов) | Широко используемые системы с ясной лицензией |
| Собственный репозиторий | Существующий путь собственных репозиториев агентов также читает `rulesets/*.json`. Пользователь один раз добавляет GitHub-URL автора, проверяет предпросмотр и тем же способом получает обновления | Автор с несколькими системами; репозиторий автора запроса уже устроен так |
| Один файл | **Import ruleset** (импортировать набор правил) принимает один `ruleset.json` | Локальные итерации или передача файла другу |

Все пути сообщества защищены **Allow custom Agent imports**. Ничто не исполняется, но текст `gm.*` попадает в промпт GM, поэтому проверка импорта прямо это сообщает и требует к набору правил такого же доверия, как к импортированному промпту агента или лорбуку.

**Правила безопасного обмена.**

- Официальные ID не имеют пространства имен (`5e-2014`). ID сообщества получают его по источнику (`<owner>/<id>` для репозитория, `local/<id>` для файла), чтобы два авторских `v20` никогда не конфликтовали и ничто не могло перекрыть официальный набор правил.
- Декларации хранятся по ID и версии. Обновление добавляет версию и никогда не переписывает ее. Игра продолжает разрешать закрепленную версию; та же версия с другими байтами отклоняется с просьбой автору повысить ее.
- Лист читается терпимо по текущей схеме набора правил: неизвестные поля сохраняются, отсутствующие получают стандартные значения, выходящие за диапазон ограничиваются при редактировании, никогда при чтении. Скриптов миграции нет.
- `RulesetRef` сообщества несет URL источника. Поэтому общий файл настройки или неактивный лист может сообщить получателю, откуда взялся отсутствующий набор правил, а не только о его отсутствии.

Персонажи передаются самостоятельно. Карточка, экспортированная с листом сообщества, сохраняет его; получатель без набора правил сохраняет лист неактивным, и тот оживает сразу после добавления репозитория автора.

## Предложение: остальная часть каталогов

Статус: формат, маршрут, Capability API 1.21 и окно выбора редактора листа реализованы (§ Что определил этап 8a). Собственные материалы SRD выпущены в пакете `ruleset-5e-2014` 0.2.0, мост к бою реализован (§ Что определил мост к бою). Масштабируемые значения каталогов, команда `use` и Refresh from ruleset тоже реализованы (§ Что определил этап 8c). Потребность возникла при первом практическом использовании листа 5e: вводить заклинания, атаки и умения класса построчно мучительно, а автор сообщества захочет поставлять содержимое своей системы так же.

**Окно выбора.** Редактор листа получает кнопку **Add from catalog** (добавить из каталога) у каждого списка, заполняемого каталогом. Она открывает поиск с объявленными фильтрами каталога, множественным выбором и отметкой уже имеющихся в листе записей, читаемой из ключа `_catalog` выбранных строк. Записи читаются из маршрута каталога при открытии, никогда раньше. **Refresh from ruleset** (обновить из набора правил) использует ту же отметку, чтобы предложить новый текст измененной автором записи (§ Что определил этап 8c).

**Записи каталога и бой.** Лист и его каталоги не заставляют бой следовать набору правил. Сражения Tactical и Classic сегодня работают на собственной боевой модели Engine (`CombatSkill`: дальность, радиус области, уровень ячейки, множитель силы относительно характеристики атаки), и Engine ничего не разрешает по собственным правилам набора. Набор правил без блока `battle` вообще не читается сражением; с блоком он передает бою здоровье, энергию, ячейки и выбранные из каталога строки через мост (§ Что определил мост к бою), всё еще на арифметике Engine. Точное разрешение по правилам (спасбросок за половину урона, усиленное применение, экономика действий, допустимая для заклинания метамагия) – код, относящийся к адаптерам каждого набора правил из документа передачи реализации боя (`game-combat-rulesets-implementation.md`, его этап 5 для `5e-2014`), а не к файлу данных. Что каталог МОЖЕТ нести – факты, нужные такому адаптеру. Поэтому запись уже имеет необязательный типизированный блок `mechanics` из этапа 8a: дальность, форму и размер области, бросок атаки или спасбросок (объявленный листом и с действием успеха), кубики и тип урона, добавку одного шага большей стоимости, цели, концентрацию. Смысл в однократном вводе SRD. Меньший шаг, возможный до любого адаптера, теперь реализован (§ Что определил мост к бою): набор правил подключается через `battle`; в начале боя боец инициализируется из листа (здоровье как доля собственного максимума Engine, запас энергии, ячейки); отмеченные каталогом строки становятся навыками Engine (дальность в клетках, область, стоимость ячеек, стихия); затем здоровье, энергия и ячейки записываются обратно. Лист имеет значение в бою, пока арифметика урона остается у Engine; документация и интерфейс прямо говорят об этом.

**Раньше отложено, теперь реализовано.** Максимумы, растущие с уровнем (очки Ki равны уровню, применения Rage из таблицы), и помощник заклинаний (`[sheet: op="cast" spell="Fireball"]`, находящий ячейку) уже готовы (§ Что определил этап 8c). Строка записи несет ссылку на значение с необязательной ступенчатой таблицей для столбца; редактор пересчитывает при редактировании, никогда при чтении; помощник – общая команда `use`.

**Более дешевые улучшения без смены формата**, которые стоит делать параллельно: вставка списка имен в список для создания строк и уже перечисленное открытое решение 1 ("предложить лист по этой карточке", с проверкой и принятием пользователем).

**Собственное содержимое для `5e-2014`** после появления формата: заклинания SRD 5.1, умения классов SRD со счетчиками ресурсов (Second Wind, Action Surge, Rage, Ki, Channel Divinity, Bardic Inspiration, Sorcery Points, Wild Shape, Lay on Hands, Arcane Recovery) и таблица оружия SRD как готовые строки атак. SRD 5.1 лицензирован по CC-BY-4.0, поэтому текст может поставляться с уже имеющейся в пакете атрибуцией. Его нужно строить из авторитетной машиночитаемой копии SRD, никогда не вводить по памяти.

**Этапы.** 8a, Engine: формат каталогов, загрузчик ресурсов и маршрут, а также окно **Add from catalog** редактора листа с регрессионными тестами на втором наборе правил не 5e. Реализовано. 8b, Agents: `ruleset-5e-2014` 0.2.0 с каталогами SRD. Выпущено. 8c, Engine: масштабируемые значения каталогов, команда `use` и Refresh from ruleset. Реализовано. Каталоги сообщества в отдельных файлах (§ Что определил этап 8a объясняет их отсутствие) стали бы еще одним этапом.

## Открытые решения с вариантами по умолчанию

1. **Спутники без листа.** По умолчанию: пустая сборка и ручной ввод. Необязательное действие "предложить лист по этой карточке", которое пользователь проверяет и принимает, – разумное позднее дополнение, совместимое с принципом "генерация не создает канонические характеристики", поскольку принятие выполняет пользователь.
2. **XP или вехи.** По умолчанию: лист хранит XP, ничто не начисляет их автоматически, уровень редактируется вручную.
3. **Имя тега команды.** `[sheet:]` – предложение; подойдет любое имя, включенное в зарезервированный набор.
4. **Кто реализует `dice-pool`.** По умолчанию: пригласить автора запроса описать его в issue и при желании внести реализацию. У него работающая реализация и знание систем; сторона Engine предоставляет границу интеграции и проверку.

5. **Слои поверх набора правил (например, Low Magic на 5e).** Для L1 решено: слои, поставляемые набором правил внутри собственного файла; см. "Что определили слои L1". L2, слои от КОГО-ТО ДРУГОГО (ресурс пакета или импортированный файл с `appliesTo: { ruleset, minVersion }`, хранимый и версионируемый как набор правил сообщества, плюс статус разрешения "слой отсутствует"), остается открытым и повторно использует формат и применение L1 без изменений. Дальнейшее проектирование откладывается до слияния L1.

## Приложение: черновик issue

> **Game Mode: выбираемые наборы правил и листы персонажей для них (сначала 5e)**
>
> Запрошено автором Marinara-RPG-Extension, которому сейчас нужны четыре или пять агентов на каждый ход каждой системы, чтобы обойти проверки только на d20 и лист с шестью характеристиками. Предложение: набор правил – проверенные данные (`ruleset.json`, ресурс пакета с зарезервированным именем файла, как `gm-verbs.json`), задающие параметры закрытого набора принадлежащих Engine видов разрешения и объявляющие полный лист персонажа. Без кода пакета, строк выражений и дополнительных вызовов модели. Листы живут в карточках и персонах как начальные сборки и копируются в каждую игру.
>
> Это трактует "закрытый реестр встроенных адаптеров" документа передачи реализации боя как относящийся к видам разрешения и боевым адаптерам, с декларациями наборов правил в виде данных. Допустимо ли это, и работает ли кто-нибудь над смежной задачей? Собственный объем – `5e-2014` на SRD 5.1. Бой не меняется и остается в документе передачи реализации боя. Полный план: `docs/development/game-rulesets-and-sheets-implementation.md`.
