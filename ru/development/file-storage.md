# Файловое хранилище

В этом руководстве описана архитектура локального хранения данных в приложении Marinara Engine. О том, как выглядят папки с точки зрения пользователя, рассказано в руководстве [Где Marinara хранит ваши данные](../data/where-data-is-stored.md).

## Источник истины

Marinara хранит строки данных приложения как снимки в формате JSON в папке `DATA_DIR/storage`:

```text
storage/
├── manifest.json
└── tables/
    ├── chats.json
    ├── characters.json
    ├── messages/
    │   ├── <encoded-chat-id>.json
    │   └── ...
    ├── message_swipes/
    │   └── <encoded-chat-id>.json
    └── ...
```

Переменная `FILE_STORAGE_DIR` переопределяет расположение папки `storage`. Каждый файл таблицы содержит массив JSON. В файле `manifest.json` записаны версия формата хранения, время сохранения, идентификатор механизма хранения и число строк по каждой зарегистрированной таблице.

### Шардированные таблицы

Таблицы, привязанные к чатам и записываемые на каждом ходе, хранятся как **один файл на чат**, а не один большой файл. В монолитном варианте каждая сохраненная строка заново сериализовала и перезаписывала всю историю всех чатов. Формат хранилища 3 разделил `messages` и `message_swipes`; формат 4 распространяет ту же структуру на `memory_chunks`, `chat_images`, `agent_runs`, `agent_memory`, `conversation_call_sessions`, `conversation_call_messages`, `game_state_snapshots`, `game_engine_state`, `game_checkpoints`, `game_turn_storyboards`, `game_scene_videos`, `spatial_context_snapshots`, `ooc_influences` и `conversation_notes`. Официальный список — `SHARDED_TABLES` в `file-backed-store.ts`; его повторяет автономная команда `unshard` в `scripts/protect-launcher-data.mjs`, а регрессионный тест следит за совпадением. Каждая таблица выбирает шард по собственной колонке `chatId`, кроме двух случаев: `message_swipes` использует родительское сообщение, а влияния и заметки — `targetChatId`. `lorebooks` и `game_turn_storyboard_keyframes` намеренно остаются монолитными.

Отслеживание изменений работает на уровне файла чата, поэтому сброс затрагивает только измененные чаты. Шард с нулевым числом строк удаляется, а не записывается как пустой массив. Имена файлов получают процентное кодирование из id чата, а для слишком длинных или зарезервированных имен используется резервный вариант с хешем. Кодирование является границей безопасности, потому что импортированные профили могут содержать произвольные ids. Файлы служат только контейнерами; строки сохраняют свои ключи.

При первом запуске сборки с новыми шардированными таблицами существующие монолитные файлы мигрируют автоматически: строки группируются по чату и записываются в шарды, затем монолитный файл **и его `.bak`** переименовываются в `.pre-shard`. Это автоматическая резервная копия до миграции, которую Engine никогда не удаляет. Маркер `.migrating` делает восстановление после сбоя однозначным. Если старая сборка затем снова создаст монолитный файл рядом с шардами, приоритет получают шарды, а конфликтующий файл изолируется с датированным суффиксом `.post-downgrade-` и никогда не объединяется. Потерявшие родителя дочерние строки попадают в шард `orphaned-rows`, а не отбрасываются. Манифест, созданный более новым форматом хранилища, не загружается.

## Работа во время выполнения

Модуль `packages/server/src/db/file-backed-store.ts` при запуске загружает снимки таблиц в память. Сервер читает и изменяет эти строки через файловые операции из `db/file-query.ts`. Модуль `db/file-schema.ts` поставляет метаданные таблиц и столбцов для определений из `db/schema/`; эти метаданные устойчивы к совпадению имен.

Текучий API из `select`, `insert`, `update` и `delete` позволяет держать сервисы хранения компактными и не зависеть от внешней базы данных или ORM. Поддерживаемые фильтры и сортировка задаются явными объектами-выражениями, поэтому хранилище никогда не разбирает строки запросов.

Таблицы объявляют естественные ключи через `fileTable(..., { uniqueBy: [...] })`. При вставке и обновлении первичные и объявленные естественные ключи проверяются по полному варианту изменения – до того, как строки в памяти будут изменены. Поэтому нарушение ограничения оставляет таблицу нетронутой. Правило может содержать предикат `when`, если уникальность нужна только для части строк.

Скачанные пакеты возможностей могут содержать собственные экземпляры файловых таблиц. Хранилище сначала сравнивает объекты по идентичности, а затем сопоставляет такие экземпляры по зарегистрированному имени таблицы. Так код хранения внутри пакета безопасно работает с таблицами приложения Marinara Engine.

## Сохранение и восстановление

Запись помечает затронутые таблицы как измененные. Короткая задержка объединяет близкие по времени изменения, а страховочный таймер периодически сбрасывает отложенную работу на диск. При штатном завершении работы сервер ждет активные записи, а затем сохраняет строки, изменившиеся во время этой записи.

Каждый снимок сначала пишется во временный файл, сбрасывается на диск и затем атомарно переименовывается. Перед заменой предыдущий исправный снимок обновляется в виде файла `.bak`. Если при запуске основной файл не читается, Marinara по возможности восстанавливает его из резервной копии. Если непригодны обе копии, Marinara переносит испорченные файлы в карантин, добавляя к имени метку времени, и запускает пустой только эту таблицу – так интерфейс остается доступным для восстановления.

## Транзакции

Транзакции используют снимки с копированием при записи, а их область видимости задает `AsyncLocalStorage`. Таблица копируется только тогда, когда транзакция впервые ее изменяет. Если функция обратного вызова выбрасывает исключение, восстанавливаются только таблицы, измененные этой транзакцией. Параллельные записи в другие таблицы при этом не теряются.

## Добавление таблицы

При добавлении постоянно хранимых данных:

1. Определите таблицу в `packages/server/src/db/schema/` через `fileTable` и файловые построители столбцов.
2. Экспортируйте ее из `db/schema/index.ts`.
3. Объявите естественные ключи через параметр таблицы `uniqueBy`.
4. Зарегистрируйте имя таблицы в `FILE_BACKED_TABLES`.
5. При необходимости опишите каскадные связи или связи с обнулением в `file-backed-store.ts`.
6. Добавьте метаданные столбцов JSON в `services/mari-db/mari-db.service.ts`, если текстовое поле содержит структурированный JSON.
7. Проверьте, что резервное копирование и восстановление профиля работают.
8. Запустите `pnpm check` и подходящие регрессионные проверки хранилища.

Определения таблиц, метаданные связей, переносимость профиля и проверки Mari DB должны оставаться согласованными в рамках одного изменения.
