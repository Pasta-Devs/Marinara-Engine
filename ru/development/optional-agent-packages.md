# Дополнительные пакеты агентов и возможностей

Статус: реализовано в цикле разработки версии v2.3.0 в рамках задачи #3612.

## Цель

Базовая сборка приложения Marinara Engine не должна ни компилировать, ни поставлять реализации дополнительных агентов и возможностей. Новая установка начинает работу вообще без дополнительных пакетов. При обновлении сохраняются те возможности, которые были доступны до появления системы пакетов.

Официальный каталог, исходный код пакетов, воспроизводимые артефакты, скрипты проверки и порядок работы над правками собраны в репозитории [Pasta-Devs/Marinara-Agents](https://github.com/Pasta-Devs/Marinara-Agents). Установленные артефакты лежат внутри указанной папки данных приложения Marinara, поэтому обновления приложения не могут их перезаписать.

## Модель пакета

Пакет агента может добавлять одного или нескольких декларативных агентов, а также дополнительные доверенные исполняемые возможности:

- серверные точки входа для маршрутов, хуков жизненного цикла, источников промптов, обработчиков результата и миграций хранилища;
- клиентские точки входа для панелей, областей чата, разделов настроек, вариантов первоначальной настройки, элементов отображения во время работы и полноэкранных поверхностей режима Game;
- общие схемы JSON и стабильные контракты передачи данных;
- принадлежащие пакету файлы ресурсов, документацию и фрагменты знаний для Professor Mari.

Пакеты рассчитаны на версионированный API возможностей приложения Marinara. Импортировать закрытые пути исходного кода движка им запрещено.

Клиентские элементы возможностей получают выбранную локаль интерфейса движка через атрибуты `lang` и `dir`, а также
через объект `capabilityProps.localization`. Интерфейсы, принадлежащие пакету, хранят собственные файлы локалей и при
отсутствии перевода откатываются на английский язык пакета; движок не переводит ни промпты пакета, ни машинные
значения, заданные пакетом. При смене локали используется то же событие `marinara-capability-props`, поэтому
установленный интерфейс перерисовывается без перезапуска движка.

### Доставка и кеширование

Файлы установленных пакетов отдаются с надежными валидаторами, полученными из хешей SHA-256 каждого файла в манифесте. Эти же значения Engine использует для повторной проверки байтов при каждом чтении. Клиентский пакет (`/api/capability-packages/<id>/client`) и все ресурсы пакета всегда проходят повторную валидацию (`no-cache` вместе с `ETag`), поэтому неизменившийся файл отвечает `304 Not Modified`, а не скачивается заново, а повторно опубликованный файл подхватывается сразу. Ничто не отдается как `immutable`: правила установки разрешают повторно публиковать ту же версию с другими байтами, поэтому адреса пакетов не зависят от содержимого.

Capability API 1.1 добавляет универсальный фасад среды выполнения в контекст
активации на сервере. Пакеты могут читать текущее состояние отладки агентов и
писать в журнал сервера через логгер Pino движка, в том числе принудительно
включая режим отладки, без импорта закрытых модулей логирования и настройки
среды выполнения. Фасад дает набор операций, а не сами объекты движка.

Capability API 1.2 добавляет операции с чатами и сообщениями в рамках
транзакции, точечную запись метаданных чата и проверку существования записей
лорбука, а также хранилище совместимости для пространственных снимков. Пакеты
могут проверять изменения предметной области внутри транзакции движка и
атомарно сохранять метаданные вместе с сообщением-владельцем, свайпом или
пространственным снимком, не получая при этом ни дескриптор базы данных, ни
объект таблицы. За откат и совместимость с историческим хранилищем отвечает
движок, за проверку и правила предметной области – пакет. Тот же API отдает
нормализованные записи чатов и персонажей, выбор подходящих записей лорбука,
разбор ответов в формате, близком к JSON, и вызовы языковой модели с уже
разрешенными настройками. Учетные данные подключений, реализации провайдеров,
дескрипторы базы данных и объекты хранилища остаются закрытыми внутри движка.

### Клиентское пространство имен хоста

Состоянием клиента и библиотеками владеет Engine, и клиентские части пакетов агентов используют их, а не встраивают в свою сборку собственные копии. У копии свое отдельное состояние: клиентские части пакетов, встроившие хранилище настроек интерфейса, при каждой загрузке записывали его более старую версию поверх настроек Engine (Pasta-Devs/Marinara-Agents#1478), а каждое встроенное хранилище чата держало тот чат, который был открыт при загрузке страницы.

Прежде чем импортировать клиентскую часть первого пакета, Engine определяет одну глобальную переменную:

```ts
globalThis.__MARINARA_HOST__ = {
  version: 1,
  capabilityApi,
  stores,
  services,
  modules,
  queryClient,
  components,
  data,
  api,
};
```

Это свойство нельзя перезаписать или переопределить, а само пространство имен и его объекты `stores`, `services`, `modules`, `components` и `data` заморожены. Загрузчик пакетов (`useCapabilityClientModules`) загружает `lib/marinara-host.ts` через `import()` и дожидается `ensureMarinaraHost()`, прежде чем импортировать клиентскую часть любого пакета, поэтому к моменту выполнения модуля пакета пространство имен уже заполнено. Engine без клиентских частей пакетов его вообще не загружает. Если загрузить его не удается (например, из-за устаревшего фрагмента сборки после обновления), каждый пакет показывает свою обычную ошибку загрузки, а остальной Engine продолжает работать. Тип TypeScript – `MarinaraHostV1` в `packages/client/src/lib/marinara-host-contract.ts`, вместе со списками с этой страницы. Сборки пакетов объявляют совпадающие структурные типы, а не импортируют исходный код Engine.

| Свойство | Значение |
| --- | --- |
| `version` | `1`. Меняется, только когда ломается структура. |
| `capabilityApi` | `supportedCapabilityApi` из Engine, например `{ major: 1, minor: 341 }`. |
| `stores` | Живые хранилища zustand `ui`, `chat`, `agent`, `sidecar`, `dialog`, `gallery`, `encounter`, `gameState` и `backfill`. `chat` включает срез ожидающих пространственных переходов. |
| `services.tts` | Модуль `lib/tts-service.ts` (`ttsService`, `playWhenAvailable`, ...). |
| `services.dialogs` | Модуль `lib/app-dialogs.ts` (`showAlertDialog`, `showConfirmDialog`, `showPromptDialog`, `showChoiceDialog`). |
| `modules` | Модули библиотек с ключами по спецификатору импорта без пути (список ниже). |
| `queryClient` | Единственный `QueryClient` из React Query, с которым рендерится Engine. |
| `components.Modal` | `Modal` из Engine с его порядком наложения и обработкой Escape и кнопки "назад". |
| `data.emojiCatalog` | Модуль `lib/emoji-catalog.generated.ts`. |
| `api` | Модуль `lib/api-client.ts` (`api`, `ApiError`, `getApiErrorMessage`, ...). |

Пакет читает свойство только после проверки, например `const host = globalThis.__MARINARA_HOST__; if (host?.version === 1 && typeof host.stores?.ui?.getState === "function")`. Пространство имен только расширяется: новое свойство появляется вместе с новой минорной версией Capability API, и пакет, которому оно нужно, требует эту минорную версию. Пакеты, собранные под пространство имен, требуют ту версию Capability API, в которой оно появилось, поэтому более старый Engine никогда их не устанавливает и сохраняет уже установленную версию. Если свойства все же нет, пакет никогда не переходит на встроенную копию сервиса Engine с состоянием: хранилища `ui` и `chat` становятся копиями только для чтения, которые ничего не записывают, а все остальные свойства сообщают, что для этой функции нужна более новая версия Marinara Engine.

**Модули хоста.** `modules[specifier]` – это ровно то, что возвращает `import * as m from "<specifier>"` в собственной сборке Engine, включая `default`, если он есть у библиотеки. Спецификаторы: `react`, `react/jsx-runtime`, `react-dom`, `react-dom/client`, `@tanstack/react-query`, `zustand`, `zustand/middleware`, `sonner`, `zod`, `i18next`, `react-i18next`, `framer-motion`, `tailwind-merge` и `clsx`. Сборка пакета сопоставляет эти спецификаторы с шимами, которые читают пространство имен, поэтому пакет рендерится единственным экземпляром React из Engine и делит с Engine кеш React Query и всплывающие уведомления.

- Пакеты никогда не рендерят `<Toaster>` и никогда не создают `QueryClient`. `toast` из `sonner` показывается там, где пользователь настроил показ всплывающих уведомлений. Настройки запросов Engine по умолчанию (`staleTime` 30 секунд, одна повторная попытка, без повторного запроса при фокусе окна) действуют, если запрос не задает собственные параметры, а новый ключ запроса, принадлежащий пакету, начинается с id пакета.
- Пакет держит собственный экземпляр i18next из `i18next.createInstance()` внутри `<I18nextProvider>`. Он никогда не использует `initReactI18next`, `setI18n` или `setDefaults`, которые заменили бы экземпляр Engine.
- `lucide-react`, `chess.js`, `scheduler` и `@marinara-engine/shared` не являются модулями хоста; пакеты встраивают в свою сборку то, что из них используют.
- Пакеты собираются под такие мажорные версии: `react` 19, `react-dom` 19, `@tanstack/react-query` 5, `zustand` 5, `sonner` 2, `zod` 3, `i18next` 26, `react-i18next` 17, `framer-motion` 13, `tailwind-merge` 3 и `clsx` 2. Переход Engine на новую мажорную версию любой из них (в первую очередь React) ломает все пакеты, собранные под старую, поэтому требует **мажорной** версии Capability API. `scripts/regressions/marinara-host-namespace.regression.ts` падает, если мажорная версия в `packages/client/package.json` меняется, а контракт – нет.

**Поля хранилищ, которые читают пакеты.** Опубликованные пакеты сейчас читают эти поля. Engine сохраняет каждое из них, а удаление или переименование любого поля требует мажорной версии Capability API (`MARINARA_HOST_STORE_FIELDS` закрепляет их через `Pick<>`):

| Хранилище | Поля |
| --- | --- |
| `ui` | `achievementsEnabled`, `debugMode`, `includeReasoningInExports`, `enableStreaming`, `userStatus`, `enterToSendConvo`, `conversationCallVoiceVolume`, `conversationCallVoiceMuted`, `setConversationCallVoiceVolume`, `setConversationCallVoiceMuted`, `conversationTimeZone`, `noodleNavigation`, `setNoodleNavigation`, `noodleSelectedPersonaId`, `setNoodleSelectedPersonaId`, `reviewImagePromptsBeforeSend`, `musicPlayerEnabled`, `musicPlayerSource`, `sidebarOpen`, `setSidebarOpen`, `chatBackground`, `setChatBackground`, `characterDetailId`, `lorebookDetailId`, `presetDetailId`, `connectionDetailId`, `agentDetailId`, `toolDetailId`, `personaDetailId`, `regexDetailId`, `characterLibraryOpen`, `botBrowserOpen`, `gameAssetsBrowserOpen`, `modal`, `rightPanelOpen`, `closeModal`, `closeRightPanel`, `closeBotBrowser`, `closeAllDetails` |
| `chat` | `activeChatId`, `activeChat`, `isStreaming`, `streamingChatId`, `abortControllers`, `reset`, `pendingSpatialTransitions`, `setPendingSpatialTransition`, `clearPendingSpatialTransition`, `setPendingSpatialTransitionStatus` |
| `agent` | `setYoutubePlay`, `reset` |
| `sidecar` | `modelDownloaded`, `modelDisplayName`, `fetchStatus` |
| `dialog` | `dialog`, `openDialog`, `closeDialog` |
| `gallery` | `pinImage`, `pinVideo` |
| `encounter` | `reset` |
| `gameState` | `current`, `setGameState`, `reset` |
| `backfill` | `resetBackfill` |

**Хранилище браузера, которым владеет Engine.** Пакеты могут читать эти ключи, но никогда не записывают и не удаляют их: `marinara-engine-ui`, `marinara-engine-ui:host`, `marinara-active-chat-id`, `marinara-input-drafts` (в local storage и session storage), `marinara-pending-spatial-transitions`, `marinara-pinned-gallery-images` и `marinara_sidecar_prompted`. Они никогда не открывают базу данных IndexedDB `marinara-tts-audio-cache`. Чтобы изменить настройку, пакет вызывает действие хранилища, например `host.stores.ui.getState().setConversationCallVoiceMuted(true)`, и Engine ее сохраняет.

**Диалоговые окна приложения.** Engine рендерит свои окна предупреждения, подтверждения, ввода и выбора на самом верхнем слое – слое командной панели, поэтому окно, которое открывает пакет, показывается поверх собственного оверлея пакета и получает фокус.

**Сборки пакетов, созданные до появления пространства имен.** Они встраивают собственную копию хранилища интерфейса версии 74 и записывают в `marinara-engine-ui` только те настройки, которые знает эта копия. Engine также сохраняет каждую запись в копию `marinara-engine-ui:host`, доступную только хосту, а при загрузке игнорирует сохраненные данные версии старше своей, пока эта копия находится в текущей версии. Engine по-прежнему задает `globalThis.React` и `globalThis.ReactDOM` для установленных сборок, которые используют классическую среду выполнения JSX.

### Ветки чата в Capability API 1.7

Capability API 1.7 добавляет в `CapabilityChatRecord` нормализованные метаданные ветки:

```ts
branch: {
  title: string | null;
  parentChatId: string | null;
  parentMessageId: string | null;
  childMessageId: string | null;
} | null;
```

`title` – это сохраненное название ветки без пробелов по краям. Корневые чаты
возвращают `null`. Для веток, которые создал сам движок, доступны прямой
родительский чат, исходное сообщение развилки и скопированное дочернее
сообщение. У пустых веток привязки к сообщениям равны null. Устаревшие ветки,
испорченные метаданные и импортированные соседние чаты группы без известной
связи возвращают null в полях происхождения: движок не восстанавливает прежние
связи по догадкам. Обычный экспорт и импорт не переносят идентификаторы
родителя и сообщений, потому что при переносе между установками они меняются.
Удаление родителя не затрагивает происхождение дочерней ветки.

### Возможности Game Experience в Capability API 1.8

Capability API 1.8 добавляет Game Experience из пакетов, контекст промпта для каждого хода Game и запись ресурсов.

Пакет может предоставить целый Game Mode, а не дополнение к встроенному режиму. Он объявляет слот `game-surface` и выбирается при создании игры в блоке Experiences мастера настройки. Выбор записывается в игру и остается неизменным до ее конца, поэтому Experience не переключается посреди прохождения. Поверхность рисует собственные HUD, меню и бой поверх общей истории и объявляет, какие встроенные системы она заменяет. Все необъявленное остается встроенным, поэтому Experience отключает только то, что действительно реализует. Необязательное поле `contributions.gameSurface.surfaceClass` называет класс, который Engine применяет к области игры, пока поверхность подключена. Таблица стилей пакета может благодаря этому менять общий интерфейс, который рисуется за пределами собственного элемента.

Пакеты с разрешением `prompt-context` добавляют текст в системный промпт каждого созданного хода Game. Пакет с живым состоянием может так согласовать модель с тем, что видит игрок. Вклад может также объявить заменяемые встроенные игровые системы; Engine перестает указывать модели управлять ими. Вклады собираются для каждого хода и никогда не обязательны: пустой результат пропускается, а ошибка или превышение срока записывается в журнал и пропускается без влияния на генерацию.

Фасад ресурсов добавляет запись к чтению, поэтому настройка пакета может найти или создать Persona игрока и ее лорбук. Хранение, валидация и идентификаторы остаются у Engine; содержимое предметной области остается у пакета.

### Ресурсы пакета в Capability API 1.10

Capability API 1.10 добавляет общую доставку статических ресурсов пакета. Манифест может объявить `contributions.assets.paths` - список разрешенных изображений (`png`/`webp`/`gif`/`jpg`/`jpeg`) и файлов JSON внутри пакета, не более 256. Engine отдает их по адресу `/api/capability-packages/<id>/assets/<path>` через ту же цепочку проверки, что применяется к значкам вкладки: удержание пути в пределах пакета, наличие хеша в `files[]`, список разрешенных пассивных типов содержимого и повторная проверка целостности при каждом чтении. Схема отвергает активные типы документов (SVG, HTML и скрипты); у каждого объявленного пути должен быть закрепленный хеш в `files[]`; внутренний файл `manifest.json` пакета нельзя отдать даже после объявления. Для `contributions.assets` требуется манифест с `schemaVersion` 2 и `capabilityApi` 1.10 или новее; манифест v1 вообще не может его объявить. Ресурсы всегда проверяются повторно: как и клиентский пакет, они несут надежный `ETag` на основе хеша манифеста и отвечают на неизменившуюся проверку кодом `304 Not Modified` без тела. Набор тайлов скачивается снова, только если его байты действительно изменились. Ответы намеренно никогда не получают `immutable`, поскольку правила установки разрешают повторно опубликовать ту же версию с другими байтами, и адрес с номером версии не зависит от содержимого. Так Experience `game-surface` может поставлять настоящую графику, а не встраивать ее в клиентский пакет.

Манифест с нарушением этих правил отклоняется при установке одним из сообщений: "A declared package asset must be listed in the package file manifest", "contributions.assets requires schemaVersion 2 and capabilityApi 1.10 or newer", ошибкой расширения схемы для пути, который не ведет к изображению или JSON, либо, если имена в архиве отличаются только регистром и превратятся в один файл в файловой системе без учета регистра, "Package contains duplicate file" / "Package manifest declares files that collide on case-insensitive filesystems".

Каждый элемент возможности получает для этого свои идентификаторы: `capabilityProps.packageId` и `capabilityProps.packageVersion` приходят вместе с `localization`. Пакет строит адреса ресурсов в виде `/api/capability-packages/<packageId>/assets/<path>`, при необходимости добавляя `?v=<packageVersion>`, чтобы новая версия сбросила промежуточный кеш. Повторно загружать список установленных пакетов или разбирать собственный адрес импорта не нужно.

### Интерфейс боя Experience в Capability API 1.11

Capability API 1.11 добавляет интерфейс боя в свойства возможности `game-surface`. `combatActive` сообщает точный момент, когда встроенный интерфейс боя действительно подключается. В отличие от него, `chatMeta.gameActiveState`, сюжетное состояние сцены GM, отстает от переключения и может указывать "combat", когда столкновения еще нет. `combatStyle` передает действующий стиль (`classic` или `tactical`). `requestCombat()` просит Engine создать столкновение тем же путем, что и кнопка Start Combat, но без окна подтверждения, поскольку собственный интерфейс Experience уже выразил намерение. Процесс генерации Engine по-прежнему решает, каким будет столкновение. Способа напрямую передать из пакета участников или состояние боя намеренно нет: бой остается под управлением Engine.

`requestCombat()` сохраняет стабильную идентичность, не показывает уведомлений на стороне пакета и возвращает код, по которому Experience рисует собственный ответ: `"started"` или отказ `"combat-active"`, `"pending"` (генерация уже идет), `"no-turn"` (GM еще не написал ход) либо `"unavailable"` (завершенная сессия или повтор). `combatPending` и `combatError` отражают ход и ошибку генерации, поэтому после сбоя пакет не остается ждать `combatActive`. Как интерфейсы 1.7 и 1.8, но в отличие от жестко ограниченного `contributions.assets` из 1.10, эти свойства передаются всем пакетам `game-surface` независимо от объявленного `capabilityApi`. Метка 1.11 показывает время их появления; пакет, которому они нужны, объявляет 1.11, и старый Engine корректно его отвергает.

### Пространственные события для владеющего Experience в Capability API 1.12

Capability API 1.12 адресует пространственные события еще и пакету Experience, которому принадлежит игра. `spatial_transition_committed`, `spatial_transition_rejected` и нетипизированный сигнал `spatial_context_refresh`, прежде адресованные только `hierarchical-maps` в событии окна `marinara-capability-server-event`, теперь дополнительно отправляются с `packageId`, равным `gameExperienceId` чата. Полезная нагрузка различается: подтвержденное событие несет `{ chatId, commandId, currentLocationId, definitionRevision, travel? }`; отклоненное несет `{ chatId, commandId, code?, message? }` без полей места, поскольку перемещения не было; сигнал обновления несет `data: null`. Experience, отправивший команду путешествия через аргумент `pendingSpatialTransition` функции `sendMessage`, может подтвердить или убрать путешествие сразу после того, как хост узнает результат, а не выводить его из последующих чтений. Версия 1.12 закрывает и пробел в World Maps: переходы, отклоненные на одном из двух тихих путей HTTP, при подтверждении хода владельца до потока во время генерации или при отдельном подтверждении REST, раньше вообще не создавали события. Теперь оба пути создают `spatial_transition_rejected` только при окончательном доказательстве, то есть коде ошибки `spatial_*`, отличном от `already_applied`. Неоднозначные сбои, например сетевая ошибка, при которой мог потеряться ответ об успешном подтверждении, вместо этого отправляют нетипизированный сигнал `spatial_context_refresh`. Получатели сверяются с сервером, а не принимают выдуманный результат. Подтвержденное событие с `travel.mode` равным `"step_by_step"` и `complete: false` означает, что путешествие продолжается; сохраняйте ожидание до завершающего события. Это мягкий интерфейс, как 1.11: события приходят независимо от объявленного `capabilityApi`. Объявляйте 1.12, только если пакет от него зависит.

### Временное сворачивание повествования в Capability API 1.13

Capability API 1.13 добавляет `requestsCollapsedNarration` в объявление интерфейса, которое пакет `game-surface` передает в `setExperienceChrome`. Пока флаг равен true, блок повествования Game Mode сворачивается до узкой ручки, чтобы Experience мог освободить экран для заставки или полноэкранного эпизода.

Это ЗАПРОС, а не настройка. Выбранное игроком состояние сворачивания никогда не записывается, а флаг действует только пока Experience является активной поверхностью. Уберите флаг или перестаньте быть активной поверхностью, и блок вернется в выбранное игроком состояние. Это гарантия, что после запроса он всегда откроется снова; пакет намеренно не может сохранить сворачивание навсегда.

Правила безопасности Engine важнее запроса. Блок принудительно открывается, когда на экране видно поле ввода игрока, в том числе в самом начале сцены до первого сегмента, и когда активны элементы перехода к следующему сегменту. Только через них можно закончить ход; пакет, способный их скрыть, мог бы навсегда заблокировать игрока. Ручка также продолжает показывать индикатор внимания при ожидающем повторе анализа сцены, генерации или генерации боя. Если игрок вручную открыл блок во время запроса, он остается открытым до конца запроса. Как 1.11 и 1.12, это мягкий интерфейс: поле действует независимо от объявленного `capabilityApi`. Метка 1.13 показывает время появления, поэтому зависящий от поля пакет объявляет 1.13.

### Capability API 1.14: поверхности трекеров и жизненный цикл агента

Capability API 1.14 добавляет два значения `contributions.slots` для активных, включенных пакетов агентов Roleplay с клиентской точкой входа:

- `roleplay-tracker` монтирует представление пакета `toolbar` в HUD Roleplay. Свойства включают `chatId`, `chatMode`, `mobileCompact`, класс хоста `toolbarButtonClass`, `onRerunTracker`, `trackerRetryBusy`, `lockMode` и `onToggleLockMode`. Обратные вызовы необязательны: проверяйте их наличие перед использованием.
- `tracker-panel` монтирует представление пакета `tracker` внутри существующей Tracker Panel с `chatId`, `chatMode` и `detached`. Используйте эту поверхность хоста вместо открытия второй панели. Оба слота также получают обычные свойства идентификации возможности и локализации.

Вклад в контекст промпта по-прежнему регистрируется через `api.registerPromptContext` и требует `prompt-context`. Запрос теперь предоставляет `targetCharacterIds`, `personaId` и `placedAgentTypes` (необязательные для совместимости). `placedAgentTypes` сообщает поставщику, какие разделы данных агентов пресет уже разместил, чтобы не дублировать контекст. Хост сохраняет идентичность пакета каждого вклада в `packageBlocks`, размещая текст пакета в соответствующем разделе агента. Поставщик текста для определенной аудитории должен учитывать переданные идентификаторы целевых персонажей.

Серверная точка входа может также зарегистрировать собственную службу жизненного цикла постобработки через `api.registerService("agent-runtime:<package-id>", service)`. Требуется `agent-runtime`; регистрация под чужим идентификатором пакета отклоняется. Необязательные хуки:

```ts
const cleanup = api.registerService(`agent-runtime:${packageId}`, {
  prepareContext({ agent, context }) {
    // Return small, JSON-serializable context for this agent, or nothing.
    return { chatId: context.chatId };
  },
  finalizeResult({ agent, context, preparedContext, result }) {
    // Validate or enrich the result before the host publishes/applies it.
    return result;
  },
});
// Return cleanup from activate(), or include it in the activation cleanup.
```

`prepareContext` выполняется до постобработки; ненулевой результат ограничен этим агентом и включается в его промпт как сериализованный контекст среды. `finalizeResult` получает это значение и сгенерированный результат, возвращая `AgentResult`. Генерация и ручной повтор откладывают публикацию до финализации. Каждый асинхронный хук ограничен двумя секундами: неудачная подготовка записывается в журнал и пропускается, а неудачная финализация превращает результат в ошибку вместо применения непроверенных данных. Это короткие хуки хоста, а не место для еще одного долгого вызова модели.

У дополнений нет отдельного ограничения по версии 1.14 для каждого поля. Пакет может проверять наличие необязательных свойств и упрощать поведение в старых Engine, но если ему нужны слоты, размещение или жизненный цикл, он должен объявить `capabilityApi: { major: 1, minor: 14 }` в манифесте v2, чтобы старый Engine корректно отказал в установке.

### Capability API 1.15: текущая конфигурация эмбеддингов

`api.runtime.resolveEmbeddings()` возвращает новый `Promise<CapabilityEmbeddingHost>` с текущей конфигурацией подключения агента пакета. Вызывайте его в начале операции эмбеддингов вместо кеширования `api.runtime.embeddings`: это снимок на момент активации, который без повторной активации не учитывает последующие изменения подключения.

```ts
const embeddings = await api.runtime.resolveEmbeddings();
const vectors = await embeddings.embed(texts, signal);
// Store/compare embeddings.spaceId with persisted vectors; do not mix embedding spaces.
```

Возвращенный хост имеет `spaceId`, `label` и `embed(texts, signal?, inputType?)` (тип входных данных описан в разделе Capability API 1.68). Разрешение использует настроенный источник эмбеддингов, а при его отсутствии или ошибке конфигурации переключается на встроенный локальный MiniLM. `embed` может вернуть `null`; пустые пакеты, более 128 текстов или более 200 000 символов суммарно отклоняются. Новый хост не пересчитывает существующие векторы, поэтому пакет должен обработать смену `spaceId` до сравнения новых векторов с сохраненными.

В текущих Engine метод доступен независимо от объявленной версии API пакета. Объявляйте API 1.15, если требуется следовать изменениям подключения. Пакет, намеренно поддерживающий старые Engine, может проверить `typeof api.runtime.resolveEmbeddings === "function"` и вернуться к `api.runtime.embeddings`, принимая ограничение снимка на момент активации.

### Capability API 1.16: команды Game Master, объявленные пакетом

Capability API 1.16 позволяет Experience объявить короткий закрытый список именованных действий Game Master – команд, которые Engine помещает в напоминание формата GM, извлекает из готового повествования и выполняет от имени пакета. Серверный код пакета при этом не запускается, поэтому Experience `game-surface` только с точками входа `agents` и `client` тоже может менять свой мир словами GM.

Весь интерфейс действует: схема, правила зарезервированных имен и владения ключами, чтение таблицы, отрисовка промпта и исполнитель. Команды пакета с таблицей и `chat-write` попадают в напоминание GM на каждом ходе Game привязанного чата и выполняются при использовании моделью. Чат без пакета или с пакетом без таблицы не разрешает ни одной команды; его ход побайтово совпадает с ходом до появления интерфейса.

Пакет объявляет таблицу как `gm-verbs.json`, перечисляет ее в `contributions.assets.paths` и закрепляет хешем в `files[]`, как любой ресурс. Поиск идет по зарезервированному имени файла; это новое соглашение: остальные файлы конвейера являются объявленными путями, читаемыми по имени (`entrypoints`, пути значков и ресурсов), и по структуре больше ничего не ищется. У пути ресурсов есть два существенных следствия. Файл в `files[]`, отсутствующий в `contributions.assets.paths`, молчит в обоих направлениях: установка и сборка каталога проходят, у пакета просто нет команд, и диагностики нигде нет. Объявленный ресурс также доступен без защиты по `/api/capability-packages/<id>/assets/gm-verbs.json`, поскольку маршрут ресурсов не проверяет привилегированный доступ: таблица никогда не должна содержать чувствительные данные. Как 1.11–1.13, это мягкий интерфейс: старый Engine видит обычный JSON-ресурс и игнорирует его, поэтому таблица не обязана сужать диапазон установки. Объявляйте `capabilityApi` 1.16 только если пакет _требует_ выполнения команд: такая декларация запрещает установку на каждом более старом Engine.

Документ имеет вид `{ "schemaVersion": 1, "verbs": [ … ] }` и содержит от одной до шестнадцати команд. Каждая команда строгая: неизвестный ключ внутри нее вызывает отказ, а не тихое принятие дополнения. Неизвестные поля рядом с `schemaVersion` и `verbs` намеренно обрабатываются двумя поверхностями по-разному: собственный читатель Engine удаляет их, чтобы таблица для новой версии сохраняла понятные этой версии команды; общая схема документа для авторских инструментов строгая и их отклоняет. Проверка по схеме, таким образом, строже поведения Engine во время выполнения, что полезно при написании:

```json
{
  "schemaVersion": 1,
  "verbs": [
    {
      "name": "weather",
      "description": "Set the sky when the weather visibly changes.",
      "effect": "state",
      "metadataKey": "pixelforgeWeather",
      "args": [
        { "name": "word", "type": "string", "enum": ["fair", "overcast", "rain", "storm", "snow"] },
        { "name": "intensity", "type": "string", "enum": ["light", "heavy"], "optional": true }
      ]
    }
  ]
}
```

Имя команды соответствует `[a-z][a-z0-9_]*`, содержит до 32 символов и не может совпадать с собственным тегом GM в скобках Engine. Проверка не учитывает регистр: напоминание выводит `[Note:` и `[Book:` с заглавной буквы, а поставляемое регулярное выражение парсера нечувствительно к регистру, поэтому `note` перекрыло бы тег журнала. Зарезервированный набор выводится из всех тегов, которые напоминания GM и группы могут выдавать во всех ветвях, и тегов, извлекаемых пятью парсерами повествования Engine: клиентскими парсером тегов и форматтером повествования, серверным редактором сегментов, анализатором сцен sidecar и переписывателем диалогов маршрута генерации. Их словарь шире напоминаний: он включает токены диалога `main`, `side`, `extra`, `action`, `thought`, `whisper` и пару QTE `qte_bonus` / `qte_result`, распознаваемую только форматтером повествования. Последняя группа объясняет необходимость защиты: команда `whisper` вырезала бы `[whisper:Tam]` из строки диалога до сохранения хода, и строка навсегда перестала бы быть диалогом. Это закреплено регрессией, включая экстракторы: парсер, дающий уникальное имя – `party-chat` / `party-turn` парсера тегов или пару QTE форматтера, – должен продолжать его давать, иначе выпадение источника ломает сборку вместо сужения защиты. Три источника без уникальных имен тоже сканируются, чтобы поймать тег, впервые появившийся у них. Полнота не обещается: встроенный тег вне сканируемых файлов или в непонятной экстрактору форме будет пропущен, поэтому при новом парсере набор расширяют. Обычные слова тоже зарезервированы: `action`, `state`, `status` и `note` – встроенные теги, поэтому отказ для простого имени обычно объясняется этим правилом, а не опечаткой. `description` занимает одну строку из 1–200 символов без квадратных скобок и переносов, потому что дословно попадает в строку команды блока `COMMANDS:`. Переносом считаются не только CR и LF, но и `U+0085`, `U+2028`, `U+2029`, завершающие строку для читателей блока. Управляющие C0 и DEL тоже запрещены – вероятнее всего встретится табуляция, – поскольку они меняют структуру без завершения строки. Дословная вставка не исключает последующий проход макросов: все напоминание раскрывается перед отправкой, поэтому `{{…}}` в описании раскрывается, включая макросы, _записывающие_ переменные чата, например `{{setvar::…}}`. Это не расширяет уже выданное `chat-write`, но легко происходит случайно; не помещайте скобки макросов в описание без намерения. Команда принимает до шести аргументов, каждый `{ name, type, enum?, maxLength?, optional? }`, с именем `[a-z][a-zA-Z0-9_]*` до 32 символов. Шаблон намеренно шире имени команды без заглавных букв: аргумент – ключ JSON, а не тег. Только строковый аргумент может иметь `enum` (1–16 различных значений: повтор ничего не добавляет и отклоняется, как остальные дубликаты таблицы). Строка _без_ enum должна объявить `maxLength` (1–500): локальный разбор исполнителя не наследует собственного предела, и неограниченный текст мог бы затянуть в пакет целый фрагмент повествования. Сочетание `enum` и `maxLength` отклоняется: enum уже ограничивает значение. Данные – плоский однострочный JSON, поскольку вложенная `}` преждевременно завершает совпадение тега. Разбирается одно вхождение каждого имени на сообщение, поэтому повторная команда применяется один раз.

Все это не нужно перечислять в описании. Строка напоминания строится из разобранной таблицы: схематические данные, затем описание, затем один пример для копирования:

```
- [weather:{"word":"fair|overcast|rain|storm|snow","intensity"?:"light|heavy"}] — Set the sky when the weather visibly changes. Example: [weather:{"word":"fair"}]
```

Именно схема учит словарю: все аргументы по порядку объявления, необязательные помечены `"name"?:` вне JSON-строки, enum показан всеми альтернативами, строка без enum – пределом, а число и логическое значение – без кавычек, поскольку валидатор отклоняет `"3"` вместо преобразования в число. Пример – один конкретный случай с одним значением enum, поэтому не годится как единственный учебный материал: GM, видящий только `{"word":"fair"}`, пишет "sunny", валидатор отклоняет не показанное ему слово, и отказ незаметен. Тег удаляется по совпадению имени, не по успешной проверке: повествование чистое, а мир не изменился. Выведение обеих частей из одной таблицы предотвращает расхождение: описание больше не хранит значения и не обещает того, что отвергнет валидатор. Используйте 200 символов для объяснения, _когда_ нужна команда, а не для повторения аргументов.

Деградация происходит для каждой команды отдельно. Непригодная команда – новый `effect`, непредставимая форма или отклоненная декларация вроде зарезервированного имени либо чужого ключа – удаляется с записью в журнале; все понятные команды продолжают работать. Это то же правило, что `parseCapabilityCatalogWithCompat` применяет к записям каталога. Отказ поэтому тихий: читайте журнал, если объявленная команда не появляется. Непригодный целиком документ (неизвестный `schemaVersion`, пустой `verbs`, не объект) дает пустую таблицу и одну запись. Таблица также отклоняется до чтения по _объявленному_ `files[].bytes` при 64 KB: `files[]` допускает до 100 MB, и другого ограничения ресурса до чтения нет. При любом отказе ход остается нетронутым.

Команда с `metadataKey` – **команда состояния**: все ее аргументы записываются под этим ключом строки метаданных чата, и пакет видит изменение через уже получаемые свойства. Без `metadataKey` это **команда события**: она доставляется вживую как клиентское событие возможности, без постоянной записи, очереди, повтора или подтверждения. `metadataKey` запрещен для события, чтобы оно не занимало незаписываемый ключ, и обязателен для состояния.

Перед выбором учитывайте различия. Запись состояния долговечна и никогда не откатывается: смена варианта, редактирование или удаление хода оставляют значение. Побеждает последний _сгенерированный_, а не последний _показанный_ вариант, поэтому текст и мир могут расходиться в одной сессии без согласования. Событие ничего не помнит: один кадр, одна синхронная отправка. Оно бесследно теряется при прерывании хода, закрытии или перезагрузке вкладки посреди потока, отправке до первого монтирования пакета, переключении игрока в другой чат и во время собственной блокировки загрузки пакета. Повторной доставки нет. Зато эффект события откатывается вместе с сюжетом, если пакет хранит его там, где перемотка восстанавливает состояние; строка метаданных чата не перематывается. Единственная потеря без следа в обоих вариантах – событие, примененное к живому состоянию, но потерянное при полной перезагрузке до следующего сохранения пакета.

Относительная семантика поэтому намеренно запрещена в обоих вариантах. Команда состояния по конструкции не выражает "добавить пять золотых": запись является абсолютной заменой. Относительная команда _события_ запрещена правилом: регенерация создает новый индекс варианта и не переносит отметки предыдущего, поэтому эффект накапливается для каждого созданного варианта. Дедупликация по `chatId:messageId:swipeIndex` защищает повторную доставку, которой канал и так не делает, но не регенерацию, которую делает. Повторное применение безопасно благодаря абсолютности, а не реестру. Относительный словарь допустим здесь только после преобразования в абсолютный для каждого сообщения.

В ходе с обоими видами синхронная отправка события приходит в пакет _до_ асинхронного обновления состояния. Обработчик события не должен рассчитывать прочитать новое значение команды состояния из того же хода.

Асимметрия отказов намеренная. Engine проверяет только форму: имена аргументов, типы, принадлежность enum, пределы строк. Семантика принадлежит пакету: имена NPC нельзя перечислить при объявлении, если мир компилируется для каждого чата. Для состояния отказ пакета _рекомендательный_: к моменту получения метаданные уже записаны. Для события тот же отказ _обязателен_: Engine ничего не зафиксировал, поэтому пакет действительно отклоняет неизвестное имя.

`metadataKey` команды состояния должен принадлежать объявляющему пакету по трем правилам. Ключ начинается с идентификатора пакета в camel case (`hierarchical-maps` → `hierarchicalMaps`), затем идет непустой суффикс с заглавной буквы, не позволяющий одному пакету присвоить чужое пространство имен префиксом. Нормализованный идентификатор не может совпадать с пространством метаданных Engine или расширять его на границе заглавной буквы. Список пространств выводится из всех ключей верхнего уровня `ChatMetadata`, собственных констант ключей Engine и ключей индексной сигнатуры интерфейса вне его объявления: `encounterActive`, `internalAssistant`, `imageGenConnectionId` и других необъявленных метаданных, невидимых первым двум источникам. Третья группа требует семи источников, поскольку Engine читает и пишет метаданные разными способами: объект вызова `patchMetadata`/`updateMetadata`; объект, _возвращаемый_ обратным вызовом обновления (примерно столь же частый); клиентская мутация `useUpdateChatMetadata()` и свойство `onMetadataChange` (вообще не используют `patchMetadata`); прямые клиентские вызовы `PATCH /chats/:id/metadata` (обходят и этот хук – так Game пишет ключи боя, сцены и повествования); чтения свойств `chatMetadata.key` и `chat.metadata.key`; чтения результата `parseChatMetadata(…)` – самый частый прием Engine и единственный, видящий такие ключи, как `scenario`; наконец, ручной список ключей метаданных чата для профилей настроек, где обнаруживаются ключи, читаемые и записываемые целиком через границы функций.

Все это закреплено регрессией, включая экстракторы. Два случая намеренно исключены из обходов. Запись, получающая переменную или результат вспомогательной функции (`patchMetadata(id, hydratedMeta)` либо такая же форма на маршруте метаданных), фиксирует ключи, недоступные статическому обходу; сейчас таких вызовов двадцать, и регрессия закрепляет число, поэтому двадцать первый ломает сборку до ручного изучения. Чтение _внутри_ функции из параметра межпроцедурное и недоступно обходу чтений: так устроен `spatialContext`, записываемый клиентом пакета `hierarchical-maps` из репозитория Agents, а читаемый здесь через вспомогательную функцию и локальный для файла разбор. Второй пробел закрывает ручной список, поэтому один из семи источников поддерживается вручную, а не выводится. Механизм называет свои слепые зоны. `persona` добавлен вручную как нижняя граница, не производимая сейчас источниками. Третье правило намеренно отклоняет целые пакеты: `conversation-calls` превращается в `conversationCalls`, а `conversationCalls` + `Enabled` уже является ключом Engine, поэтому пакет не может владеть метаданными под своим идентификатором. `noodle` и `background` в том же положении; `background` само является ключом Engine. Они все еще могут объявлять события, не владеющие ключами. Ключи плоские и верхнего уровня, потому что именно такую структуру читает существующий механизм согласования пакета.

Команды работают только для установленного и готового пакета с `chat-write`. Это разрешение также ограничивает записи через API хранения пакета: сообщения, метаданные чата, события roleplay и пространственные снимки. `chat-read` ограничивает чтение чатов, сообщений, состояния игры и пространственных снимков. Проверки действуют и в транзакциях хранения, и в блокировках чата; право записи не дает права чтения. Собственные вызовы хранения Engine остаются доверенными.

После установки подробности **Download Agents** (загрузка агентов) показывают разрешения установленной версии. Если версия каталога просит другие разрешения, они показаны отдельно. Установка и обновление кода по-прежнему требуют существующего одобрения, привязанного к точной версии и контрольной сумме; команды модели не требуют отдельного одобрения на каждом ходе.

Это проверки API, не песочница JavaScript. Разрешения сети, хранения и UI – декларации доступа. Браузерный и серверный код пакетов остается доверенным и может обращаться к окружению хоста; устанавливайте только доверенные пакеты. Проверяется готовность, а не возможность отдавать файлы: обновление, оставившее `restart-required`, останавливает разрешение команд до перезапуска Engine.

### Capability API 1.17: подготовка Experience перед первым ходом

Пакет `game-surface` может объявить `contributions.gameSurface.prepareBeforeStart: true` при версии схемы 2 и Capability API 1.17. Engine монтирует эту поверхность, когда игра готова, до включения **Start Game** (начать игру). Классические игры и пакеты без этого флага сохраняют прежний порядок запуска.

Основная поверхность, включившая эту возможность, получает два дополнительных свойства:

- `startup: boolean` остается true, пока игрок не завершит вступление Engine кнопкой **Continue** (продолжить). Пока значение true, приостановите симуляцию мира и действия игрока.
- `setStartupReady(context: string | null): void` сообщает состояние подготовки. Передавайте `null` во время загрузки, сохранения или восстановления после сбоя. Передавайте строку только после того, как фактический мир надежно сохранен и пригоден к использованию; пустая строка разрешает запуск без дополнительного контекста.

Хост блокирует **Start Game**, подтверждение подготовки виджетов и повторные попытки первого хода до получения строки готовности. Во время блокировки собственный интерфейс загрузки и ошибки с повторной попыткой пакета остается видимым. После готовности пакет скрывается за обычным вступлением Engine. **Continue** открывает обычную поверхность, которая может монтироваться заново: сделайте подготовку мира идемпотентной и восстанавливайте сохраненное состояние вместо повторной генерации. Возврат к игре, вступление которой уже завершено, не повторяет начальную подготовку.

Контекст вступления ограничен **8 000 символами**. Некорректный или слишком большой контекст сохраняет блокировку запуска и показывает ошибку; хост не обрезает факты о мире. Передайте компактное описание подготовленной начальной локации и ее фактического состава персонажей. Engine добавляет этот текст к существующему `generationGuide` первого хода с источником `game_start`, чтобы вступление использовало уже существующий мир. Это не регистрирует контекст для последующих ходов; для них продолжайте использовать обычный вклад пакета в промпт или контекст генерации хода.

Обратные вызовы готовности относятся к смонтированному чату, игре и пакету. Запоздалые вызовы из другой области игнорируются. Сбой модуля или среды выполнения блокирует запуск, а не считает отсутствие контекста мира успехом. После перезагрузки пакет должен сообщать готовность на основе сохраненного мира. Серверный поставщик контекста промпта по-прежнему работает только на чтение и ограничен коротким сроком выполнения; не используйте его для генерации мира или длительной блокировки запуска.

### Capability API 1.19: инструменты из пакетов

Capability API 1.16 позволял пакету побудить модель что-то _сказать_, чтобы затем на это отреагировать. Эта версия позволяет модели что-то _вызвать_. Пакет с новым разрешением `tools` регистрирует именованный инструмент в серверной точке входа. Engine предлагает его вместе со встроенными инструментами на каждом ходе каждого чата, проверяет вызов по JSON Schema пакета и передает аргументы обработчику.

```ts
export async function activate({ api }) {
  api.registerTool({
    name: "set_time",
    description: "Move the world clock forward or back.",
    parameters: {
      type: "object",
      properties: {
        action: { type: "string", enum: ["advance", "rewind"] },
        minutes: { type: "integer", minimum: 0 },
      },
      required: ["action", "minutes"],
      additionalProperties: false,
    },
    handler: async (args, { chatId }) => {
      const clock = await moveClock(chatId, args.action, args.minutes);
      return { time: clock.label };
    },
  });
}
```

Вызовы инструментов выбраны вместо формата ответа намеренно. Формат занимает весь ответ: повествование пришлось бы поместить в поле JSON-объекта, и оно не могло бы поступать потоком. Вызов инструмента может идти рядом с текстом, пока модель пишет свой ход. Пакет получает аргументы, уже ограниченные провайдером, вместо извлечения их из готового повествования. Схема задает обязательные правила; соглашение лишь просит модель их соблюдать.

Разница особенно заметна с перечислениями. Если пакет знает двенадцать мест, он может внести их названия в схему. Тринадцатое название будет отклонено до передачи обработчику. Существующий валидатор аргументов Engine указывает допустимые значения, чтобы модель могла исправить вызов. Возвращенное обработчиком значение показывается модели как результат инструмента.

Перед созданием инструмента учитывайте следующие правила:

- Имена имеют вид `<packageId>_<name>`, где `-` заменяется на `_`: `set_time` из `world-clock` становится `world_clock_set_time`. Имя, уже занятое другим пакетом, отклоняется. Встроенные и включенные пользовательские инструменты сохраняют совпадающие имена; определение пакета не добавляется. Полное имя ограничено **64 символами**. Порядок одинаков для определений и выполнения: встроенный инструмент, пользовательский, инструмент пакета.
- Инструменты добавляются, пока пакет активен. Дополнительного переключателя для каждого чата, как у встроенных инструментов, нет: решение принимается выдачей разрешения и регистрацией. Выбранный провайдер должен поддерживать нативные вызовы инструментов.
- Схема параметров копируется и компилируется при регистрации. Если Engine не может ее скомпилировать, активация завершается ошибкой, заметной при разработке, а не посреди хода.
- Исключение обработчика помечает вызов как неудачный и записывается в журнал; его сообщение модели не передается. Через **10 секунд** без результата ход также перестает ждать. Обработчик продолжает работать, но больше не блокирует ход.
- Результат должен сериализоваться в объем не более **64 KiB**. Более крупный или несериализуемый результат приводит к ошибке вызова, а не вытесняет разговор из контекста. Описания и результаты считаются доверенным содержимым пакета. Проверяйте `chatId` перед чтением или изменением данных чата.
- Каждое определение сериализуется в запрос к провайдеру на каждом ходе и учитывается при подгонке контекста. Ограничения: **16 инструментов на пакет**, **64 во всех пакетах**, **512 символов** в описании и **8 KiB** в схеме параметров. Превышение вызывает исключение и срывает активацию. Повторная регистрация собственного имени заменяет инструмент без расхода дополнительного места.
- Контекст активации перестает работать после ее завершения. Если пакет сохранит `api` и позже вызовет `registerTool` из обратного вызова, регистрация будет отклонена. Завершенная среда не может регистрировать инструменты или заменять инструменты новой активации.
- Деактивация, обновление или удаление пакета освобождают его инструменты. Модель не получает инструмент, пакет которого уже не может ответить. Инструменты удаляются до ожидания очистки; каждый обратный вызов очистки ограничен 8 секундами.

Эти ограничения относятся только к асинхронному ожиданию. Пакеты выполняются как доверенный код в процессе сервера; таймер не может прервать синхронную работу, блокирующую цикл событий. Для принудительной отмены нужен отдельный рабочий поток или процесс; этот API такой изоляции не предоставляет.

`api.registerTool` существует только начиная с этой версии Engine. Пакет, которому он нужен, должен объявить `capabilityApi` 1.19 и откажется устанавливаться на более старой версии.

## Условия решений и модель решений

Пользовательская **Decision model** (модель решений) отвечает да/нет и выбирает варианты для утверждений о недавнем чате. [Модели решений](../connections/decision-models.md) объясняют, что это и как их настроить.

Шаблон промпта агента из пакета может использовать условия решений точно так же, как пользовательский агент: `{{#if decision:"..."}}` и `{{#if decision_choice:"..." == "..."}}`. Engine находит их в шаблоне, задает вопросы до запуска агента (после ответа для агента постобработки) и разрешает шаблон по ответам. Версия API возможностей на это не влияет. [Условные промпты](../prompts/conditional-prompts.md#asking-the-decision-model) описывают синтаксис и формулировки, а [Создание собственных агентов](../agents/custom-agents.md#decision-statements-in-the-agents-prompt) – чтение в разных фазах агента.

Серверный код пакета также может задавать настроенной у пользователя модели решений ограниченные вопросы да/нет и Choice о контексте, который предоставляет пакет, через `api.runtime.decisions.evaluate(...)`. Он использует ту же модель решений, что и вопросы активации агентов и условные промпты (управляемая локальная модель или подключение модели решений), и никогда не раскрывает ключи или внутреннее устройство Engine. `decisions` необязателен и не требует более нового API возможностей или разрешения: проверьте `typeof api.runtime.decisions?.evaluate === "function"` и в более старых версиях Engine используйте запасной вариант.

```ts
const result = await api.runtime.decisions?.evaluate({
  messages: [{ role: "user", content: "The tavern falls silent as the stranger draws a blade." }],
  questions: [
    { id: "danger", question: "Someone is about to be attacked." },
    { id: "mood", question: "The mood of the scene is", options: ["calm", "tense", "festive"] },
  ],
  // Optional: pass `signal` to cancel and `debugMode: true` to log the Decision prompt.
});
// null: no Decision model is configured, or it gave no answer (unreachable, timed out or cancelled).
if (result && (result.answers.danger ?? 0) >= result.threshold) {
  // ...
}
```

- `messages` – собственный контекст пакета, от самых старых сообщений к новым (не более 200 сообщений и 200 000 символов; `name` сообщения – не более 100 символов). Самые старые сообщения отбрасываются, чтобы уместиться в модель.
- Каждый `question` – не более 500 символов; id должны быть уникальными. У вопроса Choice не менее двух `options`, а ответ – один из них или `"none of these"`.
- Один запрос может запросить не больше ответов, чем задает лимит пользователя **Decision statements per turn** (утверждения решений за один ответ); каждый вариант Choice считается один раз, плюс один. Недопустимый запрос выбрасывает `TypeError`.
- `answers` содержит вероятность ответа "да" для каждого вопроса да/нет, а вопрос, которого в нем нет, остался без ответа. Сравнивайте ее с `threshold` – собственной рабочей точкой модели: вероятности разных моделей решений несопоставимы.

Каждое использование проектируйте и для пользователя без модели решений. Утверждение без ответа считается нет, поэтому ветка `{{else}}` или отсутствие текста должны быть разумным вариантом по умолчанию. Пишите для любой модели решений, не требуя Jev: локальные модели чата и другие поддерживаемые бэкенды используют тот же синтаксис, но могут отвечать иначе. Прежде чем полагаться на конкретную оценку, число запросов или кешированный ответ, прочитайте [Пороги](../connections/decision-models.md#thresholds) и [Ограничения и стоимость](../prompts/conditional-prompts.md#limits-and-cost).

### Примечание для разработчиков Experience в Game Mode

Бой Engine сам решает, что делают обычные враги. Каждый враг на стороне GM, кроме босса, получает роль по навыкам и классу (bruiser, bulwark, skirmisher, marksman, spellcaster, supporter или controller), мастерство по уровню, если враг не задал свое (novice, trained, veteran или master), и темперамент, например reckless, cautious, opportunistic или protective. Beasts и monstrosities всегда mindless. Код Engine выбирает их по начальному значению без вызова модели, а сложность игры меняет последовательность поведения согласно типу. Только авторскими боссами GM управляет через вызов модели. См. [ИИ боя Game Mode](game-combat-ai-design.md).

Готовятся дальнейшие улучшения боя. Прежде чем включать модель решений в боевой конвейер, проверьте, не выполняет ли обычный бой Engine нужную работу. Если врагу нужна определенная личность, сначала задайте подходящие мастерство и темперамент. Решение на каждом ходе врага добавит работу модели и срок ожидания; размещенный бэкенд добавит сетевые запросы и расходы. Бой будет зависеть от модели, которую пользователь мог не настроить, поэтому понадобится разумное поведение при отсутствии ответа.

## Доверие и установка

Официальный каталог – это версионированный документ в формате JSON, который проверяется по схеме и загружается по HTTPS. Каждая запись выпуска содержит неизменяемые адреса артефактов, контрольные суммы SHA-256, размер в байтах, совместимость с движком, список разрешений и признак того, нужен ли перезапуск для его среды выполнения.

Обновления требуют согласия пользователя: если не считать одноразовых миграций, которые сохраняют бывшие встроенные возможности обновленной установки (см. [Миграция для совместимости](#compatibility-migration)), при запуске никакие пакеты не скачиваются и не устанавливаются. `GET /api/capability-packages/updates/pending` перечисляет каждый установленный официальный пакет, у которого версия в каталоге новее и совместима с работающим движком и API возможностей, и пропускает версию, от которой пользователь уже отказался. Клиент показывает их в одном запросе **Agent updates available** (доступны обновления агентов). **Update all** (обновить все) устанавливает каждый из них обычным конвейером установки, с привязкой к предложенной версии и SHA-256 артефакта. **Not now** (не сейчас) записывает отклоненные версии в `DATA_DIR/capability-packages/update-decisions-v1.json` (`POST /api/capability-packages/updates/decline`), поэтому эта версия больше не предлагается, а более новая предлагается. **Update** (обновить) в любом случае остается доступной в **Download Agents**. Сбои изолированы: проблема с одним пакетом не затрагивает остальные. Когда каталог недоступен или проверка не прошла, уже имеющиеся файлы и состояние реестра продолжают работать, а при неудачной проверке готовности серверной среды выполнения включается откат на предыдущую версию.

Примечания к выпуску публикуются как `notes.json` рядом с `catalog.json`, который они описывают, и никогда не помещаются в запись каталога или в манифест: более старый движок отбрасывает запись каталога с незнакомым ключом. Каждое ожидающее обновление несет в `releaseNotes` примечания всех версий после установленной вплоть до предложенной, от новых к старым, а `releaseHighlight` равно true, если хотя бы одно из них помечено как изменение, которое пользователь заметит. Примечания – обычный текст, они никогда не отображаются как Markdown или HTML.

Установщик обязан:

1. требовать привилегированного доступа через loopback или права администратора;
2. соблюдать HTTPS, ограничения на объем скачивания и тайм-ауты;
3. проверять доверие к каталогу и контрольную сумму SHA-256 артефакта до распаковки;
4. отклонять абсолютные пути, выход за пределы папки, ссылки, файлы устройств и незаявленные файлы;
5. проверять манифест и совместимость с движком;
6. распаковывать во временную папку рядом с целевой;
7. активировать пакет атомарно и только после успешной проверки;
8. сохранять предыдущую версию до успешного запуска новой среды выполнения;
9. откатывать активацию при сбое;
10. никогда не запускать скрипты установки, обновления и удаления.

Официальный каталог включает только доверенные исполняемые пакеты от самого проекта. Для сторонних пакетов в будущем понадобится отдельная, явно описанная модель доверия.

## Поведение во время работы и перезапуск

Реестром установленных пакетов владеет сервер, он же сообщает клиентам о доступных возможностях. Декларативные и перезагружаемые модули активируются сразу. После активации интерфейс сбрасывает кеш запросов каталога, агентов, возможностей режима и активного чата.

Манифест может объявлять `restartRequired` только тогда, когда хост не может безопасно перезагрузить эту точку входа. Успешная активация на ходу показывает `Agent installed. It is ready to use.` Активация с перезапуском показывает `Agent installed. Restart Marinara Engine to finish setup.`

Пакеты пошаговых игр перезагружаются на ходу: при установке их серверный движок и ручной запуск слеш-командой регистрируются сразу, а при удалении среда выполнения отключается без перезапуска движка. Настройки **Conversation Commands** (команды в режиме Conversation) для отдельного чата задают только то, может ли персонаж отправить скрытую команду пакета; на слеш-команду, которую вводите вы, они не влияют. В текущих официальных манифестах пошаговых игр осторожная устаревшая пометка о перезапуске сохраняется для совместимости с движком версии 2.x. Движок версии 3.x распознает тип `turn-game`, выполняет безопасную активацию на ходу и возвращает пакет как активный и готовый к работе.

### Место на диске: копии для выполнения и сохраняемые версии

Серверная часть пакета не запускается из `DATA_DIR/capability-packages/versions/<id>/<version>`. При каждой активации Engine проверяет установленные файлы, копирует их в новую папку внутри `DATA_DIR/capability-runtime-snapshots` и импортирует копию. Копия удаляется, когда эта среда выполнения останавливается.

- **Копии для выполнения.** Копия содержит все проверенные файлы манифеста, кроме клиентской точки входа. Сервер ее никогда не загружает, а браузер получает ее из `versions/`. Ресурсы в копии остаются, поэтому сервер может читать файлы рядом со своим `server.mjs`, как Quartermaster делает с `icons/`. Скопированные файлы доступны только для чтения.
- **Очистка при запуске.** При сбое или принудительной остановке удаление копии пропускается. При каждом запуске, до активации любого пакета, Engine удаляет все записи в `capability-runtime-snapshots`, кроме общих ссылок `node_modules`, потому что новый процесс не может использовать ни одну из них. Сначала он делает файлы, доступные только для чтения, доступными для записи (это нужно в Windows) и никогда не переходит по ссылкам. До этого шага доходит только процесс, который держит аренду записи хранилища, поэтому второй экземпляр Engine, запущенный с той же папкой данных, останавливается при открытии хранилища и никогда не удаляет копии работающего Engine.
- **Сохраняемые версии.** В `versions/<id>` хранятся текущая версия и `previousVersion`, которую восстанавливает откат, если новая серверная среда выполнения не запускается. Более старые версии, а также версия, с которой откатилось неудачное обновление, удаляются после успешной активации или успешного обновления, а также при запуске. Пакет, обновление которого ждет перезапуска (`restart-required`) или среда выполнения которого еще не запущена (`readiness: "pending"`), хранит все версии, пока не запустится.
- **Никогда не удаляются:** данные пакетов (папки вроде `DATA_DIR/long-term-memory` и таблицы пакета в `storage`), чаты, настройки, `installed.json`, решения об обновлениях, папки `.install-*` и папки `versions/` для id, которых нет в реестре. Удаление пакета, как и раньше, убирает его код и сохраняет его данные.

## Миграция для совместимости

При первом запуске после обновления:

- пользовательские агенты остаются без изменений;
- каждый устаревший встроенный агент, видимый в этой установке, отмечается как установленный;
- карты, звонки в режиме Conversation и игры в режиме Conversation сохраняют прежнюю доступность;
- существующие настройки отдельных чатов, снимки, состояние игры, история звонков и память агентов остаются на месте;
- миграция идемпотентна и отмечается как завершенная только после того, как все записи о доступности устаревших возможностей надежно сохранены.

Артефакты устаревших пакетов остаются доступными в официальном каталоге как источники для миграции. В новой установке они не показываются и не активируются, пока вы их не установите.

## Удаление

Удаление убирает пакет из выбора в активных чатах, стирает настройки его агента и скачанные исполняемые файлы, а при необходимости отключает его среду выполнения при перезапуске. Прежние чаты, сообщения, снимки карт, сводки звонков и записи завершенных игр остаются доступными для чтения, поэтому удаление пакета не уничтожает вашу работу. Безвозвратное удаление исторических данных – это отдельное действие, которое вы выполняете сами.

Любое удаление требует подтверждения. Затронутые чаты возвращаются к обычным базовым экранам, и история при этом не портится.

## Интерфейс каталога

В панели **Agents** (агенты) есть элемент `Download Agents` – такой же, как кнопка `Download` в панелях Characters и Personas, которая открывает Card Browser. Он открывает адаптивную библиотеку на весь экран: поиск, типы пакетов, сведения о совместимости, состояние установки и обновления, разрешения, занимаемое место, документация и кнопки удаления.

На компьютере это список для просмотра и область с подробностями рядом. На телефоне – одна область с явной кнопкой возврата и крупными элементами под палец. Состояния "пусто", "нет сети", "несовместимо", "скачивание повреждено", "установка прервана", "доступно обновление", "выполнен откат" и "нужен перезапуск" проработаны как полноценные, а не как редкие исключения.

## Условие завершения выноса

Вынос считается завершенным только при выполнении всех условий: реализации пакета больше нет в рабочих сборках клиента и сервера, новая установка не может ее активировать без скачивания пакета, обновленная установка ее сохраняет, а установка, обновление и удаление пакета проходят на компьютере, на телефоне и в файловых системах, совместимых с Termux.

### Capability API 1.30: шкалы ран, расход на проверку и бой со шкалой

Элемент `live.tracks` набора правил может объявить `levels` и `kinds`, превращая ограниченное целое число в ШКАЛУ РАН: столбец ячеек с собственными подписями и штрафами, в которых размещаются отметки. `levels` содержит 1–16 уровней от лучшего к худшему, каждый с `label` и целым `penalty`. `kinds` содержит 1–6 видов урона, каждый с `id`, короткой подписью `label` и отдельным `severity`. `kinds` без `levels` отклоняется: отмечать было бы нечего. `resolution.penaltyFrom` указывает шкалу, чей штраф действует на каждый бросок: у `dice-pool` он вычитает кости, не опуская число ниже `pool.min`, а у `dice-sum` дает постоянный модификатор.

Остальные дополнения этого раздела тоже относятся к 1.30; пакет, использующий ЛЮБОЕ из них, объявляет 1.30:

- `combat.health` может указывать шкалу ран вместо запаса. Тогда `combat.damageKinds` задает отметки для видов урона: `default`, необязательное сопоставление `byType` и `marks`, где `per-blow` отмечает ячейку за попадание, а `per-point` считает уровни здоровья по урону. `damageKinds` обязательно для шкалы ран и отклоняется для запаса.
- `resolution.spend` (только `dice-pool`): запас, расходуемый на проверку, стоимость платежа, покупает ли он `successes` или `dice`, и `perCheck`, предел на бросок.
- `mechanics.check` записи каталога: влияние ВЫБРАННОЙ персонажем записи на проверку в виде `reroll` (`upTo` и `once` или `until`), `dice`, `successes` или `threshold`. Тоже только для пулов костей.

```json
{
  "capabilityApi": { "major": 1, "minor": 30 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

Длина шкалы ран задается уровнями, поэтому `min` равно 0, а `max` – `levels.length`. Другое объявление отклоняется, а не исправляется молча. `resolution.penaltyFrom` должно ссылаться на шкалу ран: обычный счетчик штрафа не имеет.

Это не мягкий интерфейс по той же причине, что и 1.20–1.28: Engine, не знающий `levels`, `kinds`, `penaltyFrom`, `damageKinds`, `resolution.spend` или `mechanics.check`, отклоняет весь файл правил. При установке читаются проверенные байты `ruleset.json`, и пакет с более старой декларацией отклоняется. Набор с обычными счетчиками, запасом здоровья и без расходов на проверку работает как прежде.

### Capability API 1.29: возможности одного боевого хода набора правил

Пять необязательных дополнений к `combat` и записям каталога, используемым в бою:

- У попадания может быть до трех ДОПОЛНИТЕЛЬНЫХ составляющих. `mechanics.plus` записи каталога и `damage.plus` действия существа имеют вид `{ dice?, flat?, type?, save?: { save,
difficulty?, onSuccess: "none" | "half" } }`: независимые броски и типы, отдельное удвоение при критическом попадании и спасброски цели, но одна проверка концентрации и падения для всего попадания.
- `combat.attacks[].strikes` – ссылка на значение, задающее число ударов за один расход бюджета списка. Остаток доступен до конца хода; пока есть хотя бы один оставшийся удар, все строки этого списка не расходуют бюджет.
- `mechanics.free` не расходует бюджет, `mechanics.gives` возвращает его только на этот ход в пределах максимума, а `mechanics.standard` позволяет покупать названные стандартные действия за другой бюджет. Запись `utility` с `gives` или `standard` предлагается, а не пропускается.
- Новый тип записи `rider` и встроенные `riders` существа пассивно добавляют урон к первому подходящему попаданию за ход или раунд, никогда не появляясь в меню.
- Закрытый список эффектов состояний получает `own-saves-advantage`, `own-saves-disadvantage`, `resist-all`, `cannot-target-source` и `cannot-approach-source`. Состояние может ограничивать спасброски через `saves`, действовать только при видимом источнике (`whileSourceInSight`) или заканчиваться при его падении (`endsWhenSourceDown`).

```json
{
  "capabilityApi": { "major": 1, "minor": 29 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

Это не мягкий интерфейс, как и 1.20–1.28: Engine, не знающий этих ключей, отклоняет весь файл правил или каталога. Установка читает проверенные байты `ruleset.json` и каждого объявленного `catalogs/<id>.json`, отклоняя более старую декларацию в обоих случаях. Новых разрешений нет; набор без этих полей работает как прежде.

### Capability API 1.28: бой набора правил на поле

Блок `combat` может задавать размер клетки в собственной единице расстояния (`distance: { label, perCell }`), включая позиционный бой. `ranged` определяет цену выстрела за обычную дальность или рядом с врагом; `cover` – прибавку укрытия к защите; `opportunity` – бюджет удара по уходящему противнику. Список атак может иметь `reach` и `range`, читаемые из столбца или общие для всех строк. `range` действия существа может быть `{ "normal": 30, "long": 120 }` вместо одного числа.

```json
{
  "capabilityApi": { "major": 1, "minor": 28 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

Объявление `ranged`, `cover`, `opportunity` или дальности оружия БЕЗ `distance` отклоняется при импорте: без клетки расстояние не имеет смысла. Поле использует генератор, местность и расстановку тактического стиля боя, поэтому не добавляет вторую модель поля или новое разрешение.

Это не мягкий интерфейс, как и 1.20–1.27: Engine, не знающий ключей, отклоняет весь файл правил или каталог с существом с двойной дальностью. Установка читает проверенные байты `ruleset.json` и всех объявленных `catalogs/<id>.json`, отклоняя более старую декларацию. Набор без расстояния работает как прежде.

### Capability API 1.27: бестиарии наборов правил

Каталог набора правил может объявить `"holds": "creatures"` и содержать блоки характеристик существ вместо строк листа. Существо описывается теми числами, которые уже объявляет блок `combat`: здоровье, которое может быть числом или костями, брошенными в начале боя, защита, модификатор инициативы, значения характеристик и модификаторы спасбросков под идентификаторами самого листа, типы урона, к которым существо устойчиво, уязвимо или невосприимчиво, состояния, в которых оно никогда не бывает, уровень угрозы, черты, которые видит Game Master, и действия. Действие может попадать, требовать спасброска, накладывать состояние, иметь ограниченное число использований, восстанавливаться броском перезарядки, выполнять за один бюджет последовательность других действий блока или покупаться собственными особыми очками существа.

```json
{
  "capabilityApi": { "major": 1, "minor": 27 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json", "catalogs/beasts.json"] } }
}
```

Каталог существ не объявляет `feeds` и никогда не предлагается в окне выбора редактора листа: его читает бой, а не лист персонажа. Бой, который его читает, – это стиль `ruleset` распорядителя боя, и собственный уровень Capability API ему не нужен: он разыгрывает тот блок `combat` и тот бестиарий, которые уже есть в установленном наборе правил.

Это не мягкий интерфейс по той же причине, что и 1.20–1.26: Engine, который не может прочитать `holds` или `creature` записи, отклоняет весь файл набора правил или файл каталога, в котором они находятся. Поэтому при установке читаются проверенные байты `ruleset.json` и каждого объявленного `catalogs/<id>.json`, и при более старой декларации любой из них отклоняется. Разрешений не нужно; набор правил без бестиария не меняется.

### Capability API 1.26: бой набора правил

Набор правил может содержать необязательный блок верхнего уровня `combat`, который говорит, как бой РАЗРЕШАЕТСЯ собственными числами набора: что бросается и против чего, экономика действий, какие списки листа являются атаками, а какие способностями, что делают его состояния, концентрация, что происходит с персонажем при нуле, какие типы урона в нем есть и по какой шкале подбирается противник. В том же выпуске `mechanics` записи каталога может указывать, сколько целей она берет, что она всегда попадает, какие состояния накладывает, какие временные очки дает, как растет вместе с листом и какой бюджет тратит.

```json
{
  "capabilityApi": { "major": 1, "minor": 26 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

Игра на наборе правил, который объявляет `combat`, при включенном распорядителе боя проводит бои по этому блоку на экране боя. Набор правил без него сражается как раньше – через свой блок `battle` или по предпочтению игрока Classic или Tactical.

Это не мягкий интерфейс по той же причине, что и 1.20–1.25: Engine, который не может прочитать `combat` или новые ключи `mechanics`, отклоняет весь файл набора правил или файл каталога, в котором они находятся. Поэтому при установке читаются проверенные байты `ruleset.json` и каждого объявленного `catalogs/<id>.json`, и при более старой декларации любой из них отклоняется. Разрешений не нужно; набор правил без того и другого не меняется.

### Capability API 1.25: слои набора правил и указания для мира

Набор правил может объявить необязательный массив верхнего уровня `layers`: именованные варианты самого себя (Low magic, Hard winter), которые игрок включает при создании игры и которые замораживаются в привязке этой игры на все время ее существования. В том же выпуске базовый блок `gm` получает необязательную строку `worldGuidance`, которую генерация мира читает один раз при настройке, чтобы мир подходил к правилам, по которым будет играть отряд.

```json
{
  "capabilityApi": { "major": 1, "minor": 25 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

Эффекты слоя – закрытый набор, и каждый из них только сужает или дописывает: указания, добавленные после собственных указаний набора правил, значения, удаленные из поля-перечисления, лестница сложности, замененная лестницей того же вида разрешения, и записи каталога, скрытые из окна выбора редактора листа. Ничего не добавляется, поэтому лист персонажа остается читаемым при любых слоях, выбранных в игре, а слой не приносит ни кода пакета, ни дополнительного вызова модели. Слои, которые поставляет не автор набора правил, появятся позже.

Это не мягкий интерфейс по той же причине, что и 1.20–1.24: Engine, который не знает `layers` или `gm.worldGuidance`, отклоняет весь файл набора правил. Поэтому при установке читаются проверенные байты `ruleset.json`, и при более старой декларации любой из этих ключей приводит к отказу. Разрешений не нужно; набор правил без того и другого не меняется.

### Capability API 1.24: вид разрешения dice-pool

`resolution` набора правил может объявить `"kind": "dice-pool"` вместо `"dice-sum"`. Тогда проверка бросает столько костей, сколько указано в листе персонажа, и считает те, что достигли цели. Можно задать удвоенные грани, взрывающиеся грани, отменяющие грани, критические провалы, исключительные успехи и диапазон ситуативных костей, которые Game Master может добавить или убрать для одной проверки.

```json
{
  "capabilityApi": { "major": 1, "minor": 24 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

Лист остается тем же листом: то, что `dice-sum` прибавляет к броску, здесь становится числом костей. Поэтому этот вид не приносит ни нового словаря листа, ни слота редактора, ни кода пакета.

Это не мягкий интерфейс по той же причине, что и 1.20–1.23: Engine, который знает только `dice-sum`, отклоняет весь файл набора правил. Поэтому при установке читаются проверенные байты `ruleset.json`, и разрешение `dice-pool` при более старой декларации отклоняется. Разрешений не нужно; набор правил, который суммирует кости, не меняется.

### Capability API 1.23: масштабируемые значения каталога

Строка записи каталога может содержать необязательное сопоставление `scaled`: до четырех собственных числовых столбцов этой строки, значение которых ведет набор правил, а не игрок. Каждый из них – обычная ссылка на значение с необязательной таблицей шагов, поэтому ресурс класса может следовать за уровнем, а число использований способности – за значением характеристики, и формату не нужно осваивать новую арифметику.

```json
{
  "capabilityApi": { "major": 1, "minor": 23 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json", "catalogs/spells.json"] } }
}
```

Значение вычисляется при редактировании листа и никогда при чтении, поэтому живое состояние, блок промпта Game Master и мост к бою продолжают читать сохраненное число.

Масштабируемая строка может находиться прямо в `ruleset.json` или в ресурсе `catalogs/<id>.json`. Манифест объявляет оба файла ресурсами, но не может показать ключи внутри них, поэтому при установке читаются проверенные байты обоих, и ключ `scaled` отклоняется при декларации старше 1.23 – точно так же, как `catalogs` при 1.21 и `battle` при 1.22. Строгая схема более старого Engine все равно отклонила бы файл, в котором он находится. Разрешений не нужно; набор правил, в каталогах которого таких строк нет, не меняется.

В том же выпуске появилась команда `[sheet: op="use" name="..."]`, которая оплачивает `mechanics.cost` записи каталога плюс одно использование каждого запаса строки, записанного этой записью. Объявления она не требует: она читает каталоги, которые Engine уже отдает.

### Capability API 1.22: блок battle

Набор правил может содержать необязательный блок `battle`, который передает бою числа из листа персонажа: живой запас, который служит очками здоровья, необязательный запас, который становится MP, запасы, которые становятся ячейками заклинаний, и списки листа, чьи отмеченные каталогом строки становятся собственными `CombatSkill` Engine. Когда бой заканчивается, потраченные в нем очки здоровья, энергия и ячейки записываются обратно теми же операциями листа, которыми пользуются кнопки самого игрока.

```json
{
  "capabilityApi": { "major": 1, "minor": 22 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

Это не адаптер боя. Арифметика урона остается за Engine, а `attackRoll`, `save`, `concentration` и `perCostStep` записи каталога никто не читает: точное по правилам разрешение относится к адаптерам отдельных наборов правил из документа передачи реализации боя. `coverage.combat` сохраняет собственное значение, и мост его никогда не читает.

Блок находится внутри `ruleset.json`, который манифест показать не может, поэтому при установке читаются проверенные байты, и ключ `battle` отклоняется при декларации старше 1.22 – точно так же, как `catalogs` при 1.21. Строгая схема более старого Engine все равно отклонила бы весь файл набора правил. Разрешений не нужно; набор правил без блока `battle` не меняется.

### Capability API 1.21: каталоги наборов правил

Набор правил может поставлять **каталоги** – именованные коллекции готовых записей (заклинаний, способностей классов, снаряжения), которые редактор листа предлагает в окне выбора, чтобы игроку не приходилось вводить список строка за строкой. Заголовок находится в `ruleset.json` под ключом `catalogs`; записи лежат либо прямо в этом заголовке, либо в собственном зарезервированном ресурсе – по одному файлу на каталог:

```json
{
  "capabilityApi": { "major": 1, "minor": 21 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json", "catalogs/spells.json"] } },
  "files": [
    { "path": "ruleset.json", "sha256": "<sha256>", "bytes": 25767 },
    { "path": "catalogs/spells.json", "sha256": "<sha256>", "bytes": 418204 }
  ]
}
```

`catalogs/<id>.json` – семейство зарезервированных ресурсов: имя файла совпадает с собственным идентификатором каталога, поэтому Engine находит файл по одному только набору правил, и никакой каталог не может назвать файл другого каталога. Ресурс каталога закрепляется хешем в `files[]`, как любой другой объявленный ресурс, поставляется только рядом с объявляющим его `ruleset.json` и отклоняется до чтения, если объявленный размер больше 2 MB (1 MB до Capability API 1.340; пакет с файлом каталога больше 1 MB объявляет 1.340). Его содержимое проходит те же проверки, что и встроенные записи, относительно того же листа, поэтому каталог никогда не может записать строку, которую лист не смог бы хранить. Не более 12 каталогов на набор правил и 2000 записей на каталог.

Клиент загружает каталог, только когда открывается окно выбора, через `GET /api/capability-packages/rulesets/catalog?rulesetId=&catalogId=&version=`. Список установленных наборов правил никогда не содержит встроенных записей, только их количество, потому что он читается при каждом открытии редактора листа. Текст каталога никогда не попадает в промпт: Game Master по-прежнему видит только то, что называет `gm.sheetSummary`, поэтому каталоги не стоят токенов.

Как и 1.20, это не мягкий интерфейс, и у проверки две половины, потому что каталоги находятся внутри файла набора правил, а не в манифесте. Объявление ресурса `catalogs/<id>.json` требует 1.21, а `ruleset.json` с ключом `catalogs` отклоняется при установке, если манифест объявляет меньшую версию: строгая схема более старого Engine все равно отклонила бы весь файл набора правил. Разрешений, как и прежде, не нужно.

### Capability API 1.20: наборы правил Game Mode

Набор правил – это правила игры в виде проверенных данных: вид разрешения, который Engine уже реализует, лист персонажа, объявленный из закрытого набора примитивов, отдых и указания для промпта Game Master. Пакет поставляет его как ресурс с зарезервированным именем `ruleset.json`, который обнаруживается по соглашению точно так же, как `gm-verbs.json`: он перечислен в `contributions.assets.paths` и закреплен хешем в `files[]`.

```json
{
  "schemaVersion": 2,
  "capabilityApi": { "major": 1, "minor": 20 },
  "id": "ruleset-5e-2014",
  "kind": ["ruleset"],
  "permissions": [],
  "entrypoints": {},
  "contributions": { "assets": { "paths": ["ruleset.json"] } },
  "files": [{ "path": "ruleset.json", "sha256": "<sha256 of the file>", "bytes": 25767 }]
}
```

Пример показывает только ключи, важные для набора правил; обычные поля манифеста (`name`, `version`, `description`, `engine`, `builtAgainst`) по-прежнему обязательны.

Пакету набора правил не нужны ни разрешения, ни серверная или клиентская точка входа, ни агент. Тип и ресурс идут вместе: пакет типа `ruleset` должен перечислять `ruleset.json`, а пакет, перечисляющий `ruleset.json`, должен объявлять этот тип, поэтому набор правил не может проникнуть под другим типом. В файле ничего не исполняется: строк-выражений нет, а механика, которую не выражает ни один вид разрешения, – это изменение Engine, добавляющее новый вид, а не то, что может сделать набор правил. Формат, собственный файл 5e от разработчиков приложения и причины его устройства описаны в [`game-rulesets-and-sheets-implementation.md`](game-rulesets-and-sheets-implementation.md).

Это не мягкий интерфейс. Пакет набора правил ничего не делает в Engine, который не может его прочитать, поэтому манифест, перечисляющий `ruleset.json`, должен объявлять Capability API 1.20, и более старый Engine корректно отказывает в установке.

Engine отклоняет ресурс до чтения, если объявленный размер больше 512 KB (256 KB до Capability API 1.340; пакет, чей набор правил больше 256 KB, объявляет 1.340), повторно сверяет его с хешем, записанным при установке, и проверяет строгой общей схемой (`packages/shared/src/schemas/ruleset.schema.ts`). Непригодный файл пропускается с одной строкой журнала, в которой названы пакет и несколько первых проблем вида `path: message`. Если два пакета объявляют один и тот же идентификатор набора правил, выбирается первый по порядку идентификаторов пакетов, а другой пропускается со строкой журнала. `engine-legacy` и `traditional` – идентификаторы, принадлежащие Engine, и файл не может их занять.

Игра закрепляет свой набор правил один раз, при создании, в `chat.metadata.gameRuleset`. Без привязки действуют собственные правила Engine, точно как раньше. Привязка, которую установка не может выполнить (пакет удален или установленное определение старше закрепленной версии), считается недоступной и никогда не перетолковывается как другой набор правил. Привязка сопоставляется по идентификатору набора правил и по пакету, который его предоставил, поэтому другой пакет, объявивший тот же идентификатор, не захватывает существующую игру.

### Capability API 1.73: агенты аватаров

Engine размещает у себя два агента аватаров: `2d-avatars` (спрайты PNGTuber и mesh-аватары) и `3d-avatars` (модели VRM). Их пакеты остаются тонкими: по одному определению агента, промпты по умолчанию, локали и запись каталога. Остальное принадлежит Engine: хранилище для каждого владельца в `DATA_DIR/avatar-models/`, импорт, лениво загружаемые рендереры, настройка на странице каждого агента в редакторе агента, режиссер стриминга, классификатор выражений и маршруты генерации. Общий контракт – `packages/shared/src/types/avatars.ts` (его схемы лежат в `schemas/avatars.schema.ts`), а клиентская половина – `packages/client/src/features/avatars/contract.ts`. Руководство пользователя – [`docs/agents/avatars.md`](../agents/avatars.md).

Нового поля манифеста нет. Пакет аватара объявляет версию схемы 2 и Capability API 1.73, поэтому Engine без этих поверхностей отказывается от установки, а не показывает в списке агента, который ничего не отображает. Изменение, которое ввело 1.73, поставило эти поверхности как бездействующие заглушки; теперь настройка, площадка аватаров и рендереры Engine находятся в `staging`, а оба пакета перечислены в предварительном каталоге. Прежде чем установка заработает, нужно опубликовать артефакты, на адреса которых они ссылаются: сама по себе запись каталога не доказывает, что скачиваемый артефакт доступен. Промпты генерации 2D-агента поставляются как коллекция шаблонов промптов `avatarGenerationTemplates` в его `defaultSettings`, с идентификаторами из `AVATAR_PROMPT_TEMPLATE_IDS`; редактор агента объединяет и сбрасывает их так же, как любую другую встроенную коллекцию шаблонов.

### Capability API 1.72: набор карт Experience

Пакет `game-surface`, который настраивается через мастер Game (`gameSurface.setup`, 1.18), может поставлять набор карт при версии схемы 2 и Capability API 1.72: собственный комплект мира, готовые миры, построенные на этом комплекте, и собственный набор тайлов. Каждый из них – это файл обмена, который Game Mode и Pixelforge уже читают и пишут (`.worldkit.json`, файлы `.world.json` и `.tilepack.json`), и одновременно объявленный ресурс с закрепленным хешем.

```json
{
  "gameSurface": {
    "setup": {},
    "mapPack": {
      "kit": "map/riverlands.worldkit.json",
      "worlds": ["map/upriver.world.json", "map/downriver.world.json"],
      "tiles": "map/riverlands.tilepack.json"
    }
  },
  "assets": {
    "paths": [
      "map/riverlands.worldkit.json",
      "map/upriver.world.json",
      "map/downriver.world.json",
      "map/riverlands.tilepack.json"
    ]
  }
}
```

`worlds` (не больше 32) и `tiles` необязательны. Файл мира может содержать сюжетный сценарий своего мира (worldgen W10), который поставляется вместе с картой как ее часть. Файл мира версии 2 содержит также `snapshot` мира – мир таким, каким он был создан (W11): Engine, чей генератор миров с тех пор изменился, читает мир из снимка точно таким, каким он был создан, так что набор продолжает работать после обновлений Engine. Записывайте файлы через **Download** (скачать) игры или мира из библиотеки (или `GET /api/game/:chatId/world/file`) – такие файлы содержат снимок. Файл набора не больше 8 MB – это самый большой файл обмена, который читает Engine (у набора тайлов собственные, меньшие пределы), поэтому мир с файлом крупнее (снимок очень большого мира) нельзя поставить в наборе. Миру, сюжет которого задает `intro`, нужен Capability API 1.339 (см. [Вступительное сообщение](../extending/writing-story-scripts.md#the-intro-message)). `tiles` может быть набором тайлов-изображений (набор тайлов версии 2: листы PNG на сетке ячеек со спрайтами из нескольких ячеек), которому нужен Capability API 1.80; Engine декодирует и проверяет его листы один раз для каждой версии пакета. Когда Experience включена, новая игра привязана к комплекту из набора; если набор поставляет миры, игрок выбирает один из них (вместе с сюжетом) и других не создает. Выключение Experience возвращает игроку собственный выбор. `POST /api/game/create` удерживает игру в той же привязке. Игра, как и любая другая, сохраняет свой комплект и мир, поэтому продолжает работать, если пакет удален, а пока пакет установлен, рисует свою общую карту мира и города тайлами набора.

Engine читает файлы через проверенный путь ресурсов (объявленный размер каждого не больше 8 MB, хеш проверяется повторно) и проверяет их так же, как файлы обмена. Набор отклоняется целиком, с указанием причины, если файл не читается, если мир сделан на другом комплекте или комплекту не подходит, или если его байты не совпадают с установленными; тогда Experience не может начать игру. Набор правил никогда не входит в набор карт: Experience, которой нужны собственные правила, поставляет отдельный пакет набора правил.

### Capability API 1.18: настройка Experience в мастере Game

Пакет `game-surface` может объявить `contributions.gameSurface.setup` при версии схемы 2 и Capability API 1.18. Engine сохраняет семь обычных шагов настройки, включая **Party** (отряд), цели, модели и лорбуки. Experiences предлагаются только для новых игр; повторное открытие настройки существующей игры сохраняет ее Experience и конфигурацию пакета. Пакеты без этого объявления сохраняют прежний диалог настройки.

```json
{
  "setup": {
    "seed": { "key": "seed", "label": "World seed" },
    "config": { "generate": true, "packWanted": true },
    "requires": { "enableCustomWidgets": false }
  }
}
```

Все три поля необязательны. Объявленное начальное число появляется под выбранной Experience с кнопкой **Randomize** (выбрать случайно). Начальное число – целое число без знака от 0 до 4294967295; пустой, дробный, отрицательный, экспоненциальный или шестнадцатеричный ввод блокирует **Start** (начать). Хост записывает числовое начальное значение и объявленные константы в `experienceConfig`; `config` не может содержать ключ начального числа. После сериализации константы должны занимать не более 8 000 символов. Подпись начального числа – текст для отображения, написанный автором пакета; опустите ее, чтобы использовать локализованную подпись Engine.

Объявленное требование к виджетам действует, пока Experience активна. Хост устанавливает элементу объявленное значение, блокирует его и объясняет, какая Experience его задала. Импорт файла настройки не может переопределить объявленное значение. Собственный прежний выбор игрока не трогается и восстанавливается, как только Experience выключают. Элементы настройки пространственной карты для этих Experiences скрыты, поэтому отдельный черновик карты, шаблон или конструктор не запускается.

Шаг **Lorebooks** (лорбуки) позволяет выбрать до 100 отдельных включенных записей, в том числе из неприкрепленных книг. Отключенные книги и записи, а также исключения чата учитываются. Эти идентификаторы передаются в `GameSetupConfig.activeLorebookEntryIds`. В `/game/setup` это дополнительные принудительные записи: они пропускают проверки вероятности, но сохраняют обычные лимиты токенов. Глобальный, привязанный к персонажам и прикрепленный лор по-прежнему участвует в обычном сканировании. Пакеты могут прочитать те же выбранные идентификаторы из конфигурации для собственного запроса генерации мира. Импортированные идентификаторы записей, которых нет на этом компьютере, указываются в отчете и пропускаются.

Импорт файла настройки восстанавливает установленную совместимую Experience и ее корректное числовое начальное значение, но отбрасывает произвольную конфигурацию пакета. Текущий манифест снова предоставляет константы. Файл без пригодного начального числа Experience оставляет заполненное заранее случайное число без изменений. Существующие игры пропускают импорт Experience с пояснением. Снимки создания сохраняют название Experience и начальное число для сводки настройки.

Независимо используйте существующее объявление готовности к запуску, если мир нужно подготовить до первого хода. Объявите API 1.18 минимальной версией пакета; старые хосты не могут интерпретировать это объявление настройки.

### Capability API 1.71: чтение сообщений так, как их читают агенты

В Roleplay сообщение может содержать шепоты, которые не входят в его `content`. Их читает каждый агент, которого запускает Engine, и пакет, который сам читает чат, теперь может прочитать тот же текст. Каждая запись из `persistence.listMessages(chatId)` получает `agentContent`: сообщение в том виде, в каком его читают агенты Engine. Каждый шепот стоит на своем месте и помечен `[Private whisper to <name>: …]`, а сообщение, которое состоит только из шепота, читается как его шепоты. Документ, который передает персонаж, например письмо, идет после сообщения. Личные заметки игрока не включаются.

`agentContent` есть только в чатах Roleplay. Его нет в других режимах и в размещенной многопользовательской комнате, где все видят, что пишут агенты. `content` никогда не меняется: это по-прежнему публичный текст. `extra` тоже не меняется: это сохраненные данные сообщения, в которых есть каждый шепот, в любом режиме. Никогда не показывайте текст, построенный на этих данных, игрокам или персонажам, которым шепот не предназначался.

```ts
const messages = await api.runtime.persistence.listMessages(chatId);
const history = messages.map((message) => message.agentContent ?? message.content);
```

Это мягкий интерфейс: более старый Engine не передает это поле, поэтому пакету, который читает `agentContent ?? content`, не нужно объявлять 1.71. Ему нужно разрешение `chat-read`, как и для `listMessages`. Шепоты приватны: все, что пакет пишет на их основе, например заметка или воспоминание, может дойти до персонажей, которым шепот не предназначался.

### Capability API 1.68: эмбеддинг поисковых запросов как запросов

`embeddings.embed(texts, signal?, inputType?)` принимает третий аргумент: передайте `"query"` для поискового текста, например запроса на извлечение воспоминаний. По умолчанию тексты считаются `"document"`. Некоторые модели эмбеддингов ожидают префикс у запросов, а некоторые еще и у документов: e5 и nomic-embed-text используют по одному префиксу для каждого вида текста, а Snowflake Arctic Embed v2 – только для запросов. Engine сам добавляет нужный префикс. Если эмбеддинг запроса создан как для документа, извлечение работает хуже. Другие модели, включая встроенный MiniLM, префикс не получают ни в каком случае. Тип входных данных не меняет `spaceId`, поэтому сохраненные векторы остаются сопоставимыми и ничего не нужно пересчитывать.

```ts
const embeddings = await api.runtime.resolveEmbeddings();
const [queryVector] = (await embeddings.embed([query], signal, "query")) ?? [];
const memoryVectors = await embeddings.embed(memoryTexts, signal); // documents
```

Это мягкий интерфейс: более старый Engine игнорирует третий аргумент, поэтому пакет может передавать его всегда и не обязан объявлять 1.68. Передавайте тип входных данных третьим аргументом, никогда не в объекте параметров: более старый Engine передает второй аргумент прямо провайдеру как сигнал отмены.

### Capability API 1.67: открытие персонажа в редакторе

Представление в браузере получает `openCharacter(characterId, { tab })`. Этот метод открывает редактор персонажа, а если указана вкладка – сразу на ней, чтобы пакет мог направить пользователя к полю карточки персонажа, которое он читает. В более старых версиях Engine его нет: прежде чем показывать ссылку, проверьте, что `openCharacter` существует.

```ts
if (typeof props.openCharacter === "function") props.openCharacter(characterId, { tab: "convo" });
```

### Capability API 1.66: сцены из цепочек сообщений пакета

Сцена Roleplay обычно ответвляется от чата Conversation (`/scene`). Пакет с новым разрешением `scenes` может сделать источником сцены собственные цепочки сообщений, например цепочку личных сообщений. Сцена остается обычным чатом сцены: тот же планировщик, то же окно предпочтений промпта, те же инструкции сцены, те же элементы управления End Scene, Discard и Convert и то же воспоминание персонажа при завершении. Пакет отвечает за сторону цепочки: что читает планировщик, блокировку на время сцены и то, что происходит со сводкой.

```ts
export async function activate({ api }) {
  api.registerSceneOrigin({
    // Planning context, or null when the thread no longer exists.
    getContext: async (threadId) => ({
      characterIds: [creatorCharacterId],
      personaId,
      connectionId: null, // the Engine's default connection
      transcript: [{ speaker: "Mina", content: "Come to my shoot tonight?" }],
      notes: "Stage persona, limits and anything else the scene writer must respect.",
    }),
    // Lock the thread. Return false when it already has an active scene.
    claim: async (threadId, { sceneChatId, characterIds }) => lockThread(threadId, sceneChatId),
    // Unlock and receive the outcome.
    release: async (threadId, end) => {
      if (!(await holdsLock(threadId, end.sceneChatId))) return;
      if (end.kind === "concluded") await saveRecap(threadId, end.summary);
      await unlockThread(threadId);
    },
  });
}
```

Представление в браузере (`home-browser-tab`) получает такие свойства:

- `startScene({ originId, prompt?, planHint?, plan?, data?, initiatorCharacterId?, initiatorName? })` открывает окно предпочтений промпта сцены, планирует и создает сцену и открывает ее чат. Передайте `plan` (`SceneFullPlan`: название, описание, скрытый сценарий, первое сообщение, системный промпт сцены, рейтинг, история отношений, руководство по участию, фон, состав персонажей), чтобы написать сцену самостоятельно; тогда окно и планировщик Engine пропускаются, и сцена создается точно по плану. Вызов завершается значением `{ chatId }` или `null`, если пользователь отменил действие или создать сцену не удалось (пользователь видит причину). Вспомогательная функция всегда использует собственный идентификатор пакета. Это удобство, а не граница: маршруты сцен принимают идентификатор любого пакета, поэтому `getContext` должен возвращать только то, что игрок и так может видеть в этой цепочке.
- `openChat(chatId)` переходит в чат – для кнопки "Go to scene" у заблокированной цепочки.
- `focusSceneOriginId` – цепочка, которую нужно показать, когда пользователь возвращается из сцены (Back, End Scene, Discard). Вызовите `onFocusSceneOriginHandled()`, когда покажете ее.

Важные правила:

- `data` – собственные настройки этой сцены, обычный JSON-объект не длиннее 4000 символов. Engine хранит его вместе со сценой и передает в `claim(originId, { sceneChatId, characterIds, data })` и в `release` как `end.data`, поэтому каждая сцена может решать за себя: `claim` может допустить сцену без блокировки (вернуть `true` и ничего не сохранять), а `release` может снять блокировку, не забирая сводку, или забрать ее в том объеме, который запросила сцена.
- Обязателен только `getContext`. Пакет, которому нужно лишь запускать сцены, опускает `claim` и `release`: ничего не блокируется, из одного источника может идти сколько угодно сцен, а по их завершении ничего не передается (**Back** по-прежнему возвращает в пакет). Опустите только `release`, чтобы блокировать без получения итога, или только `claim`, чтобы получать итоги без блокировки.
- Одна регистрация на пакет: повторная регистрация заменяет прежнюю, а деактивация удаляет ее.
- `characterIds` должны быть персонажами Engine; неизвестные идентификаторы отбрасываются, а контекст без единого известного персонажа отклоняется. Неизвестный `personaId` считается отсутствующим. `notes` обрезается до 8000 символов и передается планировщику, а вместе с перепиской – модели, которая пишет сцену, как скрытый контекст.
- `claim` выполняется после того, как чат сцены создан. `false` отбрасывает его с кодом 409, исключение – с кодом 503. У `getContext`, `claim` и `release` по 8 секунд: запоздавшие `getContext` или `claim` считаются сбоем (503, чат сцены удаляется), а запоздавший `release` записывается в журнал и отбрасывается.
- `release` получает `concluded` (с `summary`, `description`, `scenario`, `rating` и составом персонажей), `abandoned`, `deleted` или `converted`. Он должен быть идемпотентным и игнорировать сцену, которая не держит блокировку. Освобождение, которое выбрасывает исключение или приходит, пока пакет неактивен, записывается в журнал и отбрасывается: чат сцены в любом случае остается завершенным, поэтому устаревшую блокировку согласуйте, прочитав чат сцены с разрешением `chat-read`. В его метаданных есть `sceneStatus`, а у завершенной сцены еще и `sceneSummary`.
- Для источника из пакета Engine ничего не пишет в чат Conversation. Воспоминание персонажа сохраняется при завершении точно так же, как для сцены из Conversation.

`scenes` отклоняется в манифесте, который объявляет `capabilityApi` старше 1.66.

### Capability API 1.376: полноэкранный режим браузера Home

Представление `home-browser-tab` получает `capabilityProps.browserFullscreen`:

- `active`: заполняет ли сейчас этот пакет область содержимого браузера Home.
- `setActive(boolean)`: включает или выключает полноэкранный режим для этого активного пакета.
- `enterLabel` и `exitLabel`: локализованные доступные подписи переключателя.

Это полноэкранный режим внутри приложения: вкладки, адресная строка и закладки Home скрыты, а верхняя панель Engine остается доступной. Он не вызывает браузерное Fullscreen API и не требует поддержки полноэкранного режима в браузере. Состояние временное и сбрасывается при уходе из пакета или Home. На каждом экране пакета оставляйте кнопку выхода и отражайте `active` через `aria-pressed`. Обновления свойств должны обновлять кнопку, не заменяя незавершенные формы. Пакеты, зависящие от этого элемента управления, объявляют Capability API 1.376 или новее; старые пакеты могут сохранить прежние макеты.

<a id="capability-api-150-professor-mari-actions"></a>

### Capability API 1.50: действия Professor Mari

Пакет с новым разрешением `mari-actions` может предлагать именованные действия для Professor Mari. Он регистрирует одну службу под собственным ID; инструмент Mari `package_service` перечисляет действия и выполняет выбранное по просьбе пользователя.

```ts
export async function activate({ api }) {
  api.registerService("mari-actions:my-package", {
    list: () => [
      {
        name: "add-idea",
        summary: "Give a Creator an idea for a post.",
        inputs: { accountId: "The Creator.", text: "The idea." },
      },
    ],
    run: async (name, input, { signal }) => {
      const parsed = schemas[name]?.safeParse(input);
      if (!parsed?.success) return { ok: false, status: 400, error: "Invalid input." };
      return { ok: true, value: await doIt(name, parsed.data, signal) };
    },
  });
}
```

Важные правила:

- Ключ должен быть `mari-actions:<package-id>` регистрирующего пакета. Без разрешения или под чужим ID регистрация выбрасывает ошибку, поэтому действие Mari всегда принадлежит указанному пакету.
- `list()` возвращает записи `{ name, summary?, inputs? }`. Имена содержат 1–80 букв, цифр, `.`, `_` или `-`; остальные записи не показываются. Mari читает `summary` и `inputs`, поэтому пишите понятно. Видны и доступны для запуска только первые 50 действий. Mari видит до 40 входов на действие; имена обрезаются до 80 символов, каждый текст до 300. `list()` должен ответить за 5 секунд, иначе действия пакета пропускаются.
- `run(name, input, { signal })` вызывается только с именем из списка и обычным JSON-объектом до 64 000 символов. Вход поступает от модели: до любых действий проверьте его собственной схемой. Верните `{ ok: true, value }` или `{ ok: false, status?, error }`; Mari видит первые 2000 символов ошибки. `signal` отменяется при остановке Mari пользователем или через 5 минут; Engine перестает ждать, поэтому остановите и свою работу.
- Engine скрывает data URL в `value` до чтения Mari и обрезает длинные ответы. Возвращайте ID и короткий текст, не файлы.
- Получение списка только читает данные. Каждый запуск считается изменением в Permissions Mode: Plan отклоняет его, Manual ждет Accept пользователя. Engine не может предварительно показать или отменить действие пакета, поэтому карточка Keep/Restore не появляется. Для труднообратимых изменений предложите свое действие отмены. По этой причине Plan отклоняет даже действия только для чтения.
- Отключение или удаление пакета удаляет его действия.

`mari-actions` отклоняется в манифесте с `capabilityApi` ниже 1.50.

### Capability API 1.36: достижения пакетов

Пакет с новым разрешением `achievements` может добавлять значки в панель **Achievements** (достижения) на главном экране, проверять, открыты ли они, и открывать их. Панель показывает их в разделе с названием пакета в заголовке, после собственных значков движка.

```ts
export async function activate({ api }) {
  api.registerAchievements([
    { id: "first_run", title: "First Run", description: "Ran the package once.", iconPath: "art/first-run.png" },
    {
      id: "ten_runs",
      title: "Regular",
      description: "Ran the package ten times.",
      target: 10,
      readProgress: () => runs,
    },
  ]);
  // Later, when the package decides a badge is earned:
  if (await api.runtime.achievements.unlock("first_run")) celebrate();
}
```

Правила, которые стоит знать:

- Идентификаторы получают пространство имен `<packageId>.<id>`. Во встроенном идентификаторе нет точки, поэтому коллизии между ними невозможны. Хост принимает локальный идентификатор или идентификатор с пространством имен и отклоняет любой идентификатор, который пакет не зарегистрировал сам.
- `unlock(id)` завершается со значением `true` только для того вызова, который открыл значок. `isUnlocked(id)` и `list()` читают состояние; `list()` возвращает собственные значки пакета вместе с прогрессом.
- Подсчет остается за пакетом. Для многоуровневого значка задаются `target` и функция обратного вызова `readProgress` – либо оба, либо ни один. Когда счетчик достигает цели, движок открывает значок при том же проходе проверки, что и собственные многоуровневые значки. Храните счетчик в хосте постоянного хранения. Если функция обратного вызова выбрасывает исключение или не завершается в течение **2 секунд**, она сообщает нулевой прогресс, а событие записывается в лог. Как и у инструментов, это ограничивает только асинхронное ожидание: синхронную работу, блокирующую цикл событий, прервать нельзя.
- `iconPath` – путь внутри корневой папки ресурсов пакета, обслуживаемый маршрутом ресурсов пакета. Закрытая карточка по-прежнему показывает замок. Если изображение не загрузилось, карточка использует `icon` (по умолчанию `trophy`).
- `title` и `description` – отображаемый текст. Языковой пакет может переопределить их через `capabilityAchievements.<packageId>.<id>.title` и `.description`.
- Не более **32 значков на пакет**. Если в группе есть хотя бы одна недопустимая запись, не регистрируется ничего.
- Деактивация или удаление пакета скрывает его значки. Полученные достижения сохраняются, как и собственные достижения движка, и снова показываются при возвращении пакета.

`api.registerAchievements` и `api.runtime.achievements` существуют только в настолько новой версии движка, поэтому использующий их пакет объявляет `capabilityApi` 1.36.

### Capability API 1.35: виджеты Home агентов

Пакет агента может предложить до трех карточек для сетки виджетов Home. Engine никогда не размещает их сам: пользователь добавляет, скрывает, восстанавливает и упорядочивает их в **Widget Manager** (диспетчер виджетов), где они сгруппированы под агентом. Engine отвечает за сетку, рамку и раскладку; пакет за содержимое карточки.

Объявляйте слот `home-widget` вместе с определениями виджетов:

```json
{
  "schemaVersion": 2,
  "capabilityApi": { "major": 1, "minor": 35 },
  "kind": ["agent"],
  "permissions": ["ui"],
  "entrypoints": { "client": "client.js" },
  "contributions": {
    "slots": ["home-widget"],
    "homeWidgets": [
      {
        "id": "latest",
        "label": "Latest Posts",
        "description": "The newest posts from the feed.",
        "size": "large",
        "iconPath": "art/widget.png",
        "accent": "violet",
        "surface": "solid",
        "header": "banner"
      }
    ]
  }
}
```

- `id` использует строчный kebab-case, не более 64 символов, уникален в пакете.
- `label` (1–80 символов) и `description` (до 200) показываются в Widget Manager. Языковой пакет может заменить их через `localizations.<locale>.homeWidgets.<id>.label` и `.description`.
- `size` равен `compact` или `large`. Большой виджет занимает больше места.
- `icon` – имя значка Engine (`activity`, `bell`, `calendar`, `chart`, `circle`, `clock`, `file`, `flame`, `heart`, `image`, `list`, `message`, `sparkles`, `star`, `zap`). `iconPath` – графика пакета (`gif`, `jpg`, `jpeg`, `png`, `webp`), которая должна быть в `files[]`.
- `accent`, `surface` и `header` выбирают готовые варианты оформления Engine.

Установка отклоняется, если пакет не является `agent` с разрешением `ui` и клиентской точкой входа, если слот и `homeWidgets` не объявлены вместе, два виджета имеют одинаковый ID или `capabilityApi` ниже 1.35.

Engine монтирует клиентский элемент с `view="widget"`. Помимо `packageId`, `packageVersion` и `localization`, `capabilityProps` содержит:

- `widgetId`, `widgetLabel`, `widgetDescription`, `widgetIcon`, `widgetIconPath`, `widgetAccent`, `widgetSurface` и `widgetHeader`: определение отображаемой карточки, чтобы одна сборка рисовала все объявленные виджеты.
- `active`: `true` только когда Home открыт и карточка видна. При `false` приостановите опрос и анимации.
- `onOpenNoodle()`: открывает собственную браузерную вкладку Home пакета. Несмотря на имя, работает с любым пакетом, объявляющим `home-browser-tab`. Без вкладки эта функция и `onOpenPost` ничего не делают.
- `onOpenPost(id)`: открывает собственную вкладку Home на элементе. `id` – строка до 128 символов; другие значения игнорируются. Элемент `view="browser"` получает `focusPostId: id` и после показа должен вызвать `onFocusPostHandled()`, чтобы фокус не повторялся. Переход на любую другую вкладку сбрасывает ожидающий фокус.

Виджет – небольшой вид агента, а не его вторая копия. Делайте его легким, а для больших задач отправляйте пользователя в браузерную вкладку.

### Capability API 1.34: существо, описанное правилами набора

Существо бестиария может иметь `sheet`: произвольно частичный лист в терминах набора правил. Бой строит его как участника группы, поэтому здоровье, защита, спасброски, инициатива, скорость и способности списков следуют объявлениям набора, а стоимость оплачивается из его собственных запасов. Рядом с листом не указываются `health`, `defense`, `initiativeModifier`, `speed`, `abilities` или `saves`; собственные действия блока могут отсутствовать:

```json
{
  "capabilityApi": { "major": 1, "minor": 34 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json", "catalogs/creatures.json"] } }
}
```

Проверка читает байты правил и все файлы каталога установки, как в 1.27. Строка листа существа может содержать `_catalog: "<catalog>/<entry>"`, ссылаясь на запись каталога, питающего список; Engine загружает эти каталоги вместе с бестиарием. Это не мягкий интерфейс, как и 1.20–1.33: неизвестный ключ отклоняет весь строгий файл каталога, поэтому пакет объявляет 1.34. Новых разрешений нет.

### Capability API 1.33: момент, которого ждет реакция

`mechanics.reaction` записи каталога может быть объектом вместо `true`. `on` называет момент, обнаруживаемый Engine, `at` указывает цель выбранного действия, а `cancels` отменяет действие, ожидающее в этом окне:

```json
{
  "capabilityApi": { "major": 1, "minor": 33 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json", "catalogs/spells.json"] } }
}
```

`on` принимает `aimed` (до попадания по владельцу записи) или `harmed` (после полученного урона); указание момента помещает запись в меню этого окна. `at` принимает `source`, автоматически выбирающее вызвавшего событие, или `chosen`, сохраняющее собственный выбор целей записи. Только запись `aimed` может использовать `cancel`: прошедшее событие отменить нельзя. Стоимость отмененного действия остается оплаченной, поскольку ее списали до вопроса.

`"reaction": true` означает лишь действие вне своего хода, чего недостаточно для предложения в окне: в меню оно не появляется и новой версии не требует. Это не мягкий интерфейс, как и 1.20–1.32: Engine, не читающий объект, отклоняет весь строгий каталог, поэтому пакет объявляет 1.33. Новых разрешений нет.

### Capability API 1.32: оружие, ограничивающее свои удары

Источник атаки может объявлять `strikesCappedBy`, логический столбец собственного списка. Отмеченная строка покупает один удар независимо от `strikes` списка: оружие с одним выстрелом сохраняет один выстрел, даже когда остальной список атакует столько раз, сколько говорит лист. Это выражает правило Loading из SRD 5.1: "you can fire only one piece of ammunition when you use an action, bonus action, or reaction to fire it, regardless of the number of attacks you can normally make."

```json
{
  "capabilityApi": { "major": 1, "minor": 32 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

Требуется соседнее `strikes`; без него поле отклоняется, поскольку список, покупающий один удар, уже ограничивает каждую строку. Это не мягкий интерфейс, как и 1.20–1.31: неизвестный ключ отклоняет весь файл правил, поэтому пакет объявляет 1.32. Новых разрешений нет.

### Capability API 1.31: интеграции генерации хоста

Серверные пакеты могут обращаться к текущим службам LLM, изображений и видео Engine через `api.runtime.integrations`. Объявите API 1.31 в манифесте и проверьте доступность хоста интеграций при активации. Старый Engine отклонит требование до активации. Операции провайдера требуют `network`; сохранение, временное размещение и удаление медиа требуют `storage`.

- `llm.createProvider(...)` принимает настройки подключения фабрики Engine, включая собственные параметры запросов и заголовки. Полученный провайдер предоставляет `chat`, `chatComplete`, `embed`, `maxContextValue` и `maxTokensOverrideValue`, без свойств с учетными данными.
- `llm.localSidecar()` возвращает локального провайдера sidecar хоста через тот же фасад.
- `llm.withFallback(...)` оборачивает провайдера, созданного тем же хостом пакета, сохраняя допуск, уведомления о резервном варианте и выбор провайдера Engine.
- `images.generate(...)` и `videos.generate(...)` используют текущие реализации Engine, отмену, журналирование запросов, сетевые проверки и очереди медиа. Передавайте `signal` вызывающего кода и `debugMode` интерфейса, если они доступны.
- `images.save`, `images.remove`, `images.stage` и `images.sweepStaged` используют безопасное сохранение галереи и жизненный цикл временных файлов. `videos.save` и `videos.remove` используют путь хранения видео. `images.resolveNovelAiRequestSize` использует нормализацию размеров NovelAI хоста. Нормализация длительности видео и публичной загрузки референсов доступна через `videos.resolveDuration` и `videos.resolveReferenceUpload`.
- `speech.transcribe(audio, { filename, mimeType, signal })` отправляет записанный звук на сервер распознавания речи, который пользователь указал в **Connections → Speech to Text**, и возвращает расшифровку либо `null`, пока этот сервер выключен, чтобы пакет продолжал использовать собственную расшифровку. Метод применяет политику адресов хоста (`STT_LOCAL_URLS_ENABLED`), ограничения размера и времени и никогда не раскрывает сохраненный ключ. `speech` необязателен и не требует более новой версии API возможностей: проверьте `typeof api.runtime.integrations?.speech?.transcribe === "function"` и в старых Engine возвращайтесь к своей расшифровке.

Типы запросов и результатов экспортирует `@marinara-engine/shared`. Построение промптов и оркестрацию пакета оставляйте в пакете; для операций провайдера используйте эти точки хоста вместо копирования служб Engine. Чистые вспомогательные функции и типы по-прежнему можно включать в пакет.

### Capability API 1.341: службы среды выполнения хоста и общие серверные библиотеки

Сервер пакета, который включает собственную копию службы Engine, запускает ее второй экземпляр с отдельным состоянием:
собственным подключением Intiface, собственным допуском к подключениям, собственной очередью метаданных чата и собственным реестром служб.
Capability API 1.341 добавляет элементы `api.runtime`, которые обращаются к действующим экземплярам Engine,
и позволяет серверам пакетов брать некоторые библиотеки из Engine вместо включения их копий. Каждый новый элемент
в `CapabilityRuntimeHost` необязателен, поэтому перед использованием проверьте, существует ли он.

- `runtime.services.get(key)` возвращает службу, которую пакет зарегистрировал через `api.registerService`, или
  `null`, если ее нет либо идет генерация в общей комнате. Метод читает реестр Engine, поэтому каждый пакет видит ту же службу.
  Ключи `agent-runtime:` и `mari-actions:` всегда возвращают `null`; только Engine читает их.
- `runtime.commands.parse(content)`, `strip(content)` и `instructions()` читают команды разговора по грамматике
  Engine и с зарегистрированными тегами всех пакетов.
- `runtime.logger.isLevelEnabled(level)` сообщает, записывает ли логгер Engine сейчас этот уровень.
- `runtime.persistence.patchChatMetadata(chatId, patch, { touchUpdatedAt })` – обновление метаданных через очередь
  Engine: одна очередь на чат, общая с собственными записями Engine, защитой общей комнаты и порядковыми номерами записей.
  Ключи обновления заменяют эти ключи, а остальные сохраняются. `patch` может быть функцией текущих метаданных.
  Внутри `withChatLock` для того же чата обновление выполняется в рамках этой блокировки. Как и `updateChatMetadata`,
  оно отклоняет новую ссылку на изображение Global Gallery, которого больше нет.
- `runtime.persistence.appendMessages(chatId, messages)` добавляет сообщения, каждое с первым свайпом, одной
  партией и возвращает их. `createChatNote` и `createChatInfluence` добавляют заметку или одноразовое влияние из
  разговора в связанный с ним чат Roleplay. Для этих четырех элементов сохранения требуется `chat-write`.
- `runtime.persistence.updateCharacterStatus(chatId, characterId, { status, activity, duration })` применяет
  `[schedule_update]` так же, как Engine после ответа в Conversation: временный статус на карточке персонажа,
  который отображается у этого персонажа во всех чатах до истечения срока. `status` – это `online`, `idle`, `dnd`
  или `offline`, длина `activity` – не больше 500 символов, и хотя бы один из этих двух параметров обязателен.
  `duration` записывается как в команде (`2h`, `30m`); если его нет или его нельзя прочитать, статус действует
  60 минут, но никогда не дольше недели. Метод возвращает `{ status, activity, expiresAt }` или `null`, если ничего
  не изменилось: заданный пользователем вручную статус имеет приоритет, а общая комната сохраняет свои распорядки.
  Метод отклоняет недопустимое обновление, чат не в режиме Conversation и персонажа, которого нет в чате;
  требуется `chat-write`. Он появился в capability API 1.341 позже первых Engine, сообщающих о поддержке 1.341,
  поэтому проверьте `typeof api.runtime.persistence.updateCharacterStatus === "function"` и пропустите смену статуса, если метода нет.
- `runtime.integrations.admission` – допуск к подключениям Engine, поэтому фоновая работа пакета ждет собственных
  запросов пользователя на том же подключении. `withProvider(provider, connectionId, mode)` оборачивает провайдера,
  созданного интеграциями того же пакета, `run(connectionId, mode, operation)` выполняет одну попытку,
  `tryBackground(connectionId)` занимает фоновое место, когда подключение свободно, а `isFailure(error)` распознает
  ошибки занятости и отклонения Engine. Разрешение не требуется, потому что метод только резервирует места.
- `runtime.integrations.haptics` (`status`, `connect`, `executeCommand`) использует единственное подключение Engine
  к Intiface Central. Требуется `network`.
- `runtime.integrations.spotify` (`commandsAvailable`, `playSong`) использует аккаунт Spotify агента Music DJ.
  `playSong` отклоняет вызов с `ConversationSpotifyCommandError`; коды `spotify_unavailable` и
  `missing_playback_scope` означают, что Spotify не настроен, поэтому молча пропустите команду. Требуется `network`.
- `runtime.integrations.speech.transcribeLocal(wav)` расшифровывает запись PCM WAV моделью Local Whisper,
  скачанной в **Connections**, и отклоняет вызов с сообщением Engine, если модель не скачана. Требуется `network`.
- `runtime.integrations.images.addToChatGallery(input)` добавляет изображение, сохраненное через `images.save`,
  в галерею чата, а `images.persistToEntityGalleries(input)` – в галереи изображенных на нем персонажей и персон,
  как это происходит с изображениями, созданными Engine. Для обоих требуется `storage`.

**Никогда не включайте собственную копию.** Если одного из этих элементов нет, пакет сообщает, что для функции нужна
более новая версия Marinara Engine. Он никогда не возвращается к включенной в пакет копии службы Engine с состоянием,
например реестра провайдеров, локального sidecar, допуска к подключениям, тактильной отдачи, Spotify, логгера, реестра
или очереди хранения, потому что вторая копия разделяет состояние, которое Engine держит в одном месте.
Чистые вспомогательные функции и типы по-прежнему можно включать в пакет.

**Общие серверные библиотеки.** Сервер пакета может не включать `zod`, `adm-zip`, `dotenv`, `nanoid` и `jsonrepair`
в свою сборку, а импортировать их по имени, как уже можно делать с `@huggingface/transformers`, `onnxruntime-node`,
`onnxruntime-web`, `sharp`, `pino`, `pino-pretty` и `undici`. Node находит их из рабочей копии пакета через две ссылки:
из `<runtime copy>/node_modules` в `DATA_DIR/capability-packages/node_modules`, а оттуда в
`packages/server/node_modules` Engine, поэтому пакет получает тот же экземпляр модуля, который использует Engine.
pnpm держит там только прямые зависимости сервера, поэтому разрешаются только эти имена; зависимость зависимости,
например `ws`, недоступна. Engine сохраняет перечисленные имена как прямые производственные зависимости
`packages/server`, и каждая установка сохраняет эту структуру: установка из исходников и через программу запуска,
Windows (где ссылка данных является соединением каталогов), Android и Termux, а также оба образа Docker.
При запуске или активации пакета Engine восстанавливает ссылку данных, если она указывает куда-то еще, в том числе
если ссылка осталась битой после переноса папки данных из другого пути установки. Все, что не является ссылкой,
остается без изменений.

**Объявление.** Пакет, использующий что-либо из этого, объявляет `schemaVersion: 2`,
`capabilityApi: { major: 1, minor: 341 }` и `builtAgainst` и сохраняет свой диапазон `engine`. Манифест
`schemaVersion: 1` никогда не проверяется на совместимость с API возможностей, поэтому его переводят на версию 2.
Допуск определяется API возможностей, а не версией Engine: Engine без этих элементов отказывает в установке или
обновлении ("Package requires capability API 1.341; this Engine supports ..."), не включает пакет в список
обновлений и оставляет установленную версию работающей.
