# План перетаскивания ресурсов в чат

## Состояние

Этапы с 1 по 4 были реализованы в ветке `drag-me-baby-one-more-time` и влиты в `staging`. Более поздняя работа (#7362) позволяет перетаскивать строки библиотеки без ручки, дает пользователю сенсорного экрана собрать стопку совместимых ресурсов касаниями вторым пальцем и показывает промежутки вставки при изменении порядка.

Автоматические проверки распознавателя работают. Для назначения персонажа и замены персоны добавлены тесты Playwright на компьютере, но локально в текущем контейнере разработки они не запускаются: Chromium не может загрузить `libnspr4.so`. Эти браузерные сценарии должна выполнять система CI или среда с системными зависимостями Playwright.

До начала оставшихся этапов выполните правила координации, принятые в репозитории:

1. Проверьте, нет ли уже задачи, связанной с ней ветки, черновика PR или карточки проекта по перетаскиванию ресурсов в чат.
2. Обозначьте в задаче видимого ответственного.
3. С началом реализации откройте черновик PR в ветку `staging`.

## Цель

Дать возможность перетаскивать поддерживаемые ресурсы из правой панели прямо в активный чат, минуя настройки чата.

В центральном окне есть две возможные цели:

- **Область чата:** меняет постоянные настройки активного чата.
- **Поле ввода:** добавляет поддерживаемое вложение в текущий черновик.

Это не универсальные цели для сброса. Цель появляется только тогда, когда для перетаскиваемого элемента там есть настоящая, уже поддерживаемая операция.

## Продуктовое правило

Перетаскивание выбирает ресурс и цель. Приложение выполняет только те операции, которые уже есть в модели данных чата и в конвейере генерации.

- Одна допустимая операция добавления: применить сразу и предложить отмену.
- Одна допустимая операция замены: спросить подтверждение, если она заменит существующее значение.
- Несколько действительно поддерживаемых операций: показать небольшое окно выбора только с ними.
- Допустимой операции нет: не включать цель.
- Ресурс уже применен: не принимать повторный сброс.
- Никакого умозрительного контекста на один ход, скрытой вставки в промпт, искусственных упоминаний и декоративных плашек.

## Текущие контракты

Существующие контракты `Chat` и `ChatMetadata` поддерживают такие постоянные операции:

- Персонажи: обновление `Chat.characterIds`.
- Персона: обновление `Chat.personaId`.
- Пресет промпта: обновление `Chat.promptPresetId`.
- Подключение: обновление `Chat.connectionId`.
- Лорбуки: обновление `ChatMetadata.activeLorebookIds`.
- Агенты: обновление `ChatMetadata.activeAgentIds` и, при согласии, `ChatMetadata.enableAgents`.
- Фон чата: обновление существующих метаданных фона чата тем же путем назначения, которым пользуется `BackgroundPicker`.

Существующие поля ввода поддерживают вложение файлов. Ссылок на персонажа, лорбук, агента, персону, пресет или подключение в пределах одного сообщения они пока не поддерживают.

## Матрица поддерживаемых действий

Распознаватель возможностей обязан также соблюдать текущие ограничения режима чата и учитывать доступность ресурса. Таблица описывает операцию для случая, когда существующий интерфейс уже разрешает ее в активном режиме.

| Ресурс | Область чата | Поле ввода | Поведение при сбросе |
| --- | --- | --- | --- |
| Персонаж | Добавить идентификатор в `characterIds` | Нет | Добавить сразу; уведомление с отменой |
| Лорбук | Добавить идентификатор в `activeLorebookIds` | Нет | Добавить сразу; уведомление с отменой |
| Агент | Добавить идентификатор в `activeAgentIds` | Нет | Добавить сразу, если агенты включены; иначе спросить подтверждение на включение агентов и добавление |
| Персона | Задать `personaId` | Нет | Задать сразу, если поле пустое; спросить подтверждение при замене другой персоны |
| Пресет промпта | Задать `promptPresetId` | Нет | Соблюдать ограничения режима; задать сразу, если поле пустое; спросить подтверждение при замене другого пресета |
| Подключение | Задать `connectionId` | Нет | Спросить подтверждение при смене текущего подключения; показать старое и новое названия подключений |
| Фон чата | Задать существующие метаданные фона чата | Нет | Использовать нынешнюю семантику назначения фона; подтверждать замену, только если этого требует существующий сценарий |
| Изображение или поддерживаемый файл | Нет | Добавить во вложения черновика | Переиспользовать существующий конвейер проверки и подготовки вложений |
| Папка персонажей, лорбуков или агентов | Нет | Нет | Цели нет |
| Элемент управления настройками | Нет | Нет | Цели нет |
| Скрипт регулярного выражения | Нет | Нет | Цели нет, пока не появится контракт назначения в пределах чата |
| Своя функция или инструмент | Нет | Нет | Цели нет, пока не появится контракт назначения в пределах чата |
| Вклад расширения | По умолчанию нет | По умолчанию нет | Только по явному согласию через будущий типизированный API вкладов |

### Правила режимов

Не дублируйте правила режимов в обработчиках перетаскивания. Распознаватель возможностей сброса должен использовать те же предикаты, что и существующий интерфейс настройки чата.

Как минимум:

- Пресеты промптов остаются недоступны в режиме Conversation – так же, как в `PresetsPanel`.
- Сброс агента возможен, только если агент установлен, доступен и подходит текущему режиму.
- Операции с персонажем, персоной, лорбуком, подключением и фоном предлагаются только там, где доступен их существующий элемент управления назначением.
- Чат без активного идентификатора не дает ни одной цели для сброса ресурса.
- Ни стриминг, ни работа агентов не должны блокировать безопасное обновление метаданных, если существующий путь изменения этого еще не делает. Перед применением замены нужно заново прочитать текущее состояние чата.

## Проектирование взаимодействия

### Начало перетаскивания

Каждая поддерживаемая строка панели записывает одну версионированную полезную нагрузку ресурса:

```ts
type ChatResourceDragPayload = {
  version: 1;
  kind: "character" | "lorebook" | "agent" | "persona" | "preset" | "connection" | "background";
  ids: string[];
  label: string;
};
```

Используйте один свой тип MIME, например `application/x-marinara-chat-resource`. На время перехода сохраните существующие нагрузки MIME для папок: перестановка папок остается отдельным допустимым прочтением того же перетаскивания.

Эффекты перетаскивания ресурса должны объявлять `copyMove`:

- Цели-папки читают перетаскивание как перемещение.
- Цели в чате читают его как копирование или назначение.

Не полагайтесь на `text/plain` для внутренних операций с ресурсами. Этот тип неоднозначен и сейчас содержит голые идентификаторы.

### Видимость целей

В покое подсказки о целях сброса скрыты.

Когда распознанное перетаскивание ресурса входит в центральное окно:

1. Разберите и проверьте типизированную нагрузку.
2. Определите допустимые действия по самому свежему состоянию активного чата.
3. Покажите только допустимые цели.
4. Пишите текст под конкретное действие, например `Add Maris to this chat`, а не общее `Drop here`.
5. Оставьте недопустимые области без изменений и без приема сброса.

При перетаскивании поддерживаемого файла подсвечивается только поле ввода. При перетаскивании персонажа, лорбука, агента, персоны, пресета, подключения или фона в первом выпуске подсвечивается только область чата.

### Сброс на область чата

Активная область сброса – это текущая область чата, независимо от того, куда прокручена лента сообщений. Сброс поверх старого сообщения ничего не вставляет в историю и не меняет контекст задним числом.

При сбросе:

1. Заново прочитайте идентификатор активного чата и его текущие данные.
2. Заново определите возможность, чтобы не выполнить устаревшее или повторное действие.
3. Применяйте сразу, если операция добавляет и однозначна.
4. Открывайте отдельное окно подтверждения для замены или включения агентов.
5. Сообщайте об успехе локализованным всплывающим уведомлением с действием отмены.
6. Сообщайте о неудачном изменении, не трогая ленту сообщений.

Не создавайте сообщений пользователя, ассистента, рассказчика или системы, чтобы записать изменение настроек. В модели сообщений нет отдельного типа для служебных событий, а события настройки не должны попадать в историю, видимую модели.

### Сброс в поле ввода

Сохраните текущее поведение с файлами и в `ChatInput`, и в `ConversationInput`:

- Проверка поддерживаемых типов и предела размера в 20 МБ.
- Подготовка изображений через `prepareImageAttachment`.
- Чтение поддерживаемых текстовых файлов и файлов PDF по текущему пути вложений.
- Сохранение черновика с ожидающими вложениями для каждого чата.

Уточните распознавание перетаскивания в поле ввода: внутренние перетаскивания ресурсов не должны включать подсветку сброса файла и потом ничего не делать.

### Подтверждение

Спрашивайте подтверждение, только когда у операции есть заметное последствие:

- Замена активной персоны.
- Замена активного пресета промпта.
- Смена активного подключения.
- Включение агентов вместе с добавлением агента.
- Любой существующий путь назначения фона, который уже требует выбора или подтверждения замены.

Там, где это уместно, окно подтверждения называет текущее и предлагаемое значения. Посторонних действий в нем быть не должно: ни создания нового чата, ни разового вызова агента, ни ссылки на ресурс в сообщении.

### Отмена

Отмена возвращает точное значение, каким оно было до сброса, а не восстановленную догадку.

- Персонаж: вернуть прежний массив `characterIds` целиком.
- Лорбук: вернуть прежний массив `activeLorebookIds` целиком.
- Агент: вернуть и `activeAgentIds`, и `enableAgents`.
- Персона, пресет, подключение и фон: вернуть прежнее значение.

Перед выполнением отмены проверьте, что в активном чате все еще стоит значение, полученное при сбросе. Если это поле успела изменить другая правка, не затирайте ее: уберите устаревшую отмену и сообщите, что чат изменился.

## Архитектура

### Общий клиентский модуль

Добавьте узкий клиентский модуль, предварительно `packages/client/src/lib/chat-resource-drag.ts`, содержащий следующее:

- Константа типа MIME.
- Тип нагрузки и ее разбор во время выполнения.
- `writeChatResourceDragPayload(dataTransfer, payload)`.
- Определение перетаскивания файлов.
- Проверки вида ресурса.

В первом выпуске держите нагрузку только на клиенте: это состояние взаимодействия в браузере, а не контракт API.

### Распознаватель возможностей

Добавьте чистый распознаватель, предварительно `packages/client/src/lib/chat-resource-drop-capabilities.ts`:

```ts
type ChatResourceDropAction =
  | { type: "add-characters"; ids: string[] }
  | { type: "add-lorebooks"; ids: string[] }
  | { type: "add-agents"; ids: string[]; mustEnableAgents: boolean }
  | { type: "set-persona"; id: string; replacesId: string | null }
  | { type: "set-preset"; id: string; replacesId: string | null }
  | { type: "set-connection"; id: string; replacesId: string | null }
  | { type: "set-background"; id: string };
```

На вход идут разобранная нагрузка ресурса, активный чат, нормализованные метаданные, текущий режим и идентификаторы доступных ресурсов. На выходе – либо одно конкретное действие, либо `null`.

Распознаватель отвечает за:

- Отсев повторов.
- Ограничения режимов.
- Фильтрацию нескольких идентификаторов.
- Проверки установки и доступности.
- Обнаружение замены.
- Выбор ключа для видимой подписи действия.

Распознаватель не меняет данные и ничего не рисует на экране.

### Координатор изменений

Добавьте один хук рядом с областью чата, предварительно `use-chat-resource-drop.ts`, который:

- читает самое свежее состояние активного чата из React Query и Zustand в момент сброса;
- вызывает `useUpdateChat` для полей чата верхнего уровня;
- вызывает `useUpdateChatMetadata` для лорбуков и агентов;
- переиспользует существующий путь изменения при назначении фона;
- открывает локализованные подтверждения через существующие вспомогательные функции окон приложения;
- создает всплывающие уведомления об успехе и об ошибке, а также защищенные действия отмены.

Не кладите асинхронную логику изменений в хранилище Zustand.

### Наложение для сброса

Добавьте один презентационный компонент на общей границе центральной области чата, а не отдельные реализации внутри каждой ленты сообщений:

- Получает текущую нагрузку перетаскивания и определенное действие.
- Накрывает область чата, не перекрывая поле ввода.
- Считает глубину `dragenter`/`dragleave`, чтобы не мигать на дочерних элементах.
- Показывает иконку, название ресурса и локализованный текст действия.
- Подстраивается под тип указателя и тему оформления.

И область Conversation, и области Roleplay и Game должны идти через один и тот же координатор. Обертки под конкретную область могут задавать геометрию, но не должны дублировать правила определения возможностей.

### Подключение панелей

Переводите перетаскиваемые строки по очереди:

1. Персонажи.
2. Лорбуки.
3. Агенты.
4. Персоны.
5. Пресеты.
6. Подключения.
7. Фоны, если существующий контракт назначения переиспользуется без натяжек.

Каждая строка сохраняет свою нагрузку для перетаскивания в папку и добавляет нагрузку ресурса чата. Поведение перемещения по папкам не меняйте.

## Этапы реализации

### Этап 1: контракт перетаскивания и наложение в центре

- Добавить модуль типизированной нагрузки и ее разбор.
- Добавить чистый распознаватель возможностей для персонажей, лорбуков и агентов.
- Добавить наложение над центральной областью чата и координатор изменений.
- Подключить строки панелей персонажей, лорбуков и агентов.
- Добавить локализованные тексты действия, подтверждения, успеха, ошибки, повтора и отмены.
- Убедиться, что внутренние перетаскивания ресурсов не включают подсветку файлов в поле ввода.

Этот этап доказывает работоспособность основного сценария добавления, ради которого возможность и задумана.

### Этап 2: ресурсы с заменой

- Добавить нагрузки для персоны, пресета и подключения.
- Добавить обнаружение замены и локализованные окна подтверждения.
- Переиспользовать существующие ограничения режимов и хуки изменения данных.
- Добавить защищенную отмену для операций замены.

### Этап 3: назначение фона

- Выяснить, может ли существующий сценарий выбора фона принять идентификатор сброшенного фона без дублирования правил.
- Добавлять перетаскивание фона только при условии, что то же назначение в пределах чата переиспользуется как есть.
- Иначе оставить фоны без поддержки и записать причину в задаче или PR.

### Этап 4: паритет для касаний и работы без перетаскивания

Первая линия реализации – перетаскивание средствами HTML на компьютере. Телефоны и планшеты не должны зависеть от точного перетаскивания между панелями.

- Добавить действие `Add to active chat` в существующее меню действий каждой поддерживаемой строки.
- Переиспользовать тот же распознаватель возможностей, подтверждения, изменения данных и поведение отмены.
- Если перетаскивание пальцем остается, использовать существующие сенсорные ручки и определять цель в центре через `elementFromPoint`.
- Не перегружать долгое нажатие на папке так, чтобы разбор по папкам стал ненадежным.

Без этого этапа возможность нельзя считать готовой на телефонах и планшетах.

На этапах 1 и 2 изменений на сервере и в общем пакете не ожидается. Если по ходу работы окажется, что операция не проходит через существующие маршруты правки чата, остановитесь и пересмотрите объем плана – не вводите скрытый промпт или новый контракт хранения.

## Требования к доступности и вводу

- Не полагайтесь на один только цвет: показывайте иконку ресурса и текст действия.
- Не требуйте наведения курсора, чтобы найти равнозначное действие без перетаскивания.
- По окнам подтверждения можно ходить с клавиатуры, а при закрытии фокус возвращается на место.
- Клавиша Esc отменяет открытое подтверждение.
- Программы чтения с экрана получают короткое объявление, когда появляется допустимая цель и когда операция удалась или не удалась.
- Наложения не должны перехватывать обычную прокрутку, пока не идет распознанное перетаскивание.
- Области нажатия соблюдают принятые минимальные размеры для сенсорных экранов.
- В режиме уменьшенной анимации меняются прозрачность и состояние, без лишнего движения.

## Локализация

Весь новый видимый текст идет через смысловые ключи локализации. Обновляйте только канонический английский каталог: языковые пакеты сообщества могут откатываться на английский.

Категории текстов:

- Подписи действий для каждого вида ресурса.
- Подтверждения замены.
- Подтверждение включения агентов.
- Всплывающие уведомления об успехе и о неудаче.
- Сообщения об отмене и об устаревшей отмене.
- Объявления для программ чтения с экрана.
- Сообщение о повторе или об уже активном ресурсе, если оно показывается.
- Действия `Add to active chat` без перетаскивания.

## Тесты

Не оставляйте в репозитории временные файлы `.test.ts`.

### Регрессионное покрытие чистых функций

Постоянные проверки распознавателя возможностей добавляйте только в существующем поддерживаемом месте и формате регрессионных тестов:

- Персонажа нет -> действие добавления.
- Персонаж уже есть -> действия нет.
- Смешанная нагрузка с несколькими персонажами -> добавляются только отсутствующие допустимые идентификаторы.
- Лорбука нет -> действие добавления.
- Лорбук уже активен -> действия нет.
- Агента нет, агенты включены -> действие добавления.
- Агента нет, агенты выключены -> действие добавления с требованием включить агентов.
- Агент недоступен -> действия нет.
- Персона при пустом поле персоны -> действие назначения без замены.
- Персона поверх другой -> действие замены.
- Пресет в неподдерживаемом режиме -> действия нет.
- Подключение совпадает с текущим -> действия нет.
- Неверная версия, неизвестный вид, испорченные идентификаторы и слишком большая нагрузка -> отказ.

### Дымовые проверки в браузере

Там, где это разумно, расширьте `pnpm smoke:ui`:

- Перетащить персонажа из панели в область чата и проверить назначение.
- Отменить действие и проверить, что прежний список персонажей вернулся.
- Проверить, что перетаскивание персонажа над полем ввода не показывает отклик сброса файла.
- Перетащить поддерживаемый файл на поле ввода и проверить, что работа с вложениями не пострадала.
- Проверить, что у уже активного ресурса нет активной цели сброса.
- Проверить, что отказ в окне подтверждения замены ничего не меняет.
- Проверить, что подтвержденная замена обновляет чат.
- Проверить, что перетаскивание по папкам по-прежнему перемещает ресурсы внутри панели.

### Ручная проверка

Проверьте на компьютере в режимах Conversation, Roleplay и Game там, где они поддерживаются:

- Темную и светлую темы оформления.
- Открытую правую панель при длинной прокрученной ленте сообщений.
- Сброс с добавлением, повторный сброс, замену, отказ, ошибку, отмену и устаревшую отмену.
- Движение курсора по вложенным элементам ленты без мигания наложения.
- Прежнее перемещение по папкам в панели.
- Прежний сброс файлов и изображений в обоих полях ввода.

Проверьте на телефоне или в окне с неточным указателем:

- Равнозначное действие `Add to active chat` без перетаскивания.
- Прежнее перетаскивание папок пальцем осталось удобным.
- Окна подтверждения помещаются на экран и закрываются.
- Ни текст, ни элементы управления не налезают друг на друга.

Обязательные команды:

```bash
pnpm localization:check
pnpm check
pnpm regression:prompt
pnpm smoke:ui
```

Команда `pnpm regression:prompt` обязательна до слияния: правка `LorebooksPanel.tsx` затрагивает активацию лорбуков, а от нее зависит сборка промпта.

## Риски и меры

### Конфликт с существующим перетаскиванием папок

Риск: эти же строки уже используют перетаскивание для переноса элементов в папки.

Мера: сохранить существующие типы MIME для папок, добавить отдельный типизированный тип MIME для ресурсов чата и дать каждой цели читать только свою нагрузку. Проверить поведение `copyMove` и регрессии с папками.

### Ложная подсветка поля ввода

Риск: нынешние обработчики `dragover` в поле ввода реагируют на любое перетаскивание, в том числе на внутренние идентификаторы ресурсов.

Мера: включать отклик поля ввода, только когда `DataTransfer.types` или `DataTransfer.items` сообщает о файлах либо о другой явно поддерживаемой нагрузке вложения.

### Устаревшее состояние чата

Риск: активный чат или назначенные ресурсы могут измениться между началом перетаскивания, сбросом, подтверждением и отменой.

Мера: определять действие по текущему состоянию при сбросе и еще раз перед изменением или отменой. Защитить отмену от затирания более свежих правок.

### Расхождение правил режимов

Риск: перетаскивание может разрешить назначение, которое запрещает интерфейс настройки.

Мера: вынести или переиспользовать общие предикаты из существующих сценариев назначения. Не зашивать вторую матрицу правил внутрь компонентов панелей.

### Скрытое разрастание поведения

Риск: если поле ввода визуально принимает ресурсы, это намекает на контекст на один ход, которого сервер не обеспечивает.

Мера: держать сброс ресурсов в поле ввода выключенным, пока не появится отдельно спроектированный контракт контекста в пределах сообщения.

### Сброс большого выделения

Риск: перетаскивание в режиме выделения может добавить неожиданно большой набор персонажей, лорбуков или агентов.

Мера: отсеивать недопустимые и уже активные идентификаторы, соблюдать существующие ограничения сервера и режима, а также спрашивать подтверждение, когда групповой сброс переходит существующий порог. Не выдумывайте новый произвольный предел.

## За рамками задачи

- Сброс ресурса на старое сообщение.
- Изменение истории промптов задним числом.
- Запись изменений настроек сообщениями в ленте.
- Персонажи, лорбуки, персоны, пресеты, подключения и агенты на один ход.
- Вызов агента сбросом в поле ввода.
- Создание нового чата сбросом в центральную область.
- Перетаскивание произвольных настроек в чат.
- Универсальный API сброса для расширений в первом выпуске.
- Перетаскивание из ленты одного чата в другой чат.

## Критерии приемки

Этап 1 считается принятым, когда выполнено следующее:

- Персонажа, лорбук или агента можно перетащить из строки правой панели в подходящую область активного чата.
- Обновляется нужное существующее поле чата, и в ленте не появляется сообщение.
- Уже активные и недоступные ресурсы не принимаются.
- Добавление агента при выключенных агентах требует явного подтверждения.
- После каждого успешного изменения предлагается защищенная отмена.
- Перетаскивание ресурсов не вызывает отклик вложений в поле ввода.
- Прежний сброс файлов-вложений работает в обоих полях ввода.
- Прежнее перетаскивание по папкам не изменилось.
- Весь новый видимый текст локализован.
- На компьютере и на телефоне доступны равнозначные действия, даже если на телефоне это пункт меню, а не перетаскивание между панелями.
- Команды `pnpm localization:check` и `pnpm check`, а также нужные дымовые проверки интерфейса проходят успешно.

Возможность целиком считается готовой, когда сделаны еще и ресурсы с заменой из этапа 2 и обязательный паритет для телефонов. Назначение фона остается необязательным, пока этап 3 не подтвердит, что его нынешнюю семантику можно переиспользовать без дублирования правил.

## Отложенное развитие

Будущая возможность контекста в пределах сообщения может сделать персонажей, лорбуки, агентов, персон, пресеты и подключения допустимыми для сброса в поле ввода. Для этого нужен отдельный контракт в общем пакете и на сервере: хранение, сборка промпта, лимит токенов, маршрутизация к провайдеру, отображение, восстановление черновика и правила истории сообщений. Протаскивать это в текущую задачу в виде клиентских плашек нельзя.
