# Условные промпты ({{#if}})

Это руководство объясняет, как работают блоки `{{#if}}` в приложении Marinara Engine. Условный блок добавляет часть промпта только тогда, когда значение подходит под заданное вами правило. Условия – часть системы макросов, поэтому они работают везде, где работают макросы: в карточках персонажей, персонах, записях лорбуков и пресетах промптов.

## Зачем нужны условные промпты

Макрос – это подстановка в двойных фигурных скобках `{{double-brace}}`, которую Marinara Engine заменяет живым значением при сборке промпта. Условный блок идет дальше. Он проверяет значение, оставляет один фрагмент текста, а остальное отбрасывает.

Вы пишете условие, текст для случая, когда условие выполняется, и (по желанию) текст для случая, когда не выполняется. Marinara проверяет условие при каждой сборке промпта. Поэтому одна и та же карточка или пресет ведут себя по-разному с разными персонажами, персонами и чатами.

Частый случай – инструкции для отдельных персонажей внутри одного общего пресета. Другой частый случай – подставлять поле только тогда, когда в нем есть текст, чтобы не отправлять модели пустой заголовок.

## Базовый синтаксис

Условный блок открывается `{{#if condition}}` и закрывается `{{/if}}`. Всё, что между ними, – это текст для случая, когда условие выполняется.

```
{{#if condition}}
Text used when the condition is true.
{{/if}}
```

Для обратного случая добавьте ветку `{{else}}`:

```
{{#if condition}}
Text used when true.
{{else}}
Text used when false.
{{/if}}
```

Дополнительные условия можно выстроить в цепочку через `{{else if}}`. Marinara проверяет ветки по очереди, сверху вниз. Она оставляет первую ветку с выполненным условием, раскрывает макросы внутри нее и отбрасывает все остальные ветки. Если ни одно условие не выполнилось, а ветки `{{else}}` нет, весь блок дает пустую строку.

```
{{#if length == "short"}}
Keep your reply to one or two sentences.
{{else if length == "long"}}
Write a detailed, multi-paragraph reply.
{{else}}
Write a reply of normal length.
{{/if}}
```

Блок можно записать в несколько строк, как выше, или в одну. Одно условие можно вложить внутрь ветки другого, более крупного условия.

## Поддерживаемые операторы

Условие обычно состоит из левого значения, оператора и правого значения – например, `char == "Alice"`. В таблице ниже собраны все доступные операторы. Каждый оператор показан в виде кода.

| Оператор | Значение |
| --- | --- |
| `==`, `=`, `is` | Равно. |
| `!=`, `is not` | Не равно. |
| `>` | Больше (только числа). |
| `<` | Меньше (только числа). |
| `>=` | Больше или равно (только числа). |
| `<=` | Меньше или равно (только числа). |
| `contains`, `includes` | Левое значение содержит правое как текст. |
| `not contains`, `not includes` | Левое значение не содержит правого. |

Сравнение подчиняется нескольким правилам:

1. Для `==`, `=`, `is`, `!=` и `is not`: если обе стороны похожи на числа, Marinara сравнивает их как числа. Поэтому `5` равно `5.0`. Иначе сравнение идет как для текста, без учета регистра. Поэтому `Mari` равно `mari`.
2. Для `>`, `<`, `>=` и `<=` обе стороны должны быть числами. Если хотя бы одна сторона не число, условие не выполняется.
3. Для `contains`, `includes`, `not contains` и `not includes` регистр не важен. Поэтому `contains "dr"` находит совпадение в тексте `Dr Smith`.

## Объединение условий через OR и AND

Оператор `||` подходит, когда достаточно любого из условий. Оператор `&&` – когда должны выполниться все условия.

```
{{#if character == "Maukie" || character == "Pantalone"}}
Use the shared Maukie and Pantalone instructions.
{{/if}}

{{#if characters contains "Maukie" && characters contains "Pantalone"}}
Both characters are present in this chat.
{{/if}}
```

Оператор `&&` вычисляется раньше `||`. Чтобы задать порядок явно, поставьте скобки:

```
{{#if (character == "Maukie" || character == "Pantalone") && scenario contains "lake"}}
Use the lakeside instructions for either character.
{{/if}}
```

Если одно и то же значение проверяется на несколько вариантов, повторяющуюся левую часть после `||` можно опустить:

```
{{#if character == "Maukie" || "Pantalone"}}
Use the shared instructions.
{{/if}}
```

Такая короткая запись означает `character == "Maukie" || character == "Pantalone"`. Она работает с операторами равенства `==`, `=` и `is`. По обе стороны `&&` пишите условия целиком: одно значение обычно не может быть равно двум разным вариантам сразу.

### Проверка на заполненность (без оператора)

Если в условии нет оператора, Marinara выполняет проверку на заполненность. Вопрос при этом простой: есть ли в значении настоящее содержимое?

```
{{#if scenario}}
Current scene: {{scenario}}
{{else}}
No specific scene is set.
{{/if}}
```

Проверка на заполненность выполняется, когда значение не пустое и не равно одному из слов: `false`, `0`, `no`, `off`, `null` или `undefined`. Регистр этих слов не важен. Такая проверка нужна, когда текст должен попадать в промпт только при заполненном поле.

### Что можно сравнивать

Левой или правой стороной условия может быть:

1. Ключевое слово поля или личности – например, `char`, `user`, `group`, `persona`, `description`, `personality`, `scenario`, `input` или `model`. Они берут те же значения, что и одноименные макросы. Ключевое слово `group` перечисляет остальных активных персонажей чата, кроме того, кто отвечает сейчас.
2. Литерал в кавычках – например, `"Alice"`.
3. Имя переменной пресета – например, `length`. Переменная пресета – это именованное значение, которое задается в пресете промпта. Смотрите [Переменные пресета](preset-variables.md).
4. Явное обращение к переменной в виде `var:name` или `var.name`.
5. Другой макрос: сначала раскрывается его значение, потом идет сравнение.
6. Вопрос модели решений в виде `decision:"..."` или `decision_choice:"..."`. См. [Вопрос модели решений](#asking-the-decision-model).

Слово без кавычек, если это не ключевое слово, Marinara считает именем переменной. Если переменной с таким именем нет, слово используется как обычный текст. Кавычки вокруг литералов снимают эту неоднозначность, поэтому в спорных случаях ставьте кавычки.

## Правила кавычек

Когда сравнение идет с конкретным текстом, берите его в кавычки. Так Marinara понимает, что перед ней точный литерал, а не ключевое слово или переменная.

```
{{#if char == "Dottore"}}
Speak in a cold, clinical tone.
{{/if}}
```

Подойдут простые двойные или простые одинарные кавычки. Marinara принимает и типографские кавычки, но простые надежнее, и именно они стоят во всех примерах в приложении. Внутри значения кавычку можно экранировать обратным слешем, а перевод строки записать как `\n`.

Литерал с пробелом всегда берите в кавычки – например, `"Dr Smith"`. Значение из нескольких слов без кавычек читается как одно имя переменной, а это почти никогда не то, что нужно.

## Групповые блоки для нескольких персонажей

В групповом чате с двумя или более персонажами групповой блок повторяет один и тот же текст для каждого персонажа. Так одним блоком описываются все персонажи сцены.

Чтобы создать групповой блок, поставьте одиночную `[` на отдельной строке, затем текст, затем одиночную `]` на отдельной строке. Внутри блока обязателен макрос персонажа – например, `{{char}}` или `{{description}}` – либо условие по персонажу вида `{{#if char == "Alice"}}`. Тогда Marinara повторяет блок для каждого персонажа и по очереди раскрывает макросы персонажа для каждого из них.

```
[
{{char}}'s current attitude:
{{#if char == "Alice"}}cheerful and open{{else}}guarded and quiet{{/if}}
]
```

В групповом чате с Alice и Bob блок сработает дважды. На первом проходе подставляется имя Alice и выбирается ее ветка. На втором – имя Bob и его ветка. За пределами группового блока макрос персонажа раскрывается только для текущего или основного персонажа.

Групповые блоки раскрываются только в чате с двумя или более персонажами. В чате с одним персонажем строки `[` и `]` остаются обычным текстом.

## Разобранные примеры (до и после)

Ниже – три полных примера вместе с тем, что получает модель.

Свой тон для конкретного персонажа внутри общего пресета:

```
{{#if char == "Dottore"}}
Speak in a cold, clinical tone.
{{else}}
Speak warmly and casually.
{{/if}}
```

Для персонажа с именем `Dottore` модель получает `Speak in a cold, clinical tone.` Для всех остальных персонажей – `Speak warmly and casually.`

Подставить поле только при заполненном значении:

```
{{#if backstory}}
Backstory to remember: {{backstory}}
{{/if}}
```

Если у персонажа заполнено поле **Backstory** (предыстория), модель получает эту строку вместе с текстом предыстории. Если поле **Backstory** пустое, весь блок дает пустую строку, и пустой заголовок никуда не отправляется.

Совпадение по части имени пользователя:

```
{{#if user contains "Dr"}}
Address the user as Doctor.
{{/if}}
```

Если имя персоны содержит `Dr`, модель получает указание обращаться к вам "Doctor". Если нет, блок дает пустую строку.

## Вопрос к модели решений

Условие может спросить **Decision model** (модель решений) о происходящем в чате. Это модель, выбранная в **Decision model** панели Connections: уже работающая локальная модель, удаленное подключение Decision или установленная модель решений. Она читает несколько последних сообщений и ваше утверждение, затем определяет, верно ли оно. В чат ничего не пишет. [Модели решений](../connections/decision-models.md) объясняют эту функцию и выбор модели.

Так пресет, карточка, запись лорбука или промпт агента отправляют инструкцию лишь тогда, когда она применима, вместо повторения "если X, сделай Y" каждый раз. Чтобы управлять активацией целой записи лорбука, а не сокращать ее текст, используйте поле [Decision](../lorebooks/entries.md#decision-activation) записи. Несколько идей:

- **Смена сцены.** Описывайте новое место или скачок времени, только если сцена действительно переместилась.
- **Типы сцен.** Загружайте правила темпа боя, близости или напряжения лишь во время такой сцены.
- **Сначала ответ на вопрос.** `{{#if decision:"In the latest message, {{user}} asks a direct question"}}Answer it before anything else.{{/if}}`
- **Настроения карточки.** Поведение "при смущении" или "при злости" в карточке появляется, только если это показывают последние сообщения.
- **Ограничение темпа.** Пресет медленного сближения может удерживать инструкции эскалации, пока отношения явно не продвинулись.
- **Групповые сцены.** В групповом блоке `{{#if decision:"{{char}} is addressed in the latest message"}}` просит отвечать напрямую лишь секцию персонажа, к которому обратились.

### Да или нет: `decision:`

```
{{#if decision:"The latest message moves the scene to a new place"}}
Open your reply by describing the new location in one or two sentences.
{{/if}}
```

Условие истинно, когда модель решений считает утверждение истинным. Оно совместимо со всем в этом руководстве: `{{else}}`, `{{else if}}`, `&&`, `||`, скобками, вложенностью и групповыми блоками.

```
{{#if char == "Dottore" && decision:"In the latest message, {{user}} says something that contradicts what they said earlier"}}
Dottore notices the inconsistency and files it away.
{{/if}}
```

Макросы утверждения подставляются заранее, поэтому `{{user}}` и `{{char}}` работают. В групповом блоке утверждение с `{{char}}` запрашивается отдельно для каждого персонажа.

### Один из нескольких ответов: `decision_choice:`

`decision_choice:` просит модель выбрать один вариант. Вариантами служат значения, с которыми вы сравниваете результат в любом месте промпта:

```
{{#if decision_choice:"Kaelen's mood in the latest message" == "angry"}}
Kaelen's lines are short and clipped.
{{else if decision_choice:"Kaelen's mood in the latest message" == "sad"}}
Kaelen speaks quietly and looks away.
{{else}}
Kaelen is his usual self.
{{/if}}
```

Здесь модель выбирает между "angry", "sad" и "none of these". Работает и сокращение: `decision_choice:"The weather in the latest message" == "rain" || "snow"` предлагает оба варианта. Пишите утверждение как тему, например "Kaelen's mood in the latest message", а варианты – как короткие ответы.

<a id="sticky-and-cooldown"></a>

### Sticky и cooldown

Утверждение может сохранять ответ на несколько последующих сообщений вместо повторной проверки каждый раз. Добавьте `sticky:` и `cooldown:` после утверждения:

```
{{#if decision:"The latest message starts a fight" sticky:3 cooldown:5}}
Keep combat pacing rules in effect.
{{/if}}
```

- **sticky:N.** После да утверждение остается истинным следующие N сообщений без проверки, сохраняя зависимый текст в промпте.
- **cooldown:N.** Начинается после sticky или сразу после да, если sticky нет. Следующие N сообщений утверждение означает нет и не запрашивается. Затем проверяется снова.
- Один отсчет – каждое новое сообщение, которое читает модель решений. Регенерация или свайп того же сообщения остаются тем же отсчетом, поэтому повтор ответа не сокращает таймер.
- Пока sticky или cooldown удерживает утверждение, оно не запрашивается и не учитывается в **Decision statements per turn** (утверждения решений за один ответ), оставляя место другому.
- Для `decision_choice:` sticky сохраняет выбранный вариант, а cooldown делает все сравнения ложными. Выбор ни одного варианта ничего не запускает.
- Утверждение в нескольких местах использует самые длинные sticky и cooldown из всех указанных.
- Peek Prompt показывает удерживаемый ответ и никогда не продвигает таймер.

Вместе они подходят для того, что должно появиться один раз и затем отдохнуть: перехода сцены, однократного напоминания или настроения на несколько сообщений. Для записи лорбука с активацией через **Decision** (решение) используйте собственные **Sticky** (удержание) и **Cooldown** (пауза) записи: sticky сохраняет запись без повторного вопроса, а запись на cooldown не проверяется.

<a id="checking-every-few-turns"></a>

### Проверка через несколько сообщений

Некоторые утверждения не нужно проверять каждый раз. Добавьте `every:` после утверждения, чтобы проверять его только через каждые N сообщений:

```
{{#if decision:"The weather changes in the latest message" every:3}}
Describe the new weather in a sentence.
{{/if}}
```

- Первый запрос выполняется при первом достижении утверждения, следующий – через 3 сообщения, и так далее.
- Изменение числа действует сразу: следующая проверка отсчитывается от последнего запроса.
- Между проверками результат означает нет, запрос не выполняется и не учитывается в **Decision statements per turn**.
- Отсчет такой же, как у sticky и cooldown: регенерация или свайп не продвигает расписание. Повторное использование ответа подчиняется [правилам кеша ответов](#answer-reuse).
- Sticky и cooldown по-прежнему удерживают ответ; `every:` лишь выбирает время проверки утверждения, которое они не удерживают.
- Утверждение в нескольких местах использует наименьшее `every:` из всех указанных.

<a id="priority"></a>

### Приоритет

Если в плане промпта больше утверждений, чем допускает **Decision statements per turn**, `priority:` определяет, какие спросить. Лимит применяется на [нескольких этапах](#statement-allowance):

```
{{#if decision:"In the latest message, a character is badly hurt" priority:high}}...{{/if}}
{{#if decision:"The latest message mentions food" priority:low}}...{{/if}}
```

- Сначала запрашиваются `priority:high`, последними – `priority:low`. Без приоритета используется средний.
- При равном приоритете решает порядок появления в промпте.
- За лимитом первыми исключаются утверждения с наименьшим приоритетом: они означают нет, и Peek Prompt их перечисляет.
- Утверждение в нескольких местах использует наивысший из заданных приоритетов.
- Сначала планируются собственные утверждения промпта: пресет, карточки, персона, заметки автора. Утверждения в тексте лорбуков планируются после определения активных записей на оставшиеся места. Поэтому они никогда не отнимают место у промпта независимо от приоритета.

Все модификаторы можно сочетать в любом порядке: `decision:"..." priority:high sticky:3 cooldown:5 every:2`.

### Нет ответа означает нет

Условие решения **ложно** при любом отсутствии ответа: модель не выбрана, не успела или завершилась с ошибкой. Для `decision_choice:` ложны все сравнения. Поэтому пользователь без модели решений получает ветку `{{else}}` или ничего.

Учитывайте это при написании:

- Используйте решение, чтобы **добавлять или сокращать указания**, а не передавать необходимое истории содержимое. Пропуск ветки должен чуть снизить точность ответа, а не сломать его.
- Дайте каждому блоку разумный вариант по умолчанию: ничего либо `{{else}}`, подходящий всегда.
- Не связывайте решения так, чтобы одна ошибка меняла несколько других.
- Не ставьте согласие, предупреждения о содержимом или инструкции безопасности в зависимость от решения. Сохраняйте их всегда.

Любая модель может ошибаться. Пишите для "модели решений", а не "требуется Jev": локальная модель чата тоже оценивает эти утверждения. Синтаксис общий, но ответы и точность могут различаться.

<a id="writing-statements"></a>

### Как писать утверждения

Эти советы получены из тестов локальной модели чата и Open-Jev 2B и 9B:

- **Сообщайте истинный или ложный факт**, как строку отчета. Не вопрос ("Did the scene change?") и не инструкцию ("If the scene changed, describe it"). Локальная модель всегда отвечала нет на инструкцию, поэтому блок никогда не выполнялся.
- **Пишите "in the latest message"**, если имеете в виду текущий момент. Модель читает несколько сообщений и ответила да на "Mira asks questions", потому что вопрос был раньше.
- **Назовите персонажа.** "He is angry" было понято как другой персонаж.
- **Опишите видимое в тексте**, действие или сказанное, а не настроение для интерпретации ("The scene is intense") или скрытое намерение ("Mira is lying").
- Пишите кратко. Обычное "and" и отрицание работали в тестах, поэтому выбирайте естественную формулировку.

Как проверить формулировку:

1. Выберите **Decision model** и нажмите **Test** (проверить). Это проверяет подключение на фиксированном примере, не ваше утверждение и не текущий чат.
2. Добавьте утверждение в промпт и отправьте характерные сообщения: часть с ожидаемым да, часть с ожидаемым нет.
3. В **Peek Prompt** (просмотр промпта) проверьте отправленную ветку. Для вероятности и результата да/нет включите [отладочный журнал](../CONFIGURATION.md#logging-levels).
4. Измените формулировку и повторите проверку. Для нового случая используйте новые сообщения или измените утверждение: успешные ответы могут [использоваться повторно](#answer-reuse). Новый предварительный просмотр Peek Prompt не спрашивает модель.

Что показали тесты. Каждую формулировку проверили на четырех размеченных ситуациях roleplay (две с ожидаемым да и две с нет) в Open-Jev 2B, Open-Jev 9B и локальной Gemma 4 E4B. Это небольшая выборка одной сцены, не общий тест точности и не проверка удаленной Jev. Таблица фиксирует наблюдения выборки и не обещает тот же результат для другой модели или чата.

| Пишите | Избегайте | Что произошло с нежелательной формулировкой |
| --- | --- | --- |
| The latest message moves the scene to a new place. | Did the scene change?  Вопрос поднял случаи "нет" Open-Jev 2B выше порога. Локальная модель не изменилась. |
| In the latest message, a character draws a weapon or attacks someone. | The scene is intense.  Все три назвали жаркий спор "intense". Значение расплывчатого слова определяет модель, не вы. |
| In the latest message, Mira asks Kaelen a direct question. | Mira asks questions.  Локальная модель и Open-Jev 9B ответили да без вопроса в последнем сообщении Mira, потому что вопрос был раньше. |
| Kaelen is angry in the latest message. | He is angry.  Локальная модель поняла "he" как злого трактирщика. |

| The latest message moves the scene to a new place. | If the scene changed, describe the new location in two sentences.  Локальная модель всегда отвечала нет на инструкцию, и блок не выполнялся. |

<a id="limits-and-cost"></a>

### Ограничения и стоимость

<a id="statement-allowance"></a>

#### Лимит утверждений

**Decision statements per turn** в **Decision model** по умолчанию равен 32. Несмотря на название, это не единый глобальный предел всех запросов Decision или расходов. Marinara применяет его поэтапно:

1. Утверждения основного промпта планируются в пределах лимита. Решения лорбука используют оставшееся после этого плана.
2. Для агентов до ответа или параллельно ему Marinara создает общий план утверждений основного промпта и промптов этих агентов, снова применяя настроенный лимит. Предыдущее использование лорбуком не вычитается, поэтому сумма может превысить настройку.
3. Агенты постобработки получают отдельный лимит после ответа. Их утверждения читают завершенный ответ.

**Вопросы активации** агентов и **Smart response order** (умный порядок ответов) не входят в эту настройку.

В план входят лишь доступные текущему этапу утверждения: включенные секции и группы пресета, выбранные варианты переменных, содержимое активированных записей лорбука. Фиксированное условие может исключить утверждение: `{{#if char == "Dottore" && decision:"..."}}` не спрашивается, когда персонаж Mira. Переменные могут меняться при сборке промпта, поэтому условие переменной не исключает утверждение заранее.

Утверждение, удерживаемое [sticky, cooldown](#sticky-and-cooldown) или [`every:`](#checking-every-few-turns), не занимает места. [Приоритет](#priority) выбирает утверждения в плане промпта. Активация лорбука расходует остаток лимита по мере рассмотрения записей. Не вошедшие утверждения означают нет и перечисляются в Peek Prompt.

#### Запросы и время

За один ответ может выполняться несколько платных запросов удаленного подключения Decision. Утверждения группируются, но активация лорбука, текст новых активных записей, рекурсивные совпадения и фазы агентов могут требовать новых групп. Вопросы активации группируются по Scan Depth и фазе; Smart order выполняет свой запрос. Лимит утверждений не ограничивает число запросов или сумму.

Локальная модель чата добавляет время обработки вместо платы удаленному провайдеру. На `decision_choice:` она отвечает отдельным вопросом да/нет для каждого варианта, поэтому один выбор может требовать нескольких генераций.

У каждого запроса есть [лимит времени](../connections/decision-models.md#time-limits): по умолчанию 1,5 секунды для подключения Decision или лимит локального backend. Несколько запросов суммируются в более долгое ожидание. Локальная модель с обязательным рассуждением воздерживается до ответа, если не включить **Also gate agents that run before the reply** (проверять также агентов до ответа).

<a id="answer-reuse"></a>

#### Повторное использование ответов

Успешные ответы обычно используются повторно для того же сообщения и модели решений, поэтому регенерация часто отправляет те же ветки без нового запроса. Кеш находится в работающем сервере и хранит до 200 ключей сообщений. Перезапуск или вытеснение из кеша может вызвать новый запрос. Новое или измененное последнее сообщение, другая модель, измененное утверждение или набор вариантов выбора тоже могут потребовать нового ответа.

Отсутствующие или неудачные ответы не кешируются как успешное нет: повторная попытка для того же сообщения может спросить снова и выбрать другую ветку. Таймеры sticky/cooldown независимы от кеша ответов.

Утверждения промптов агентов используют те же правила. Ранние/параллельные агенты читают состояние до ответа, агенты постобработки – готовый ответ, поэтому измененный свайп может потребовать новых ответов. Ручной перезапуск агента использует успешные ответы, еще сохраненные для его входных данных. См. [Утверждения решений в промпте агента](../agents/custom-agents.md#decision-statements-in-the-agents-prompt).

<a id="prompt-caching"></a>

#### Кеширование промпта

**Кеш промпта** провайдера независим от кеша ответов Decision в Marinara. Он повторно использует неизменный префикс промпта модели чата. Смена ветки решения может запретить повторное использование начиная с этого места; более ранний неизменный префикс может сохраниться. Точная часть и стоимость зависят от провайдера, границ кеша, минимальной длины и срока жизни.

**Размещайте изменяемые блоки решений ближе к концу промпта**, например в инструкциях после истории или неглубокой заметке автора. Раннее изменение может лишить большей части экономии. Оставляйте решение в начале лишь при редких изменениях ответа и подходящих там инструкциях. Это касается и вариантов переменных пресета: их текст попадает туда, где стоит `{{name}}`.

При прямом подключении Anthropic с включенным **Enable prompt caching** (включить кеширование промпта) Marinara отмечает конец системного промпта и сообщение на **Cache depth** (глубина кеша) сообщений раньше последнего, по умолчанию 5. Изменение до истории может сделать недействительной системную границу и последующую историю, хотя более ранний совпадающий префикс еще пригоден. Изменение после отмеченной границы истории может сохранить этот кешированный префикс. Изменение между границами может сохранить системный префикс, потеряв часть кешированной истории. Чтение и запись кеша стоят по-разному.

Минимальная длина и поддерживаемые границы зависят от модели и могут меняться. Подробности и оплату проверяйте в актуальном [руководстве Anthropic по кешированию](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) или [руководстве OpenAI по кешированию](https://developers.openai.com/api/docs/guides/prompt-caching).

<a id="when-a-decision-branch-never-appears"></a>

### Если ветка решения никогда не появляется

Если пользователь сообщает, что ветка решения никогда не появляется, вероятные причины по порядку:

1. **Модель решений не выбрана.** Все условия решений всегда ложны. Редактор показывает предупреждение под использующим их полем.
2. **Модель решений не отвечает.** У удаленного подключения неверный ключ, нет средств или действует ограничение; локальная модель остановлена или слишком медленная; установленная модель решений не запустилась.
3. **Это рассуждающая модель**, которая воздерживается до ответа.
4. **Слишком много утверждений на соответствующем этапе планирования**, сверх его лимита.
5. **Ответ есть, но ниже порога.** Обычно причина в формулировке или в более низкой оценке модели, чем вы ожидали.

Спросите пользователя, какую модель решений он выбрал и что сообщает **Test**. **Peek Prompt** показывает реально отправленные ветки. Если нужен новый предварительный просмотр, он перечисляет утверждения без ответа, которые там означают нет. При уровне журнала debug записываются утверждение, ответ и то, был ли он прочитан как да; см. [Уровни журнала](../CONFIGURATION.md#logging-levels).

Причина редко в пресете. Если дело в нем, обычно виновата формулировка или ветка с необходимым промпту содержимым.
