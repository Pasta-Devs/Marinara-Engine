# Удаленный доступ: вход и список разрешенных адресов

В этом руководстве вы узнаете, как открыть Marinara Engine с другого устройства – с телефона, ноутбука или из контейнера Docker. Здесь разобран основной вариант – вход. Дальше идут список разрешенных адресов, прокси со входом, HTTPS, раздел Admin Access и сообщение о заблокированном сохранении (CSRF). Почти все настройки из этого руководства живут в файле `.env` на сервере, а не в приложении.

Небольшой словарь, который понадобится по ходу чтения:

- Файл `.env`: обычный текстовый файл с настройками в папке Marinara Engine, рядом с `package.json`.
- Loopback: сама машина, на которой запущен сервер. Ее адрес – `127.0.0.1` или `localhost`.
- Удаленный доступ: открытие приложения Marinara с любого устройства, кроме машины с сервером.

## Что Marinara блокирует по умолчанию

Чтобы защитить данные, свежая установка Marinara отклоняет подключения с других устройств, пока не настроен контроль доступа. По умолчанию доверие есть только к трем видам клиентов:

1. Loopback (`127.0.0.1` или `::1`) – сама машина, на которой работает сервер. Посетители, которых передает дальше обратный прокси или туннель на той же машине, сюда не относятся; см. раздел [Обратные прокси и туннели на том же компьютере](#reverse-proxies-and-tunnels-on-the-same-computer).
2. Устройства Tailscale в вашей сети tailnet. Tailscale – это программа для частной сети, и ее адреса лежат в диапазоне `100.64.0.0/10`.
3. Клиенты Docker на том же хосте. Marinara распознает обычный диапазон моста `172.16.0.0/12` и точный шлюз контейнера по умолчанию, а это покрывает и Docker Desktop, и собственные пулы адресов.

Все остальное – телефон в той же сети Wi-Fi или клиент из интернета – блокируется, пока не выбран один из вариантов ниже. Заблокированное устройство, открывшее Marinara в браузере, видит темную страницу настройки. Ее заголовок читается **This Marinara Engine install needs a login before remote devices can connect.** На странице есть форма для одноразового кода настройки из журнала сервера, поэтому вход можно задать прямо с этого устройства.

Если ничего не делать и пароль так и не задать, Marinara останется закрытой для всех, кроме этих трех доверенных источников. Это безопасное поведение по умолчанию.

## Где лежит файл .env

Все настройки доступа находятся в файле `.env` в корне проекта, рядом с `package.json`. Если такого файла еще нет, скопируйте пример:

```bash
cp .env.example .env
```

Откройте `.env` в любом текстовом редакторе. Большинство настроек доступа – Basic Auth, список разрешенных адресов, секрет администратора и доверенные источники CSRF – применяются за пару секунд без перезапуска. Перезапуск все же нужен нескольким низкоуровневым настройкам: `PORT`, `HOST` и путям к сертификату HTTPS.

Бывает, что другие устройства вообще не достают до сервера: вместо ошибки 403 они получают тайм-аут. Скорее всего, сервер слушает только локальную машину. Разрешите ему слушать все сетевые интерфейсы:

```env
HOST=0.0.0.0
```

Скрипты запуска (`start.bat`, `start.sh`) выставляют `HOST=0.0.0.0` сами. При прямом запуске `pnpm start` этого не происходит.

Адрес привязки по умолчанию в зависимости от способа запуска Marinara:

| Способ запуска | Значение `HOST` по умолчанию |
| --- | --- |
| `pnpm start`, `start-local.bat` | `127.0.0.1` |
| `start.sh`, `start.bat`, установщик Windows, `start-termux.sh` | `0.0.0.0` |
| Образ Docker | `0.0.0.0` внутри контейнера |
| `docker-compose.yml` | Публикует порт только на `127.0.0.1` |

## Какой вариант выбрать

Читайте по порядку и остановитесь на первом подходящем пункте.

1. Вы подключаетесь только через Tailscale или только из контейнеров Docker на том же хосте. Делать ничего не нужно, все уже работает.
2. Вы хотите открывать Marinara с телефона, планшета или ноутбука в домашней сети Wi-Fi. Задайте вход (вариант 1 ниже).
3. Вы открываете Marinara в интернет. Задайте вход и используйте HTTPS.
4. Прокси со входом в вашей сети, например tinyauth, Authelia или Authentik, уже просит каждого посетителя войти. Прочитайте раздел [Прокси со входом (forward auth)](#login-proxies-forward-auth).

Вход – самый гибкий вариант. Он работает с любого адреса, не требует настройки на каждом устройстве, а каждый браузер остается в системе.

<a id="option-1-login-recommended"></a>

## Вариант 1: вход (рекомендуется)

Вход – это имя пользователя и пароль, которые нужны каждому удаленному устройству. Задать его можно тремя способами:

- **В Settings.** В браузере, где вы уже вошли, или на компьютере, на котором работает Marinara (откройте `http://localhost:7860`), перейдите в **Settings → Advanced → Access**. Задайте имя пользователя и пароль в разделе **Remote login**. Пока входа нет, устройство, которое Marinara отклоняет, например браузер на хосте Docker, может ввести код настройки из журнала сервера на этой же странице.
- **С кодом настройки, с любого устройства.** Пока вход не задан и сервер слушает не только loopback, он печатает в своем журнале одноразовый код настройки. Строка журнала начинается с `[login] One-time setup code:`. Найдите ее в терминале, где работает Marinara. В Docker выполните `docker logs <container> 2>&1 | grep "setup code"`. Предупреждение об отказе в журнале повторяет код, пока входа нет. Затем откройте Marinara на любом устройстве. На странице, которая блокирует устройство, есть форма для кода настройки, имени пользователя и пароля. Код выглядит как `XXXX-XXXX-XXXX-XXXX`. Заглавные буквы, пробелы и дефисы не важны. Каждый код работает один раз; перезапуск или сброс печатает новый. В Docker страница также показывает, как задать вход в файле `.env` в папке данных (`/app/data/.env`) или в списке `environment:` вашего файла compose (затем выполните `docker compose up -d`). Так удобно в установках Docker и NAS без браузера на хосте. Marinara показывает баннер об отсутствующем входе локальным посетителям и выполненным входам в виде карточки внизу экрана.
- **В `.env`.** Добавьте две строки:

```env
BASIC_AUTH_USER=alice
BASIC_AUTH_PASS=correct-horse-battery-staple
```

Вход в `.env` главнее входа, заданного в приложении, и менять его можно только в `.env`. Сохраните `.env`; изменение применяется за пару секунд, перезапуск не нужен.

Придумайте надежный и неповторяющийся пароль. Приложение требует не меньше 10 символов. Случайный пароль можно сгенерировать:

```bash
openssl rand -base64 24
```

Затем выполните эти шаги на удаленном устройстве.

1. Откройте Marinara в браузере по адресу сервера, например `http://192.168.1.50:7860`.
2. Войдите на странице входа со своими именем пользователя и паролем.
3. Приложение должно загрузиться. Браузер остается в системе до года, пока вы не выйдете. Скрипты и клиенты API отправляют имя пользователя и пароль с каждым запросом (Basic Auth).

Чтобы войти на другом устройстве, не вводя пароль, используйте код сопряжения. На устройстве, где вход уже выполнен, откройте **Settings → Advanced → Access** и выберите **Add a device**. Затем введите код на странице входа нового устройства. Код работает один раз, в течение нескольких минут. Просроченный код получает собственное сообщение; создайте новый. В разделе **Signed-in devices** видно каждое устройство со способом входа и датой первого входа. Выйти можно на любом устройстве, в том числе на том, которым вы пользуетесь. Пароль тоже можно изменить или убрать. Для этого Marinara запрашивает текущий пароль, если только вы не работаете на компьютере, где запущена Marinara, или не задали `ADMIN_SECRET`.

Если вы забыли пароль, выполните `pnpm reset-login` на компьютере, где запущена Marinara. В Docker выполните `docker exec <container> node scripts/reset-login.mjs`. Команда удаляет вход, заданный в приложении, и выводит из системы все браузеры. Если сервер слушает не только loopback, он затем печатает новый код настройки. Только если эта команда не помогает, удалите вместо нее `.remote-login.json` и `.remote-sessions.json` из папки данных. При `/app/data` по умолчанию выполните `docker exec <container> rm -f /app/data/.remote-login.json /app/data/.remote-sessions.json`; если вы изменили `DATA_DIR`, используйте эту папку. Вход в `.env` вы меняете в `.env`.

**Сервер без монитора и без браузера?** Обычная установка на сервере без монитора слушает только loopback и не печатает код настройки. На своем компьютере выполните `ssh -L 7860:127.0.0.1:7860 user@server`. Затем откройте там `http://localhost:7860` и используйте **Settings**.

После 10 разных неверных паролей или кодов в течение 15 минут Marinara отклоняет попытки входа с этого адреса ответом **429 Too Many Requests**, пока эти 15 минут не истекут. Верный пароль, введенный раньше, сбрасывает счетчик. У посетителей, которых передает дальше обратный прокси или туннель на хосте, счетчик общий, и вход одного из них его не сбрасывает. Перезапуск сервера тоже сбрасывает счетчик. Браузер, который уже входил раньше, по-прежнему пускают с верным паролем, поэтому чужие неверные пароли не могут закрыть вам вход с устройства, которым вы уже пользуетесь. Страница входа показывает, сколько минут ждать. Если вы забыли пароль, на странице входа есть подсказка **Forgot the password?**.

По умолчанию браузер в запросе показывает надпись **Marinara Engine**. Этот текст меняется переменной `BASIC_AUTH_REALM`.

Некоторые клиенты проходят без пароля, даже когда Basic Auth включен:

- Loopback (`127.0.0.1`, `::1`) – на самой машине с сервером пароль не нужен никогда. Посетителям, которых передает дальше обратный прокси или туннель на этой машине, он все равно нужен.
- Любой адрес из `IP_ALLOWLIST`. Осторожно: заданный список заодно блокирует все адреса, которых в нем нет (см. вариант 2).
- Прямой трафик Tailscale (`100.64.0.0/10`) – если не выключить обход для него.
- Трафик моста и шлюза Docker – только пока не заданы ни вход, ни список разрешенных адресов, ни `TRUSTED_AUTH_PROXY` (см. раздел [Обход для Tailscale и Docker](#tailscale-and-docker-bypass)).
- Адрес `/api/health`, чтобы продолжали работать системы мониторинга. Посетитель, который не может открыть приложение, получает только `{"status": "ok"}`; сведения о версии, системе и моделях остаются на этом компьютере, в доверенных сетях и в браузерах с выполненным входом.

Важно: Basic Auth только кодирует пароль, но не шифрует его. Любой, кто слушает незашифрованное соединение, сможет его прочитать. Если Marinara открыта в интернет, используйте Basic Auth вместе с HTTPS (см. ниже).

## Вариант 2: список разрешенных адресов

Список разрешенных адресов пускает определенные адреса без пароля. Это удобно, когда у ваших устройств постоянные IP-адреса. Задайте адреса или диапазоны через запятую:

```env
IP_ALLOWLIST=192.168.1.0/24,203.0.113.42
```

Запись `/24` в примере – это нотация CIDR. CIDR – короткий способ записать целый диапазон адресов одной строкой. Например, `192.168.1.0/24` покрывает все адреса от `192.168.1.0` до `192.168.1.255`. Адрес без слеша, вроде `203.0.113.42`, соответствует только одному устройству.

Как ведет себя список разрешенных адресов:

- Любой адрес, которого нет в списке, получает отказ **403 Forbidden**.
- Loopback разрешен всегда, поэтому локальный доступ вы себе не закроете. Посетители, которых передает дальше обратный прокси или туннель на той же машине, не считаются loopback, поэтому список разрешенных адресов их блокирует. За прокси используйте Basic Auth.
- В Docker Desktop, OrbStack и rootless Docker все устройства попадают в контейнер с одного и того же адреса шлюза, поэтому список разрешенных адресов не может их различить. Там используйте Basic Auth.
- Прямой трафик Tailscale тоже проходит мимо списка, если не выключить обход для него. Трафик моста и шлюза Docker проходит мимо списка, только пока не заданы ни вход, ни список разрешенных адресов, ни действующий `TRUSTED_AUTH_PROXY` (см. раздел [Обход для Tailscale и Docker](#tailscale-and-docker-bypass)).
- Неверные записи игнорируются и попадают в журнал сервера. Сервер из-за них не падает.
- Список остается строгим и при включенном Basic Auth. Перечисленные адреса проходят без пароля. Все остальные по-прежнему блокируются с ответом **403 Forbidden** и запроса пароля даже не видят.

Смешанную схему – когда адреса из списка проходят без пароля, а все прочие входят по паролю – список создать не может. Если вы хотите, чтобы другие устройства входили по паролю, оставьте `IP_ALLOWLIST` незаданной и обойдитесь одним Basic Auth.

Проверку можно на время отключить, не удаляя сам список. Это выручает, когда вы разбираетесь с доступом с нового IP-адреса. Переведите флаг включения в false:

```env
IP_ALLOWLIST_ENABLED=false
```

## Обход для частной сети (справка)

Несколько флагов снимают блокировку для доверенной частной сети. Они нужны для особых случаев. Вход – лучший выбор. О флагах и их рисках читайте в разделе [Управление доступом](CONFIGURATION.md#access-control).

<a id="tailscale-and-docker-bypass"></a>

## Обход для Tailscale и Docker

По умолчанию Marinara доверяет устройству, которое подключается напрямую через вашу сеть Tailscale. Она также доверяет собственному хосту контейнера Docker. Вход, список разрешенных адресов или `TRUSTED_AUTH_PROXY` отключает автоматическое доверие к Docker, поэтому каждому устройству тогда нужны вход или место в списке. О флагах, которые это меняют, читайте в разделе [Управление доступом](CONFIGURATION.md#access-control).

<a id="reverse-proxies-and-tunnels-on-the-same-computer"></a>

## Обратные прокси и туннели на том же компьютере

Обратный прокси или туннель на машине, где работает Marinara, – например nginx, Caddy, Traefik, Cloudflare Tunnel, Tailscale Serve или Funnel либо ngrok – подключается к Marinara через loopback. Marinara распознает это по заголовкам пересылки, которые добавляет прокси: `Forwarded`, `X-Forwarded-For`, `X-Real-IP`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `CF-Connecting-IP`, `True-Client-IP`, заголовкам идентификации Tailscale или `Via`. Marinara также распознает запрос, который приходит по HTTP/1.0, потому что браузеры его не используют, а nginx по умолчанию использует его в `proxy_pass`. Marinara также распознает запрос, в котором Host указывает на другой компьютер, например на домен или адрес в локальной сети, даже если прокси не добавляет никаких заголовков. После этого каждый такой запрос обрабатывается как запрос удаленного посетителя, которым он и является:

- Действует вход (см. [Вариант 1](#option-1-login-recommended)). Без него посетители видят страницу настройки. Задайте вход в **Settings** на этом компьютере или в `.env`.
- `IP_ALLOWLIST` блокирует пересланных посетителей, потому что прокси скрывает их настоящие адреса.
- Для опасных действий нужен секрет администратора, а функции, доступные только через loopback, остаются недоступными.

Ваш собственный браузер на этой машине, открытый по адресу `http://127.0.0.1:7860` или `http://localhost:7860`, по-прежнему работает без пароля.

Caddy, Traefik, Cloudflare Tunnel, Tailscale и ngrok добавляют заголовки пересылки по умолчанию. Для nginx эту строку в блок `location` по-прежнему рекомендуется добавить:

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

Инструменты, которые пересылают соединения как есть, например `socat` или `ssh -R`, не добавляют заголовков, поэтому их трафик выглядит локальным. Не используйте их, чтобы открыть доступ к Marinara.

Если ваш прокси уже заставляет каждого посетителя войти, прежде чем что-либо пересылать, см. раздел [Прокси со входом (forward auth)](#login-proxies-forward-auth).

## Прокси со входом (forward auth)

Прокси forward auth, например [tinyauth](https://tinyauth.app), [Authelia](https://www.authelia.com), [Authentik](https://goauthentik.io) или oauth2-proxy, просит каждого посетителя войти, прежде чем пересылать запрос. Если такой прокси – единственный путь к Marinara, второй вход в Marinara можно пропустить. Не задавайте это без такого прокси. Укажите адрес прокси в `.env`:

```env
TRUSTED_AUTH_PROXY=192.168.1.5
```

Тогда Marinara впускает каждый запрос, соединение которого приходит с этого адреса. Marinara не просит для них собственный вход и не печатает код настройки. Marinara проверяет адрес самого соединения. Заголовки пересылки, например `X-Forwarded-For`, для этого решения она игнорирует. Запросы от прокси также проходят `IP_ALLOWLIST`, потому что прокси решает, кого впускать. Они не считаются локальными, поэтому для привилегированных действий по-прежнему нужен секрет администратора. **Settings → Advanced → Access** показывает **Trusted login proxy: Set**, пока настройка действует.

Прежде чем ее задать:

- **Прокси должен требовать вход на каждом пути.** Это включает `/api/`, соединения WebSocket и статические файлы. Путь, который прокси пропускает без входа, открыт для всех.
- **Marinara не должна быть доступна в обход прокси.** Привяжите Marinara к адресу, который доступен только прокси, или закройте ее порт брандмауэром. В Docker поместите прокси и Marinara в одну сеть Docker, дайте прокси фиксированный адрес в ней и не публикуйте порт Marinara. Если прокси работает на хосте Docker, публикуйте порт только на loopback (`127.0.0.1:7860:7860`): Docker Desktop и OrbStack показывают каждого клиента LAN опубликованного порта с адреса шлюза Docker, то есть с того же адреса, что и прокси. Если другое устройство может подключиться к Marinara напрямую, оно пропускает вход прокси.
- **Укажите только собственный адрес прокси.** Диапазон должен оставаться в пространстве частных адресов; Marinara игнорирует другие диапазоны. Для каждого такого диапазона она пишет в журнал предупреждение, потому что каждое устройство в диапазоне пропускает вход.
- **Добавьте публичное имя, как для любого другого прокси.** Внесите имя хоста в `TRUSTED_HOSTS`, а источник – в `CSRF_TRUSTED_ORIGINS` (см. [Почему сохранение блокируется (CSRF)](#why-is-my-save-blocked-csrf)).

Когда задан `TRUSTED_AUTH_PROXY`, Marinara также отключает автоматическое доверие к Docker. Прямым посетителям, которые не являются прокси, нужны вход Marinara или список разрешенных адресов. Тогда Marinara также не показывает баннер "входа еще нет".

Если прокси работает на том же компьютере, что и Marinara, задайте `TRUSTED_AUTH_PROXY=127.0.0.1` и направьте прокси на `127.0.0.1:7860`, а не на `localhost:7860`. Прокси, который обращается к `localhost`, может подключиться с `::1`, что не совпадает с `127.0.0.1`. Тогда любой другой прокси или туннель на этом компьютере тоже получает доверие, поэтому задавайте это, только когда прокси со входом – единственный. Это не дает посетителям, которых передает прокси, доступа к локальной машине.

Пример для Caddy, где Marinara работает по адресу `192.168.1.20:7860`:

```caddy
marinara.example.com {
  forward_auth tinyauth:3000 {
    uri /api/auth/caddy
  }
  reverse_proxy 192.168.1.20:7860
}
```

Для Authelia используйте `forward_auth authelia:9091` с `uri /api/authz/forward-auth`. Authentik также отдает собственные страницы входа через прокси. Поместите его строки в блок `route`, чтобы Caddy сохранил их порядок, а путь outpost не проходил через сам forward auth:

```caddy
marinara.example.com {
  route {
    reverse_proxy /outpost.goauthentik.io/* authentik-server:9000
    forward_auth authentik-server:9000 {
      uri /outpost.goauthentik.io/auth/caddy
    }
    reverse_proxy 192.168.1.20:7860
  }
}
```

Для Traefik и nginx следуйте руководству вашего прокси по forward auth. Marinara нужен только адрес прокси.

## Работа по HTTPS

HTTPS шифрует соединение с помощью TLS. TLS – это шифрование, которое превращает обычный адрес `http` в защищенный `https`. Всегда используйте HTTPS, если установка доступна за пределами полностью доверенной частной сети – особенно вместе с Basic Auth.

Добавить его можно двумя способами.

1. Встроенный TLS. Укажите серверу файлы сертификата и закрытого ключа:

```env
SSL_CERT=/path/to/cert.pem
SSL_KEY=/path/to/key.pem
```

2. Обратный прокси-сервер. Поставьте перед Marinara nginx, Caddy, Traefik или Cloudflare Tunnel. Прокси-сервер берет HTTPS на себя и пересылает запросы в Marinara по обычному HTTP на той же машине. Сначала прочитайте раздел [Обратные прокси и туннели на том же компьютере](#reverse-proxies-and-tunnels-on-the-same-computer).

Сертификат и ключ нужны до того, как вы зададите `SSL_CERT` и `SSL_KEY`. Для локального использования их создает, например, `mkcert`, а для публичного домена – `certbot`. Если файлов нет или их не удается прочитать, сервер останавливается при запуске и показывает точные пути, по которым он искал.

## Раздел Admin Access и опасные действия

Часть действий особенно чувствительна: удаление данных, создание и скачивание резервных копий, импорт и экспорт профилей, установка тем оформления и установка среды Local Model. Для них нужен отдельный общий секрет – секрет администратора – вдобавок к выбранному выше варианту доступа.

На машине с loopback такие действия обычно работают и без секрета администратора. С удаленного устройства секрет надо настроить. Выполните эти шаги.

1. В файле `.env` задайте надежное случайное значение и сохраните файл. Оно применяется за пару секунд, перезапуск не нужен.

```env
ADMIN_SECRET=some-long-random-string
```

2. На удаленном устройстве откройте Marinara и перейдите в панель **Settings** (настройки), затем на вкладку **Advanced**, затем в раздел **Admin Access** (доступ администратора).
3. Вставьте то же значение в поле (подсказка в поле читается **ADMIN_SECRET**) и нажмите кнопку **Save** (сохранить).
4. Должно появиться сообщение **Admin secret saved for this browser**.

Что стоит знать про секрет администратора:

- Он хранится только в этом одном браузере и между устройствами не синхронизируется. В каждом браузере, откуда нужны опасные действия, его придется вставить отдельно.
- Нажатие кнопки **Save** с пустым полем стирает секрет и показывает сообщение **Admin secret cleared**.
- Если тот, кто управляет сервером, задал `MARINARA_REQUIRE_ADMIN_SECRET_ON_LOOPBACK=true`, секрет понадобится даже на машине с loopback.
- Это не то же самое, что Basic Auth, и работать они могут вместе. Basic Auth закрывает все приложение, а секрет администратора – только опасные действия.

Если опасное действие на удаленном устройстве не срабатывает, Marinara показывает сообщение об ошибке с двумя способами исправления. Первый – открыть приложение через localhost. Второй – задать `ADMIN_SECRET` в файле `.env` на сервере, а затем вставить то же значение в **Settings** > **Advanced** > **Admin Access**.

<a id="why-is-my-save-blocked-csrf"></a>

## Почему сохранение блокируется (CSRF)

CSRF – это подделка межсайтового запроса. Так называется защита, которая не дает другому открытому в браузере сайту тихо менять что-то в Marinara без вашего разрешения. Она работает сама, включать ее не нужно.

Иногда CSRF блокирует и ваши собственные сохранения. Обычно это происходит, когда вы открываете Marinara по публичному доменному имени или на нестандартном порту, которому сервер пока не доверяет. Понять это можно по двум признакам.

- Красная полоса сверху приложения предупреждает, что **Saves will silently fail**, потому что этому источнику нет доверия. В полосе показана точная строка для `.env` и есть кнопка **Copy** (копировать).
- Если сохранение действительно отклонено, появляется небольшое всплывающее сообщение. Его заголовок – **Save blocked: missing CSRF header**, **Save blocked: cross-site request rejected** или **Save blocked: origin not trusted**.

Чтобы это исправить, добавьте свой адрес в список доверенных в `.env`:

```env
CSRF_TRUSTED_ORIGINS=https://chat.example.com,http://203.0.113.10:7831
```

Если вы работаете через публичный домен или обратный прокси-сервер, разрешите заодно и имя хоста:

```env
TRUSTED_HOSTS=chat.example.com
```

Прямым адресам в сети LAN, адресам Tailscale, IPv4 и IPv6 переменная `TRUSTED_HOSTS` не нужна. Локальные имена `.local` и `.home.arpa`, а также однословные имена машин принимаются автоматически. Точное имя хоста, уже перечисленное в `CSRF_TRUSTED_ORIGINS`, тоже принимается.

Источникам loopback, обычным адресам в сети LAN, адресам Tailscale (`100.64.0.0/10`) и моста Docker (`172.16.0.0/12`) доверие есть по умолчанию. Перечислять нужно только публичные IP-адреса и доменные имена. Изменение применяется за пару секунд, без перезапуска.

## Отдельно о заблокированных локальных провайдерах

Допустим, вы подключаете Marinara к локальному провайдеру ИИ – например, к тому, который работает на вашей же машине. Запрос может быть отклонен с упоминанием "private, loopback, metadata, or reserved IP range". Это уже другая проверка безопасности – защита SSRF. SSRF – это подделка запроса на стороне сервера. Такая проверка не дает серверу обращаться к частным адресам, пока вы это не разрешите. В тексте ошибки названа точная переменная для `.env`, например `PROVIDER_LOCAL_URLS_ENABLED`. Полный список смотрите в руководстве [Настройки сервера: справочник](CONFIGURATION.md).

## Доступ с телефона или планшета

Чтобы открыть Marinara с телефона или планшета в той же сети:

1. Проверьте, что сервер слушает все интерфейсы: в `.env` должно быть `HOST=0.0.0.0`.
2. Задайте вход (вариант 1 выше). С телефона это можно сделать на странице, которая вас блокирует, с кодом настройки из журнала сервера.
3. Узнайте локальный IP-адрес машины с сервером (например, `192.168.1.50`).
4. На телефоне откройте в браузере `http://192.168.1.50:7860`. Порт по умолчанию – `7860`.
5. Войдите со своими именем пользователя и паролем.

Если страница вообще не открывается, до сервера, скорее всего, не доходит запрос. Проверьте `HOST=0.0.0.0` и значение `PORT`. Если вместо этого приходит ошибка 403, устройство до сервера достает, но доступ ему еще не открыт. Перепроверьте выбранный вариант.

<a id="locked-out-after-updating"></a>

## Нет доступа после обновления

Новые версии просят войти, если визит приходит через обратный прокси, туннель, Tailscale Serve или Tailscale Funnel. Старые версии пускали такие визиты без пароля. Если теперь вы видите страницу входа, страницу настройки или **403**, причина в этом.

**Примечание об обновлении:** если вы используете Tailscale Serve или другой прокси на том же компьютере и никогда не задавали пароль, после обновления другие ваши устройства остаются без доступа. Прокси на том же компьютере обычно обращается к серверу, который слушает только loopback, поэтому сервер не печатает код настройки. Задайте вход на компьютере, где запущена Marinara.

Чтобы вернуться:

1. Откройте Marinara на компьютере, где она запущена, по адресу `http://localhost:7860` (или со своим `PORT`). Для локального доступа пароль не нужен. На сервере без монитора сначала выполните на своем компьютере `ssh -L 7860:127.0.0.1:7860 user@server`, затем откройте там `http://localhost:7860`. В Docker это работает, только пока не заданы ни вход, ни `IP_ALLOWLIST`. Иначе введите код настройки из журнала сервера (`docker logs <container> 2>&1 | grep "setup code"`) на странице, которая вас блокирует, или в **Settings → Advanced → Access**, либо воспользуйтесь браузером, в котором вход еще выполнен.
2. Перейдите в **Settings → Advanced → Access** и задайте имя пользователя и пароль в разделе **Remote login**. Или откройте файл `.env` на этом компьютере и задайте `BASIC_AUTH_USER` и `BASIC_AUTH_PASS`. Если задан `IP_ALLOWLIST`, добавьте в него адрес другого устройства или уберите его: устройство, которого нет в списке, получает **403** даже со входом.
3. Войдите с другого устройства с этим именем пользователя и паролем.

## Поисковые системы

Marinara просит поисковые системы не индексировать его страницы (`X-Robots-Tag: noindex, nofollow`). Это не защищает вашу установку и не удаляет страницы, которые уже проиндексированы. Чтобы установка оставалась закрытой, используйте описанные выше средства контроля доступа.
