# Основы движка: обзор серии

Эта страница описывает вклад в основы движка (issue #6624). Первоначальный большой pull request разделен на восемь PR, от A до H, для независимой проверки. Все они используют уже работающий код Marinara Engine. Существующие API не переименовываются, общий логгер не заменяется, соглашения файлов сохраняются. Изменения для всех явно отмечены; остальное выключено до включения пользователем.

D–H следуют за A: используют его реестр переключателей (`isFeatureEnabled`, Settings > Advanced > Features), контекст журналирования и помощники best-effort либо расширяют этапы запуска и диагностический маршрут. Каждый добавляет свои переключатели, записи CHANGELOG и раздел этой страницы.

Каждая часть A описывает текущее состояние, дополнения, неизменное поведение, проверку и отключение или откат.

По умолчанию изменения данных, промптов, повторов и запускаемых компонентов выключены, управляются переменной окружения или **Settings > Advanced > Features** (Настройки > Дополнительно > Функции, A6). Без включения поведение прежнее. Исправления, запуск тестов и дополнительные помощники не имеют переключателя; это указано отдельно.

Откат: коммиты A упорядочены и затрагивают общие файлы (`app.ts`, `index.ts`, `runtime-config.ts`, `capability-module-runtime.service.ts`, `CHANGELOG.md`). Откатывайте от нового к старому, чтобы избежать конфликтов.

Большинство проверок используют существующий запуск регрессий. Сначала один раз соберите общий пакет (`pnpm build:shared`), затем выполняйте команды из корня репозитория.

<a id="pr-a-foundations"></a>

# PR A: Основы

> **Перебазировано на обновление моделей Decision.** Вызовы Decision уже выполняются внутри нуждающегося в них запроса и несут его `requestId`. Процессы sidecar решений и утилит стартуют в корневом контексте журнала: последующие записи не сохраняют ID первого запроса. Неисправный слот Decision дает одно предупреждение с ограничением частоты, а не несколько за ход. Отмена пользователем записывается на info; отброшенные утверждения подсчитываются на warn, текст только на debug. Остановка обоих sidecar оформлена именованными этапами. Decision не проходит через обертку повторов провайдера, поэтому двойных повторов нет.

<a id="a1-test-harness-each-regression-file-runs-in-its-own-data-folder"></a>

## A1. Тестовая среда: отдельная папка данных для каждого файла регрессии

**Текущее состояние.** `scripts/run-regressions.mjs` находит регрессии и выполняет по одной через `runRegression()`, обрабатывая сроки и сигналы (`terminateActiveChild`, `releaseActiveChild`, `FILE_TIMEOUT_MS`). Каждый дочерний процесс получает весь `process.env` разработчика. Сервер уже позволяет перенаправить `.env` через `MARINARA_ENV_FILE` (`getEnvFilePath()` в `packages/server/src/config/runtime-config.ts`); `e2e/start-servers.mjs` уже изолирует серверы так.

**Дополнения.** Помощник `regressionEnvironment(scratchDir)`. `runRegression()` создает временную папку для каждого файла (`marinara-regression-*` в системной временной папке), размещая там `DATA_DIR`, `FILE_STORAGE_DIR` и `MARINARA_ENV_FILE` дочернего процесса. Она удаляется после успеха, ошибки, тайм-аута или невозможности запуска. Неизолированный тест больше не читает `.env` разработчика и не конфликтует с арендой записи реальных данных.

**Без изменений.** Функции, `--filter`/`--list`, сроки, сводка, скрипты `package.json` и CI. Тесты со своими переменными сохраняют значения. Видимое отличие: экспортированные в оболочке `DATA_DIR`, `FILE_STORAGE_DIR` и `MARINARA_ENV_FILE` заменяются для каждого файла. Это намеренно и касается только тестов.

**Как проверить.**

```sh
node scripts/run-regressions.mjs --filter env-watcher
```

Во временной папке после этого не должно остаться `marinara-regression-*`.

**Как отключить / откатить.** Переключателя нет, изоляция стандартная. Откат коммита запуска тестов возвращает прежний вариант; сначала откатите новые коммиты, общие только по `CHANGELOG.md` и `CONTRIBUTING.md`. Исключение вроде `MARINARA_REGRESSION_INHERIT_STORAGE=1` потребовало бы нескольких строк, но незапрошенную настройку не добавляли.

<a id="a2-logging-follow-one-request-one-boot-and-one-failure"></a>

## A2. Журналирование: один запрос, один запуск, одна ошибка

**Текущее состояние.** `packages/server/src/lib/logger.ts` экспортирует общий Pino `logger`. `protectTerminalLogger` защищает сервер от закрытого терминала, `logDebugOverride` обеспечивает отладку из интерфейса. Logging в `CONTRIBUTING.md` требует общего логгера, объекта ошибки первым, спецификаторов формата и четырех уровней; правила соблюдены. В `app.ts` функция `buildApp()` передавала Fastify собственные настройки, создавая второй Pino того же уровня. Счетчик `req-1`/`req-2` сбрасывался при запуске.

**Дополнения.** Подробности в `docs/development/logging.md`, теперь связанном с разделом Logging в `CONTRIBUTING.md`.

- Fastify использует общий логгер (`loggerInstance: logger`). `req.log` разделяет сериализаторы и следует горячим перезагрузкам `LOG_LEVEL` через `followLogLevel`, отписываемый при закрытии. Это соответствует `CONTRIBUTING.md`.
- Любая запись, вызванная запросом, содержит `requestId`, даже внутри служб (`lib/log-context.ts`, контекст `AsyncLocalStorage` и примесь Pino). UUID либо корректный клиентский `x-request-id` возвращается в заголовке `x-request-id` для отчетов.
- Каждая запись содержит `bootId`, различающий запуски в одном файле.
- Шкала запуска `lib/startup-timeline.ts`: этапы `app.ts`/`index.ts` обернуты в `startup.phase("name", fn)`. Строка info `[startup] Ready in N ms` перечисляет самые медленные; сбой запуска называет этап.
- Одна запись на сбой: провайдеры и инструменты пробрасывают ошибку без предварительного журналирования. Неудачная генерация дает один error. Пользовательская остановка – info через `failureLevel(err)`; цепочка `cause` сохраняется.
- Повторные ошибки проверок состояния, опросов планировщика и поставщиков контекста используют `logRateLimited` со счетчиком `suppressedRepeats`.
- Вывод моделей, запросы бросков костей, тела токенов Spotify и опросов видео переходят на debug; warn содержит только длину.
- Три регрессии: `logging-request-trail`, `logging-failure-lines`, `logging-startup-timeline`.

**Без изменений.** Экспорт и файл `logger`, `protectTerminalLogger`, `logDebugOverride`, поля `pid`/`hostname`, вызовы `logger.*`/`req.log`. `LogController` Fastify расширяется подклассом, не заменяется. `LOG_LEVEL` (по умолчанию `warn`) и `LOG_DISABLE_REQUEST_LOGGING` прежние. Консоль `pnpm dev` не показывает новых полей: pino-pretty скрывает `bootId` вместе с `hostname`. `CONTRIBUTING.md` лишь дополнен.

Изменения описаны в `logging.md`:

- `requestId` заменяет `reqId` Fastify; сохраненные фильтры `reqId` требуют нового имени.
- Входящие запросы и ненайденные маршруты больше не содержат строку параметров, способную раскрыть токен. Другие поля `req` остаются, добавлено `route`.
- Новая строка info `Client aborted request`, тоже отключаемая через `LOG_DISABLE_REQUEST_LOGGING`.
- Этап с собственным временем `selfMs`, без вложенных шагов, свыше 15 с дает warn, видимый по умолчанию. Вложенность (`app.build` охватывает `buildApp`) не меняет принцип: уровень зависит от собственного времени, один медленный шаг – одна строка.

**Как проверить.**

```sh
node scripts/run-regressions.mjs --filter logging-
```

Либо запустите сервер, отправьте запрос и найдите возвращенный `x-request-id` через `grep`.

**Как отключить / откатить.** `LOG_DISABLE_REQUEST_LOGGING=true` по-прежнему скрывает запросы; `LOG_LEVEL=warn` уже скрывает новые info. Для полного удаления откатите коммит журналирования после более новых коммитов кода.

<a id="a3-performance"></a>

## A3. Производительность

Обе опции выключены по умолчанию; промпты и данные тогда побайтово прежние. Описаны в `.env.example` и таблице Lorebooks в `docs/CONFIGURATION.md`.

<a id="a3a-stable-lorebook-group-winners-lorebook_stable_group_winners-switch-stablelorebookgrouppicks"></a>

### A3a. Стабильные победители групп лорбука (`LOREBOOK_STABLE_GROUP_WINNERS`, переключатель `stableLorebookGroupPicks`)

**Текущее состояние.** `applyGroupSelection()` в `packages/server/src/services/lorebook/keyword-scanner.ts` выбирает взвешенного победителя группы включения (`pickWeightedGroupEntry`), предпочитая закрепленные записи. Источник случайности внедряемый (`random`, по умолчанию `Math.random`), что упростило изменение. Новый выбор при каждой генерации может сменить победителя без других изменений, меняя префикс промпта и нарушая кеширование.

**Дополнения.** Необязательный `groupSeed` в `applyGroupSelection`/`ScanOptions`. При включении `processLorebooks` передает ID чата: одинаковые активные кандидаты дают одного победителя на каждом ходу этого чата. Разные чаты и наборы могут различаться. Пара `stableHash` + `createSeededRandom` из Active Context (Активный контекст) перенесена без изменений из `lorebooks.routes.ts` в общий `lorebook/seeded-random.ts`. С A6 также **Stable lorebook picks** (Стабильный выбор лорбука); переменная окружения приоритетна.

**Без изменений.** Имена и сигнатуры с необязательным параметром, закрепление и веса. Внедренная случайность по-прежнему управляет вероятностными проверками; включенный seed все равно определяет победителей, согласуя Active Context с генерацией. При отключении нет seed и используется прежний путь.

**Как проверить.** `node scripts/run-regressions.mjs --filter lorebook-group-seed` проверяет переменную и переключатель.

**Как отключить / откатить.** Не задавайте `LOREBOOK_STABLE_GROUP_WINNERS` и оставьте переключатель выключенным.

<a id="a3b-compact-stored-lorebook-scans-lorebook_compact_stored_scans"></a>

### A3b. Уплотнение сохраненных сканирований лорбука (`LOREBOOK_COMPACT_STORED_SCANS`)

**Текущее состояние.** Каждое сгенерированное сообщение хранит полный текст активных записей в `extra.lorebookScan`, в строке и каждом свайпе. Active Context показывает точный контекст, но длинные чаты с большими лорбуками значительно увеличивают таблицы.

**Дополнения.** При включении последнее сообщение ассистента или рассказчика, используемое Active Context и повторами агентов, сохраняет полный текст в строке и всех свайпах. Возврат к свайпу показывает исходный текст. Сканирование имитированного пользовательского хода уплотняется и никогда не занимает это место. Старые сообщения хранят лишь ID, имена, ключи и оценки. Уплотнение не идет в пути сохранения генерации: фоновая задача обрабатывает предыдущее сообщение, по одной очереди сообщений. Ошибки используют `logRateLimited` и повторяются при следующем сохранении. После удаления новых сообщений Active Context (`lorebooks.routes.ts`) и повторы (`retry-agents-route.ts` через `storedContentForTextlessScanEntries`) берут текущий сохраненный текст записи. `scripts/compact-lorebook-scans.mjs` применяет правило к старым чатам: пробный запуск по умолчанию, отказ при аренде записи сервера, копии обеих таблиц перед `--apply`.

**Без изменений.** Выключено: нет новых записей, структура прежняя. Формат скана и ответы маршрутов Active Context/повторов сохраняются; подстановка только при отсутствии текста. Две стандартные поправки затрагивают старые сканы без текста: Active Context показывает сохраненный текст вместо пустой строки; повторы включают записи вместо их пропуска.

**Как проверить.** `node scripts/run-regressions.mjs --filter lorebook-scan-compaction` проверяет стандартную структуру, возврат свайпов, имитированные ходы, обработку старых сообщений при первом сохранении, подстановку через настоящий маршрут Active Context и скрипт обслуживания.

**Как отключить / откатить.** `LOREBOOK_COMPACT_STORED_SCANS` не задана либо `false`. Уже уплотненные сообщения остаются такими; последнее сохраняет текст. Копии после `--apply` позволяют восстановить прежнюю структуру.

<a id="a4-robustness"></a>

## A4. Надежность

Все изменения управляются выключенными по умолчанию переменными, описанными в таблице надежности `docs/CONFIGURATION.md` и `.env.example`. Отдельные файлы позволяют независимо проверять, выделять и откатывать. Новые параметры/поля необязательны; `isRateLimitError` и `base-provider.ts` этот коммит не меняет.

<a id="a4a-storage-writes"></a>

### A4a. Запись данных

**Текущее состояние.** `packages/server/src/db/file-backed-store.ts` сбрасывает измененные фрагменты и `manifest.json` через `serializeTableRows()`/`atomicWriteFile()`, сохраняя `.bak` для восстановления. Атомарная запись и резервирование остаются.

**Дополнения.**

- `STORAGE_SKIP_UNCHANGED_WRITES` пропускает запись при совпадении содержимого с последней устойчивой записью процесса, если файл сохранил размер и mtime. Восстановленный из `.bak` файл всегда перезаписывается.
- `STORAGE_YIELDING_SERIALIZE` сериализует большие фрагменты интервалами по 12 мс, уступая циклу событий. Длинный чат не блокирует другие запросы; результат побайтово совпадает с `serializeTableRows`.

**Без изменений.** Обе выключены: `serializeTableRows`, `beforeTableWrite`, `atomicWriteFile` как прежде. Любая реальная запись через `atomicWriteFile`.

**Как проверить.** `node scripts/run-regressions.mjs --filter robustness-storage-write`

**Как отключить / откатить.** Не задавайте обе настройки.

<a id="a4b-windows-boot"></a>

### A4b. Запуск Windows

**Текущее состояние.** Аренда определяет загрузку ОС через `readBootId()` в `file-backed-store.ts`, запускающий PowerShell каждый раз (около 1,5–2 с в Windows), плюс запрос идентичности `reg.exe`.

**Дополнения.**

- `STORAGE_CACHE_WINDOWS_BOOT_ID` кеширует точный результат на одну загрузку ОС в `DATA_DIR/.writer-boot-id.json` (`db/writer-boot-id-cache.ts`). Ничего в `LOCALAPPDATA`.
- Всегда активно: `reg.exe` и PowerShell получают `windowsHide`; запуск без консоли больше не вызывает мигание окна. Других эффектов нет.

**Без изменений.** Логика аренды и проверка; при отключении проверка при каждом запуске.

**Как проверить.** `node scripts/run-regressions.mjs --filter robustness-boot-performance`

**Как отключить / откатить.** Не задавайте настройку либо удалите `.writer-boot-id.json`.

<a id="a4c-shutdown"></a>

### A4c. Завершение

**Текущее состояние.** `packages/server/src/index.ts` обрабатывает SIGINT, SIGTERM и вне Windows SIGHUP через `shutdown(signal)`, игнорирует повторы с warn, включает 8-секундный `armShutdownDeadline` и ждет все среды выполнения перед `closeDB()`. Порядок сохраняется.

**Дополнения.** `lib/shutdown-signals.ts` и `lib/shutdown-steps.ts`, используемые `index.ts`/`app.ts`:

- `SHUTDOWN_WINDOWS_CONSOLE_SIGNALS`: Ctrl+Break и закрытие консоли выполняют то же корректное завершение в пределах примерно 5 с Windows.
- `SHUTDOWN_FORCE_EXIT_ON_REPEAT`: второе Ctrl+C позднее 1,5 с после первого принудительно завершает процесс.
- `SHUTDOWN_EARLY_FLUSH`: ожидающие сохранения начинают сброс сразу по сигналу. Ошибка здесь не дублируется: хранилище уже записало ее и повторяет при закрытии.
- `SHUTDOWN_RUNTIME_STOP_BUDGET_MS` (максимум 2500, по умолчанию 0 = ждать всех): после сигнала `closeDB()` выполняется по истечении бюджета, даже если среда зависла. Две последние опции только для сигналов; перезапуск Advanced Settings в `admin.routes.ts` прежний.
- Всегда активно: три остановки именованы; ошибка или длительность свыше 1 с записывается с этапом.

**Без изменений.** Все выключено: те же сигналы, повторы игнорируются, все остановки до `closeDB()`, срок 8 с.

**Как проверить.** `node scripts/run-regressions.mjs --filter robustness-shutdown-safety`

**Как отключить / откатить.** Не задавайте настройки; первые две требуют перезапуска, что сообщает наблюдатель окружения.

<a id="a4d-provider-retry-on-transient-network-errors-provider_retry_transient_errors-switch-providerretry"></a>

### A4d. Повторы временных сетевых ошибок провайдера (`PROVIDER_RETRY_TRANSIENT_ERRORS`, переключатель `providerRetry`)

**Текущее состояние.** `RateLimitAwareProvider` в `packages/server/src/services/llm/rate-limit-aware-provider.ts` повторяет ограничения частоты с увеличением ожидания до `MAX_RATE_LIMIT_RETRIES`, учитывая `Retry-After`. `connection-fallback-provider.ts` переходит к запасному подключению. Оба механизма работают; отказ подключения или 502 просто завершал генерацию ошибкой.

**Дополнения.** Отказ/недоступность подключения или 502/503: максимум два повтора со случайным ожиданием 0,5–2 с (`Retry-After` до 5 с), только до получения пользователем текста или рассуждения. Никогда 504 или сброс сокета. Не применяется к основному подключению с доступным запасным (`transientRetry: false`), сохраняя быстрый переход. Основные подключения со своим wrapper, например переданным пакетом возможностей в `llm.withFallback`, тоже исключены. С A6 есть **Retry failed provider calls** (Повторять неудачные вызовы); переменная окружения приоритетна.

**Без изменений.** Ограничения частоты: прежнее расписание, без случайных задержек, те же callback. `isRateLimitError`/`base-provider.ts` не изменены.

**Как проверить.** `node scripts/run-regressions.mjs --filter robustness-provider-resilience`

**Как отключить / откатить.** Переменная не задана, переключатель выключен.

<a id="a5-startup-internal-requests-wait-until-route-registration-has-ended"></a>

## A5. Запуск: внутренние запросы ждут регистрации маршрутов

Всегда активное исправление, не настройка.

**Текущее состояние.** `buildApp()` в `packages/server/src/app.ts` регистрирует основные маршруты, ждет `capabilityModuleRuntime.start(app)`, активирующий пакеты через `activateOne()` в `services/capability-packages/capability-module-runtime.service.ts`, затем запускает `startServerAutonomousScheduler(app)`. Внутренний `app.inject()` вызывают пакеты через `runCapabilityInternalRoute()` в `capability-route-registration.service.ts`, планировщик в `server-autonomous-scheduler.service.ts` и `routes/generate/prompt-preview.ts`. Первый `inject()` запускает всю Fastify-инстанцию; потом нельзя добавлять маршруты, hooks и плагины. Если фоновая задача (таймер пакета или рано запущенный worker) вызывала `inject()`, пока `buildApp()` еще регистрировал маршруты, все последующие пакеты падали с "Root plugin has already booted", а следующий `addHook` выбрасывал ошибку и останавливал сервер. `catch` в `activateOne()` журналирует и вызывает `capabilityPackageManager.rollbackRuntime()` либо сохраняет статус/готовность `"error"`. Здоровый пакет мог оставаться откатанным или `"error"` при следующих запусках.

**Дополнения.**

- `lib/fastify-inject-gate.ts`: `buildApp()` вызывает `holdInjectUntilRegistered(app)` сразу после создания экземпляра и освобождает перед `return app`. Предыдущие `app.inject()`, promise или callback, ждут и достигают позже добавленных маршрутов. Если удержанный `inject()` выбрасывает ошибку, callback получает ее.
- `activate()`/`selfCheck()` входят в регистрацию; ожидание их собственных маршрутов заблокировалось бы. `activateOne()` запускает их в `failInjectFastDuring()`: прямой `inject()` сразу дает `InjectDuringRegistrationError` (`code`: `MARINARA_INJECT_DURING_REGISTRATION`). Не активируется только этот пакет; запуск продолжается. Таймеры после возврата `activate()` ждут как фоновые вызовы.
- Другие удержанные вызовы предупреждают со стеком вызывающего через 60 с и отклоняются через 10 минут с той же ошибкой. Зависший запуск сообщает о сбое. Таймеры без ссылок не удерживают процесс.
- `isHostLifecycleActivationError()` в `capability-module-runtime.service.ts` распознает `AVV_ERR_ROOT_PLG_BOOTED` ("Root plugin has already booted") и `FST_ERR_INSTANCE_ALREADY_LISTENING` ("Fastify instance is already listening"). Нет отката или сохраненного статуса/готовности `"error"`: версия и статус остаются, следующий запуск активирует нормально. Один warn и запись диагностики. Другие ошибки сохраняют error, откат и `"error"`.
- Регрессия: `startup-inject-gate`.

**Без изменений.** После `buildApp()` вызов `app.inject()` снова оригинальный Fastify без wrapper. Цепочная форма (`app.inject()` без аргументов) никогда не удерживается. Порядок, маршруты, `runCapabilityInternalRoute()`, планировщик и последующие активации/обновления прежние. Один случай на работающем сервере: пакет, активированный из интерфейса и добавляющий новый маршрут, получает `FST_ERR_INSTANCE_ALREADY_LISTENING`, но новая версия остается до следующего запуска, без отката. Вызывающий все равно получает ошибку.

**Как проверить.**

```sh
node scripts/run-regressions.mjs --filter startup-inject-gate
```

Проверяет освобождение и поздний маршрут, callback, немедленный сбой внутри `activate()`, таймер из `activate()`, предел 10 минут с короткими тестовыми значениями, установку/освобождение в `buildApp()` и возврат до отката с одним предупреждением при ошибке жизненного цикла хоста.

**Как отключить / откатить.** Переключателя нет. `MARINARA_INJECT_DURING_REGISTRATION` – код `InjectDuringRegistrationError`, не настройка. Откатите коммит блокировки inject.
