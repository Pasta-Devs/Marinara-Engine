# Marinara Engine की समस्याएँ सुलझाना

इस गाइड में Marinara Engine की आम समस्याएँ और उनके हल दिए गए हैं। अपनी दिक्कत से मिलता-जुलता सेक्शन ढूँढें, फिर स्टेप्स पर चलें। यहाँ कुछ काम न आए तो आखिरी सेक्शन, ज़्यादा मदद पाना, देखें।

## सबसे पहले ये आज़माएँ

बहुत सी समस्याएँ दो छोटे स्टेप से ही ठीक हो जाती हैं।

1. पेज को हार्ड रिफ़्रेश करें। Windows या Linux पर **Ctrl+Shift+R** दबाएँ, Mac पर **Cmd+Shift+R**।
2. सर्वर कंसोल (वह टर्मिनल विंडो जिसमें Marinara चलता है) में लाल एरर लाइनें देखें। असली दिक्कत आमतौर पर उन्हीं लाइनों में लिखी होती है।

टीम से मदद माँगनी हो तो पहले **Debug mode** (डीबग मोड) चालू करें, ताकि सर्वर प्रॉम्प्ट (वह टेक्स्ट जो Marinara Engine AI को भेजता है) और जवाब लॉग करे। इस गाइड के आखिर में ज़्यादा मदद पाना देखें।

## इंस्टॉल और लॉन्च की समस्याएँ

### Windows: pnpm इंस्टॉल करते समय EPERM या corepack सिग्नेचर एरर

pnpm वह पैकेज मैनेजर है जिससे Marinara अपना कोड इंस्टॉल करता है। अगर `EPERM: operation not permitted` दिखे या corepack का सिग्नेचर वेरिफ़िकेशन फ़ेल हो जाए, तो इसका मतलब है कि corepack, Node के इंस्टॉल फ़ोल्डर में लिख नहीं पाया।

इनमें से कोई एक उपाय अपनाएँ:

1. अपने टर्मिनल पर राइट-क्लिक करें, Run as administrator चुनें, फिर लॉन्चर दोबारा चलाएँ।
2. pnpm खुद इंस्टॉल करें। यह कमांड चलाएँ, फिर लॉन्चर दोबारा चलाएँ:

```bash
npm install -g pnpm
```

3. एडमिनिस्ट्रेटर टर्मिनल में corepack अपडेट करें, फिर लॉन्चर दोबारा चलाएँ:

```bash
npm install -g corepack
```

### Windows: shared पैकेज बनाते समय `'pnpm' is not recognized`

Marinara v2.3.0 में pnpm, Corepack के ज़रिए तो चालू हो जाता था, पर shared-पैकेज बिल्ड के दौरान काम रुक जाता था, क्योंकि वह बिल्ड एक दूसरा, ग्लोबल `pnpm` एक्ज़ीक्यूटेबल चलाने की कोशिश करता था। v2.3.1 में यह नेस्टेड ज़रूरत हटा दी गई है। फ़ेल हुए लॉन्चर को बंद करें और `start.bat` दोबारा चलाएँ, ताकि रीबिल्ड से पहले वह सही बिल्ड स्क्रिप्ट ले सके। डेटा हटाने की ज़रूरत नहीं है।

अगर चेकआउट खुद अपडेट न हो पा रहा हो, तो Marinara फ़ोल्डर में `git pull` चलाएँ और उसे दोबारा शुरू करें। v2.3.0 के लिए अस्थायी उपाय यह है: तय किया हुआ पैकेज मैनेजर ग्लोबल इंस्टॉल करें, लॉन्चर दोबारा चलाएँ, और फिर सामान्य तरीके से अपडेट करें:

```bash
npm install -g pnpm@10.33.2
```

### Linux: इंस्टॉल के दौरान ERR_PNPM_ENAMETOOLONG

इसका मतलब है कि किसी पुराने इंस्टॉल ने लंबे फ़ोल्डर पथ पीछे छोड़ दिए हैं। Marinara फ़ोल्डर में जाकर अधूरा इंस्टॉल हटाएँ और लॉन्चर दोबारा चलाएँ:

```bash
rm -rf node_modules .pnpm .pnpm-store
```

फिर `./start.sh` से Marinara दोबारा शुरू करें। हाथ से इंस्टॉल करते हों, तो ये फ़ोल्डर हटाने के बाद `pnpm install` चलाएँ।

### इंस्टॉल के दौरान ERR_PNPM_TRUST_DOWNGRADE

यह लगभग हमेशा अधूरे इंस्टॉल की वजह से होता है। पहले लॉन्चर दोबारा चलाएँ, ताकि वह वर्कस्पेस ठीक कर सके। हाथ से इंस्टॉल करते हों, तो Marinara फ़ोल्डर में यह एक ही कमांड चलाएँ:

```bash
pnpm --config.trustPolicy=off --config.confirmModulesPurge=false install --frozen-lockfile
```

## खाली, पुरानी या पुराने वर्ज़न जैसी दिखने वाली स्क्रीन

कभी-कभी सर्वर चल रहा होता है, फिर भी ब्राउज़र में खाली पेज दिखता है, या अपडेट के बाद भी ऐप पुराने वर्ज़न जैसा लगता है। ऐसे में ब्राउज़र ने वेब ऐप की पुरानी कॉपी कैश में रखी हुई है।

1. हार्ड रिफ़्रेश करें (**Ctrl+Shift+R** या **Cmd+Shift+R**)।
2. इससे बात न बने तो **Settings** (सेटिंग्स) खोलें, **Advanced** टैब पर जाएँ, फिर **Updates** सेक्शन में **Refresh App** पर क्लिक करें।

**Refresh App** ब्राउज़र का सर्विस वर्कर (बैकग्राउंड में चलने वाली वह स्क्रिप्ट जो वेब ऐप को कैश करती है) और ब्राउज़र कैश साफ़ करता है, फिर पेज दोबारा लोड करता है। इससे डेटा नहीं बदलता। चैट, सेटिंग्स और बाकी लोकल डेटा जस का तस रहता है। इससे सर्वर का कोड अपडेट नहीं होता, इसलिए यह असली अपडेट की जगह नहीं ले सकता। ऐप को खुद अपडेट करने के लिए [Marinara Engine को अपडेट करना](UPGRADING.md) देखें।

## डाउनलोड किए जाने वाले एजेंट की समस्याएँ

अगर **Agents → Download Agents** (एजेंट → एजेंट डाउनलोड करें) कहे कि कैटलॉग उपलब्ध नहीं है, तो ध्यान रखें: आधिकारिक [Pasta-Devs/Marinara-Agents](https://github.com/Pasta-Devs/Marinara-Agents) कैटलॉग तक GitHub HTTPS के ज़रिए उस मशीन की पहुँच होनी चाहिए जिस पर Marinara सर्वर चल रहा है, सिर्फ़ ब्राउज़र की नहीं। इंस्टॉल हो चुके एजेंट अपने मौजूदा वर्ज़न पर ऑफ़लाइन भी काम करते रहते हैं। सर्वर का कनेक्शन ठीक करें, फिर कैटलॉग देखने और अपडेट जाँचने के लिए **Refresh** या **Try again** पर क्लिक करें।

अगर इंस्टॉल किया हुआ मैप या कॉल न दिखे, तो Marinara Engine को पूरी तरह बंद करके दोबारा शुरू करें। रूट देने वाले ऐसे पैकेज अगली बार प्रोसेस शुरू होने तक **Restart required** स्थिति में ही रहते हैं। Conversation गेम्स का मामला अलग है: Engine के मौजूदा बिल्ड उन्हें तुरंत चालू कर देते हैं। इंस्टॉलेशन फ़ेल हुआ हो तो कैटलॉग रिफ़्रेश करें, फिर देखें कि गेम तैयार दिख रहा है या नहीं। किसी चैट की **Commands** सेटिंग्स में उसे जोड़ना सिर्फ़ तब ज़रूरी है जब आप चाहें कि कैरेक्टर खुद उसे शुरू करें, गेम की मैन्युअल स्लैश कमांड के लिए नहीं।

अगर किसी पुराने इंस्टॉलेशन का पहला पैकेज माइग्रेशन पूरा न हो पाए, तो `data/capability-packages` फ़ोल्डर या अपना चैट डेटा न हटाएँ। Marinara माइग्रेशन अधूरा छोड़ देता है और अगली बार शुरू होने पर दोबारा कोशिश करता है। कैटलॉग तक पहुँच न होने पर भी चैट के मौजूदा चुनाव और सेटिंग्स सेव रहती हैं।

पैकेज डाउनलोड तब ठुकरा दिए जाते हैं जब उनका चेकसम, घोषित फ़ाइल लिस्ट, Engine वर्ज़न रेंज या आर्काइव पथ आधिकारिक कैटलॉग से मेल न खाएँ। पहले Marinara Engine अपडेट करें, कैटलॉग रिफ़्रेश करें, फिर दोबारा कोशिश करें। किसी आर्टिफ़ैक्ट को हाथ से डेटा फ़ोल्डर में न निकालें।

एजेंट अपडेट शुरुआत में कभी अपने आप लागू नहीं होते। जब कोई नया, चलने लायक वर्ज़न मिलता है, Marinara पूछता है कि उसे लागू करना है या नहीं। इंस्टॉल किया हुआ वर्ज़न बनाए रखने के लिए **No** चुनें; **Update** बटन **Agents → Download Agents** में मौजूद रहता है। अपडेट फ़ेल होने पर भी इंस्टॉल किया हुआ वर्ज़न रजिस्टर रहता है, और अभी-अभी अपडेट हुआ सर्वर रनटाइम अगर शुरुआत की सेल्फ़-चेक में फ़ेल हो जाए तो पिछले वर्ज़न पर लौट आता है।

## दूसरे डिवाइस से Marinara तक पहुँचना

अगर फ़ोन, टैबलेट या नेटवर्क के किसी दूसरे कंप्यूटर से Marinara नहीं खुल रहा, तो ये जाँचें एक-एक करके करें।

- सर्वर को ऐसे पते पर बाइंड करें जहाँ तक पहुँचा जा सके। डिफ़ॉल्ट रूप से सर्वर `127.0.0.1` (लूपबैक, यानी सिर्फ़ आपकी अपनी मशीन) पर सुनता है। शेल लॉन्चर आपके लिए `HOST=0.0.0.0` सेट कर देते हैं। अगर आपने हाथ से `pnpm start` चलाया है, तो पहले अपनी `.env` फ़ाइल में `HOST=0.0.0.0` सेट करें।
- जाँच लें कि दोनों डिवाइस एक ही Wi-Fi नेटवर्क पर हैं।
- जाँच लें कि कोई फ़ायरवॉल उस पोर्ट को ब्लॉक तो नहीं कर रहा। डिफ़ॉल्ट पोर्ट `7860` है, या जो आपने `PORT` में सेट किया हो।
- एक्सेस कंट्रोल सेट करें। सामान्य नेटवर्क या पब्लिक क्लाइंट के लिए `.env` में `BASIC_AUTH_USER` और `BASIC_AUTH_PASS` सेट करें। लूपबैक बिना पासवर्ड के ही चलता रहता है। Tailscale से आने वाला सीधा ट्रैफ़िक और उसी होस्ट का Docker ब्रिज या पहचाना गया कंटेनर गेटवे डिफ़ॉल्ट रूप से भरोसेमंद माना जाता है; प्रॉक्सी से फ़ॉरवर्ड हुए Docker ट्रैफ़िक के लिए सामान्य अनुमति ज़रूरी है, जब तक आप खुद `REQUIRE_AUTH_FOR_DOCKER_PROXY=false` सेट न करें।
- उस डिवाइस से खास अधिकार वाले काम (बैकअप, डेटा मिटाना, अपडेट) करने के लिए सर्वर की `.env` में `ADMIN_SECRET` सेट करें। फिर वही वैल्यू उस डिवाइस पर **Settings** > **Advanced** > **Admin Access** में पेस्ट करें और **Save** पर क्लिक करें।
- अगर आप पब्लिक या रिवर्स-प्रॉक्सी डोमेन इस्तेमाल करते हैं और **Untrusted request host** दिखे, तो `.env` में `TRUSTED_HOSTS` में उसका पूरा होस्टनेम जोड़ें। फ़ोन, LAN कंप्यूटर और Tailscale पीयर जिन सीधे IP पतों का इस्तेमाल करते हैं, वे अपने आप स्वीकार होते रहते हैं।

पूरी जानकारी के लिए [रिमोट एक्सेस](REMOTE_ACCESS.md) और [अक्सर पूछे जाने वाले सवाल](FAQ.md) देखें।

## सेव ब्लॉक होना, या सेटिंग्स का टिक न पाना

अगर सेव होता हुआ लगे पर पेज दोबारा लोड करने पर पुरानी वैल्यू लौट आए, तो Marinara की क्रॉस-साइट सुरक्षा उसे रोक रही है। CSRF (क्रॉस-साइट रिक्वेस्ट फ़ोर्जरी) सुरक्षा डेटा बदलने वाले कामों की पहरेदारी करती है। यह सिर्फ़ कुछ ब्राउज़र ऑरिजिन पर भरोसा करती है।

इनमें से एक या दोनों निशानियाँ दिखेंगी:

- स्क्रीन के ऊपर लाल बैनर, जो चेतावनी देता है कि यह ऑरिजिन भरोसेमंद नहीं है, इसलिए सेव चुपचाप फ़ेल हो जाएँगे।
- **Save blocked: missing CSRF header**, **Save blocked: cross-site request rejected**, या **Save blocked: origin not trusted** शीर्षक वाला टोस्ट।

लूपबैक, प्राइवेट नेटवर्क पते, Tailscale और Docker ब्रिज अपने आप भरोसेमंद माने जाते हैं। ऐसा आमतौर पर तभी होता है जब आप Marinara तक किसी पब्लिक IP पते या डोमेन नाम से पहुँचते हैं। उस पते को `.env` में `CSRF_TRUSTED_ORIGINS` में जोड़ें। एक से ज़्यादा हों तो कॉमा से अलग करके लिखें, जैसे:

```bash
CSRF_TRUSTED_ORIGINS=http://203.0.113.10:7831,https://chat.example.com
```

रीस्टार्ट की ज़रूरत नहीं है। बैनर पर मौजूद Copy बटन आपके लिए पूरी लाइन तैयार कर देता है। ज़्यादा जानकारी के लिए [रिमोट एक्सेस](REMOTE_ACCESS.md) देखें।

## कनेक्शन और जेनरेशन की एरर

जेनरेशन की एरर स्क्रीन के नीचे टोस्ट के रूप में दिखती है। कनेक्शन फ़ेल हुआ हो तो टोस्ट में वजह लिखी होती है। टोस्ट इतनी देर टिकता है कि उसे पढ़कर कॉपी किया जा सके।

- **No API connection configured for this chat**: चैट के लिए कोई कनेक्शन नहीं चुना गया है। **Connections** (कनेक्शन) पैनल खोलें, एक कनेक्शन बनाएँ, फिर उसे चैट के लिए चुनें। देखें [किसी AI प्रोवाइडर से कनेक्ट करना](connections/connecting-to-a-provider.md)। API कुंजी प्रोवाइडर से मिला एक गुप्त कोड है, जिससे Marinara उनके मॉडल इस्तेमाल कर पाता है।
- मॉडल कोई पैरामीटर स्वीकार नहीं करता: टोस्ट बताता है कि कौन-सा। **Chat Settings** (चैट सेटिंग्स) > **Advanced Parameters** खोलें और वह पैरामीटर ढूँढें। उसके नाम के आगे वाला स्विच बंद करें (टूलटिप में लिखा होता है "This parameter is sent to the model")।
- मॉडल कहता है कि कोई पैरामीटर ज़रूरी है: वही करें, पर उस पैरामीटर के आगे वाला स्विच चालू करें।
- **The AI returned an empty response. Try sending your message again.**: संदेश दोबारा भेजें। बार-बार ऐसा हो तो कोई दूसरा मॉडल या कनेक्शन आज़माएँ।
- **A generation is already in progress for this chat**: एक जवाब अभी स्ट्रीम हो रहा है। उसके पूरा होने का इंतज़ार करें या Stop बटन पर क्लिक करें, फिर दोबारा कोशिश करें।
- **No connections are marked for the random pool**: आपने रैंडम कनेक्शन रूटिंग चालू की है, पर पूल के लिए कोई कनेक्शन नहीं चुना। पूल में कम से कम एक कनेक्शन जोड़ें, या रैंडम रूटिंग बंद कर दें।

## Local Model की समस्याएँ

**Local Model** (लोकल मॉडल) वह AI मॉडल है जो बिना API कुंजी के आपकी अपनी मशीन पर चलता है। कुछ एरर संदेशों में इस फ़ीचर के लिए sidecar शब्द आता है।

- अगर रनटाइम इंस्टॉल करते समय **Sidecar runtime install is disabled** दिखे, तो सर्वर ने सुरक्षा के लिए यह काम बंद कर रखा है। अपनी मशीन पर `.env` में `SIDECAR_RUNTIME_INSTALL_ENABLED=true` सेट करें। दूसरे डिवाइस से करना हो तो पहले अपना एडमिन सीक्रेट **Settings** > **Advanced** > **Admin Access** में पेस्ट करें।
- अगर मॉडल डाउनलोड या सेटअप किसी दूसरे डिवाइस से (नेटवर्क पते या Docker से) फ़ेल हो, तो वहाँ भी एडमिन सीक्रेट की ज़रूरत पड़ सकती है। अपनी मशीन पर एडमिन सीक्रेट नहीं चाहिए। सीक्रेट कहाँ पेस्ट करना है, यह ऊपर वाले बिंदु में लिखा है।
- अगर साथ आए llama.cpp, MLX, uv या MLX डिपेंडेंसी-लॉक की जाँच में फ़ाइल का आकार या SHA-256 मेल न खाए, तो Marinara उसे निकालने या इंस्टॉल करने से पहले ही हटा या ठुकरा चुका होता है। Marinara अपडेट या दोबारा इंस्टॉल करके फिर कोशिश करें; ठुकराए गए आर्टिफ़ैक्ट को हाथ से न चलाएँ, न खोलें, न बदलें, न बायपास करें।

### मेंटेनर के लिए: पिन किए हुए लोकल रनटाइम अपडेट करना

GitHub से बने सोर्स आर्काइव के बाइट हमेशा एक जैसे रहेंगे, इसकी कोई गारंटी नहीं, भले ही उनके कमिट की सामग्री न बदले। मेल न खाने की समस्या को कभी इस तरह "ठीक" न करें कि यूज़र की मशीन पर दिखे बाइट स्वीकार कर लिए जाएँ या वेरिफ़िकेशन कमज़ोर कर दिया जाए। रनटाइम इनपुट दोबारा पिन करना सिर्फ़ रिव्यू किए गए Engine बदलाव में ही करें:

1. कोई न बदलने वाला अपस्ट्रीम रिविज़न या रिलीज़ एसेट चुनें और अपस्ट्रीम के बदलाव रिव्यू करें।
2. आर्टिफ़ैक्ट को किसी अस्थायी फ़ोल्डर में डाउनलोड करें, उसके बाइट की सटीक गिनती नोट करें, और उसका SHA-256 डाइजेस्ट अलग से निकालें।
3. `runtime-integrity-manifest.ts` में रिविज़न, URL, साइज़ और डाइजेस्ट अपडेट करें। MLX के लिए Apple Silicon/Python 3.12 पर पिन किए गए uv वर्ज़न के साथ `packages/server/src/assets/mlx-runtime-requirements.lock` को उसकी `.in` फ़ाइल से दोबारा बनाएँ, हर डिपेंडेंसी बदलाव रिव्यू करें, और `requirementsLockSha256` अपडेट करें।
4. `pnpm regression:runtime-integrity`, `pnpm check` चलाएँ, और प्रभावित प्लैटफ़ॉर्म पर एक असली, साफ़ रनटाइम इंस्टॉलेशन करके देखें।
5. यूज़र से दोबारा कोशिश करने को कहने से पहले रिव्यू किया हुआ Engine अपडेट रिलीज़ करें। चेकसम को हाथ से बदलने का विकल्प न दें।

पूरे सेटअप के लिए [Local Model का सेटअप](connections/local-model.md) देखें।

## मेमोरी और सारांश

### Memory Recall कुछ याद नहीं रखता

**Memory Recall** (मेमोरी रिकॉल) पिछले संदेशों में खोजता है और सबसे मिलते-जुलते संदेश चुपचाप वापस प्रॉम्प्ट में जोड़ देता है। अगर लगे कि उसे कुछ याद ही नहीं रहता, तो ये जाँचें।

1. **Chat Settings** > **Memory Recall** खोलें और देखें कि **Enable Memory Recall** चालू है।
2. **Access memories for this chat** खोलें। **Memories for This Chat** विंडो में हर चंक की स्थिति देखें।
3. **Waiting for vector** स्थिति का मतलब है कि मेमोरी अभी तैयार हो रही है। थोड़ा रुककर दोबारा चैट करें।
4. **Embedding unavailable** स्थिति का मतलब है कि कोई एम्बेडिंग (टेक्स्ट का संख्यात्मक रूप) सोर्स काम नहीं कर रहा। एम्बेडिंग के लिए कोई कनेक्शन सेट करें, या साथ आए लोकल मॉडल को लोड होने दें। देखें [Local Model का सेटअप](connections/local-model.md)।

कोई मेमोरी बनने के लिए कम से कम 5 नए संदेश चाहिए। रिकॉल सिर्फ़ वही मेमोरी दिखाता है जो आपके नए संदेश से काफ़ी मिलती-जुलती हो, इसलिए मेमोरी मौजूद होने पर भी कुछ न मिलना मुमकिन है।

### सारांश नहीं बन रहे

चैट के सारांश लिखने के लिए एक चालू टेक्स्ट कनेक्शन चाहिए।

- Roleplay मोड में **Chat Summary** पॉपओवर खोलें और देखें कि कनेक्शन सेट है। पुरानी चैट की भरपाई के लिए **Backfill Summary** इस्तेमाल करें।
- Conversation मोड में **Automatic Summarization** खोलें और जिन दिनों का सारांश फ़ेल हुआ, उनके लिए **Backfill** इस्तेमाल करें।
- अगर आपकी चैट में एजेंट के लिखे को मंज़ूरी चाहिए, तो AI सारांश लागू होने से पहले आपकी समीक्षा का इंतज़ार करता है।
- बार-बार फ़ेल होने वाला सारांश (जैसे गलत API कुंजी की वजह से) कुछ देर बाद अपने आप दोबारा आज़माया जाता है। कनेक्शन ठीक करें, फिर **Backfill** इस्तेमाल करें।

## Card Browser की समस्याएँ

**Card Browser** (कार्ड ब्राउज़र) से पब्लिक कैरेक्टर साइटें खोजकर कैरेक्टर इंपोर्ट किए जा सकते हैं। इसे ऊपर की पट्टी में **Card Browser** आइकन से खोलें, फिर **Download Cards** पर क्लिक करें।

- अगर JannyAI सर्च या कोई कैरेक्टर पेज Cloudflare ब्लॉक के साथ फ़ेल हो, तो Marinara एक संदेश दिखाता है। उसमें कहा जाता है कि उसी ब्राउज़र में एक बार JannyAI साइट खोलकर चुनौती पूरी करें, फिर दोबारा कोशिश करें।
- अगर सर्वर रीस्टार्ट करने के बाद आपका CharacterTavern या Pygmalion लॉगिन काम करना बंद कर दे, तो यह सामान्य है। वे लॉगिन सिर्फ़ सर्वर की मेमोरी में रहते हैं और रीस्टार्ट पर मिट जाते हैं। लॉगिन विंडो खोलें और अपनी कुकी या टोकन दोबारा पेस्ट करें।

## मीडिया जेनरेशन की समस्याएँ

### जटिल सीन में स्प्राइट का बैकग्राउंड ठीक से नहीं हटता

जेनरेट किए गए स्थिर स्प्राइट आम तौर पर नेटिव ट्रांसपेरेंसी या अपने आप बनने वाले सपाट क्रोमा मैट पर चलते हैं। साथ आया क्लीनअप पुराने सफ़ेद मैट भी पहचानता है, सब्जेक्ट के भीतर की बारीकियाँ बचाता है, अल्फ़ा किनारे को नरम करता है, और मैट के रंग का फैलाव हटाता है। फ़ोटो खींचा हुआ कमरा, बारीक नज़ारा, गहरी परछाइयाँ, या ऐसा सब्जेक्ट जिसके रंग बैकग्राउंड से मिलते हों, तब भी वैकल्पिक AI फ़ॉलबैक की ज़रूरत पड़ सकती है:

```bash
pnpm backgroundremover:install
```

फिर Marinara दोबारा शुरू करें और स्प्राइट जेनरेशन विंडो में **Reapply Cleanup** पर क्लिक करें। Marinara तब भी पहले साथ आए मैट वाले रास्ते को ही आज़माएगा और AI मॉडल तभी इस्तेमाल करेगा जब किनारा एक-सा न लगे। इंस्टॉल फ़ेल हो जाए तो:

- देख लें कि Python 3.9 से 3.11 इंस्टॉल है। इससे नए Python वर्ज़न धीमे नेटिव बिल्ड करा सकते हैं।
- `pnpm backgroundremover:reinstall` से टूल दोबारा बनाएँ।
- समस्या सुलझाते समय AI फ़ॉलबैक के बिना अपने आप मैट क्लीनअप कराने के लिए `.env` में `SPRITE_BACKGROUND_REMOVAL_ENGINE=builtin` सेट करें।

### Game Mode या Roleplay के स्टोरीबोर्ड नहीं दिखते

Game Mode Storyboards पूरे हो चुके GM (कहानी चलाने वाला AI) नैरेशन को कीफ़्रेम इमेज और वैकल्पिक क्लिप में बदलते हैं। Roleplay Storyboards पूरी हो चुकी बातचीत को जोड़ते हैं और नतीजा असिस्टेंट के जवाब के ठीक बाद वहीं दिखाते हैं।

- देख लें कि **Agents** > **Download Agents** से **Storyboard** इंस्टॉल है, फिर उस चैट के लिए **Enable Agents** और **Enable Storyboards** चालू करें।
- मैन्युअल सीन वीडियो के लिए पहले **Gallery** (गैलरी) में कोई इमेज जेनरेट करें या अपलोड करें, फिर उसका **Video** या **Animate** एक्शन इस्तेमाल करें। **Gallery** में **Images** और **Videos** अलग टैब में होते हैं, इसलिए **Videos** टैब देखें।
- अपने आप बनने वाले Game Mode Storyboards के लिए **Chat Settings** > **Agents** > **Storyboards** खोलें और देखें कि **Automatic Storyboard Illustrations** चालू है। क्लिप भी चाहिए तो **Automatic Storyboard Animations** भी चालू करें।
- Roleplay में चैट में **Storyboard** एजेंट जोड़ें। **Still images** या **Animations** चुनें, **Messages per episode** सेट करें, और Storyboard के लिए इमेज कनेक्शन चुनें। **Manual only** चुनने पर यह गैलरी के **Create storyboard** से चलता है।
- कीफ़्रेम इमेज के लिए इमेज कनेक्शन चाहिए। क्लिप के लिए वीडियो कनेक्शन भी चाहिए।
- अगर सारे कैरेक्टर एक साथ रखने पर कस्टम प्रॉम्प्ट बेहतर काम करे, तो **Use NovelAI Character Prompts** बंद कर दें।
- धीमे प्रोवाइडर पर टाइमआउट (सर्वर धीमे काम का कितनी देर इंतज़ार करता है) हो सकता है। `.env` में `IMAGE_GEN_TIMEOUT_MS` या `VIDEO_GEN_TIMEOUT_MS` बढ़ाएँ, फिर Marinara दोबारा शुरू करें। सर्वर ये वैल्यू सिर्फ़ शुरू होते समय पढ़ता है।

दोनों तरीकों के लिए [Storyboard एजेंट गाइड](game/storyboard.md) देखें, और गेम सेटअप के लिए [Game Mode: शुरुआत](game/getting-started.md)।

### Game Mode की वर्ल्ड जेनरेशन में JSON एरर दिखती है

अगर गेम शुरू करते समय मॉडल टूटा हुआ JSON लौटाए और काम रुक जाए, तो Marinara पूरा टर्न फेंकने के बजाय **Repair JSON** विंडो खोल देता है। JSON वह संरचित टेक्स्ट फ़ॉर्मैट है जो मॉडल को लौटाना ही होता है।

1. एडिटर में ब्रैकेट, कॉमा या फ़ील्ड ठीक करें। टेक्स्ट सही पार्स होते ही बैनर में **JSON is valid.** दिखने लगता है।
2. लेआउट सुधारने के लिए **Format** पर क्लिक करें।
3. पूरा जवाब दोबारा जेनरेट किए बिना उसे इस्तेमाल करने के लिए **Apply Repaired JSON** पर क्लिक करें।

## वॉइस, कॉल और TTS

- अगर कॉल के दौरान कैरेक्टर बोलें नहीं, तो Text to Speech सेट नहीं है। **Connections** > **Text to Speech** खोलें, इसे चालू करें, कोई सोर्स चुनें, अपनी कुंजी डालें, आवाज़ चुनें, और सेव करें। जिस कैरेक्टर की कोई आवाज़ न हो, वह सिर्फ़ टेक्स्ट में दिखता है।
- अगर माइक्रोफ़ोन काम न करे, तो शायद लोकल स्पीच मॉडल चाहिए। **Agents > Download Agents** से **Calls** इंस्टॉल करें, फिर **Connections** > **Local Model** खोलें, कार्ड को फैलाएँ, **Local Speech Model** ढूँढें, कोई Whisper मॉडल चुनें, और **Download Whisper** पर क्लिक करें। खास तौर पर Firefox में यह ज़रूरी है, क्योंकि उसमें ब्राउज़र स्पीच रिकग्निशन नहीं है। Calls अनइंस्टॉल करने पर उसके Whisper मॉडल भी हट जाते हैं और डिस्क की जगह वापस मिल जाती है।
- Lite बिल्ड पर **Local Whisper is disabled in Lite mode** संदेश का मतलब है कि वह छोटा बिल्ड लोकल स्पीच मॉडल नहीं चला सकता। इसकी जगह पूरा Marinara इंस्टॉल इस्तेमाल करें।

### रिमोट या नेटवर्क इंस्टॉल पर Music DJ का Spotify लॉगिन फ़ेल होता है

Music DJ एजेंट का Spotify मोड OAuth इस्तेमाल करता है। OAuth में लॉगिन का काम आगे सौंप दिया जाता है और Spotify आपको एक कॉलबैक पते पर वापस भेजता है। रीडायरेक्ट URI वही कॉलबैक पता है, और Spotify सिर्फ़ `https://` पते या लूपबैक पता `http://127.0.0.1` स्वीकार करता है। सादे नेटवर्क IP पते वह ठुकरा देता है।

- अगर आप Marinara को localhost पर खोलते हैं, तो एडिटर में `127.0.0.1` वाला कॉलबैक दिखता है। उसे Spotify में रजिस्टर करें, लॉगिन पूरा हो जाएगा।
- अगर आप Marinara तक HTTPS से पहुँचते हैं, तो एडिटर आपका HTTPS कॉलबैक दिखाता है। उसे रजिस्टर करें।
- अगर HTTPS ऊपर ही खत्म हो जाता है और होस्ट मेल नहीं खाता, तो `.env` में `SPOTIFY_REDIRECT_URI` को अपने पब्लिक कॉलबैक पते पर सेट करें।
- सादे HTTP वाले नेटवर्क इंस्टॉल पर पॉपअप लोड नहीं हो पाता, पर एड्रेस बार में सही कोड फिर भी मौजूद रहता है। पॉपअप से पूरा URL कॉपी करें। फिर Connect बटन के नीचे **Browser couldn't reach the callback?** को फैलाएँ और वहाँ पेस्ट करें। पेस्ट किया गया URL 10 मिनट तक चलता है।

सबसे साफ़ और टिकाऊ हल यही है कि सर्वर को HTTPS के पीछे रखा जाए। आखिरी बार Marinara Engine 2.2.0 पर जाँचा गया। Spotify ने ये नियम फ़रवरी 2025 में सख्त किए थे।

## स्टोरेज और डेटा

### अपडेट के बाद डेटा गायब लगता है

अगर अपडेट के बाद आपकी चैट या प्रीसेट गायब लगें, तो अभी कोई डेटा फ़ोल्डर न हटाएँ। Marinara आपका मौजूदा डेटा अपने डेटा फ़ोल्डर के अंदर `storage` फ़ोल्डर में रखता है।

`storage` फ़ोल्डर इन दोनों लोकल जगहों पर देखें:

1. `packages/server/data/`
2. `data/`

सर्वर शुरू होते समय जो डेटा और स्टोरेज फ़ोल्डर उसने तय किए, उन्हें प्रिंट कर देता है।

### बैकअप या एक्सपोर्ट पर 403 आता है

लूपबैक सेशन बिना एडमिन सीक्रेट के बैकअप बना सकते हैं। किसी दूसरे डिवाइस, नेटवर्क पते या Docker से बैकअप और प्रोफ़ाइल एक्सपोर्ट के लिए इससे ज़्यादा चाहिए। सर्वर पर `ADMIN_SECRET` सेट करें और वही वैल्यू **Settings** > **Advanced** > **Admin Access** में सेव करें। अगर लूपबैक पर भी सीक्रेट अनिवार्य करना हो, तो `MARINARA_REQUIRE_ADMIN_SECRET_ON_LOOPBACK=true` सेट करें।

## Android और Docker

### Android ऐप Connecting या Waiting for Server पर अटक जाता है

Android ऐप, Termux के ऊपर एक छोटा सा खोल भर है। Termux, Android का Linux टर्मिनल ऐप है, और असली Marinara सर्वर वही चलाता है।

1. **Install / Start Marinara** पर टैप करें।
2. अगर Android, Termux इंस्टॉल करने की अनुमति माँगे, तो मंज़ूरी दें।
3. अगर Android, Termux में कमांड चलाने की अनुमति माँगे, तो दे दें।
4. लॉन्चर के पूरा होने और सर्वर के शुरू होने का इंतज़ार करें, फिर ऐप पर लौटें।

यह भी देख लें कि ऐप और Termux एक ही पोर्ट इस्तेमाल कर रहे हैं। डिफ़ॉल्ट `7860` है। अगर आपने ऐप किसी दूसरे पोर्ट के साथ बनाया है, तो Termux की `.env` में भी वही `PORT` सेट करें।

### Android localhost लॉगिन पेज खोलता है या 401/503 लौटाता है

APK के ज़रिए मैनेज किए गए Termux इंस्टॉल localhost को हर इंस्टॉल के अलग निजी सीक्रेट से सुरक्षित करते हैं। Android ऐप अपने-आप ऑथेंटिकेट होता है। उसी फ़ोन के दूसरे ब्राउज़र में `/android-login` खोलें और इस Termux कमांड से दिखने वाली वैल्यू पेस्ट करें:

```bash
cat ~/.marinara-engine/android-secret
```

लोकल `mari` CLI वही फ़ाइल अपने-आप पढ़ती है। 401 का मतलब है कि पेस्ट किया सीक्रेट या ऑथेंटिकेशन चैलेंज ठुकरा दिया गया; `/android-login` दोबारा लोड करें और मौजूदा वैल्यू पेस्ट करें। 503 का मतलब है कि सर्वर को गलत फ़ॉर्मेट वाला सेट किया गया सीक्रेट मिला। `./start-termux.sh` से दोबारा शुरू करें। अगर लॉन्चर बताए कि उसकी सीक्रेट फ़ाइल गलत या खाली है, तो Android ऐप पर लौटें और **Install / Start Marinara** पर टैप करें, ताकि APK इसे फिर से बना सके। इस सीक्रेट को स्क्रीनशॉट या समस्या रिपोर्ट में न डालें।

### Android अपडेट exit status 134 पर रुक जाता है

exit status 134 का मतलब आमतौर पर यह है कि बिल्ड के किसी चरण में Android की मेमोरी खत्म हो गई। नए लॉन्चर से दोबारा अपडेट करें:

```bash
./start-termux.sh
```

फिर भी रुक जाए, तो बाकी Android ऐप बंद करें, Termux दोबारा खोलें, और कमांड फिर चलाएँ।

### Marinara चलते समय Termux बंद या रीस्टार्ट हो जाता है

सर्वर चलने के दौरान लॉन्चर Android wake lock माँगता है और हर सर्वर सेशन को `~/.marinara-engine/logs/` में सेव करता है। अचानक रीस्टार्ट के बाद रिपोर्ट में सबसे नई `server-*.log` फ़ाइल जोड़ें। अगर फ़ाइल के अंत में Marinara या Node का एरर नहीं है, तो संभवतः Android या फ़ोन निर्माता ने सर्वर प्रोसेस के बाहर Termux को बंद किया था।

Android सेटिंग्स में Termux को बैकग्राउंड में चलने दें और उसके लिए बैटरी ऑप्टिमाइज़ेशन हटाएँ। जिन डिवाइस पर Termux:API ऐड-ऑन चलता है, वहाँ वह ऐड-ऑन और `termux-api` पैकेज इंस्टॉल करें, ताकि `termux-wake-lock` उपलब्ध हो। ये सेटिंग्स निर्माता के हर तरह के प्रोसेस किल को नहीं रोक सकतीं, पर आम idle-suspension कारण को हटाती हैं और स्थायी लॉग ऐप के स्तर की विफलताओं के प्रमाण बचाकर रखता है।

### डिपेंडेंसी इंस्टॉल करते समय Android अपडेट की जगह खत्म हो जाती है

बना हुआ Marinara ऐप कई गीगाबाइट का नहीं होता, और Noodle अपने AI मॉडल डाउनलोड नहीं करता। अपडेट के दौरान अस्थायी रूप से बहुत जगह घिरने की वजह आमतौर पर pnpm का डिपेंडेंसी स्टोर और वर्चुअल स्टोर होता है, खास तौर पर कई रिलीज़ के बाद या बीच में रुके ज़बरदस्ती वाले रीइंस्टॉल के बाद।

मौजूदा लॉन्चर पुरानी रिलीज़ के बचे हुए पैकेज हटा देता है और एक ही अपडेट के लिए डिपेंडेंसी स्टोर बार-बार नहीं बनाता। अगर किसी पुराने लॉन्चर ने डिवाइस पहले ही भर दी है, तो दोबारा कोशिश करने से पहले लॉन्चर अपडेट करें और उसका बिना इस्तेमाल वाला कैश खाली करें:

```bash
cd Marinara-Engine
git pull --ff-only
pnpm store prune
./start-termux.sh
```

`data`, `storage` या `marinara-engine.db` न हटाएँ; इन जगहों पर आपकी चैट और सेटिंग्स हो सकती हैं। कमांड फिर भी रुक जाए, तो `Installing dependencies` से शुरू होने वाली लाइनें कॉपी करें और रिपोर्ट में फ़ोन की खाली जगह और मेमोरी के आँकड़े भी दें।

### Android पर Stable और Staging के बीच बदलने पर इन-ऐप अपडेट फ़ेल होता है

चैनल बदलने (Stable ↔ Staging) पर लगभग पूरी डिपेंडेंसी दोबारा इंस्टॉल होती है, और Termux के धीमे स्टोरेज पर इसमें सामान्य अपडेट से कहीं ज़्यादा समय लग सकता है। अब इन-ऐप अपडेटर Android पर हर चरण को अतिरिक्त समय देता है, इसलिए जो चैनल स्विच पहले सिर्फ़ `Update failed: Command failed: corepack pnpm ... install` लिखकर रुक जाता था, वह अब पूरा होना चाहिए।

अगर अपडेट फिर भी फ़ेल हो, तो एरर अब उस चरण का नाम बताती है जो फ़ेल हुआ, और उसके आउटपुट का आखिरी हिस्सा भी दिखाती है। उस संदेश को पढ़ें: डिपेंडेंसी या लॉकफ़ाइल की असली गड़बड़ी वहीं लिखी होती है। एरर के संकेत में दी गई मैन्युअल कमांड से Termux में अपडेट हाथ से भी चलाया जा सकता है, या पहले जगह खाली कर सकते हैं:

```bash
cd Marinara-Engine
pnpm store prune
./start-termux.sh
```

### Noodle में `Etc/Unknown` दिखता है या शेड्यूल गलत टाइमज़ोन इस्तेमाल करते हैं

Conversation शेड्यूल के लिए Conversation Chat Settings या किसी कैरेक्टर का शेड्यूल एडिटर खोलें और **Schedule timezone** चुनें। यह चुनाव हर Conversation चैट पर लागू होता है, बैकग्राउंड में चलने वाले ऑटोनॉमस संदेशों पर भी, और **Use device** से इसे रीसेट किया जा सकता है।

Noodle या सर्वर के उन जॉब के लिए जिन पर Conversation का ओवरराइड नहीं है, `.env` से कोई भी खाली `TZ=` लाइन हटाएँ और Marinara दोबारा शुरू करें, ताकि सर्वर होस्ट का टाइमज़ोन ले सके। होस्ट का फ़ॉलबैक खुद चुनना हो, तो कोई सही IANA नाम सेट करें, जैसे `TZ=Europe/Warsaw` या `TZ=America/New_York`। मौजूदा रिलीज़ खाली वैल्यू को सेट न होना मानती हैं, फिर भी Node की टाइमज़ोन स्थिति और शेड्यूल किए गए जॉब ठीक से दोबारा बनने के लिए रीस्टार्ट ज़रूरी है।

### वॉल्यूम माउंट पर कंटेनर की permission denied एरर

अगर Docker या Podman कंटेनर डेटा वॉल्यूम पर परमिशन एरर के साथ फ़ेल हो:

- अपडेट के बाद नेम्ड वॉल्यूम के लिए नई इमेज खींचें और `docker compose pull && docker compose up -d` से दोबारा शुरू करें। आधिकारिक इमेज शुरू होते समय ओनरशिप ठीक कर देती है।
- बाइंड माउंट के लिए होस्ट फ़ोल्डर को यूज़र और ग्रुप ID `1000` के लिए लिखने योग्य बनाएँ, या उसकी जगह नेम्ड वॉल्यूम इस्तेमाल करें।
- Fedora या RHEL जैसे SELinux वाले सिस्टम पर वॉल्यूम माउंट में `:Z` सफ़िक्स जोड़ें।

### Raspberry Pi 4 पर Lite कंटेनर क्रैश होता है

अगर Raspberry Pi 4 या उस जैसे किसी ARM डिवाइस पर lite कंटेनर हर AI रिक्वेस्ट भेजते ही रीस्टार्ट हो जाए, तो एग्ज़िट कोड देखें। Exit 132 या SIGILL कुछ ARM चिप पर lite इमेज के Node बिल्ड की एक जानी-पहचानी अपस्ट्रीम गड़बड़ी की ओर इशारा करता है। SIGILL का मतलब है कि प्रोग्राम ने ऐसा निर्देश चलाया जो CPU चला ही नहीं सकता।

सामान्य (non-lite) इमेज पर इसका असर नहीं है। जब तक अपस्ट्रीम फ़िक्स नहीं आता, उस डिवाइस पर सामान्य इमेज इस्तेमाल करें। जिन lite इमेज पर यह दिक्कत मालूम है, उनमें `1.5.7-lite` और `1.5.8-lite` शामिल हैं। आखिरी बार Marinara Engine 2.2.0 पर जाँचा गया।

### Addons में External Extensions नहीं दिखता

यह सेक्शन जान-बूझकर तब तक छिपा रहता है जब तक दोनों सुरक्षा गेट न खुल जाएँ:

1. होस्ट की `.env` में `ENABLE_EXTERNAL_EXTENSIONS=true` सेट करें।
2. कॉन्फ़िगरेशन वॉचर के लिए करीब दो सेकंड रुकें, फिर **Settings → Advanced → Danger Zone** खोलें, डेटा मिटाने वाले कंट्रोल से नीचे स्क्रॉल करें, और **Allow third-party extension imports** चालू करें।

अगर Danger Zone वाला स्विच काम ही न कर रहा हो, तो या तो होस्ट का फ़्लैग अब भी false है, या ऐप ने बदलाव देखा नहीं है। जाँच लें कि आपने वही चालू `.env` पथ बदला है जो [सर्वर कॉन्फ़िगरेशन](CONFIGURATION.md) में बताया गया है। Docker पर वह आमतौर पर `/app/data/.env` होता है।

जब तक कोई एक गेट बंद है, बाहरी, पुराने, प्रोफ़ाइल से इंपोर्ट किए गए, हाथ से सेव किए गए और अनजान सोर्स वाले एक्सटेंशन रिकॉर्ड न दिखते हैं, न चल सकते हैं। गेट दोबारा खोलने पर वे अपने आप चालू नहीं होते।

### इंपोर्ट किया गया ब्राउज़र एक्सटेंशन दिखता तो है, पर काम नहीं करता

**Settings → Addons → External Extensions** में एक्सटेंशन खोलें और **Requested access** देखें। जो पुराने पैकेज बिना कैपेबिलिटी घोषणा के `marinara.extension` v1 फ़ॉर्मैट इस्तेमाल करते हैं, उनमें **Full page access** दिखना चाहिए। सिर्फ़ उसी हैश को मंज़ूरी दें जिसे आपने खुद देखा हो और जिस पर भरोसा हो।

अगर कोई पुराना पैकेज दोबारा एक्सपोर्ट करते समय कैपेबिलिटी की खाली लिस्ट के साथ आया हो, तो Marinara उसे सुरक्षित सैंडबॉक्स एक्सटेंशन मानता है; वहाँ DOM पर निर्भर कोड काम नहीं करेगा। उसके मेनिफ़ेस्ट में `full_page_access` तभी जोड़ें जब आप समझते हों कि उस कोड को पूरे Marinara पेज, ब्राउज़र स्टोरेज, नेटवर्क API और सेम-ऑरिजिन सेशन तक पहुँच मिल जाएगी।

फ़ुल पेज वाला एक्सटेंशन बंद करने के बाद अगर कोई टूलबार आइटम, ओवरले, लिसनर या दिखने वाला बदलाव बचा रह जाए, तो Marinara दोबारा लोड करें। सफ़ाई पूरी होगी, इसकी गारंटी नहीं, क्योंकि पेज का कोड Marinara की ट्रैक की जाने वाली कम्पैटिबिलिटी API के बाहर भी असर छोड़ सकता है।

### कोई Server Extension कहता है कि सपोर्टेड सैंडबॉक्स उपलब्ध नहीं है

Server Extensions सिर्फ़ macOS Seatbelt या Linux Bubblewrap के साथ चलते हैं। Linux होस्ट पर `bwrap` इंस्टॉल करें, फिर Marinara दोबारा शुरू करें। Windows, Android और बाकी असमर्थित होस्ट, Server Extension को मुख्य सर्वर प्रोसेस में चलाने के बजाय जान-बूझकर चलाने से मना कर देते हैं। Browser Extensions फिर भी अपना ओपेक-ऑरिजिन Worker सैंडबॉक्स इस्तेमाल कर सकते हैं।

## ज़्यादा मदद पाना

अगर अब भी मदद चाहिए, तो पहले पूरी जानकारी जुटा लें।

1. **Settings** > **Advanced** > **Message Tools** खोलें और **Debug mode** चालू करें। इससे प्रॉम्प्ट और जवाब के पेलोड सर्वर कंसोल में लॉग होते हैं, जिन्हें आप साझा कर सकते हैं।
2. अपना ऑपरेटिंग सिस्टम, अपना Node.js वर्ज़न, और सर्वर कंसोल से पूरी एरर का टेक्स्ट नोट करें।

डीबग आउटपुट साझा करने से पहले उसमें से API कुंजियाँ, एक्सेस टोकन, एडमिन सीक्रेट, निजी प्रॉम्प्ट और निजी चैट की सामग्री हटा दें।
