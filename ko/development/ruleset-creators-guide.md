# 규칙 집합 제작자 가이드

이 가이드에서는 참고 페이지를 열기 전에 자신의 탁상 게임 시스템에 맞는 **Game Mode**(게임 모드) 규칙 집합을 계획하는 방법을 설명합니다. 규칙 집합의 각 부분이 어떻게 맞물리는지, 어떤 선택이 가장 중요한지, 서로 매우 다른 16개 시스템을 변환하며 무엇을 배웠는지 다룹니다. 키별 참고 자료는 [Game Mode 규칙 집합 작성하기](../extending/writing-rulesets.md)에서 시작하며, 아래 각 절에는 요약한 내용을 자세히 설명하는 페이지의 링크가 있습니다.

규칙 집합은 시스템의 작동 방식을 Marinara Engine에 알려 주는 JSON 파일 하나(또는 파일 패키지)입니다. 그러면 Engine이 모든 판정을 굴리고 시트의 모든 변경을 적용하며, 정해진 규칙에 따라 전투 전체를 진행할 수 있습니다. 규칙 집합에는 코드가 없으므로, Engine이 이미 아는 메커니즘의 빈칸을 채우며 설계합니다. Engine이 모르는 메커니즘은 Engine 기능 요청으로 제안해야 합니다.

아래 각 키에는 그 키가 추가된 Capability API 마이너 버전을 적었습니다. 해당 키를 사용하는 패키지는 그 마이너 버전 이상을 선언합니다([버전 관리, 시험과 게시](#versioning-testing-and-publishing) 참고).

혼동하기 쉬운 용어가 두 가지 있습니다.

- **Classic과 Tactical**은 _전투 스타일_입니다. 전열과 후열이 있는 메뉴 전투, 또는 보드 위의 전투를 뜻합니다. 규칙 집합의 유무와 관계없이 모든 게임은 둘 중 하나로 플레이합니다.
- **Marinara 자체 규칙**은 규칙 집합이 없는 게임에서 사용하는 규칙입니다. 규칙 집합은 이를 대체합니다.

## 규칙 집합의 구성

규칙 집합은 최대 512 KB의 JSON 파일 하나이며, 가져올 때 전체를 검증합니다. 더 큰 규칙 집합은 카탈로그를 나눠 패키지로 만듭니다. 사용하는 주사위에 가장 가까운 예제를 복사해 시작하세요.

- [`ember-roads.json`](../examples/rulesets/ember-roads.json): 2d6에 능력치를 더합니다.
- [`gravewatch.json`](../examples/rulesets/gravewatch.json): d10 풀입니다.
- Marinara-Agents의 완전한 [5e (SRD 5.1) 패키지](https://github.com/Pasta-Devs/Marinara-Agents/tree/staging/packages/ruleset-5e-2014).

자동 완성과 오타 검사를 사용하려면 `$schema` 줄로 편집기에 [JSON Schema](../extending/ruleset.schema.json)를 지정하세요.

| 키 | 내용 | 참고 자료 |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schemaVersion`, `id`, `version`, `name`, `edition`, `license` | 식별 정보. `version`은 변경을 게시할 때마다 올리는 정수입니다 | [규칙 집합 작성하기](../extending/writing-rulesets.md) |
| `coverage` | 규칙 집합의 지원 범위(판정, 전투 등)와 설정 마법사에 표시할 한 줄 요약 | [규칙 집합 작성하기](../extending/writing-rulesets.md) |
| `resolution` | 판정을 굴리는 방법. 다섯 종류 중 하나와 결과 구간, 자원 소비와 재굴림 | [판정](../extending/ruleset-checks.md) |
| `sheet` | 능력치, 기술, 필드, 목록, 실시간 풀, 트랙, 상태, 부상 트랙, 페널티, 마이그레이션 | [시트](../extending/ruleset-sheets.md) |
| `party`, `clocks` | 공유 파티 시트(조직, 함선, 이야기 점수)와 진행 시계 | [시트](../extending/ruleset-sheets.md) |
| `rests` | 휴식 종류별로 회복하고 지우는 내용 | [시트](../extending/ruleset-sheets.md) |
| `gm`, `gmReference` | Game Master 텍스트, 캐릭터별 요약, 상대를 조작하는 주체, 최대 16,000자의 규칙 참고 자료 | [시트](../extending/ruleset-sheets.md) |
| `catalogs` | 기성 항목(주문, 재능, 생물). 각 항목에 선택적 `mechanics` 블록을 둘 수 있습니다 | [카탈로그](../extending/ruleset-catalogs.md), [메커니즘](../extending/ruleset-mechanics.md), [빌더](../extending/ruleset-character-builder.md) |
| `items` | 분류, 무기, 방어구, 탄약, 전리품, 돈, 시작 장비, 시장 | [아이템](../extending/ruleset-items.md) |
| `battle` | 시트의 숫자를 Marinara 자체 Classic과 Tactical 전투에 빌려줍니다 | [전투](../extending/ruleset-combat.md) |
| `combat` | 도감, 보드, 반응과 겨루기를 갖추고 자체 규칙으로 전투 전체를 진행합니다 | [전투](../extending/ruleset-combat.md) |
| `layers` | 플레이어가 한 게임에 켜는 변형(Low magic, Hard winter) | [레이어와 번역](../extending/ruleset-layers-and-translations.md) |

**ID.** 규칙 집합 ID에는 소문자, 숫자, 단일 하이픈을 씁니다(`ember-roads`). 시트 안의 ID에는 소문자, 숫자, 밑줄을 쓰며 문자로 시작합니다(`grit_max`). 저장된 캐릭터, 카탈로그를 빌려 쓰는 다른 규칙 집합, Experience 오버레이가 모두 이 ID를 가리키므로 게시한 뒤에는 ID를 유지하세요.

**프롬프트에 안전한 텍스트.** 모델에 전달되는 모든 것(이름, 라벨, Game Master 텍스트)은 한 줄이며, 대괄호와 `{{`, `}}`를 포함하지 않습니다.

**패키지.** 파일 하나에 담기에는 너무 큰 규칙 집합은 `<id>.ruleset.json`으로 배포합니다. 매니페스트, `ruleset.json`, 최대 12개의 `catalogs/<id>.json` 파일(각 2 MB), 최대 40개의 번역을 모두 base64로 담습니다. zip은 거부됩니다. Pixelforge 같은 규칙 집합 편집기가 이 파일을 만듭니다. 매니페스트는 규칙 집합에 필요한 Capability API 마이너 버전을 선언합니다.

**규칙 집합의 분류 위치.** 가져온 파일은 `local/<id>`, GitHub 저장소의 것은 `<owner>/<id>`가 되며, 공식 카탈로그의 것은 접두사 없는 ID를 유지합니다. 두 작성자가 각자 `v20`을 게시해도 충돌하지 않습니다.

## 판정, 주사위와 시트

가장 먼저 내릴 가장 큰 결정은 `resolution.kind`입니다. 나머지 모든 것을 이 종류에 따라 읽기 때문입니다. Game Master는 기술과 난이도만 지정합니다. Engine이 주사위를 굴리고 시트 값으로 계산한 뒤 모델에 결과를 알려 주므로, 모델에 계산을 요구하는 Game Master 텍스트를 쓰지 마세요.

| 종류 | 굴리는 방법 | 적합한 시스템 |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `dice-sum` | 주사위를 굴리고 시트 숫자를 더해 난이도 이상을 얻습니다. 사용자 지정 눈, 계속 이어 굴리기와 폭발 주사위를 지원합니다 | d20 게임, 2d6에 능력치를 더하는 시스템, Fate(4dF의 눈을 −1/0/+1로 정의), Rolemaster |
| `dice-pool` | 시트에서 읽은 개수만큼 주사위를 던져 목표에 도달한 개수를 셉니다. 목표는 시트에서 읽거나 판정마다 정할 수 있으며, 이상이나 이하로 비교합니다 | World of Darkness, Exalted, Shadowrun 계열, Lasers & Feelings |
| `dice-highest` | 풀을 던져 가장 높은 주사위를 읽거나 높은 주사위 몇 개를 더합니다. 주사위가 없는 경우의 규칙과 두 번째 "어둠" 주사위 묶음을 지원합니다 | Blades in the Dark와 기타 Forged in the Dark 게임, Trophy Dark |
| `roll-against` | 시트 숫자 이하(또는 이상)로 굴립니다 | Call of Cthulhu, GURPS, BRP, 올드스쿨의 X-in-6 |
| `symbol-pool` | 서술형 주사위를 구성하고 승급한 뒤 반대 기호를 상쇄합니다 | Genesys와 유사한 시스템 |

그다음 시스템에 필요한 것을 추가하세요. 모두 [규칙 집합 판정](../extending/ruleset-checks.md)에 설명되어 있습니다.

- **결과 구간**(`resolution.outcomes`, 1.135): 차이나 합계에 따라 이름 붙은 결과 둘부터 여덟까지를 정합니다. 성공 정도, "대가가 따르는 성공", 어려운 성공과 극단적 성공 등이 해당합니다. 각 구간에는 실제 플레이에서 무엇을 뜻하는지 Game Master에게 알려 주는 한 줄을 넣을 수 있습니다. 변환한 시스템 전반에서 가장 널리 필요했던 기능입니다.
- **자체 방식으로 굴리는 판정**(`resolution.overrides`, 1.140): 일부 기술에 다른 주사위를 씁니다. 도둑 기술은 d100, Open Doors는 d6로 굴리는 d20 게임의 경우 등입니다.
- **자원 소비로 굴림 바꾸기**(`resolution.spend`)와 무료 재굴림(`resolution.reroll`): 성공을 얻기 위한 의지력, 행운, 영웅 점수 등입니다. `perCheck`는 한 굴림에 살 수 있는 양을 제한하므로, 풀이 가득 차 있어도 확실한 성공을 살 수는 없습니다.
- **굴림을 바꾸는 부적**: 캐릭터가 고른 카탈로그 항목에 `mechanics.check`를 두고, 그 항목 자체의 비용으로 지불합니다.

**판정이 아직 할 수 없는 것.** 대항 풀(두 사람이 굴린 결과를 비교)과 OpenD6처럼 와일드 주사위가 있는 합산 풀입니다. 둘 다 Engine 안에 새 판정 종류가 필요합니다. 시스템에 이 중 하나가 필요하다면 계산 과정을 보여 주는 굴림 몇 개와 함께 Engine 저장소에 기능 요청을 여세요. 그 굴림이 테스트가 됩니다.

**시트**([규칙 집합 시트](../extending/ruleset-sheets.md))에는 능력치, 기술, 필드, 목록과 파생 값, 그리고 플레이 중 Engine이 바꾸는 실시간 상태가 들어갑니다.

- **풀**: 체력, 의지력, 모트, 주문 슬롯 등이며 시트 명령과 휴식으로 소비하고 회복합니다.
- **트랙**: 스트레스, Ruin, XP 등이며 가득 찰 때 발동하는 효과가 있습니다.
- **부상 트랙**: 체력을 숫자 하나 대신 이름 붙은 단계나 번호가 있는 칸으로 나타내며, 굴림에 페널티를 줍니다.
- **실시간 상태**: 형태, 자세, 아니마 등이며 유지되는 동안 굴림을 바꿀 수 있습니다.
- **파티 시트와 시계**: 조직, 함선, 공유 이야기 점수와 4, 6, 8칸의 진행 시계입니다.

Game Master는 Engine이 자동으로 가르치는 시트 명령으로 시트를 바꾸며, 규칙 집합에서 정한 ID를 사용합니다. 따라서 `gm.sheetGuidance`에서 명령을 설명하지 않습니다. 영구 성장(XP, 점 추가, 레벨 상승)은 카탈로그 시트 명령을 사용합니다. [규칙 집합 카탈로그](../extending/ruleset-catalogs.md)를 참고하세요.

**캐릭터 만들기.** [캐릭터 빌더](../extending/ruleset-character-builder.md)는 정의한 단계에 따라 플레이어를 안내합니다. 출신과 클래스, 점수(굴리기, 구매, 배정), 숙련, 주문, 장비와 시작 화폐를 다루며, 규칙에 맞는지 검사하고 공유 파티도 만듭니다. 카탈로그는 `from`(1.220)으로 다른 설치된 규칙 집합의 카탈로그를 빌릴 수 있으므로, 5e 변형은 SRD의 생물과 주문을 복사하는 대신 재사용할 수 있습니다.

**Game Master 텍스트.** `gm.checkGuidance`와 `gm.sheetGuidance`(각 1,500자)는 매 턴 전송되므로 간결하게 쓰세요. `gm.worldGuidance`는 세계를 만들 때 한 번 읽습니다("화약 없음", "마법은 드묾"). `gmReference`는 고정된 시스템 프롬프트에 최대 16,000자의 더 자세한 규칙을 담습니다. `gm.sheetSummary`는 모델이 캐릭터별로 볼 내용을 고르며, 그 안의 모든 것은 매 턴 토큰을 사용합니다. 전부 직접 쓴 말로 작성하고 규칙서 텍스트를 복사하지 마세요.

## 전투

규칙 집합은 세 가지 깊이 중 하나로 전투에 참여합니다. 얕게 시작한 뒤 나중에 더 깊이 들어갈 수 있습니다. 시스템의 정체성이 전투에 얼마나 담겨 있는지에 따라 고르세요.

| 깊이 | 작성할 내용 | 전투에서 일어나는 일 | 적합한 용도 |
| -------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 없음 | `battle`이나 `combat` 블록 없음 | Marinara 자체 Classic 또는 Tactical 전투가 전투 참가자를 직접 구성합니다. 시트는 바뀌지 않습니다 | 전투를 이야기로 다루는 서사 중심 시스템(Fate, Blades, Trophy) |
| 시트 빌려주기 | `battle` 블록: 체력 풀, 선택적 에너지 풀, 주문 슬롯, 최대 8개의 기술 목록 | Marinara의 계산과 주사위를 쓰되, 시작 체력은 시트의 체력 비율과 같으며 결과를 시트에 다시 씁니다 | 결과를 지속시키고 싶은 가벼운 시스템 |
| 자체 규칙 | `combat` 블록 | 자체 주사위로 모든 공격, 내성과 겨루기를 해결합니다. 상대는 도감이나 위협 척도에서 나오며, 모든 비용은 발생할 때마다 시트에 기록합니다 | 세부 규칙이 많은 전술 시스템(5e, Pathfinder, Storyteller, Genesys) |

**`combat` 블록**은 Engine이 아는 세 종류 중 하나의 매개변수를 정합니다. `attack-vs-defense`(방어 수치에 맞서 굴리는 주사위), `dice-pool`(성공 수를 세는 자체 풀), `symbol-pool`(자원 소비가 있는 서술형 주사위, 1.382)입니다. 핵심은 `health`(감소하는 풀, 표시하는 부상 트랙, 또는 채워지는 일반 트랙, 1.383), `defense`, `initiative`, `attackRoll`, 행동 `economy`, 그리고 `attacks`와 `abilities`가 되는 목록입니다. 작은 완성 블록은 약 25줄입니다. [규칙 집합 전투](../extending/ruleset-combat.md#combat-a-fight-your-own-rules-resolve)의 Ember Roads 블록이 좋은 템플릿입니다.

핵심 요소 외에도 시스템에 필요한 것을 추가하세요.

- **상태**: 정해진 목록의 효과를 사용합니다(방어, 공격 굴림, 내성, 겨루기, 속도, 최대 체력, 주고받는 피해).
- **내성**, 집중, 죽어 가는 규칙, **창**에서 대기하는 반응(항목은 `used`, `aimed`, `hit`, `harmed`, `falls`, `turn-start`를 기다릴 수 있음).
- 붙잡기, 밀치기와 벗어나기를 위한 **겨루기**.
- **생물**: 전투가 읽는 도감 카탈로그이며 능력치 블록, 행동, 감각과 주문 시전을 담습니다. **위협 척도**가 있으면 Game Master가 한 전투에 쓸 상대를 만들 수 있으며, `combat.threat.budget`(1.803)은 난이도별 경험치 예산에 맞춰 조우를 구성합니다.
- 카탈로그 항목의 **항목 메커니즘**: 범위 모양, 지속 영역, 벽, 소환, 치료와 감각입니다. [규칙 집합 항목 메커니즘](../extending/ruleset-mechanics.md)을 참고하세요.

**Classic 또는 Tactical.** 자체 규칙 전투에 보드가 생기려면 `combat`이 `distance`(`label`, `perCell`)를 선언하고 시트나 생물이 이동을 제공해야 합니다. 없으면 Tactical 게임에서도 머릿속으로 상황을 그리며 자체 규칙을 플레이합니다. 규칙이 위치(범위, 근접 거리, 측면 공격)에 의존한다면 `"styles": ["tactical"]`(1.379)을 설정해 해당 규칙 집합을 쓰는 모든 게임에 보드를 제공하세요.

**생물 그림**은 규칙과 별개입니다. [생물 팩](../extending/writing-creature-packs.md)(`.creatures.json`, Pixelforge에서 가장 쉽게 제작)은 생물 ID를 맞춰 도감의 생물을 Tactical 보드에 그립니다. 그림이 없는 생물은 토큰으로 남습니다.

**알려진 한계**는 [아직 지원하지 않는 것](../extending/ruleset-combat.md#not-yet)에 나와 있습니다. 변환 중 가장 자주 부딪힌 것은 대항 방어 굴림(Dodge와 Fight Back, Parry와 Block), 명중 부위, 진영별 우선권, 반응에 대한 반응이었습니다. Game Master는 Engine의 전투 진행에 맞춰 이 부분을 서술합니다.

## 전투 AI: 사고방식, 성향과 상대를 조작하는 주체

Engine은 다른 사람이 조작하지 않는 모든 상대와 AI 동료를 턴마다 모델을 호출하지 않고 조작합니다. 특정 규칙 집합에 얽매이지 않습니다. 5e뿐 아니라 Storyteller, Exalted, 올드스쿨, Call of Cthulhu, GURPS와 Genesys 변환으로도 시험했습니다. 아래 키가 하나도 없어도 작동하며, 키를 사용하면 생물이 자기답게 싸웁니다. 모두 [규칙 집합 항목 메커니즘](../extending/ruleset-mechanics.md)에 있고, 설계는 [Game Mode 전투 AI](game-combat-ai.md)에 있습니다.

| 키 | 제어하는 내용 | API |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| 생물의 `mind`, 또는 능력치를 기준으로 한 `combat.minds` 등급 | 사고의 정도: `mindless`, `instinct`, `cunning`, `tactical`, `genius`. 야수는 기본적으로 본능에 따라 행동하고, 구조물과 점액류는 사고하지 않습니다 | 1.761 |
| `behavior.temperament` | 싸우는 방식: reckless(무모함), cautious(신중함), opportunistic(기회주의), protective(보호), supportive(지원), disciplined(절제), cowardly(겁 많음), patient(인내), methodical(체계적), coordinated(협력) | 1.763 |
| 이야기에서만 지정하는 성향 | `fanatical`(결코 사기가 꺾이지 않음), `arrogant`(전력을 아끼며, 전설급이고 불리해지면 공중으로 올라감), `territorial`, `cruel`, `honourable`(파티에 Surrender를 제공), `hungry`(희생자를 끌고 감). 무작위로 배정하지 않습니다 | 1.778 ~ 1.784 |
| `behavior.role` | bruiser(근접 공격수), bulwark(방벽), skirmisher(기동전투원), marksman(명사수), spellcaster(주문 시전자), supporter(지원자), controller(제어자), `solo`(1.776). 지정하지 않으면 능력을 바탕으로 배정합니다 | 1.763 |
| `behavior.targets`, `opens`, `pack`, `ambush` | 대상 우선순위, 첫 행동, 무리 전술, 숨어 기다리기 | 1.763 |
| `behavior.shifts` | 체력이 크게 줄거나, 아군이나 지휘자가 쓰러지거나, 궁지에 몰렸을 때 바뀌는 성향 | 1.779 |
| `combat.morale` | 적이 언제 어떻게 용기를 시험하는지(점수 이하로 2d6 굴리기 또는 내성), 누가 항복하는지 | 1.762, 1.775 |
| `gm.opposition: "game-master"` | Game Master가 Engine이 제공하는 적법한 선택지 중에서 골라 모든 상대를 조작하며, 필요하면 Engine이 대신합니다 | 1.774 |

`behavior`는 전체 `combat` 블록, 생물 유형, 개별 능력치 블록에 둘 수 있으며, 각각 앞선 값을 덮어씁니다. SRD의 예: 늑대 `{"targets": ["wounded"], "pack": true}`, 고블린 `{"temperament": "cowardly", "targets": ["weakest"]}`, 구울 `{"ambush": true}`.

**보드 전투에서 AI에 필요한 것**은 `combat.distance`, 이동(`combat.economy.movement` 또는 생물의 `speed`), 원거리 공격과 무기 행의 `range`, 영역을 타격하는 모든 것의 `area`입니다. 사거리가 없으면 권총도 팔이 닿는 거리에서만 작동합니다. 범위가 없으면 AI는 흩어지지 않습니다.

**서사 중심 시스템.** 기본적으로 Engine은 일반 적을, Game Master는 보스를 조작합니다. 상대를 피해보다 이야기로 다루는 시스템(Fate, Blades, Trophy, Lasers & Feelings)에서는 `gm.opposition: "game-master"`로 모델이 모든 상대를 그 인물답게 연기하게 할 수 있습니다. 플레이어가 설정 중 "GM directs bosses"(GM이 보스를 지휘함)를 켠 경우에만 적용됩니다. 이것이 전투 중 모델 호출에 대한 동의이기 때문입니다.

**전투 블록이 없어도** Classic과 Tactical 전투에서 사기를 사용합니다. 보스가 아니고 사고할 수 있는 적은 각자 사고방식과 성향에 따라 2 ~ 12의 점수를 얻으며, 사고하는 적은 항복할 수 있습니다. 조우 작성자는 한 편의 `leader`를 표시할 수 있습니다.

**파티 성향.** 게임을 시작할 때 각 파티원은 Description(설명)을 바탕으로 성향을 받으며, 세션 종료 검토에서 이야기상의 이유가 있을 때만 바뀝니다. AI 동료는 그 성향에 따라 싸웁니다. 규칙 집합이 이를 설정하지는 않지만 Game Master 텍스트에서 활용할 수 있습니다.

## 레이어, 오버레이와 마이그레이션

세 메커니즘은 규칙 집합을 포크하지 않고 바꿉니다. 플레이어가 고르는 변형에는 레이어를, 한 모험에 속하는 콘텐츠에는 오버레이를, 시트 구조를 바꿀 때는 마이그레이션을 사용하세요.

**레이어**(`layers`, 최대 12개)는 New Game 마법사의 토글이며, 해당 게임의 수명 동안 고정됩니다. 레이어는 범위를 좁히거나 텍스트를 추가할 수만 있고, 규칙을 추가할 수는 없습니다.

- Game Master 지침 덧붙이기(`gm.guidance`, `gm.worldGuidance`, 레이어당 4,000자);
- 열거형 필드의 값 제거, 난이도 사다리 교체, 선언한 필터로 카탈로그 항목 숨기기;
- 화폐 제거(1.64), 시장 판매자 제거, 아이템을 판매하지 않는 것으로 표시, 전리품 표 교체(1.813);
- 다른 레이어와의 `conflicts` 선언.

레이어는 필드, 값, 기술, 풀, 휴식, 판매자나 전리품 표를 추가하거나, 판정 종류를 바꾸거나, 전투 숫자를 건드릴 수 없습니다. 레이어가 제거한 것도 캐릭터는 계속 보유합니다. SRD의 **Low magic** 레이어가 좋은 본보기입니다. 주문을 5레벨까지로 제한하고, 고급보다 높은 등급의 아이템을 더 드물게 하고 보통 판매하지 않게 하며, 강한 마법 생물을 무작위 조우에서 제외하고, 세계 지침에서 Game Master에게 마법이 드문 이유를 설명하도록 요청합니다. 다른 작성자도 이를 복사할 수 있습니다. 다른 사람의 규칙 집합을 위한 레이어는 아직 지원하지 않습니다.

**오버레이**(1.355)는 Experience가 켜져 있는 동안 그 Experience의 지도 팩이 규칙 집합에 생물, 상태, 시트 상태, 아이템과 트랙(1.367)을 추가하게 합니다. 모험 전용 괴물과 전리품은 기본 규칙 집합 대신 오버레이에 두세요. 기존 ID를 재사용하거나 규칙 집합에 맞지 않는 오버레이는 통째로 버립니다. 이것도 ID를 유지해야 하는 이유입니다. 참고 자료: [규칙 집합 오버레이](optional-agent-packages.md#capability-api-1355-ruleset-overlays).

**마이그레이션**(`sheet.migrations`, 1.77)은 필드 이름을 바꾸거나, 레벨 하나를 클래스별 레벨로 나누거나, 풀을 나눌 때 저장된 캐릭터를 어떻게 옮길지 정합니다. 추가만 할 때는 마이그레이션이 필요하지 않습니다. 시트 구조가 바뀌면 `sheet.version`을 올리세요. 참고 자료: [레이어, 번역과 마이그레이션](../extending/ruleset-layers-and-translations.md).

## 번역

규칙 집합은 영어로 작성하고, 다른 언어는 각각 별도 번역 파일로 배포하세요(1.811). 번역은 표시 전용입니다. 규칙, 시트 명령, Game Master에게 전달하는 모든 것은 영어로 유지되므로 번역이 게임을 망가뜨릴 수 없습니다.

번역은 영어 문자열을 한 글자도 바꾸지 않고 키로 사용합니다.

```json
{
  "_meta": { "locale": "ru", "direction": "ltr" },
  "package": { "name": "5e (SRD 5.1)" },
  "ruleset": { "Prone": "Лежащий", "Fire Bolt": "Огненный снаряд", "Goblin": "Гоблин" }
}
```

- 언어 코드는 Engine 자체 코드와 일치합니다(`ru`, `pt-BR`, `zh-Hans`). 없거나 빈 문자열은 영어로 표시하며, `pt-BR`은 먼저 `pt`로 대체를 시도합니다.
- **공유 패키지 파일 안에서는** `locales/<language>.json`에 넣으며, 최대 40개이며 각 8 MB입니다. 가져오기는 Engine의 현재 언어만 보관합니다. 언어를 바꾸려면 언어를 변경한 뒤 다시 가져오세요.
- **공식 카탈로그에서는** 각 언어가 별도 팩인 `<id>-<version>.<language>.json`이며, 카탈로그 항목의 `locales` 아래 URL, sha256, 크기, 번역한 스토어 이름과 설명을 기재합니다. Engine은 현재 언어의 팩만 다운로드하며, 언어가 바뀌면 교체합니다. SRD의 11개 언어를 한 파일에 모두 담았을 때 다운로드 크기가 7 MB에서 34 MB로 늘어났기 때문에 팩을 분리합니다.
- 번역을 고쳐도 새 `version`은 필요하지 않습니다.

SRD 패키지는 이 방식으로 11개 언어를 배포하므로 본보기로 삼으세요. 참고 자료: [번역](../extending/ruleset-layers-and-translations.md#translations).

## 5e (SRD 5.1) 패키지: 전체 규모의 예제

Marinara-Agents의 [ruleset-5e-2014 패키지](https://github.com/Pasta-Devs/Marinara-Agents/tree/staging/packages/ruleset-5e-2014)는 이 페이지의 거의 모든 기능을 사용하므로, 키의 실제 사용례를 보고 싶을 때 참고하세요. 본보기로 삼을 만한 점은 다음과 같습니다.

- **구성**: `ruleset.json`과 `catalogs/` 아래 카탈로그별 파일(생물, 주문, 마법 아이템 등)을 `.ruleset.json` 패키지로 만듭니다. README와 MODELING.md는 각 규칙을 어떻게 모델링했는지 설명합니다.
- **라이선스**: `license` 아래 CC BY 4.0 저작자 표시와 "제휴 관계 없음" 문구를 넣으며, 어디에도 상표로 등록된 제품 이름을 쓰지 않습니다.
- **완전한 전투**: 행동, 보너스 행동, 반응 예산과 집중, Shield와 Counterspell 같은 반응, 보드, 사고방식과 성향이 있는 완전한 생물 도감, 조우 예산을 갖춘 d20 `attack-vs-defense` 블록입니다.
- **빌더**: 종족, 클래스, 굴리거나 구매한 점수, 숙련, 주문과 시작 장비입니다.
- **레이어**(Low magic)와 필요할 때 받는 팩으로 제공하는 **11개 번역**.
- **고정된 ID**: 다른 규칙 집합이 생물과 주문을 빌려 쓰므로 ID는 바뀌지 않습니다.
- **회귀 테스트**는 변경할 때마다 별도 CI 작업으로 실행됩니다.

시스템이 d20 변형이라면 카탈로그를 복사하는 대신 `from`(1.220)으로 빌리는 방식을 고려하세요.

## 유사 시스템 설계: 변환에서 얻은 교훈

커뮤니티 모음에 있는 16개 시스템을 이 형식으로 변환했습니다. 규칙이 가벼운 이야기 게임부터 Rolemaster까지 포함합니다. 가장 큰 교훈은 이곳의 규칙 집합이 제안에 그치지 않고 실제로 적용된다는 점입니다. Engine이 모든 판정을 굴리고 시트의 모든 변경을 적용하므로, "GM이 처리할 것"으로 남긴 부분은 실제로 처리되지 않습니다. Engine이 맡는 부분과 Game Master가 서술할 부분을 일찍 정하세요.

| 시스템 계열 | 예 | 판정 | 구현에 도움이 된 키 | Game Master에게 맡긴 부분 |
| ------------------ | ----------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 세부 규칙이 많은 d20과 d% | 5e, Pathfinder 2e, Rolemaster | `dice-sum` | 성공 정도를 위한 결과 구간, Rolemaster의 `openEnded`와 `unmodified`, 큰 표를 위한 `gmReference` | Pathfinder의 중첩되지 않는 보너스 유형, 결과 구간을 벗어나는 Rolemaster의 치명타 표 |
| 올드스쿨 | OSE | `dice-sum` | 도둑 기술(d100)과 X-in-6(d6)을 위한 `resolution.overrides`, 2d6 사기 | 진영별 우선권(개별 우선권으로 플레이) |
| 목표 이하 굴림 | Call of Cthulhu 7e, GURPS Lite | `roll-against` | `against`, 보너스와 페널티 `tens` 주사위, 대성공 눈, 어려운 성공과 극단적 성공 구간 | 대항 Dodge, Fight Back, Parry, GURPS 명중 부위 |
| Storyteller 풀 | V20, W20, Exalted 3e, Exalted WoD | `dice-pool` | 페널티가 있는 부상 트랙, 실시간 상태(형태, 아니마), 1이 성공을 상쇄하지 않도록 하는 재정의, 풀 기반 `combat` 블록 | 항목으로 작성하지 않은 범위 Discipline과 Gift |
| Forged in the Dark | Blades in the Dark, Trophy Dark | `dice-highest` | `keep`, `zeroDice`, `dark` 주사위 묶음, 구간(6 / 4 ~ 5 / 1 ~ 3), `onFull`이 있는 트랙, 시계, 조직을 위한 파티 시트 | `gm.opposition: "game-master"`를 통한 전투 |
| 태세 풀 | Lasers & Feelings, 자체 제작 게임 | `dice-pool` | 시트에서 읽는 `target`, `stances`(미만 또는 초과), 정확한 일치를 위한 `exact`, 함선을 위한 파티 시트 | 이야기로 다루는 전투 |
| Fate | Fate Core | `dice-sum` | 4dF용 사용자 지정 눈, 비김과 멋진 성공을 위한 구간 | 이야기로 다루는 발현과 역발현, 이야기로 다루는 전투 |
| 서술형 주사위 | Genesys | `symbol-pool` | `combat.kind: "symbol-pool"`과 그 안의 `symbols.spends`, 피해 흡수, 채워지는 Wounds 트랙의 체력 | 전투 밖 판정의 자원 소비 |

**변환에서 얻은 실용적인 조언:**

1. **주사위, 시트, Game Master 텍스트 순으로 시작하세요.** 카탈로그나 전투를 추가하기 전에 판정 하나가 올바르게 굴러가게 하세요.
2. **시스템에 결과 구간이 있다면 빠짐없이 사용하세요.** 각 구간의 `text`는 실제 플레이에서 일어나는 일을 모델에 알려 주며, 서사 중심 시스템은 여기에 기반합니다.
3. **반쯤 맞는 전투 블록보다 전투 블록이 없는 편이 낫습니다.** 서사 중심 시스템은 규칙을 절반만 모델링한 전투 블록보다 Marinara 자체 전투(또는 Game Master의 상대 조작)로 더 잘 플레이할 수 있습니다.
4. **전투를 작성한다면 보드의 기본 요소를 제공하세요**: `distance`, 이동, 원거리 무기의 사거리, 적어도 하나의 범위 공격입니다. AI로 시험한 변환은 모두 이 중 일부가 빠져 있었으며, 전투가 정체되거나 위치를 전혀 활용하지 않았습니다.
5. **이동이 축척에 맞는지 확인하세요.** 한 칸이 2미터일 때 속도 2인 생물은 언덕을 오르지 못해 전투가 정체되었습니다.
6. **출처를 적어 두세요.** 규칙 집합마다 각 원본 규칙과 변환 방법을 나열하는 메모 파일을 두세요. 특히 서로 충돌하는 해석 중 하나를 고른 부분을 적으세요. 검토자가 가장 먼저 요청하는 자료입니다.
7. **Engine에 정말로 메커니즘이 없다면** `gmReference`에서 Game Master에게 맡기고 계산 과정을 담은 예제와 함께 기능 요청을 여세요. 이 페이지의 많은 기능(결과 구간, `dice-highest`, `roll-against`, 기호 전투, 시계, 파티 시트)은 변환 작업에서 필요로 했기 때문에 생겼습니다.

## 버전 관리, 시험과 게시

**중요한 버전 번호는 두 가지입니다.** 규칙 집합의 `version`은 변경을 게시할 때마다 올리는 정수입니다. 설치한 버전은 다시 쓰이지 않으며, 모든 게임은 만들어질 때의 정확한 버전에 계속 묶이므로 진행 중인 캠페인의 계산 방식은 바뀌지 않습니다. **Capability API** 버전은 파일에 필요한 Engine 기능을 나타냅니다. 패키지 매니페스트는 `schemaVersion: 2`와 `capabilityApi: { "major": 1, "minor": N }`을 선언합니다. 여기서 N은 사용하는 모든 키의 마이너 버전 중 가장 높은 값이므로, 이전 Engine에는 해당 규칙 집합이 제공되지 않습니다. 공식 카탈로그 규칙 집합은 최소 1.374가 필요합니다. 직접 가져오는 일반 파일은 읽는 Engine이 검증하므로 별도 선언이 필요하지 않습니다.

**초안 작성 반복.** 편집하고, `version`을 올리고, 가져온 뒤 새 게임을 시작하세요. 같은 버전인데 내용이 다른 파일은 가져오기를 거부합니다. 이전 버전은 규칙 집합을 제거할 때까지 설치된 상태로 남습니다. 시트 구조가 바뀌면 `sheet.version`을 올리고, 값을 옮길 때는 마이그레이션을 작성하세요.

**시험.**

- 작성 중 편집기가 오타와 잘못된 타입을 잡도록 `$schema` 줄을 사용하세요.
- 가져오세요. **Settings → Advanced → Danger Zone → Allow custom Agent imports**(설정 → 고급 → 위험 구역 → 사용자 지정 에이전트 가져오기 허용)를 켜고, **Agents → Import agents → Game Mode ruleset**(에이전트 → 에이전트 가져오기 → Game Mode 규칙 집합)을 사용하세요. 검토 화면은 무엇이든 저장하기 전에 아무 대상도 가리키지 않는 이름을 포함해 모든 문제를 경로와 함께 나열합니다.
- 선언한 종류마다 판정을 몇 번씩 플레이하세요. 재정의, 자원 소비와 각 결과 구간도 포함하세요. 로그에 실제 계산이 나옵니다.
- `combat` 블록이 있다면 Classic과 Tactical 양쪽에서 AI 동료와 함께 각 사고방식의 생물을 상대로 싸워 보세요. 정체(아무도 상대에게 닿지 못함), 범위로 인한 아군 오사, 최선의 행동을 전혀 사용하지 않는 적을 살펴보세요.
- 각 레이어를 켜고 끄며, 번역을 배포한다면 Engine의 언어도 바꿔 보세요.
- Experience가 규칙 집합에 오버레이를 적용한다면 `POST /api/game/experience/check`가 맞지 않는 부분을 보고합니다.
- 시스템을 모르는 플레이테스터에게 빌더로 캐릭터를 만들어 보도록 요청하세요.

**게시.** 가장 간단한 것부터 다섯 가지 방법이 있습니다(자세한 내용은 [규칙 집합 공유하기](../extending/writing-rulesets.md#sharing-your-ruleset) 참고).

1. `.json` 파일을 보내세요.
2. 카탈로그와 번역을 담은 `.ruleset.json` 패키지를 보내세요.
3. 공개 GitHub 저장소의 `rulesets/` 아래에 넣으세요(최대 32개 파일). 사용자가 저장소를 사용자 지정 소스로 추가하면 GitHub 이름 아래 분류됩니다.
4. `ruleset-5e-2014`처럼 구성해 [Marinara-Agents](https://github.com/Pasta-Devs/Marinara-Agents)에 풀 리퀘스트로 공식 카탈로그 등재를 제안하세요. 널리 플레이되고 라이선스가 명확한 시스템을 위한 방법입니다.
5. 지도 팩으로 규칙 집합에 모험 콘텐츠 오버레이를 적용하는 Experience를 배포하세요.

**라이선스.** 공유할 권리가 있는 규칙 텍스트만 게시하세요. 많은 시스템에 공개 라이선스로 제공되는 참조 문서가 있습니다. SPDX ID와 필수 저작자 표시를 `license` 아래에 넣으세요. 규칙 집합에 주로 필요한 것은 이름과 숫자이므로 Game Master 텍스트는 모두 직접 쓴 말로 작성하세요.

### 공유 전 확인 사항

- [ ] ID가 확정되었고 ID 규칙을 따릅니다.
- [ ] `license`에 SPDX ID와 저작자 표시가 있으며, 상표로 등록된 이름을 허가 없이 사용하지 않습니다.
- [ ] 모든 판정 종류, 재정의, 자원 소비와 구간을 게임에서 적어도 한 번씩 굴렸습니다.
- [ ] `gm.checkGuidance`와 `gm.sheetGuidance`가 짧고, 모델에 계산을 요구하지 않으며, 직접 쓴 말로 작성되어 있습니다.
- [ ] 규칙 집합이 허용하는 각 스타일로 전투를 플레이했거나, `combat.styles`로 스타일을 제한합니다.
- [ ] 패키지 매니페스트가 올바른 Capability API 마이너 버전을 선언합니다.
- [ ] 다른 사람이 가진 마지막 파일보다 `version`을 올렸습니다.
- [ ] 메모 파일에 각 원본 규칙을 어떻게 변환했는지 설명되어 있습니다.
