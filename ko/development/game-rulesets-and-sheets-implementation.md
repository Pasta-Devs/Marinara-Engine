# Game Mode 규칙 집합과 규칙 집합 캐릭터 시트: 구현 인계

상태: 진행 중. 2026년 9월 18일 `staging`의 `459f8b85`(v2.4.6)를 기준으로 작성했습니다. 슬라이스 1(공유 스키마, 고정 참조, 레지스트리와 Capability API 1.20), 슬라이스 2(`dice-sum` 해결기, `who=`, Game Master 리마인더 교체), 슬라이스 3(카드와 페르소나의 시트), 슬라이스 4(Rules 선택, 생성 시 고정, 설정 시 복사와 설정 공유), 슬라이스 5(게임 내 시트, 실시간 상태와 `[sheet:]` 명령), 슬라이스 7a(커뮤니티 경로), 슬라이스 8a(카탈로그 형식과 라우트, Capability API 1.21), 전투 연결( `battle` 블록, 공유 도우미와 Capability API 1.22), 슬라이스 8c(시트에 따라 조정되는 카탈로그 값, `use` 명령, Refresh from ruleset과 Capability API 1.23), 슬라이스 7b(`dice-pool` 해결 유형, `with=`, `threshold=`, `bonus=` 태그 속성과 Capability API 1.24), 레이어 L1(규칙 집합 자체 파일에 포함하는 변형, 마법사의 레이어 토글, `gm.worldGuidance` 슬롯과 Capability API 1.25), 실제 규칙 집합 전투 C1(`combat` 블록, 순수 해결기, 규칙 효과 추가와 Capability API 1.26), C2(생물 도감, 생물 행동과 위협 제한, Capability API 1.27), C3a(서버 자체 원장에서 전투를 해결하는 전투 디렉터), C3b(그 전투를 규칙 집합 자체 용어로 화면에서 진행), C4a(위치, 근접 거리와 사거리, 범위, 엄폐와 기회 타격, Capability API 1.28), C4b(전장에 그린 전투), C5a(한 턴에 할 수 있는 것: 두 번째 피해 절, 예산 한 번으로 여러 타격, 행동 체계를 바꾸는 능력, 부가 효과, 새 상태 효과와 Capability API 1.29)는 구현되었습니다. 클라이언트 부분이 있는 경우 그 부분도 포함합니다. C5a 이후 슬라이스는 아직 제안입니다. '형식 결정' 절은 구현된 형식이 첫 초안과 다른 곳 및 이유를 기록합니다. 이 문서는 `game-combat-rulesets-implementation.md`(전투 인계)를 보완합니다. 두 문서가 다른 부분은 '전투 인계와의 관계' 절에서 명시하고, 조용히 덮어쓰는 대신 승인을 요청합니다.

동반 파일: [`ruleset-5e-2014.example.json`](ruleset-5e-2014.example.json). 첫 규칙 집합 정의이자 '시트 전체'가 뜻하는 바의 정확한 명세이며, 슬라이스 1 회귀 검증이 검사하는 파일입니다. 형식의 기준은 `packages/shared/src/schemas/ruleset.schema.ts`의 zod 스키마입니다.

## 이유

테이블탑 시스템 열여섯 개를 오버레이로 제공하는 [Marinara-RPG-Extension](https://github.com/Kenhito/Marinara-RPG-Extension) 작성자의 기능 요청입니다. Game Mode 판정은 d20과 Engine 수정치에 묶여 있고, 시트는 능력치 여섯 개이며, 현재 다른 시스템을 실행하려면 규칙 집합마다 매 턴 에이전트 네다섯 개가 필요합니다. 작성자는 네이티브 실행을 원합니다. 해당 프로젝트의 `docs/ENGINE-CONSTRAINTS.md`는 유용한 요구 사항 목록이지만, 오버레이 구조 자체가 목표는 아닙니다.

공식 제공 범위는 **SRD 5.1에 고정한 5e(`5e-2014`)**입니다. V20과 다른 시스템은 같은 데이터 형식을 통해 커뮤니티 작성자에게 맡깁니다(슬라이스 7). 따라서 형식이 5e 모양으로 굳어서는 안 됩니다.

## 제품 계약

1. 규칙 집합은 게임을 만들 때 선택하고 그 게임의 수명 동안 고정합니다. Experience, 전투 표현, 참여 방식, 조종자와는 독립적입니다.
2. 고정한 규칙 집합이 없으면 `engine-legacy`입니다. 프롬프트를 포함해 현재 동작을 바이트 단위로 그대로 유지합니다.
3. **규칙 집합은 모델 호출을 추가하지 않습니다.** 판정은 기존 주사위 흐름을 이용합니다. 시트 변경은 GM 자체 서술 안의 태그를 이용합니다. 프롬프트 문맥은 시트와 규칙 집합 데이터로 문자열을 조립합니다. 어떤 규칙 집합도 `api.registerTool`을 쓰지 않으며 매 턴 에이전트를 제공하지 않습니다.
4. Engine이 굴림, 수정치, 자원 계산과 적법성을 담당합니다. GM은 무엇을 얼마나 어렵게 판정할지 선택하고 실제 결과를 서술합니다.
5. 캐릭터 카드나 페르소나의 시트는 그 규칙 집합에서 해당 캐릭터의 **시작 빌드**입니다. 게임은 사본을 가져갑니다. 게임의 어떤 것도 라이브러리에 되돌려 쓰지 않습니다.
6. 규칙 집합은 지원 범위를 선언하고 UI는 게임 시작 전에 보여 줍니다. 전투 인계 문서의 어댑터가 해당 규칙 집합에 마련되기 전까지 전투는 `engine-legacy`로 실행하며 UI가 이를 평이한 말로 알립니다.

## 전투 인계와의 관계

전투 인계에는 '내장 순수 TypeScript 어댑터의 닫힌 레지스트리로 시작한다. 스크립트 언어나 임의 실행 가능한 규칙 패키지를 추가하지 않는다'고 되어 있습니다.

다음은 제안하는 해석입니다. 슬라이스 1은 이를 기반으로 하며, 이슈는 유지관리자에게 이 해석과 확장된 `RulesetRef`에 대한 승인을 요청합니다.

- **닫힌 레지스트리**는 Engine TypeScript 안의 _해결 유형_과 _파생 연산_ 집합입니다. 유형 추가는 회귀 검증을 포함한 Engine PR로 합니다.
- **규칙 집합 정의**는 유형에 매개변수를 주고 시트를 선언하는 검증된 데이터입니다. 표현식 문자열이 없고 평가 실행되지 않으며 패키지 코드를 가져오지 않습니다.
- **전투 어댑터는 Engine TypeScript로 유지하며**, 전투 인계의 설명 그대로 같은 규칙 집합 ID를 키로 씁니다. 데이터로 선언 순서, 행동 체계, 반응 창을 적절히 표현할 수 없으며 이 문서도 시도하지 않습니다.
- 두 문서는 하나의 `RulesetRef`를 공유합니다. 이 문서는 게임에 고정하며, 전투 인계는 각 조우에 스냅샷을 저장합니다.

이렇게 하면 실행 가능한 경로를 열지 않으면서 에이전트 패키지 목표에 맞게 기본 배포에서 선택적 규칙 콘텐츠를 제외할 수 있습니다.

**전투 연결과 이 경계.** 연결 기능('전투 연결에서 확정한 것' 절)은 그 해석 옆의 별도 구조가 아니라 그 아래에 놓입니다. 해결 규칙은 추가하지 않습니다. `battle` 블록으로 참여한 규칙 집합에 대해 시트와 Engine의 기존 전투 모델 사이 경계를 넘어 양방향으로 숫자를 옮깁니다. 공격 굴림, 내성 굴림, 집중을 적용하지 않고 피해 계산도 바꾸지 않으므로 어느 시스템의 전투도 구현했다고 주장하지 않습니다. 일반 기능이므로 도입 당일부터 5e뿐 아니라 커뮤니티 2d6 시스템에도 쓸 수 있습니다. 또한 규칙 집합별로 명시적으로 대체됩니다. 진짜 전투 어댑터가 생기면 그 어댑터가 전투를 맡고 연결 기능은 물러납니다. 가장 가까이 닿는 경계가 이 문서가 아닌 전투 인계의 경계이므로, PR은 유지관리자에게 이를 승인해 달라고 요청합니다.

## 형식 결정

형식은 아직 아무도 쓰지 않은 규칙 집합을 지원해야 합니다. 그중 많은 것은 5e 파일을 예제로 읽은 AI 에이전트가 초안을 쓸 것입니다. 5e 파일에 필요했던 것은 모두 이름을 가진 일반적인 기본 요소가 되어, 작성자가 어떤 것을 '5e 방식으로만 할 수 있다'고 결론내리지 않게 했습니다.

- **특별한 ID는 없습니다.** Engine은 `level`, `dex`, `slots`, `hp`를 찾지 않습니다. 숙련 보너스는 `resolution.proficiency.bonus`가 참조하는 값이며 생략할 수도 있습니다. 그러면 단계는 `flat` 보너스를 씁니다. 레벨 표는 일반 필드를 읽는 일반 `stepTable` 파생 값입니다.
- **주사위는 `dice-sum`의 매개변수입니다**(`{ count, sides }`). 규칙 집합이 주사위 하나를 굴리지 않으면 자연 눈 결과 설정을 거부합니다.
- **능력치 수정치는 고정 연산입니다.** `floorHalfMinusTen`, `identity`(점수 자체가 수정치), 또는 `stepTable`입니다.
- **내성은 기술처럼 목록입니다.** '능력치마다 하나'가 아니므로 내성이 세 개인 시스템도 표현할 수 있습니다. 기술과 내성은 능력치를 생략할 수 있습니다.
- **모든 기술과 내성은 시트에 자유로운 수치 보너스를 가질 수 있습니다**(`bonuses`). 새로운 기본 요소 없이 랭크 기반 시스템과 아이템 보너스를 지원합니다.
- **수동 점수는 연산이 아닙니다.** `{ "const": 10 }`과 `{ "skillMod": "perception" }`의 `sum`입니다.
- **행이 자원인 목록은 `pools`를 선언합니다**(이름, 최대치와 선택적 재충전 열). 휴식은 `recharge`로 거른 `listPools`로 복구합니다. '카운터'라는 말을 아는 구성 요소는 없습니다.
- **휴식량은 고정 형태입니다.** `to`(`"max"`, `"min"` 또는 수치)나 `by`(상수, 또는 반올림 방식과 하한이 있는 최대치 비율)입니다. 5e의 '히트 다이스 절반, 최소 하나'는 `{ "fractionOfMax": 0.5, "round": "down", "min": 1 }`입니다.
- **풀은 비어 있는 상태로 시작할 수 있습니다**(`start: "empty"`). 스트레스, 타락 같은 증가하는 트랙에 씁니다.
- **`gm.sheetSummary`**는 간결한 프롬프트 블록에 표시할 필드, 파생 값, 목록을 지정하므로 Engine이 'AC, 수동 Perception, 준비한 주문'을 하드코딩하지 않습니다.
- **모든 객체에서 `$comment`를 허용하고** 루트에서 `$schema`를 허용합니다. 둘 다 검증 전에 제거합니다. 나머지는 엄격합니다. Engine이 일부만 이해하는 규칙 집합은 게임 계산을 조용히 바꿀 수 있으므로, 알 수 없는 키는 파일 전체를 거부하며 작성자가 처리할 수 있는 `path: message` 행을 나열합니다.
- **항목이 구역을 지정하기 전에 구역을 선언합니다.** 따라서 편집기의 모든 그룹에 라벨이 있습니다.
- **파생 값은 자신보다 위에서 선언한 값만 읽습니다.** 순환을 표현할 수 없게 됩니다. 숙련 보너스를 공급하는 값과 그 위의 모든 값은 기술이나 내성 수정치를 읽을 수 없습니다.
- **모든 라벨과 지침 문자열은 gm-verbs 프롬프트 위생 규칙을 따릅니다.** 한 줄이며 제어 문자, 대괄호, 매크로 중괄호가 없습니다.
- **패키지는 종류 `ruleset`을 선언하고**, 권한도 진입점도 필요 없으며 `ruleset.json`을 나열할 때 Capability API 1.20을 선언해야 합니다.

## 슬라이스 2에서 확정한 것

- **해결기는 기존 문맥 뒤에 놓입니다.** `SkillCheckModifierContext`에 선택적 `ruleset`을 추가합니다. 모든 호출자가 이미 `resolveSkillCheckWithContext`를 거치므로 엔드포인트, 생성 후처리, 한 요청 주사위와 결과를 미리 볼 수 있는 풀이 새 호출 지점 없이 규칙 집합에 닿습니다.
- **완성되어 보이는 태그도 시트와 대조해 감사합니다.** `engine-legacy`에서는 계산이 맞는 완성 태그를 그대로 허용합니다. 문맥을 불러오지 않고 시트에 대해 감사하지 않으며 다시 굴리지도 않습니다. 규칙 집합 게임에서는 생성 라우트가 `rulesetPinned` 힌트를 전달하고 이런 태그도 문맥을 불러옵니다. 규칙 집합에서 나올 수 없는 수정치, 주사위 수, 자연 눈 결과가 있으면 태그를 다시 굴리도록 돌려보냅니다. 힌트는 기존 게임이 완성 태그에 대해 계속 문맥을 불러오지 않게 하려고 존재합니다.
- **설치 상태가 충족하지 못하는 고정 참조는 안전하게 실패합니다.** 문맥 로딩이 예외를 내며, 태그 처리기의 기존 실패 경로는 판정을 아직 굴려야 하는 희소한 상태로 저장합니다.
- **`who=`는 결과에 실립니다.** `SkillCheckResult.who`는 규칙 집합 해결기만 설정하고 직렬화기가 기록하므로 기존 기록의 바이트는 그대로입니다.
- **낯선 이는 수정치 없이 굴립니다.** 파티 카드와 일치하지 않거나 두 카드가 공유하는 `who=`는 수정치를 전혀 받지 않습니다. 규칙 집합의 기본값이 모든 시스템에서 중립은 아니기 때문입니다. 시트가 없는 파티원(또는 플레이어)은 설정 시 복사하는 규칙 집합의 빈 기본 빌드로 굴립니다. 규칙 집합이 모르는 기술 이름도 아무것도 더하지 않습니다. 능력치를 추측해 대체하지 않습니다. 플레이어 자신의 카드는 파티원과 공유하는 이름에 대해 우선권을 유지합니다.
- **주입한 d20과 플레이어가 미리 굴린 d20은 규칙 집합이 d20 하나를 굴릴 때만 존중합니다.** 다른 주사위는 Engine의 공정한 주사위에서 나옵니다.
- **엔드포인트 난이도 상한은 40으로 유지합니다**(`ponytail:` 표시). 생성 후처리는 더 넓은 사다리를 존중합니다.
- **시트 블록과 시트 명령은 실시간 상태와 함께 슬라이스 5에서 다룹니다.** 슬라이스 2는 리마인더의 판정 줄만 교체하고 다른 주사위 표기법을 가르치는 줄을 제거합니다. 규칙 집합 게임은 규칙 시스템 하나를 쓰기 때문입니다.

## 슬라이스 3에서 확정한 것

- **저장 경계는 한도만 검사하고 형태는 검사하지 않습니다.** 캐릭터 확장과 페르소나 능력치 스키마에 `rulesetSheets`를 레코드로 선언합니다. 키는 규칙 집합 ID여야 하고 값은 최대 64 KB 객체이며 최대 32개입니다. 규칙 집합이 설치되지 않았을 수 있으므로 여기서 시트 형태는 검증하지 않습니다. 한도를 깨는 업데이트는 메시지와 함께 거부합니다.

- **값은 편집할 때만 범위를 제한하고 읽을 때는 제한하지 않습니다.** 규칙 집합이 더는 제공하지 않는 저장된 숙련 단계도 원래대로 표시합니다.
- **설치 목록을 불러오기 전에는 휴면 상태라고 부르지 않습니다.** 느린 요청 때문에 유효한 시트를 누락으로 표시하지 않습니다.

## 슬라이스 4에서 확정한 것

- **서버가 고정 참조를 만듭니다.** 마법사가 `GameSetupConfig`로 `ruleset`을 보내지만 `id`만 신뢰합니다. `POST /game/create`가 자체 레지스트리에서 `RulesetRef`를 다시 만들고 `gameSetupConfig.ruleset`과 `chat.metadata.gameRuleset` 양쪽에 씁니다. 설치되지 않은 규칙 집합은 `ruleset_not_installed`로 거부하며 다른 규칙으로 바꾸지 않습니다.
- **규칙 집합이 없는 게임에는 키를 더하지 않습니다.** `gameRuleset`은 규칙 집합을 선택했을 때만 기록하므로 기존 메타데이터의 바이트가 유지됩니다.
- **설정 시 복사는 한곳에 있습니다.** `applyGameSetupPayload`가 파티와 페르소나의 저장된 시트를 직접 읽으므로 두 설정 진입점(`/game/setup`, `/game/setup/apply-json`)이 같은 방식으로 복사합니다. 카드는 기존 `rpgStats`처럼 정규화한 이름으로 맞추며, 파티원과 이름이 같으면 페르소나가 우선합니다. 저장된 시트가 없는 멤버는 빈 기본 빌드를 받습니다.
- **설정 공유는 Experience 규칙을 따릅니다.** 현재 설치에 공유 버전 이상이 있으면 공유한 규칙 집합을 새 게임에 복원하고, 없으면 제외합니다. 마법사는 파일의 `rulesetName` 라벨로 빠진 규칙 집합 이름을 보여 줍니다. 공유 파일의 고정 참조는 신뢰할 수 없는 입력이며 `rulesetRefSchema`로 읽습니다.
- **Rules 블록은 별도 구성 요소**(`GameSetupRulesChooser`)이며 Combat Preference 옆에 배치합니다. 규칙 집합이 하나 이상 설치된 새 게임에서만 렌더링합니다.

## 슬라이스 5에서 확정한 것

- **실시간 상태는 자체 스냅샷 열입니다.** `game_state_snapshots.ruleset_live`는 정규화된 카드 이름을 키로 쓰는 `RulesetLiveStates`를 담습니다. 파일 기반 저장소의 새 열은 `STORAGE_VERSION`을 올릴 필요가 없습니다. 예전 행은 열을 null로 읽으며, null은 모든 풀이 기본 상태라는 뜻입니다. 여러 추적기가 아는 필드만으로 `playerStats`를 재구성하므로 그 안의 키로 넣지 않습니다.
- **실시간 상태는 희소합니다.** 설정한 값만 저장하고 기본값으로 돌아온 값은 다시 제거합니다. 따라서 건드리지 않은 '가득 찬' 풀은 레벨 상승으로 최대치가 올라가면 따라가며, 아무것도 소모하지 않은 캐릭터는 항목 자체가 없습니다.
- **턴은 시작 당시 상태를 기준으로 계산합니다.** `[sheet:]` 명령은 답변이 재작성될 때마다 저장 전에, 그 턴 바로 앞 행의 실시간 상태 위에 적용합니다. 이어쓰기라면 이어쓰는 메시지가 이미 가진 행을 씁니다. 재생성한 턴은 그 이전 메시지에서 기준 상태를 구하므로 두 번 소모하지 않고, 각 스와이프는 끝난 상태를 보존합니다.
- **규칙 집합 게임의 모든 저장 턴은 변경 여부와 관계없이 행을 씁니다.** 다음 턴, 스와이프, 새 세션에 항상 출발할 행이 있도록 합니다. 나중에 같은 메시지와 스와이프를 재구성하는 추적기도 실시간 상태를 보존합니다. 호출자가 값을 전달하지 않으면 `create`는 교체할 행에서 가져옵니다.
- **명령은 Engine의 것이고, 이름은 규칙 집합의 것입니다.** 문법(`spend`, `restore`, `damage`, `temp`, `track`, `condition`, `note`, `rest`, 그리고 `restore`로 읽는 `heal`)은 모든 규칙 집합에 같습니다. 첫 제안의 `concentrate`는 일반적인 `note`가 되었습니다. '집중'은 한 시스템의 용어이기 때문입니다. 풀, 트랙, 상태, 메모, 휴식 이름은 규칙 집합에서 오고 ID나 라벨로 맞춥니다.
- **저장된 답변이 기록입니다.** 각 명령은 그 자리에서 `result="ok" now="…"` 또는 `result="refused" reason="…"`로 다시 씁니다. 모델이 직접 쓴 결과는 무시합니다. 거부된 명령은 아무것도 바꾸지 않고 로그에 남으며, 클라이언트는 턴마다 한 번 알립니다.
- **시트는 프롬프트 뒤쪽에서 Game Master에게 전달됩니다.** 시트 블록과 명령 줄은 매 턴 형식 리마인더의 일부이며 시스템 프롬프트에는 넣지 않습니다. 실시간 상태는 매 턴 바뀌고 제공자가 캐시하는 것은 시스템 프롬프트이기 때문입니다. 규칙 집합이 없으면 리마인더는 바이트 단위로 같습니다.
- **플레이어도 같은 규칙으로 편집합니다.** 게임 내 시트는 모든 버튼에 `applyRulesetSheetOp`를 적용하고 `PATCH /chats/:id/game-state`로 저장합니다. 이 경로는 실시간 상태 한도를 검사하며(`rulesetLiveStatesSchema`) 다른 것은 판단하지 않습니다. 플레이어 자신의 게임이기 때문입니다.
- **`sheet`는 예약되어 있습니다.** 같은 이름의 패키지 동사는 거부하며, 동사 이름 검사가 리마인더에서 가르치는 태그를 찾습니다.
- **여기서는 미구현:** 파티원 자신의 턴(`/party-turn`)에는 시트 명령을 적용하지 않습니다. Game Master 답변에만 적용합니다.

## 슬라이스 7a에서 확정한 것

- **저장.** 커뮤니티 규칙 집합은 새 파일 기반 테이블 `game_rulesets`에 네임스페이스 ID와 버전마다 한 행씩 저장하며, 가져온 원문 그대로와 sha256을 담습니다. 저장 형식은 올리지 않습니다. 테이블은 소유자도 연쇄 삭제도 없으며, 규칙 집합을 제공한 저장소를 제거하면 `repositoryId`만 비웁니다.
- **ID.** 파일은 항상 접두사 없는 ID를 가집니다. Engine은 선택한 파일을 `local/<id>`, 저장소를 `<owner>/<id>`(소문자 GitHub 소유자)로 분류합니다. 레지스트리가 `definition.id`를 네임스페이스 ID로 바꾸므로 시트, 고정 참조, 마법사가 모두 그것을 키로 씁니다. GitHub 계정 이름 `local`은 거부하여 사용자의 자체 규칙 집합 사이에 다른 사람이 등록하지 못하게 합니다.
- **버전.** 저장된 버전은 다시 쓰지 않습니다. 같은 바이트면 아무 작업도 하지 않고, 기존 버전에 다른 바이트가 오면 거부하며(`RulesetVersionConflictError`) 작성자에게 버전을 올리라는 메시지를 줍니다. 커뮤니티 고정 참조는 지정한 정확한 버전을 찾으며, 사라졌으면 `version-missing`입니다. 공식 패키지는 '설치 버전이 고정 버전 이상'이라는 규칙을 유지합니다.
- **허용 조건.** 단일 파일 가져오기는 특권 접근과 **Allow custom Agent imports**가 필요합니다. 저장소 경로는 여기에 자체 환경 플래그도 유지합니다. 가져오기가 꺼지면 `/game/create`가 커뮤니티 규칙 집합을 거부하고(`ruleset_imports_disabled`) 마법사도 제외합니다. 그러나 해결 처리는 정책을 참조하지 않으므로 기존 게임은 계속 작동합니다. 제거는 특권 접근만 필요하므로 가져오기가 꺼져도 됩니다.
- **제거.** `DELETE /api/game-rulesets?rulesetId=`는 저장된 모든 버전을 지웁니다. 게임이 규칙 집합을 고정했으면 개수와 함께 409 `ruleset_in_use`를 반환하고, 클라이언트가 다시 물은 뒤 `force=true`로 재시도합니다.
- **검토.** 규칙 집합에는 기능 권한이 없으므로 해당 체크박스도 없습니다. 검토 화면은 정체성, 라이선스, 지원 범위, 판정 굴림 방식, Game Master 텍스트 원문을 보여 주며 그 텍스트가 모델로 전송된다고 알립니다.
- **저장소 경로.** `<top>/rulesets/*.json`의 직계 파일만 읽으며, 최대 32개이고 각각 `RULESET_MAX_BYTES`까지입니다. 저장소는 에이전트, 규칙 집합 또는 둘 다 담을 수 있습니다. 사용할 수 없는 파일 하나는 이유를 표시하는 미리보기 행이 되며 저장소 전체를 실패시키지 않습니다. 상류에서 철회한 규칙 집합도 설치 상태를 유지합니다.
- **작성.** `docs/extending/writing-rulesets.md`는 한계를 먼저 설명합니다. `docs/extending/ruleset.schema.json`은 `pnpm ruleset:schema`로 zod 스키마에서 생성하며 오래되면 회귀 검증이 실패합니다. 가이드는 해결 유형마다 예제 하나를 제공하고 둘 다 d20 형태가 아닙니다. Ember Roads는 2d6, Gravewatch는 10면체 풀을 굴립니다. 회귀 검증이 둘을 검증하며, 공개 스키마가 모든 유형의 멤버를 담는지도 확인합니다.

## 슬라이스 8a에서 확정한 것

- **헤더는 규칙 집합에 있고, 항목은 밖에 둘 수 있습니다.** `ruleset.json`에 선택적 `catalogs` 배열(최대 12개)을 추가합니다. 각 헤더는 `id`, `label`, 공급할 시트 목록 `feeds`(1~8개), 선언한 `filters`, 선택적 `units`, 그리고 `entries`(인라인) 또는 `asset` 중 정확히 하나를 가집니다. 카탈로그가 없으면 빈 배열 대신 키 자체를 생략하므로 카탈로그 이전 파일도 같은 바이트로 파싱됩니다.
- **자산 경로는 선택하지 않고 도출합니다.** `asset`은 `catalogs/<the catalog's id>.json`과 같아야 합니다. 따라서 라우트가 규칙 집합만으로 파일을 찾고 어떤 카탈로그도 다른 카탈로그 파일을 지정할 수 없습니다.
- **도우미 하나가 목록이 담을 수 있는 것을 정합니다.** 공유 패키지에서 내보내는 `rulesetListRowIssues(list, values)`가 '이 행을 저장할 수 있는가'에 대한 유일한 답입니다. 스키마는 모든 인라인 항목에 실행하고, `parseRulesetCatalogFile`은 읽을 때 자산의 항목에 실행하며, 클라이언트는 플레이어가 고른 행에 다시 실행합니다. 따라서 카탈로그가 편집기에서 거부할 값을 쓰는 일은 없습니다. `rulesetCatalogEntryIssues(definition, catalog, entries)`는 두 검증 경로가 호출하는 공유 래퍼입니다.
- **설정 시처럼 선택 시에도 복사합니다.** `rowsFromCatalogEntry`는 예약 키 `RULESET_CATALOG_ROW_KEY = "_catalog"` 하나를 가진 행을 반환하며 값은 `<catalogId>/<entryId>`입니다. 열 ID는 문자로 시작해야 하므로 충돌하지 않습니다. 행은 사본입니다. 플레이어가 편집하고, 규칙 집합을 제거해도 시트는 읽을 수 있으며, 새 규칙 집합 버전이 캐릭터를 다시 쓰지 않습니다.
- **상한.** 규칙 집합당 카탈로그 12개, 카탈로그당 공급 목록 8개와 필터 8개, 인라인과 자산 모두 카탈로그당 항목 2000개, 항목당 행 6개, 자산당 `RULESET_CATALOG_MAX_BYTES = 1 MB`입니다. 파일을 읽기 전에 매니페스트가 선언한 `files[].bytes`로 확인합니다.
- **목록은 작게 유지합니다.** `GET /api/capability-packages/rulesets`는 시트 편집기를 열 때마다 읽으므로 인라인 `entries`를 제거하고 대신 `entryCount`를 보고합니다. 카탈로그 없는 규칙 집합은 이전과 바이트 단위로 같게 나열합니다. `GET /api/capability-packages/rulesets/catalog?rulesetId=&catalogId=&version=`는 인라인 항목 또는 파싱하고 검증한 자산으로 카탈로그 하나를 제공합니다. `/rulesets`와 같은 이유로 특권 제한은 없으며, 패키지 ID에 가려지지 않도록 `/:id/...` 라우트보다 앞에 등록합니다. 알 수 없는 규칙 집합, 버전, 카탈로그는 코드가 있는 404이고, Engine이 읽지 않는 자산은 작성자용 문제 행이 있는 422입니다.
- **Capability API 1.21은 두 부분입니다.** `catalogs/<id>.json` 자산을 선언하려면 1.21과 옆의 `ruleset.json`이 필요합니다. 카탈로그는 규칙 집합 파일 내부에도 있고 매니페스트에서 보이지 않으므로, 설치 시 검증된 바이트를 읽고 낮은 선언 아래의 `catalogs` 키를 거부합니다. 파싱할 수 없는 규칙 집합이 설치를 실패시키지는 않습니다. 로그 한 줄을 남기고 레지스트리의 보고로 유지합니다.
- **`mechanics`는 검증하며 일부를 사용합니다.** 선택적 블록(종류, 사거리, 범위, 표적, 아군 공격, 양, 피해 유형, 공격 굴림, 내성, 비용, 비용 단계당 효과, 집중, 반응)은 닫힌 엄격한 어휘이므로 언젠가 읽는 기능이 생길 때가 아니라 지금 오타가 드러납니다. 슬라이스 8a는 검증하고 선택기에 짧은 한 줄을 보여 주기만 했습니다. 전투 연결은 종류, 사거리, 범위, 아군 공격, 양, 피해 유형, 비용, 반응(반응 항목 제외용)을 사용합니다. 공격 굴림, 내성, 집중, 비용 단계당 효과는 여전히 아무것도 읽지 않습니다.
- **알려진 한계: 커뮤니티 카탈로그는 인라인만 가능합니다.** 단일 파일로 가져오거나 GitHub 저장소에서 받은 규칙 집합은 카탈로그를 한 파일 안에, 따라서 기존 256 KB 상한 안에 담습니다. 커뮤니티 규칙 집합의 별도 카탈로그 파일(`rulesets/<id>/catalogs/*.json`)은 의도적으로 제외했습니다. 저장소 경로는 `rulesets/`의 직계 파일만 읽고, 단일 파일 경로는 정의상 파일 하나이기 때문입니다. 목록이 256 KB보다 긴 커뮤니티 작성자는 대신 패키지를 배포합니다. 실제 제약이 되면 별도 슬라이스로 다룹니다.
- **증명은 두 번째 비 d20 규칙 집합입니다.** `docs/examples/rulesets/ember-roads.json`에 `knacks` 목록, 행이 풀인 `tricks` 목록, 둘에 공급하는 카탈로그를 추가했습니다. 두 행을 쓰는 항목과 `mechanics`가 있는 항목도 있습니다. 형식의 어느 부분도 5e 모양이 아니며, 회귀 검증은 5e 대신 이 파일을 읽습니다.

## 전투 연결에서 확정한 것

- **규칙 집합이 사용을 선택하며, 선언하지 않으면 아무것도 바뀌지 않습니다.** `ruleset.json`에 선택적 `battle` 블록을 추가합니다. `health`(필수, 체력이 되는 실시간 풀), 선택적 `energy`(MP가 되는 풀), 선택적 `slots`(1~9 레벨의 풀), 선택적 `skills`(최대 8개 시트 목록, 각각 선택적 `onlyWhen` 불리언 열과 선택적 `alwaysWhen: { column, equals }` 예외)입니다. 블록이 없으면 전투는 이전과 바이트 단위로 같습니다. Capability API 1.22이며, 매니페스트가 아닌 규칙 집합 파일 안의 블록이므로 `catalogs`처럼 설치 시 제한합니다.
- **모든 이름은 선언한 실시간 풀을 가리킵니다.** 행이 풀인 목록은 체력이 될 수 없습니다. 행 풀은 행 이름을 키로 쓰며 시트를 편집할 때 생기고 사라지기 때문입니다. 체력과 에너지는 달라야 하고, 슬롯 풀과 레벨은 각각 고유해야 하며, 목록이 있어야 합니다. `onlyWhen`은 불리언 열, `alwaysWhen.column`은 같은 목록의 열이어야 합니다.
- **연결은 세 개의 순수 공유 도우미입니다.** `packages/shared/src/features/rulesets/combat-bridge.ts`의 `seedCombatantFromSheet`, `combatSkillsFromSheet`, `sheetOpsFromCombatResult`에 `applyCombatResultToLive`를 더하며, 양방향 체력이 모두 거치는 단일 변환 `carryHealthShare`를 기반으로 합니다. I/O도 예외 던지기도 서버 라우트도 없습니다. 클라이언트가 세 전투 UI 모두가 공유하는 한 경계 양쪽에서 호출합니다.
- **체력은 양방향 모두 최대치에 대한 비율로 전달합니다.** 첫 브라우저 확인에서 발견했습니다. Engine은 레벨 1 전투원을 약 60 체력으로 만들고 한 타격에 11~15 피해를 줍니다. 반면 Ember Roads 캐릭터는 Grit 9, 레벨 1 5e 위저드는 체력 8입니다. 피해 계산은 Engine의 것이며 그대로 유지하므로, 시트의 원시 수치를 빌려주면 매 전투 첫 타격에 연결된 캐릭터가 쓰러졌습니다. 전투원은 Engine 자체 `maxHp`를 유지하고 시트 체력 풀과 같은 비율에서 시작합니다. 되돌려 쓰기는 최종 비율을 시트 척도로 읽어 차이를 씁니다. 에너지와 슬롯은 절댓값입니다. 작은 개수이며 비용은 같은 시트에서 오고 Engine이 하나씩 소모하기 때문입니다. 토스트, `docs/game/combat.md`, 규칙 집합 가이드가 모두 전투의 수치는 Marinara의 것이라고 설명합니다.
- **비율 자체로 시트가 바뀌지 않습니다.** 전투원의 체력이 움직이지 않은 전투는 체력 연산을 전혀 쓰지 않으므로 두 번의 반올림으로 시트가 1점 어긋날 수 없습니다. 양방향 모두 0보다 큰 값은 1 미만으로 변환하지 않으므로 누구도 반올림 때문에 전투나 시트에서 탈락하지 않습니다.
- **체력 0은 실제 수치입니다.** 체력 풀이 빈 멤버는 쓰러진 상태로 전투를 시작하며, 이는 전투 안에서 쓰러진 멤버의 상태와 같습니다. 1로 제한하면 시트에 없는 체력을 지어냅니다. 전원이 쓰러진 파티는 즉시 패배하며 전투를 끝냅니다. 그것이 정확한 결과입니다. 반대도 같습니다. 0인 전투원은 시트를 0으로 씁니다.
- **카탈로그 표시가 있는 행만 기술이 됩니다.** 직접 입력한 행 뒤에는 `mechanics`가 없으므로 수치로 바꿀 것이 없습니다. Engine이 소모할 수 없는 풀(체력, 풀 그룹, 클래스 자원)의 비용은 무료로 만드는 대신 기술을 제거합니다. `utility`와 반응 항목도 제외합니다.
- **`power`는 계산값이 아니라 보정값입니다.** 전투원 공격력의 배율이므로 연결 기능은 평균량을 7로 나누고 0.5~3으로 제한합니다. 그러면 기본 무기가 Engine 자체 기본 기술 수준(공격 1.35, 회복 1.15)에 놓이고, 3레벨 범위 주문은 생성 기술에 이미 적용하는 상한에 닿습니다. 더 큰 주사위 풀이 더 작은 배율을 내지는 않습니다.
- **되돌려 쓰기는 시트 자체 규칙을 거칩니다.** 각 차이는 `damage`, `restore`, `spend` 연산이 되어 `applyRulesetSheetOp`로 적용합니다. 따라서 Game Master나 플레이어에게서 왔다면 시트가 거부할 값을 전투가 쓸 수 없습니다. 되돌려 쓰기는 전부 성공하거나 전부 취소하는 방식이 아닙니다. 거부한 연산은 건너뛰고 호출자에게 반환하며, 허용한 연산은 적용된 채로 남습니다. 중단한 전투는 아무것도 쓰지 않습니다. 전투가 일어나지 않은 셈입니다.
- **요약은 시트에 필요한 내용을 담습니다.** `buildTacticalSummary`는 이제 디렉터 요약이 이미 하던 대로 `mp`, `maxMp`, `spellSlots`를 보고합니다.
- **연결이 의도적으로 읽지 않는 것.** `attackRoll`, `save`, `concentration`, `perCostStep`은 검증만 하고 사용하지 않으며, `coverage.combat`는 자체 의미를 유지합니다. 적용한다면 시스템의 전투를 구현했다는 주장이 되며, 그것은 전투 인계의 작업입니다.

## 슬라이스 8c에서 확정한 것

시트에 따라 조정되는 카탈로그 값, `use` 명령, Refresh from ruleset의 세 부분이 모두 들어갔습니다.

- **행은 규칙 집합이 관리하는 숫자 네 개를 가질 수 있습니다.** 카탈로그 항목 행에 선택적 `scaled` 맵을 추가합니다. 해당 행 자체의 `number` 열 최대 네 개이며, 각각 `{ from: <value reference>, table?: <step table> }`입니다. `table`이 없으면 참조 값을 그대로 취합니다(재주의 사용 횟수가 능력치와 같음). 있으면 값을 표에서 찾습니다(레벨별 Rage). 더 복잡한 것은 규칙 집합이 선언하고 항목이 가리키는 `derived` 값이므로 형식에 새 계산법을 넣지 않습니다. `values`는 시트를 알기 전 행의 단순 수치를 계속 담습니다.
- **두 카탈로그 형태를 같은 검사로 검증합니다.** 교차 검사는 인라인과 자산 항목 모두가 거치는 `rulesetCatalogEntryIssues`에 있습니다. 따라서 어떤 배포 방식이든 조정 행에 같은 규칙을 적용합니다. 키는 그 행 목록의 `number` 열이고 `from`이 해석되어야 하며, 그 행은 해당 목록에 대한 항목의 유일한 행이어야 합니다. 시트에서 표시된 행을 추측 없이 하나의 명세에 연결하기 위해서입니다. 다른 모든 값 참조를 검증하던 `checkRef` 클로저는 공유 `rulesetValueRefIssues`가 되었으므로, 파생 값에서 유효한 참조는 조정 열에서도 유효합니다. 조정 열은 실시간 풀의 `max`처럼 선언된 어떤 파생 값도 지정할 수 있습니다. 시트 자체의 위에서 아래 순서 밖에 있기 때문입니다.
- **읽을 때가 아닌 편집할 때 적용합니다.** `packages/shared/src/features/rulesets/scaled-rows.ts`의 `recomputeScaledRows(definition, build, catalogs)`는 바뀐 것이 없으면 같은 빌드 참조를 반환하므로 열기만 한 시트는 다시 쓰지 않습니다. 값은 들어갈 열에 맞춥니다(`min`, `max`로 제한하고 정수 열이면 내림). 따라서 편집기가 거부할 값을 쓸 수 없습니다. 실시간 상태, 프롬프트 블록, 전투 연결, 서버는 계속 저장된 수치를 읽습니다. `scaledRowColumns`는 편집기에 잠글 셀을 알려 줍니다.
- **없는 카탈로그에서 추측하지 않습니다.** `_catalog` 표시가 없는 행, 호출자가 가져오지 않은 카탈로그, 사라진 항목은 모두 그대로 둡니다. 해당 행에 대한 규칙 집합의 의도를 알 수 없기 때문입니다.
- **`use`는 '주문'이라는 말을 쓰지 않는 시전 도우미입니다.** `[sheet: who="Name" op="use" name="..."]`이며, `heal`이 `restore`의 별칭인 것처럼 `op="cast"`와 `spell=`을 별칭으로 둡니다. 모든 `mechanics.cost` 항목과 같은 항목이 쓴 각 목록 행 풀에서 하나씩을 지불합니다. 그룹을 지정한 비용은 선언 순서대로 그 그룹에서 감당 가능한 첫 풀에서 내며, 더 높은 풀로 자동 승급하지 않습니다. 그룹은 항상 사다리가 아니기 때문입니다. `pool=`은 상위 단계 사용이며 같은 그룹 안의 단일 비용에만 허용합니다. 전부 성공하거나 전부 취소합니다. 작업 사본에서 각 단계를 `applyRulesetSheetOp`로 실행하고 처음 거부되면 명령 전체를 거부합니다. 비용 없는 항목은 `ok`이며 아무것도 바꾸지 않습니다. 새 거부 사유는 `unknown-entry`, `ambiguous-entry`, `bad-pool`입니다.
- **이름은 Game Master에게 보여 준 것입니다.** 행은 `gm.sheetSummary` 이름 열, 그다음 `pools.nameColumn`, 그다음 목록의 첫 텍스트 열과 원본 항목의 `label`에 응답하므로 이름을 바꿔도 작동합니다. 불러올 수 없던 카탈로그는 `unknown-entry`로 처리하고 서버 로그에 남깁니다. Engine이 가격을 알 수 없으며 지어내지 않기 때문입니다.
- **카탈로그는 턴에 필요할 때만 읽습니다.** `loadTurnRulesetCatalogs`는 답변에 `use`나 `cast` 명령이 없으면 아무것도 읽지 않고, 있으면 파티 자체 행이 가리키는 카탈로그만 읽습니다. 라우트의 자산 읽기 부분은 `services/game/ruleset-catalog.service.ts`로 옮겼습니다. 카탈로그 열기와 읽기를 두 단계로 나눠 라우트가 1 MB를 파싱하기 전에 여전히 304를 응답할 수 있습니다. 불러오기 실패는 `logger.warn`이며 턴을 잃지 않습니다.
- **Capability API 1.23은 바이트에서 읽습니다.** `scaled`는 엄격한 파일의 새 키이므로 오래된 Engine은 이를 담은 내용을 거부합니다. 설치 시에는 `ruleset.json`과 선언된 모든 `catalogs/<id>.json`의 검증된 바이트가 이미 있으므로 둘 다 검사합니다. 조정 행은 인라인이든 자산이든 1.23이 필요합니다. 파싱할 수 없는 파일은 늘 그랬듯 검사를 건너뜁니다.
- **새로고침은 규칙 집합의 새 텍스트만 제공합니다.** `packages/client/src/lib/ruleset-catalog.ts`의 `planCatalogRefresh`와 `applyCatalogRefresh`는 항목이 실제로 설정하는 `text`, `longtext`, `dice`, `enum` 열만 비교하며, 조정 열이나 열 자체가 거부할 값은 비교하지 않습니다. 숫자나 불리언에는 플레이어 상태가 있고 병합 기준도 저장되어 있지 않으므로 그대로 둡니다. 작성 가이드에 한계로 설명합니다. 행 수가 맞으면 같은 목록에서 동일 표시가 있는 행들의 위치로 원본 항목 행과 연결하고, 그렇지 않으면 항목이 목록에 한 행만 쓸 때 연결합니다. 원본 항목이 사라진 행은 조용히 건너뜁니다.
- **검토하고 적용하며, 플레이어 몰래 적용하지 않습니다.** 차이가 없으면 아무것도 그리지 않습니다. 다른 행이 있는 목록은 평범한 한 줄과 **Review**(검토) 버튼을 표시합니다. 시트를 입력하는 동안 재발표하지 않도록 실시간 알림 영역으로 만들지 않습니다. 버튼은 `RulesetCatalogRefreshModal`을 열어 각 행의 다른 열에서 시트 텍스트와 규칙 집합 텍스트를 나란히 보여 주고, 기본 선택된 행별 체크를 제공합니다. **Update selected**(선택 항목 업데이트)는 한 번의 `commit`으로 모두 적용하며 다른 열만 쓰고 `_catalog` 표시를 포함한 행의 나머지 키를 유지합니다. 취소하면 바뀌지 않습니다.
- **편집기는 시트가 가리키는 것만 불러옵니다.** `RulesetSheetEditor`는 빌드 자체 표시의 카탈로그를 선택기 자체 `rulesetCatalogQuery`에 대한 `useQueries`로 가져옵니다. 선택기, 전투 사전 가져오기, 편집기가 캐시 하나를 공유하고 표시 없는 빌드는 아무것도 가져오지 않습니다. 대기 중이거나 실패한 로딩은 '아직 카탈로그 없음'으로 읽어 아무것도 잠그거나 재계산하지 않습니다. `commit`은 여전히 유일한 변경 경로이며 이제 패치한 빌드에 `recomputeScaledRows`를 실행합니다. 시트를 열기만 해서는 `onChange`를 부르지 않습니다. 카탈로그 도착 전에 편집한 시트는 도착할 때 한 번 최신 상태로 맞춥니다.
- **두 예제에서 입증했습니다.** `docs/examples/rulesets/ember-roads.json`은 레벨 자체가 없는 2d6 시스템에서 표 없이 능력치로 재주 사용 횟수를 조정합니다. 5e 예제는 클래스 자원이 단계 표를 통해 `level`을 따르는 테스트 카탈로그와 함께 사용합니다. `scripts/regressions/game-ruleset-scaled-rows.regression.ts`, 실시간 및 카탈로그 회귀의 `use` 사례, 그리고 두 예제의 새로고침을 다루는 클라이언트 경로 `scripts/regressions/ruleset-catalog-refresh.regression.ts`로 검증합니다.

## 슬라이스 7b에서 확정한 것

두 번째 해결 유형 `dice-pool`입니다. 계획은 이미 풀 시스템을 운영하는 커뮤니티 작성자와 함께 명세를 정하는 것이었지만 아무도 답하지 않았습니다. 따라서 실제 풀 시스템에 필요한 내용에서 어휘를 가져왔으며 PR에서 해당 검토를 요청합니다.

- **같은 시트이지만 숫자의 의미는 다릅니다.** 시트가 판정용으로 이미 계산하는 모든 것(능력치 수정치, 숙련 단계 보너스, 항목별 자유 보너스)은 `dice-pool`에서는 주사위 수입니다. 새 시트 어휘도, 새 편집기도, 수치를 선언하는 두 번째 방식도 없습니다. `formatRulesetCheckValue(definition, value)`가 숫자를 "+5" 또는 "5 dice"로 표시할지 정하는 유일한 곳이며, 프롬프트 시트 블록, 편집기, 게임 내 시트가 모두 거칩니다.
- **유형은 구조상 시트 계산을 공유합니다.** `abilityModifier`, `proficiency`, `proficiencyTiers`를 한 객체로 만들어 두 유니온 멤버에 펼칩니다. 따라서 곱할 보너스 없는 배율을 거부하는 교차 검사가 둘 다 실행되며, dice-sum 전용 규칙(자연 눈은 단일 주사위 필요)은 자체 분기 안에 남습니다.
- **이 유형이 표현하는 것.** `die.sides`, `pool`(시트 수치를 제한할 범위이며 `min` 0이면 빈 풀이 굴림 없이 실패 가능), `target`(고정 또는 Game Master가 바꿀 수 있는 범위), `double`, `explode`(연쇄되며 풀 자체 최대치로 제한), `cancel`, `botch`, `exceptional`, `situationalDice`, 그리고 단계별 선택적 목표를 가진 필요 성공 수의 `difficultyLadder`입니다. 발동할 수 없는 규칙은 가져올 때 거부합니다. 주사위 범위 밖의 눈, 성공이기도 한 취소 눈, Game Master가 설정할 수 없는 목표를 지정한 사다리 단계가 해당합니다.
- **대실패는 취소 전에 읽습니다.** 규칙은 '성공한 주사위가 하나도 없고 대실패 눈이 나옴'입니다. 따라서 유일한 성공이 취소된 풀은 대실패가 아닌 실패입니다. 대실패는 판정을 실패시키므로 대실패와 성공을 함께 보고할 수 없습니다.
- **판정별 속성 세 개는 거부 대신 범위를 제한합니다.** `threshold=`(목표가 조정 가능할 때만), `bonus=`(`situationalDice`가 있을 때만), `with=`(기술이나 내성을 자체 능력치 대신 다른 능력치로 굴림)입니다. 선언 범위 밖 값은 가까운 끝으로 맞추고, 규칙 집합에 없는 능력치는 디버그 한 줄과 함께 무시합니다. 해결된 기록은 결과(`SkillCheckResult.threshold`, `bonusDice`, `withAbility`)에서 쓰므로 원래 요구가 아니라 실제 적용을 보여 줍니다. 아무것도 굴리지 않은 희소 재작성만 요구를 원래대로 유지합니다. 수정치 함수를 공유하므로 `with=`는 두 유형에 모두 작동하며 5e 규칙 집합은 "Strength (Intimidation)"을 별도 구현 없이 얻습니다.
- **풀 결과는 항상 Engine이 만듭니다.** `rulesetVouchesFor`는 풀을 보증하지 않습니다. 숫자는 감사할 수 있지만 여러 주사위에는 내부적으로 일관된 결과가 너무 많아 감사로 제약할 수 없기 때문입니다. 따라서 `isRulesetRollableSkillCheckTag`는 모델이 습관적으로 쓴 어떤 `dice=`나 `resolution=`도 허용하고 `mode=`는 무시합니다. 풀은 시트에서 오며 이 유형에는 이점이 없기 때문입니다. 플레이어가 턴 전에 굴린 주사위는 적용하지 않습니다.
- **난이도는 성공 수입니다.** `isResolvableSkillCheckRequest`의 상한은 d20 범위가 아닌 `rulesetPoolMaxSuccesses`입니다. 최대 풀에 같은 수의 연쇄 주사위를 더하고 눈을 두 번 셀 때 두 배로 한 수로, 스키마가 사다리 단계나 `exceptional`에 허용하는 같은 값입니다. 결과를 미리 보는 풀이 규칙 집합 로딩 전에 쓰인 DC를 제한하므로 해결기가 한 번 더 제한합니다.
- **결과를 미리 보는 단일 요청 풀은 참여하지 않습니다.** 그 풀은 20면체를 담으므로 `dice-pool` 게임은 2d6 `dice-sum` 규칙 집합처럼 비공개 분기를 택합니다. 판정은 Engine이 굴리고 풀 값은 소모하지 않으며, 자신이 결정하지 않은 굴림에 슬롯을 기록하지 않습니다. 풀 규칙 집합에는 `dice` 자체가 없으므로 같은 조건 검사가 이제 주사위보다 유형을 먼저 읽습니다. 굴림 자리표시자(`[[roll: 1d8+NAME]]`)는 풀 규칙 집합에서 시트 이름을 해석하지 않고 프롬프트에도 안내하지 않습니다. 피해 굴림에 더한 주사위 수는 다른 의미의 숫자가 되기 때문입니다.
- **`SkillCheckResult`에 `threshold?`가 추가되었습니다.** 두 풀 경로가 모두 설정합니다. `dice-pool` 규칙 집합은 자체 규칙이 선택한 목표를 알고, 기존 `resolution="successes"` 태그는 전달받은 목표를 압니다. 직렬화기가 결과에서 `threshold=`를 쓰므로 두 표기가 어긋날 수 없으며 기존 경로의 바이트는 변하지 않습니다.
- **Capability API 1.24는 바이트에서 읽습니다.** `dice-pool` 해결은 오래된 Engine의 엄격한 스키마가 즉시 거부하는 형태입니다. 따라서 설치가 `ruleset.json`을 읽고 낮은 선언에서 유형을 거부합니다. 1.21의 `catalogs`, 1.22의 `battle`, 1.23의 `scaled`와 같은 방식입니다.
- **의도적으로 제외하고 문서에 명시한 것.** 가장 높은 주사위 선택(결과 유형에 없는 부분 성공 단계가 필요), 능력치와 비교하는 스탠스 풀, 기호 주사위, 대항 풀, 하향 판정과 끝없이 확장되는 백분위, 와일드 주사위가 있는 합산 풀입니다. 각각 별도 유형이 되어야 합니다. 자원을 써서 사는 재굴림과 자동 성공은 해결기 규칙이 아닌 Game Master의 `bonus=`와 `[sheet:]` 명령으로 처리합니다.
- **검증.** `docs/examples/rulesets/gravewatch.json`은 Ember Roads와 함께 제공하는 독창적인 10면체 풀 시스템입니다. `scripts/regressions/game-ruleset-dice-pool.regression.ts`는 스키마 거부, 주입한 주사위 수열을 사용한 모든 특수 규칙, 범위 제한, 태그 속성, 유형별 프롬프트 줄, 시트 블록 표현, 1.24 설치 제한, 변경 없는 기존 풀 경로, 사전 결과 풀이 비공개로 돌아가는 동작을 고정 검증합니다.

## 레이어 L1에서 확정한 것

'미결정 사항' 5번의 슬라이스 L1입니다. 레이어는 규칙 집합 자체 파일 안에 제공하는 변형이므로, 고정된 게임에서 사라질 수 없고 새 저장소나 경로, API 번호 외의 설치 제한이 필요 없습니다. L2(다른 사람이 제공하는 레이어)는 열린 과제로 남습니다.

- **효과는 닫힌 집합이며 모두 좁히거나 덧붙입니다.** `gm.checkGuidance`와 새 `gm.worldGuidance`에 지침을 더하고, 열거형 필드에서 값을 제거하고, 같은 해결 유형의 사다리로 난이도를 바꾸고, 시트 편집기 선택기에서 카탈로그 항목을 숨깁니다. 레이어는 항목을 추가하지 않습니다. 추가한 값은 시트의 다른 모든 독자와 그 레이어를 끈 모든 게임에 알려지지 않은 값이 되기 때문입니다. 모델 호출, 실시간 상태, 전투 수치도 추가하지 않습니다.
- **`gm.worldGuidance`는 레이어 키가 아닌 기본 슬롯입니다.** 기본 규칙 집합에는 게임이 생성될 세계를 정할 수단이 없었습니다. `/game/setup`이 고정 참조를 한 번 해석하고 레이어를 적용한 `worldGuidance`를 `buildSetupPrompt`에 전달하면 `<ruleset_world>`로 렌더링합니다. 설정 때 한 번 읽고 턴에는 전달하지 않습니다. 기존 설정 프롬프트 디버그 로그가 나머지와 함께 출력합니다.
- **선택은 이를 위해 존재하며 비어 있던 고정 참조의 `options` 레코드에 동결됩니다.** `/game/create`는 `rulesetLayerSelectionIssues`로 정의와 대조해 검증하며, 플레이어가 선택하지 않은 규칙으로 게임을 시작하는 대신 `ruleset_layer_unknown` 또는 `ruleset_layer_conflict`를 400으로 응답합니다. Engine이 소유하지 않은 키는 손대지 않고 함께 보냅니다. 레코드는 들어올 때만 `RULESET_REF_MAX_OPTIONS`로 제한하고, 고정 참조 자체는 계속 관대하게 읽습니다. 기존 게임을 읽을 수 없게 만들면 안 되기 때문입니다.
- **정확히 한곳에서 적용합니다.** `resolveGameRuleset`이 유효 정의를 반환하므로 프롬프트, 해결기, 시트 블록, 편집기, 전투 연결은 자체 변경 없이 모두 레이어가 적용된 규칙 집합을 봅니다. `baseDefinition`과 활성 `layers: {id,label}[]`도 노출합니다. 레지스트리 객체의 동일성을 유지해야 하는 호출자가 없어 다른 것은 바뀌지 않았습니다.
- **유효 정의를 재검증하되 두 완화를 문서화했습니다.** `rulesetEffectiveDefinitionSchema`는 파일 스키마에서 네임스페이스 ID를 허용하고(레지스트리가 커뮤니티 ID를 다시 지정하며 파일 스키마는 슬래시를 거부), 지침 상한을 느슨하게 한 것입니다. 레이어가 파일당 1500자로 제한된 텍스트에 덧붙이기 때문입니다. 그래도 기본값과 레이어별 4000을 합한 상한이 있습니다. 유효 정의에서 건너뛰는 유일한 규칙은 레이어와 필드 간 교차 검사입니다. 제거 대상 값은 이미 사라져 있으며, 그것이 의도입니다.
- **레이어 때문에 게임이 규칙 집합을 잃지 않습니다.** `applyRulesetLayers`는 예외를 던지지 않습니다. 모든 활성 레이어를 함께 검증하고, 실패할 때만 하나씩 더해 작동하는 것만 유지합니다. 파일에 더는 없는 선택된 레이어와 충돌 쌍 중 나중 것은 적용하지 않을 뿐입니다. 매 턴 해석하므로 둘 다 경고가 아닌 디버그 로그로 남깁니다.
- **지침은 빈 줄이 아닌 공백으로 연결합니다.** 형식의 모든 지침 문자열은 `promptSafeText` 규칙상 한 줄이며, Game Master 리마인더는 `checkGuidance`를 하나의 글머리표 안에 렌더링합니다. 줄바꿈은 새 지시문처럼 읽힐 수 있습니다.
- **충돌은 대칭이며 나중 레이어를 버립니다.** 쌍의 한쪽만 지정하면 충분하고 선언 순서로 결정하므로 같은 두 선택은 항상 같은 규칙을 만듭니다.
- **캐릭터를 다시 쓰지 않습니다.** 이미 제거된 열거 값을 가진 시트는 유지하고 표시하며, 편집기가 선택지 제공만 중단합니다. 레이어가 숨긴 카탈로그 항목은 선택기에서 제외되지만 플레이어가 이미 고른 행은 남습니다. `catalogEntryHiddenByLayers`가 선택기 필터이며, 규칙 집합 자체 항목은 건드리지 않습니다.
- **클라이언트 부분은 같은 두 도우미를 기반으로 합니다.** `GameSetupRulesChooser`는 선택한 규칙 집합 아래 레이어별 체크박스를 그리고, 선택한 레이어가 배제하는 쪽을 비활성화하며 이름을 표시합니다. `packages/client/src/lib/ruleset-layers.ts`는 순수 부분, 즉 토글, 옵션 레코드, 설치 정의에 없는 레이어 ID를 버리는 복원을 담습니다. `useGameRuleset`은 고정 참조의 레이어를 한 번 적용하므로 게임 안의 모든 독자가 유효 정의를 보며, 시트 제목에 규칙 집합 이름과 활성 레이어를 표시합니다. 선택기는 `visibleCatalogEntries`로 제공 범위만 좁히고 다른 것은 바꾸지 않습니다. Refresh from ruleset과 조정 열은 쿼리에서 카탈로그를 직접 읽고, 캐릭터와 페르소나 편집기는 옵션을 전혀 전달하지 않아 아무것도 숨기지 않습니다. `scripts/regressions/ruleset-layers-client.regression.ts`가 이를 모두 고정 검증합니다.
- **Capability API 1.25**는 바이트에서 읽으며, 1.21의 `catalogs`, 1.22의 `battle`, 1.23의 `scaled`, 1.24의 `dice-pool`과 같습니다. 비어 있지 않은 `layers` 배열 또는 기본 `gm.worldGuidance`가 있으면 선언이 필요합니다.
- **세 예제 모두로 입증했습니다.** Ember Roads에 "Hard winter"(더 가혹한 사다리, 두 지침 슬롯, Grit을 쓰는 재주를 선택기에서 숨기는 규칙), Gravewatch에 "The long night"(단계별 목표가 있는 성공 수 사다리로 d20 전용 형태가 아님을 입증), 5e 초안에 "Low magic"(주문 시전 열거형에서 값 두 개 제거)과 충돌하는 "High magic"을 추가했습니다. `scripts/regressions/game-ruleset-layers.regression.ts`는 스키마 거부, 모든 예제의 모든 조합 적용, 같은 참조 반환, 대체 처리, 라우트 거부와 고정 참조 동결, 리마인더, 세계 프롬프트, 1.25 제한을 고정 검증합니다.

## 실제 규칙 집합 전투

**결정.** 전투가 규칙 집합별 TypeScript 어댑터여야 하는지 데이터여야 하는지 묻자, 사용자는 [#6361](https://github.com/Pasta-Devs/Marinara-Engine/issues/6361)에서 '실현할 수 있는 가장 충실한 5e 전투를 위해 필요한 것은 무엇이든 하며, PR 순서는 알아서 정하라'고 결정했습니다. 따라서 `combat` 블록은 `resolution`과 함께 Engine 소유 유형에 매개변수를 주는 검증된 데이터가 됩니다. 전투 인계가 예약한 `5e-2014` 어댑터는 5e 패키지 자체 데이터가 되며, 형식은 절대 5e 모양이 아니라는 기존 규칙은 유지됩니다. 충실도는 한 시스템의 용어를 지정하는 파일이 아니라 풍부한 고정 어휘와 패키지 데이터에서 나옵니다.

**구조.** 다음 순서의 네 경계입니다.

1. `packages/shared/src/features/ruleset-combat/`의 순수 공유 해결기입니다. I/O가 없고 굴림기를 주입하며 단순 직렬화 가능 상태를 사용합니다. 행동하는 모두가 하나의 합법 메뉴에서 ID를 선택합니다.
2. 전투 디렉터의 기존 원장 위에 서버 소유 세션 하나를 두고, `classic`, `tactical` 옆의 세 번째 `style`로 사용합니다. 같은 저장 행, 리비전, 멱등성, 뮤텍스, 창, 단일 '후보 ID 선택' 모델 호출을 쓰며 두 번째 원장은 없습니다.
3. 기존 셸을 이미 허용하는 `directed` prop으로 구동하되 하드코딩된 메뉴를 선택지 메뉴로 바꾸고 로그에는 실제 굴림을 넣습니다.
4. 연결 기능은 규칙 집합별로 물러납니다. `combat`를 선언한 규칙 집합은 `battle` 경로를 쓰지 않으며 `coverage.combat`가 마침내 의미를 갖습니다.

**슬라이스.** C1은 스키마와 해결기입니다. C2는 생물 도감 카탈로그, 능력치 블록 행동, 연속 행동과 재충전, 위협 제한, 5e 패키지 자체 생물과 강화된 주문입니다. C3는 디렉터의 `ruleset` 스타일이며 C3a(세션, 라우트, 영속화, 메뉴 기반 적 선택)와 C3b(실제 수치를 쓰는 Classic 셸, `coverage.combat` 참)로 나눕니다. C4는 보드이며 C4a(형식, 위치, 이동, 근접 거리와 사거리, 범위, 엄폐, 기회 공격, 선택기와 뷰)와 C4b(Tactical 스타일의 기존 모습을 활용한 화면 보드)로 나눕니다. C5는 턴에 할 수 있는 일과 턴을 중단하는 것으로, C5a(턴 행동 체계, 부가 효과와 상태 어휘)와 C5b(창 자체: 보류한 걷기와 고유 행동을 구매하는 창)로 나눕니다. C5c 이후는 창을 여는 다른 상황, 전설 행동, 대항 판정, 나머지 상태입니다.

### C1에서 확정한 것

- **블록은 선택 사항이며, 없으면 빈 값 대신 생략하고 `battle` 옆에 둡니다.** 규칙 집합은 둘 다 가질 수 있습니다. `combat`를 쓰기에는 오래된 Engine이 연결 기능으로 돌아가며, 한 전투가 둘을 함께 쓰지는 않습니다. Capability API 1.26이며 규칙 집합 자체 바이트에서 읽습니다. 1.21의 `catalogs`, 1.22의 `battle`, 1.23의 `scaled`, 1.24의 `dice-pool`, 1.25의 `layers`와 같습니다.
- **종류는 `attack-vs-defense` 하나로**, `dice-sum`처럼 매개변수를 줍니다. 우선권과 공격 주사위를 선언하므로 2d6 시스템에 별도 종류가 필요 없습니다. `dice-pool` 규칙 집합에는 난이도와 비교할 합계가 없으므로 전투 안의 내성 굴림은 공격 주사위를 굴립니다. 작성 가이드도 이를 설명합니다.
- **모든 이름은 규칙 집합의 것이며 전부 교차 검증합니다.** 체력 풀은 비어 시작하지 않는 선언된 실시간 풀이어야 하고, 방어와 우선권 수정치는 값 참조입니다. 공격 열은 지정한 목록에 속하며 올바른 자료형이어야 하고, 능력 목록은 `battle.skills`처럼 거릅니다. 상태는 시트 자체 ID를 닫힌 효과 목록에 대응시키고, 집중은 실시간 텍스트와 내성을, 빈사는 서로 다른 트랙 둘을 지정합니다. 예산 ID는 고유하며 `attacks[].budget`, `abilities[].budget`, `mechanics.budget`은 선언된 예산을 지정합니다.
- **행동 체계는 예산 목록입니다.** 각각 턴 또는 라운드 `per`와 횟수가 있습니다. 처음 선언한 예산이 주 예산이고 표준 행동이 소모하는 것입니다. 표준 행동은 Engine의 것이며 대안은 모든 파일에서 '행동'을 말하는 두 번째 방법이었으므로 키 대신 관례를 썼습니다.
- **`mechanics`에 선택적이며 기존 내용에 더해지는 여섯 키를 추가했습니다.** `targetCount`, `autoHit`, `applies`(상태, 지속 시간, 끝내는 선택적 내성), `temporary`, `scales`(값 참조의 단계 표에서 가져오는 추가 주사위), `budget`입니다. `rulesetCatalogEntryIssues`가 검사하므로 인라인과 자산 카탈로그에 같은 규칙을 적용합니다.
- **시트 기반과 블록 기반 전투원.** 파티원은 `evaluateRulesetSheet`, `resolveRulesetValueRef`, `readRulesetLive`, `rulesetCheckModifier`로 읽고, 조우 안에 실린 실시간 블롭에 `applyRulesetSheetOp`로 씁니다. 따라서 체력, 자원, 상태, 집중은 전투 중과 후 모두 시트의 것이며 중간 재로딩도 정확합니다. 상대는 단순 능력치 블록이며 조우 안에만 존재합니다.
- **합법성은 메뉴 한곳에만 있습니다.** `rulesetCombatOptions`는 시트 자체 `use` 명령의 모의 실행(`planRulesetUse`, 재구현 대신 재사용)으로 비용을 산정해 지금 감당 가능한 것을 제시합니다. 같은 계열의 더 높은 풀을 쓰는 상위 단계 사용도 포함하며, `perCostStep`은 선언된 풀과 지불 풀 사이 단계마다 한 번씩 주사위를 더합니다.
- **정의는 상태의 일부가 아닌 매개변수입니다.** `rulesetCombatOptions`, `applyRulesetCombatChoice`, `advanceRulesetTurn`, `rulesetEncounterSummary`는 모두 고정 참조가 해석한 정의를 받습니다. 상태는 `{ id, version }`을 담아 저장된 전투가 무엇으로 해결되었는지 밝히며 저장할 만큼 작게 유지합니다. 파티원의 카탈로그는 자신의 행이 가리키는 항목만 남깁니다.
- **이벤트는 결론이 아니라 계산을 담습니다.** 실제 주사위 눈, 수정치, 합계, 맞선 방어 또는 난이도, 저항이 한 일, 남은 양입니다. 로그는 직접 계산 없이 "17 + 5 = 22 against 15: hit, 9 slashing"을 출력할 수 있습니다.
- **예외를 던지지 않습니다.** 불법 선택은 받은 상태를 같은 참조로 그대로 반환하고, 닫힌 목록의 사유를 가진 `refused` 이벤트 하나를 반환합니다.
- **C1에서 의도적으로 하지 않는 것**은 경계를 남겨 두고 작성 가이드에 명시합니다. 위치, 거리, 근접 거리, 사거리, 지도상 범위, 엄폐와 이동(`range`, `area`, `economy.movement`, 거리를 읽는 네 상태 효과는 검증하되 읽지 않음), 반응과 창(`cannot-react`, `reaction` 항목은 메뉴에서 제외), 생물 도감과 다중 공격과 재충전, 상대가 누구를 공격할지 선택하는 일입니다. 아직 플레이할 수 있는 것은 없습니다. 라우트, 세션, 화면이 없습니다.
- **정해진 주사위로 두 예제에서 입증했습니다.** `scripts/regressions/game-ruleset-combat-core.regression.ts`는 스키마 거부, 규칙 효과 교차 검사, 우선권과 두 동률 처리, 메뉴, 행동 체계, 명중, 빗나감, 특별한 눈, 치명타, 이점과 불리점 상쇄, 저항·취약·면역이 있는 유형 피해, 임시 점수 우선 소모, 절반 또는 무피해 내성, 범위의 피해 굴림 공유, 시트를 통한 슬롯 소모와 빈 슬롯 거부, 상위 단계 사용, 조정되는 소마법, 내성 종료와 기간이 있는 상태, 피해로 끊기고 두 번째 능력으로 대체되는 집중, 특별한 눈의 회생과 세 실패의 죽음을 포함한 빈사, 0에서의 회복, 승리, 패배, 요약, 1.26 설치 제한, 전투 중 `JSON.parse(JSON.stringify(...))`를 거치는 상태를 고정 검증합니다.

### C2에서 확정한 것

- **카탈로그는 담은 내용을 명시합니다.** `holds`는 `"rows"`(기본값이므로 이 릴리스 이전 카탈로그는 그대로) 또는 `"creatures"`입니다. 생물 도감은 `feeds`를 선언하지 않고 `combat` 블록과 `threat` 척도가 필요합니다. 시트 편집기 선택기는 `feeds`를 기준으로 하므로 도감을 보거나 제공하지 않습니다. 항목은 `rows` 또는 `creature` 중 하나를 가지며 둘 다 있거나 둘 다 없을 수 없습니다. 생물은 자체 행동으로 하는 일을 말하므로 `mechanics`가 없습니다. 혼합 카탈로그는 인라인과 `catalogs/<id>.json` 자산 모두에서 거부하며, 둘 다 `rulesetCatalogEntryIssues`가 검사합니다.
- **생물은 `combat`가 이미 선언한 키로 작성합니다.** 숫자 또는 조우 생성 시 굴리는 주사위로 표현하는 체력, 방어, 우선권 수정치, 시트 자체 ID 아래의 능력치와 내성 수정치, 선언된 피해 유형별 저항, 시트 자체 상태별 면역, 규칙 집합 자체 척도의 단계, Game Master에게 보여 주되 해결하지 않는 프롬프트 안전 특성, 그리고 행동입니다. Capability API 1.27이며 1.21~1.26과 똑같이 규칙 집합 자체 바이트에서 읽습니다.
- **능력치 블록은 자체 내성 난이도를 가집니다.** `save.difficulty`, 또는 행동이 자체 내성을 요구하지 않을 때 내성으로 끝나는 상태용 `saveDifficulty`이며, 내성을 요구하는 곳에는 둘 중 하나가 필수입니다. 카탈로그 행의 C1 규칙(능력 원본이 수치를 공급)은 여기에 대응 항목이 없습니다. 블록은 시트가 아니기 때문입니다.
- **생물 행동에만 있는 네 가지:** `uses`(조우별 또는 일별), `recharge`(사용 시 소모, 보유자의 턴 시작에 굴리고 `from` 이상이면 회복, 시작 시 사용 가능), `sequence`(같은 블록의 다른 행동을 순서대로 실행, 전체 예산 한 번, 각 부분의 표적과 굴림 독립, 다른 연속 행동 지정 불가), `signature`(블록 자체 `signaturePoints`로 구매, 자신의 턴 시작에 보충, 자신의 턴 메뉴에는 없음)입니다. `rulesetSignatureOptions`가 비용을 정하고 `applyRulesetCombatChoice`가 지불하며, C5b가 두 턴 사이에 여는 창에서만 가능합니다.
- **연속 행동은 모든 부분의 표적을 받습니다.** 적게 주면 각 부분은 목록 앞의 표적을 쓰므로 ID 하나는 '전부 같은 표적'입니다. 전투가 이미 끝난 표적의 부분은 건너뛰고 새 표적을 고르지 않습니다. 선택은 호출자의 일입니다.
- **제한은 제안에만 적용합니다.** 제공된 생물 도감은 작성자 데이터이므로 원문대로 사용합니다. Game Master가 만든 생물은 `clampRulesetStatBlock`을 거쳐 체력을 단계 범위로, 방어와 명중과 내성 난이도를 단계보다 최대 2 높게 맞춥니다. 규칙 집합에 없는 이름과 여섯 개를 넘는 행동을 버리고 최강 라운드가 단계 `damagePerRound` 상한에 맞을 때까지 피해를 줄입니다. 주사위 개수, 고정 부분, 연속 행동의 타격 하나, 주사위 면 수 순서이며 어떤 것도 0으로 만들지 않습니다. 선언되지 않은 단계는 가장 낮은 것으로 돌아가고, 모든 변경은 로그용 평이한 문장으로 반환합니다.
- **`damagePerRound`는 연속 행동을 포함한 전체 라운드에서 한 표적이 받는 양입니다.** 공격 한 번이 아닙니다. 제한이 묶어야 하는 것은 라운드이기 때문입니다.
- **조회는 정확한 참조, 단순 이름, 없음 순서입니다.** `findRulesetCreature`는 `<catalogId>/<entryId>`를 맞추고, 다음으로 대소문자와 문장부호를 제외한 라벨이나 ID를 맞추며, 없으면 null을 반환합니다. 전달한 카탈로그에 없는 참조는 숫자 없는 생물을 들이지 않고 그 상대를 전투에서 제외하며 `unknown-creature`가 있는 `refused` 이벤트 하나를 남깁니다.
- **두 예제 모두에서 입증했습니다.** `scripts/regressions/game-ruleset-combat-creatures.regression.ts`를 사용합니다. Ember Roads는 독창적인 생물 셋과 세 단계 위협 척도, 5e 초안은 생물 넷을 제공하며 어느 파일 형식도 다른 쪽 용어를 알지 못합니다.

### C3a에서 확정한 것

C3는 둘로 나눕니다. C3a는 서버 부분, C3b는 화면입니다. 형식이 바뀌지 않았으므로 Capability API는 올리지 않습니다.

- **원장 하나, 세 번째 `style`.** `DirectedCombatView.style`에 `"ruleset"`을 추가합니다. 같은 저장 행과 네임스페이스, 같은 리비전·인스턴스·요청 ID 멱등성, 같은 채팅별 큐, 같은 '모델은 Engine이 열거한 메뉴에서 후보 ID만 고른다'는 규칙을 씁니다. 플레이어의 선호인 `GameCombatStyle`은 두 값으로 유지합니다. 규칙 집합 스타일은 선호가 아니라 `combat` 블록이 있는 규칙 집합 게임에 적용되는 방식입니다.
- **스타일 자체 로직은 별도 파일에 둡니다.** `ruleset-combat-director.service.ts`는 `(definition, state)`에 대해 순수하므로 회귀 검증이 데이터베이스 없이 전투 전체를 진행합니다. 기존 `combat-director.service.ts`에는 세 분기 지점만 추가했습니다. 확장된 `style`, 저장 상태의 `rulesetFight` 필드, 그리고 해결할 수 없는 전투에 작업 큐가 돌지 않도록 하는 `advanceCombatDirector`와 `commandCombatDirector`의 조기 반환입니다.
- **전투를 어떤 규칙으로 해결할지는 서버가 정합니다.** `/start`가 채팅의 고정 참조를 직접 해석하고 규칙 집합이나 `combat` 블록이 없는 게임을 거부합니다. 파티는 `rulesetSheetBuildsByName`을 통해 채팅 자체 시트에서 읽습니다. 이 함수는 공유 전투 연결로 옮겨 `battle` 연결과 이 스타일이 같은 규칙으로 전투원과 시트를 맞추게 했습니다. 클라이언트가 보낸 시트는 읽지 않으며, 시트가 없는 멤버는 이름으로 거부합니다.
- **상대의 수치**는 다음 순서로 구합니다. Game Master가 지정한 참조에 `findRulesetCreature`, 다음으로 상대 자체 이름에 같은 조회, 다음으로 공유 생물 형태의 제안에 `clampRulesetStatBlock`, 마지막으로 단계 자체 수치로 단순 블록을 만듭니다(`rulesetTierStatBlock`: 체력 범위 중간값, 단계의 방어와 명중, `damagePerRound` 중간값을 고정·무유형 피해로 주는 공격 하나). 모든 대체 과정과 제한 행은 세션의 `adjustments`에 보관하고 한 번 로그에 남깁니다.
- **Engine 자체 `party`와 `enemies`는 매 단계 후 동기화합니다.** `handleCombatEnd`, 전투 요약과 일지가 읽고 전투 종료 시 `CombatSummary`도 여기서 채우기 때문입니다. 승자는 `rulesetEncounterOutcome`이 정하며, 체력은 같은 숫자이므로 일치합니다.
- **행동이 허용되면 원장 저장 안에서 실시간 시트 상태를 씁니다.** 새 블롭은 응답에 실려 돌아오므로 클라이언트 저장소가 다시 가져올 필요 없습니다. 쓰기가 실패하면 단계가 실패하므로 원장과 시트가 어긋날 수 없으며 이 스타일에는 전투 종료 시 되돌려 쓰기가 전혀 없습니다.
- **메뉴는 전송받으며 계산하지 않습니다.** `rulesetOptionTargets`는 해결기 옆의 새 공유 도우미이며 `applyRulesetCombatChoice` 자체 표적 검사도 이제 이를 거칩니다. 따라서 클라이언트에 제공하는 목록과 규칙이 허용하는 목록이 같습니다.
- **`continue`는 사람이 조종하지 않는 행동자의 정확히 한 턴을 해결합니다.** 하는 모든 행동, 턴 종료, 다음 행동자까지입니다. 선택기는 메뉴를 `CombatAiCandidate`로 만들고 기존 `chooseCombatCandidate`가 고르게 하므로 다른 두 스타일과 같은 전술로 규칙 집합 전투를 평가합니다. 턴당 행동 열두 개로 제한하고 반드시 턴을 끝내며 폭발을 아군에게 겨누지 않습니다. 표적이 아군인지는 선택지를 어느 편용으로 썼는지가 아니라 표적 자체에서 읽습니다. 아군 공격을 허용하는 작성자에게 필요한 방식입니다.
- **보스는 대신 창을 엽니다.** 후보마다 `CombatDecisionOption` 하나를 두고 `optionId`, `targetIds`, `label`을 추가 확장합니다. 기존 `continue` 작업이 `buildCombatBossPrompt` 옆의 규칙 집합 인식 프롬프트 빌더로 응답합니다. 같은 JSON 전용 `{"candidateId"}` 답, 같은 디버그 줄, 같은 10초 제한, 같은 호출 상한, 쓸모없는 출력이나 메뉴에 없는 ID가 오면 같은 로컬 선택기 대체를 씁니다.
- **거부는 아무것도 바꾸지 않으며** 리비전을 올리거나 요청 ID를 소비하지 않습니다. 해결기 자체 사유를 안정적인 `code` 필드(`ruleset_combat_<refusal>`)에 담아 400으로 답합니다.
- **규칙 집합이 사라진 전투**는 500이나 다른 규칙의 해결 대신 결과 `flee`로 종료된 상태와 이유를 설명하는 디렉터 이벤트 하나를 반환합니다. 이 결과는 저장하지 않으므로 규칙 집합을 다시 설치하면 같은 전투를 중단한 곳에서 계속할 수 있습니다.
- **청사진은 규칙 집합의 용어를 씁니다.** 채팅의 규칙 집합이 `combat`를 선언하면 `/encounter/init`이 위협 단계와 크기를 제한한 도감 색인(선언 순서의 처음 60개 이름)을 나열하고 각 상대의 `creature`, `tier`, `proposed` 블록을 요청합니다. 규칙 집합이 없거나 `combat`가 없는 게임은 기존 프롬프트를 그대로 받으며, 잘못된 `proposed`는 청사진 전체를 실패시키지 않고 버립니다.
- **검증:** `scripts/regressions/ruleset-combat-director.regression.ts`(순수, 두 예제 규칙 집합)와 `ruleset-combat-director-route.regression.ts`(실제 라우트, 실시간 쓰기, 변하지 않은 Classic 전투, 모델을 모의한 보스 창, 청사진 프롬프트)에서 검증했습니다.

### C3b에서 확정한 것

C3b는 화면입니다. 형식은 바뀌지 않았고 아래 공유 추가 세 항목은 Engine 밖에서 쓰지 않는 필드이므로 여전히 Capability API를 올리지 않습니다.

- **한 판단으로 전투가 규칙 집합 자체의 것인지 정하고 모두가 읽습니다.** `packages/client/src/lib/ruleset-combat-bridge.ts`의 `isRulesetCombatFight({ combatDirector, definition, anchor })`입니다. 셋 모두 충족해야 합니다. 파일이 선언한 블록에서 읽으며 `coverage.combat`로 판단하지 않습니다. 후자는 파일 내용이 아닌 작성자의 주장이기 때문입니다. 설정 마법사와 가져오기 검토도 같은 검사로 전투가 어떻게 동작할지 설명합니다.
- **무대는 Classic 셸입니다.** `GameCombatUI`의 `directed` prop에 선택적 `ruleset` 부분을 추가합니다. 없으면 모든 Classic 경로는 기존 그대로이며, 있으면 하드코딩된 공격/기술/방어 메뉴와 하위 단계, 방향키 처리를 모두 규칙 집합 메뉴로 바꿉니다. 초상화, 체력 막대와 애니메이션은 이미 서버가 동기화하는 `party`, `enemies`를 읽으므로 전혀 손대지 않았습니다.
- **화면은 적법성이나 계산을 산출하지 않습니다.** 메뉴, 합법 표적 ID, 비용, 예측, 로그의 모든 숫자는 서버 뷰에서 옵니다. 규칙이 거부하는 선택지는 보내지 않으므로 클라이언트가 회색으로 비활성화하지 않습니다. 400 거부는 `code`별 번역 문장으로 표시하고 이 빌드가 모르는 코드는 서버 자체 문장으로 대체합니다.
- **용어는 규칙 집합의 것입니다.** 예산, 상태, 내성, 트랙, 단계, 풀, 공격 굴림이 대항하는 값은 모두 파일의 라벨을 출력하므로 5e는 "Armor Class", Ember Roads는 "Guard"라고 표시합니다. Engine이 이름을 정하는 것은 유형 자체의 고정 표준 행동 목록과 턴 종료뿐입니다.
- **로그는 순수 모듈 하나**, `packages/client/src/lib/ruleset-combat-log.ts`로 구현하여 이벤트 유형마다 문장을 고정 검증할 수 있습니다. 더하는 값이 없는 굴림은 주사위만 출력합니다. 여러 주사위의 합이 채택 값이면 그 묶음을 출력합니다. 이점과 불리점은 이벤트가 어느 쪽인지 알려 줄 때만 두 주사위와 채택한 하나를 표시합니다.
- **연결 기능은 바로 그 전투에 대해서만 물러납니다.** 서버가 허용된 단계를 즉시 썼으므로 `startBattleParty`는 시트에서 초기화하지 않고 `handleCombatEnd`는 `applyRulesetBattleResult`를 부르지 않습니다. `battle`은 있고 `combat`는 없는 규칙 집합과 디렉터가 없는 게임은 기존 연결을 그대로 유지합니다.
- **전투 회고는 실제 요약입니다.** `CombatSummary`에 `RulesetEncounterSummary`를 담는 선택적 `ruleset` 필드를 추가합니다. 회고는 백분율 줄 대신 규칙 집합 자체 풀의 체력 값과 최대치, 누가 쓰러졌거나 빈사 또는 안정 상태인지, 라벨별 상태, 자체 라운드 수, 시트를 최신 상태로 유지했다는 한 줄을 출력합니다.
- **작은 공유 추가 세 가지는 모두 증분입니다.** `RulesetEncounterSummary.party[].stable`(없으면 회고에서 악화를 멈춘 사람과 아직 시간이 흐르는 사람을 구분할 수 없음), `CombatSummary.ruleset`, 그리고 청사진 자체 용어가 클라이언트 경로를 거쳐 `/start`에 닿도록 `CombatEnemy`와 `Combatant`의 `creature`/`tier`/`proposed`를 추가합니다.
- **작은 서버 변경 하나:** `syncRulesetCombatants`가 이제 전투의 라운드로 디렉터 자체 `round`를 설정합니다. 전에는 계속 1이어서 전투 내내 "Round 1", 회고에 "after 1 round"로 표시되었습니다.
- **검증:** `scripts/regressions/ruleset-combat-screen-client.regression.ts`(실제 영어 카탈로그를 통한 두 예제 규칙 집합의 모든 이벤트 문장, 메뉴 그룹, 표적 선택, 모든 조합의 위 판단, 실제 요약의 회고)와 `e2e/game-combat-director.e2e.ts`의 세 번째 모드에서 검증했습니다. 후자는 실제 라우트로 Ember Roads를 가져와 전투를 진행합니다.

### C5a에서 확정한 것

C5a는 공유 및 서버 측에서 한 턴이 할 수 있는 일입니다. 모든 내용은 선택적 추가이며, 아무것도 선언하지 않은 규칙 집합은 이전과 바이트 단위로 똑같이 해결됩니다.

- **한 타격이 여러 양으로 구성될 수 있습니다.** 카탈로그 항목의 `mechanics.plus`와 생물 행동의 `damage.plus`는 최대 세 절입니다. 각각 따로 굴리고 유형을 가지며, 표적 자체 내성을 따로 적용하고, 치명타로 따로 두 배가 되며, 표적에게 자체 내성을 요구할 수 있습니다(`onSuccess: "none"`은 해당 절을 없애고 `"half"`는 절반을 남김). 함께 만든 타격은 합산 피해로 집중을 한 번 검사하고 쓰러짐도 한 번 검사합니다. 예측, 위협 제한, 라운드당 피해 측정은 모두 절을 포함합니다. 예측은 타격이 할 일을 말하므로 내성 조건이 있는 절도 전량 계산합니다.
- **예산 한 번으로 여러 타격을 얻습니다.** `combat.attacks[].strikes`는 값 참조입니다. 첫 실행에서 예산을 쓰고 나머지를 `combatant.strikesLeft`에 둡니다. 보유분이 있는 동안 `strikes`를 선언한 목록의 모든 행을 예산 없이 제시하며, 메뉴에 잔량을 표시할 수 있도록 `option.strikes`를 담습니다. 다른 무기, 다른 표적, 사이의 걷기가 모두 예외 처리 없이 메뉴에서 나옵니다. 한 번 지불해 한 번 타격하는 목록은 보유분을 만들지 않고 이벤트도 내지 않으므로 기존 로그는 변하지 않습니다.
- **행동 체계를 바꾸는 능력.** `mechanics.free`는 예산을 쓰지 않고, `mechanics.gives`는 쓰는 순간 예산에 더하며 도착값을 제한합니다. `mechanics.standard`는 지정한 표준 행동을 `standard:<id>@<budget>`으로 제공하고 이를 부여한 능력 기준으로 가격을 정합니다. `gives`나 `standard`를 선언한 `utility` 항목은 버리지 않고 행동으로 만들며, `standard`만 있는 항목 자체는 메뉴에서 제외합니다. 허용은 누가 실행하는 행동이 아니기 때문입니다.
- **부가 효과.** 새 카탈로그 항목 종류 `rider`와 생물 자체 `riders[]`입니다. 지속 효과로 메뉴에 나오지 않으며 기간의 첫 조건 충족 명중에 절 하나를 추가합니다. 적용 공격은 전투 시작 시 한 번, 지정한 공격 목록과 그 행의 참으로 평가되는 열 하나에서 구하므로 해결 중 시트를 다시 읽지 않습니다. `oncePer: "turn"`은 누구의 턴이든 매 턴 시작에 초기화되어, 다른 이가 행동할 때 가한 타격에도 붙을 수 있습니다.
- **상태 어휘.** 새 효과 다섯과 `saves`(두 내성 효과가 대상으로 하는 내성), `whileSourceInSight`(그 상태 모든 효과의 조건), `endsWhenSourceDown`을 추가합니다. 추적 상태는 이미 부여자를 기록하므로 원본에 묶인 세 효과를 위해 새로 저장할 것은 없었습니다.
- **검증:** `scripts/regressions/game-ruleset-combat-core.regression.ts`의 C5a 블록(거부, 절, 타격, 행동 체계, 부가 효과, 상태, 두 예제, 해당 키가 전혀 없는 규칙 집합의 같은 전투와 이벤트별 비교)과 `game-ruleset-combat-grid.regression.ts`의 보드 전용 상태 사례로 입증했습니다.
- **C5b 이후로 남긴 것:** `on`은 `hit` 하나뿐이므로 부가 효과는 여전히 자동 발동합니다. `combat.standard`는 기존 규칙 집합이 모두 그 방식으로 작성했으므로 단순 문자열의 고정 목록으로 유지했습니다. 회피가 맞기 어려워지는 것 외에 하는 일은 옆의 `combat.standardEffects.dodge.saves`에서 설명합니다.

### C5b에서 확정한 것

C5b는 창입니다. 현재 행동자가 아닌 누군가를 위해 한 단계와 다음 단계 사이에 전투를 보류합니다.

- **새 키도 Capability API 상승도 없습니다.** 창이 읽는 어휘는 모두 이미 있었습니다. `combat.opportunity.budget`은 지나가는 이를 치는 비용을, 생물의 `signature`와 `signaturePoints`는 점수로 살 것을 정합니다. 달라진 점은 Engine이 대신 결정하지 않고 묻는 것입니다. 전에는 기회 타격을 보유자 대신 실행했고, 고유 행동은 자신의 턴이 아닌 아무 순간에나 구매할 수 있었습니다. 이 슬라이스 전 패키지도 같은 전투를 질문 하나씩 하며 진행합니다.
- **창은 상태 안에 있습니다.** `RulesetEncounterState.window`는 종류, 연 계기, 아직 답할 사람을 담고, 걷기가 열었다면 남은 걷기까지 담습니다. 이미 지난 칸, 남은 칸, 지불한 것, 이미 질문한 모두입니다. 걷는 중 저장한 전투는 같은 사람에게 질문이 남고 같은 칸을 더 걸어야 하는 상태로 돌아옵니다. `windows`는 지금까지 열린 모든 창을 세므로 이미 닫힌 창에 쓴 답을 대체 창에 소비하지 않고 거부합니다.
- **창이 열려 있으면 다른 것은 움직이지 않습니다.** 턴 종료를 포함한 다른 선택은 모두 `window-open`으로 거부하고, 다른 창을 지정한 답은 `stale-window`로 거부합니다. 진입점은 같습니다. `applyRulesetCombatChoice`가 턴 선택과 똑같이 `rulesetWindowOptions` 또는 `RULESET_PASS_OPTION`에서 답을 받습니다.
- **각자 한 번 답합니다.** 창은 대기 중인 전투원에게 공격이든 넘기기든 한 번만 묻습니다. 답할 수단이 없는 사람은 넘기기만 있는 메뉴를 위해 전투를 붙잡지 않고 제외합니다. 경로가 같은 근접 거리를 몇 번 벗어나든 걷기 전체에 각자 기회는 한 번입니다.
- **마지막 타격이 전투를 끝냈어도 걷기는 마무리합니다.** 걷기 자체 이벤트가 이동자가 실제 어디에 멈췄는지 말하기 때문입니다.
- **디렉터가 진행합니다.** 창에 있는 참가자 중 사람이 조종하지 않는 모두는 그 자리에서 창 자체 메뉴와 자신의 턴을 하는 같은 점수 평가로 답합니다. Game Master의 보스는 Game Master 자체 결정으로 질문받고, 순간을 흘려보내는 것도 답입니다. 창은 누군가 자신의 파티원일 때만 대기하며, 클라이언트는 `DirectedRulesetView.window`로 질문과 Pass를 그립니다.
- **검증:** `scripts/regressions/game-ruleset-combat-grid.regression.ts`의 창 블록(보류, 메뉴, 타격, 넘기기, 거부, 걷기당 한 번 기회), `game-ruleset-combat-creatures.regression.ts`의 고유 행동 창, `ruleset-combat-director-route.regression.ts`의 보스 자체 창으로 입증했습니다.
- **C5c 이후로 남긴 것:** 창을 여는 다른 상황입니다. `reaction`으로 표시된 카탈로그 항목은 아직 계기를 지정하지 않으므로 어느 메뉴에도 없습니다. 반응이 무엇에 응답하는지 표현할 어휘, 대응과 함께 필요한 중첩·취소·환급은 다음 슬라이스에서 다룹니다.

### C5c에서 확정한 것

C5c는 순간입니다. 반응이 어느 순간을 기다리는지 정하여, `reaction`으로 표시한 항목이 마침내 속할 창을 갖게 합니다.

- **`mechanics.reaction`은 `true` 대신 객체일 수 있습니다.** `on`은 순간, `at`은 실행 내용을 누구에게 겨눌지 정하고, `cancels`는 창이 보류한 것을 중단합니다. `true`는 여전히 턴에 실행하지 않는다는 기존 뜻일 뿐이며, 그만 쓰는 항목은 여전히 어느 메뉴에도 없습니다. Capability API 1.33이며 1.23과 1.26~1.30처럼 카탈로그 자산 자체 바이트에서 읽습니다.
- **Engine이 감지해야 하므로 순간은 두 가지입니다.** `aimed`는 보유자에게 무엇이 적용되기 전, `harmed`는 무언가 그를 다치게 한 뒤입니다. 효과 목록과 같은 이유로 목록은 닫혀 있습니다. 감시하지 않는 순간에는 아무것도 창을 열 수 없습니다.
- **`aimed`는 상대편에 대해서만, `harmed`는 누구에게나 열립니다.** 겨눔은 누군가 자신에게 무엇을 하려는지에 관한 것이며 아군의 회복은 대응할 위협이 아닙니다. 열렸다면 Engine이 맡은 아군이 자기 편의 회복을 취소할 수도 있습니다. 다쳤다는 것은 누가 했든 자신에 관한 사실이며, 원인에게 되돌려 겨누는 반응은 일반 표적 적법성으로 여전히 아군을 제외합니다.
- **재개 상태는 자기 종류를 밝힙니다.** 걷기는 `kind: "walk"`, 행동은 `kind: "action"`입니다. C5b에서 걷는 중 저장한 전투의 재개 상태에는 종류가 없으며, 가능한 유일한 종류인 걷기로 읽습니다.
- **Engine은 순간을 흘려보낼 수 있습니다.** 창 메뉴는 '순간을 넘기기'를 턴 종료처럼 평가하는 후보로 담아, 쓸 반응이 있다고 항상 쓰지는 않게 합니다. C5b의 걸어 나가는 상대에 대한 타격도 포함합니다. 표적을 고르게 하지 않지만 누군가에게 적용되는 선택지(이동자 또는 순간의 원인)는 실제 그에게 할 효과로 평가합니다(`rulesetWindowTargetOf`). 규칙이 거부한 선택기 답은 넘기고 로그에 남깁니다. 거부는 기록되지 않아 그렇지 않으면 그 넘김이 선택처럼 보일 수 있기 때문입니다.
- **비용은 누구에게 묻기 전에 지불됩니다.** `aimed` 창은 예산과 풀을 소모한 뒤 열리므로, 취소 답은 행동 발생을 막을 뿐 구매 사실을 없애지 않습니다. '무효화된 주문도 슬롯을 소모하는가'에 대한 전투 자체 답이며, 다른 답을 원하는 규칙 집합에는 현재 없는 환급 어휘가 필요합니다.
- **`harmed`는 행동 자체가 기록한 피해에서 읽으며**, 모두 해결한 뒤 처리하므로 해결기 내부는 창의 존재를 알 필요 없습니다. 세 명을 해친 행동은 세 명을 나열하는 창 하나를 엽니다.
- **`at: "source"`는 표적을 제공하지 않고 채웁니다.** 대부분은 순간을 일으킨 이만 표적이므로 선택지에는 표적 목록이 없고 클라이언트도 선택기를 보여 주지 않습니다. `at: "chosen"`은 항목 자체 표적을 유지합니다.
- **취소하는 `utility` 항목도 하는 일이 있습니다.** 지금까지 `gives`와 `standard`가 없는 `utility` 항목은 해결할 것이 없다고 버렸지만, 무언가를 취소하는 것도 해결입니다.
- **여전히 한 번에 창 하나입니다.** 창 안에서 생긴 것은 다른 창을 열지 않으므로 대응에 다시 대응할 수 없고, 누군가를 해치는 반응도 두 번째 순간을 열지 않습니다. 소스에 이 한계를 표시했고, 전투 인계가 설명한 제한된 스택을 확장 경로로 적었습니다.
- **검증:** `scripts/regressions/game-ruleset-combat-core.regression.ts`의 순간 블록으로 확인합니다. 어느 턴 메뉴에도 없음, 창과 계기, 해당 순간을 기다리는 것만 메뉴에 포함, 취소, 어느 경우든 예산 소모, 넘기면 보류 행동 통과, 피해가 여는 두 번째 순간, 원인에게 되돌려 겨누는 답, 세 번째 창 없음이 대상입니다.
- **Engine이 조종하는 파티원의 더 큰 풀 지불.** [이슈 #6528](https://github.com/Pasta-Devs/Marinara-Engine/issues/6528)에서 같은 경계의 문제라 함께 반영했습니다. 플레이어에게는 능력을 지불할 풀을 제시했지만 Engine 선택기는 기본 비용만 봐서, Engine에 맡긴 캐릭터는 더 강해지는 주문을 시전하지 않았습니다. 이제 후보 빌더는 지불 방식마다 후보 하나를 만들며 각자 `choice.payWith`, 추가 단계가 실제로 주는 효과 예측, 풀 이름 라벨, 금액뿐 아니라 올라간 단계 수도 세는 가격을 담습니다. 큰 버전을 무료로 오인하지 않기 위해서입니다. **상대는 올라갈 것이 없어 그대로입니다.** 능력치 블록 행동은 풀 비용이 없으므로 Engine이 맡은 상대나 Game Master의 보스 모두 더 크게 지불할 방법이 없습니다. 블록에 자체 풀을 주는 것은 이 변경이 아닌 형식 변경입니다. (그 변경이 바로 다음에 왔습니다. 시트로 쓴 생물은 풀을 갖고 다른 참가자처럼 큰 지불을 제시받습니다. '생물 시트에서 확정한 것'을 참고하세요.)
- **이후로 남긴 것:** 응답 대상을 멈추는 대신 그 수치를 바꾸는 반응입니다. 상태 어휘는 수정치가 아닌 닫힌 이름 목록이므로 '다음 자신의 턴까지 맞기 어려워짐'은 반응이든 다른 것이든 아직 규칙 집합이 표현할 수 없습니다. 반응보다는 상태에 관한 문제입니다.

### 생물 시트에서 확정한 것

[이슈 #6610](https://github.com/Pasta-Devs/Marinara-Engine/issues/6610): 규칙 집합 자체 용어로 작성한 도감 생물입니다. 모든 규칙 집합의 상대가 고정된 단순 수치 묶음에 맞는 것은 아니며, 상대는 없는 풀에서 아무것도 지불할 수 없었습니다.

- **생물은 `sheet`를 가질 수 있습니다.** 캐릭터 시트 자체 형태에서 모든 부분이 선택적이며 `live`는 없습니다. 도감은 작성된 데이터이므로 엄격합니다. Capability API 1.34이며 1.27처럼 규칙 집합과 카탈로그 파일 자체 바이트에서 읽습니다.
- **각 수치의 출처는 하나입니다.** 시트가 있으면 옆의 `health`, `defense`, `initiativeModifier`, `speed`, `abilities`, `saves`를 거부하며 블록 행동이 없어도 됩니다. 시트가 없으면 이전처럼 처음 세 값과 행동 하나가 필수입니다. 공개 JSON Schema도 양쪽을 명시합니다(생성기의 `oneSourceForCreature`).
- **빌더 하나를 씁니다.** `encounter.ts`의 `sheetCombatant`가 파티원과 시트 기반 상대를 똑같이 만들어 둘이 어긋날 수 없습니다. 블록이 더하는 것(자체 행동, 고유 점수, 부가 효과, 견디는 피해)은 위에 얹습니다.
- **작성된 데이터로 검증합니다.** 모든 ID는 시트 선언과, 기술과 내성은 제공하는 단계와 비교합니다. 점수와 보너스는 범위 내 정수, 행 수는 목록별 `maxItems`로 검사합니다. 필드와 행 셀은 공유 `rulesetListRowIssues`(이제 필드에도 실행)로 검사합니다. `_catalog`는 목록에 공급하는 카탈로그인지 확인하고, 인라인이면 항목이 있는지도 확인합니다.
- **라우트가 시트가 읽는 것을 불러옵니다.** `rulesetBestiarySheetCatalogIds`가 도감 시트의 행 선택 원본 카탈로그를 지정하며, 시트가 지정한 경우에만 도감 뒤에 불러옵니다.
- **풀과 더 큰 지불은 별도 작업 없이 적용됩니다.** 후보 빌더는 진영이 아닌 행동에 올라갈 풀이 있는지만 봤으므로 시트가 있는 상대는 Engine 선택기와 이미 `payWith`를 담던 Game Master 결정 모두에서 더 큰 지불을 제시받습니다.
- **이제 상대도 부상 트랙에 표시할 수 있습니다.** 자체 내성을 먼저 읽고 나서 트랙에 표시하므로, 시트 생물에는 저항으로 트랙을 표현하지 못하던 제한이 사라졌습니다. 직접 수치로 쓴 생물은 여전히 점수를 잃습니다.
- **여전히 상대입니다.** 0에서의 패배는 진영으로 결정하며 죽음 트랙도 같습니다. 실시간 되돌려 쓰기도 시트 유무뿐 아니라 진영으로 구분합니다. 그렇지 않으면 파티원과 같은 이름의 시트 기반 상대가 그 멤버의 저장된 시트를 덮어썼을 것입니다.
- **Game Master가 만든 상대도 시트일 수 있습니다.** 창작 마법사도 슬롯과 주문이 필요하기 때문입니다(PR에서 사용자가 결정). `rulesetProposedCreatureSchema`는 관대한 `sheet`(캐릭터 빌드 스키마)를 받고, 옆에 적은 숫자는 제안 전체를 거부하지 않고 버립니다. `hold.ts`가 세 단계로 제한합니다. `readProposedRulesetSheet`는 규칙 집합에 없는 이름을 버리고 값을 맞추며 카탈로그 항목 이름의 행을 해당 항목으로 바꿉니다(라우트는 제안 시트가 채우는 목록에 공급하는 모든 카탈로그를 읽음). `holdRulesetSheetHealth`는 체력 풀이 읽는 단일 필드나 필드 하나가 있는 `sum`을 통해 체력을 단계 범위로 옮기고, 다른 식은 설명 한 줄과 함께 그대로 둡니다. 전투를 만든 뒤 `holdRulesetCombatant`가 전투원 자체에서 방어·명중·내성 난이도를 제한하고 감당 가능한 최대 지불까지 세어 최강 라운드 피해를 줄입니다. 한 번 지불해 얻은 타격은 보유한 채 어느 타격 행에도 쓸 수 있으므로, 타격 라운드는 지불한 행과 나머지 타격을 가장 강한 타격 행에 쓰는 것으로 측정합니다. 시트 옆 블록 부분은 여전히 일반 제한을 거칩니다. 청사진 프롬프트는 `EncounterSheetBrief`를 담습니다. ID, 허용 값, 전투가 읽는 목록, 각 목록의 카탈로그가 열리는 기준 필드, 목록당 최대 60개 카탈로그 이름입니다.
- **보스가 아닌 창작 적은 규칙 집합 자체 클래스를 따릅니다.** 사용자는 'Sorcerer가 전체 주문 목록에 접근하지 않도록' 하라고 결정했습니다. 형식 변경은 필요 없었습니다. 카탈로그 필터의 `startFrom`이 이미 항목 분류용 시트 필드를 지정하며, `restrictRulesetSheetEntries`는 `sheetFieldMatchTexts`(선택기와 전투가 일치하도록 공유로 이동)로 필터와 시트 값이 맞는 항목만 유지합니다. 클래스 레벨별 슬롯 수는 어느 규칙 집합도 선언하지 않습니다(5e는 필드에 직접 입력). 따라서 맞춰 제한할 클래스 표는 없고, 단계 제한이 그 슬롯으로 살 수 있는 것을 제한합니다.
- **열린 선택은 모델 호출 없이 기질과 역량으로 채웁니다.** `fillRulesetSheetChoices`는 생물이 선택하는 모든 목록(`onlyWhen`이 있는 능력 원본)에 열려 있고 자체 풀로 지불 가능한 항목을 채웁니다. 풀 단계별 고정 수(초보부터 달인까지 1, 2, 2, 3)와 무제한 사용 항목 수(2, 2, 3, 3)까지입니다. 규칙 집합이 클래스 선택 수를 선언할 때까지 Engine 측 제한입니다. 항목 성격(피해, 지원, 제어, 턴을 바꾸는 효과)과 전투 AI 자체 기질로 가중치를 주고, 높은 역량은 턴을 바꾸는 효과 비중을 높입니다. 라우트는 전투 구성 전에 선택기가 쓸 같은 유닛과 시드로 적의 전술을 정하여, 하나의 기질로 선택을 채우고 싸우게 합니다. 보스는 두 과정에서 모두 제외하며 Game Master가 전부 작성합니다.
- **열거형 필드를 좁힌 레이어 때문에 생물이 사라지지 않습니다.** 생물의 열거 값은 정의 자체 `layers`에서 읽은 레이어 제거 값일 수 있으나 다른 미선언 값은 안 됩니다. `refineRulesetDefinition`은 `layersApplied`를, 레이어 적용 정의를 가질 수 있는 게임 카탈로그 로더는 `narrowedByLayers`를 전달합니다. 따라서 레이어가 조용히 빠지거나 제거 값 때문에 도감 파일이 거부되지 않으며 오타는 계속 거부합니다. 패키지 설치는 카탈로그 파일을 파싱하지 않으므로 설정할 설치 시 경로가 없습니다.
- **`no-health`.** 계산 결과 체력이 없는 시트는 죽일 수 없는 채 합류하지 않고 전투 시 고유 사유와 함께 제외합니다. 도감은 범위 밖 필드가 있으면 이미 가져올 때 거부하므로, 합계가 0인 공식이나 손으로 만든 블록이 이 경우에 도달합니다.
- **모든 거부 사유는 양쪽에 문장이 있습니다.** C5b의 `window-open`, `stale-window`는 영어 카탈로그와 서버에 문장이 없었고 C4a의 위치 관련 네 사유도 서버 문장이 없었습니다. 이제 모두 있으며, 양쪽 없이 사유를 추가하면 화면 클라이언트 검증이 실패합니다.
- **검증:** `scripts/regressions/game-ruleset-combat-creature-sheets.regression.ts`(단일 출처, ID와 참조, 5e 초안과 Ember Roads에서 파티원과 같은 수치, 시트 옆 블록 보존, 자체 Luck, 해결기·Engine 선택기·Game Master의 더 큰 슬롯, 부상 트랙과 면역, 패배, 투영, 쓰기, 거부, 제안과 1.34 제한), 다른 카탈로그의 주문을 쓰는 라우트 검증의 시전자, JSON Schema 검증으로 입증했습니다.

### C4a에서 확정한 것

C4a는 공유 계층과 서버 측의 보드입니다. C4b는 이를 그리는 화면입니다.

- **한 칸이 나타내는 거리는 규칙 집합이 정하며, 이를 선언해야 전투에 위치를 부여할 수 있습니다.** 새로운 선택적 `combat.distance: { label, perCell }`이 추가되었습니다. 블록의 세계가 나타내는 모든 거리는 이 단위입니다. `economy.movement`, 생물의 `speed`, 무기의 `reach`와 `range`, 생물 행동의 `reach`와 `range`가 해당합니다. 자체 `units.distance`를 선언한 카탈로그는 자신의 `perCell`로 `mechanics.range`와 `area.size`를 변환하며, 선언하지 않은 카탈로그는 블록의 값을 사용합니다. Capability API 1.28이며, 1.21 이후의 모든 단계와 마찬가지로 규칙 집합 자체 바이트에서 읽습니다.
- **기존에 작동하던 것은 바뀌지 않았습니다.** 보드 없는 전투는 이전과 바이트 단위로 동일합니다. 이제 칸 크기를 선언하는 규칙 집합 자체와 모든 새 키를 제거한 사본에서 같은 시나리오의 전체 이벤트 로그를 비교합니다. 새 필드가 모두 선택적이며 해당 기능이 없는 전투에는 존재하지 않으므로 상태 버전은 `v: 1`을 유지했습니다.
- **모두 보드에 있거나, 아무도 없습니다.** `createRulesetEncounter`는 선택적 `board: { grid, placements }`를 받고, 규칙 집합이 `distance`를 선언하고 모든 전투원이 격자 안에 칸을 가질 때에만 저장합니다. 한 명이라도 배치가 없으면 전투 전체를 상상 속 전장으로 유지합니다. 누군가 아무 곳에도 서 있지 않은 전투에서는 거리에 관한 질문에 답할 수 없기 때문입니다.
- **격자는 전술 엔진의 것을 그대로 사용합니다.** 서버는 진영, 보스 표시, 타일만 가진 대리 유닛을 사용하여 전술 스타일과 같은 시드와 같은 커서에서 `generateTacticalBattlefield`와 `placeSpawns`를 호출합니다. 이를 위해 `placeSpawns`는 구조적 타입인 `TacticalPlaceable`을 받도록 확장했으며, `TacticalUnit`은 이미 이를 만족합니다. 두 번째 생성기나 지형 표를 만들지 않았고, 이 전투만의 보드 크기도 없습니다.
- **인접한 여덟 방향은 각각 한 칸이며, 거리는 두 축 차이 중 큰 값입니다.** 이 기능이 대상으로 삼는 테이블톱 격자가 사용하는 방식입니다. 의도적으로 전술 엔진 자체의 네 방향과 맨해튼 거리를 사용하지 않으며, 전술 엔진의 전투에서는 기존 방식을 그대로 유지합니다. 지형의 `moveCost`는 칸에 들어가는 비용입니다. 단단한 장애물이 있는 칸에는 들어갈 수 없고, 두 장애물 사이의 모서리를 가로지를 수 없으며, 아군을 지나칠 수는 있지만 누구와도 같은 칸에서 멈출 수 없습니다.
- **새로운 순수 모듈 하나**, `packages/shared/src/features/ruleset-combat/grid.ts`에 `rulesetInCells`, `rulesetCellDistance`, `rulesetReachableCells`, `rulesetLineOfSight`, `rulesetAreaCells`, `rulesetOpportunityAttack`이 있습니다. 이전 연결 계층의 단일 반경이 아니라 실제 폭발형, 원뿔형, 직선형 범위를 처리합니다.
- **메뉴가 여전히 유일한 적법성 기준입니다.** 걸어갈 수 있는 곳, 옵션이 겨냥할 수 있는 대상, 범위 모양을 조준할 수 있는 곳은 모두 해결 시 선택을 검사하는 하나의 규칙입니다. 더 가까웠다면 허용될 대상은 단순한 `bad-target`이 아니라 `out-of-reach` 또는 `no-line-of-sight`로 거부합니다.
- **선택기가 이동합니다.** 도달 가능한 모든 칸에서 각 옵션을 평가하고, 그 이동이 유발할 각 공격만큼 점수를 깎습니다. 현재 위치에서 이미 최선의 행동을 할 수 있으면 이동하지 않는 편을 택하며, 닿는 대상이 없으면 거리를 좁힙니다(규칙 집합에 `dash`가 있으면 먼저 질주합니다). 검토할 칸은 48개, Game Master 창의 후보는 24개로 제한합니다.
- **검증 완료**: `scripts/regressions/game-ruleset-combat-grid.regression.ts`에서 직접 그린 보드, 지정된 주사위 결과, 두 예제 규칙 집합, 바이트 단위 비교를 검증하고, `ruleset-combat-director.regression.ts`와 `ruleset-combat-director-route.regression.ts`의 위치가 있는 사례도 검증합니다.
- **추후 과제**: 3/4 엄폐와 완전 엄폐, 고도, 장애물 위 비행, 좁은 틈 통과, 은신, 강제 이동입니다. 반응 창 자체는 C5b입니다.

### C4b에서 확정한 것

C4b는 화면에 보이는 보드입니다. C4a가 해결한 내용을 그리며 자체적으로 결정하는 것은 없습니다.

- **화면은 선호 설정이 아니라 뷰를 따릅니다.** 규칙 집합 뷰에 `grid`가 있으면 `DirectedCombatUI`가 보드를 표시하고, 없으면 Classic 무대를 유지합니다. 전투가 규칙 집합 자체 전투이고 게임의 전투 선호가 Tactical이며 해석된 규칙 집합이 `combat.distance`를 선언할 때에만 클라이언트가 `/start`에 `positioned: true`를 보냅니다. 보드를 표시할 수 있는지는 여전히 서버가 결정합니다.
- **표시 전용 컴포넌트 하나**, `RulesetCombatBoard.tsx`를 추가했습니다. `TacticalCombatUI`의 구조는 바꾸지 않았습니다. 팔레트, 텍스처, 지형 아이콘, 타일 그림자, 키프레임, 토큰 도우미를 수정 없이 `lib/tactical-board-look.ts`로 옮겨 두 보드가 함께 가져옵니다. 따라서 두 보드는 하나의 제품처럼 보이고 새 지형 테마도 서로 달라지지 않습니다.
- **클라이언트는 아무것도 계산하지 않습니다.** 도달 가능한 칸과 비용, 경로, 이동이 반응을 유발하는 대상, 선택 가능한 대상, 범위가 겨냥할 수 있는 곳과 그 안에 들어오는 모든 대상은 뷰에서 가져옵니다. `lib/ruleset-combat-board.ts`는 이를 칸별로 색인합니다. 여기서 유도하는 유일한 수치는 칸 수에 `perCell`을 곱한 규칙 집합 자체 거리이며, 화면 전체가 이 단위를 사용합니다.
- **칸마다 초점을 받을 요소는 하나입니다.** 타일은 순환 tabindex와 화살표 키 이동을 지원하는 버튼입니다. 토큰은 그 위에 `pointer-events-none`으로 그리므로 토큰을 누르는 것은 그 칸을 누르는 것과 같고, 키보드 동작도 하나의 의미를 가집니다. Escape는 미완성 선택을 취소하고 키보드 제어를 메뉴로 돌려줍니다. 이는 C3 규칙으로, 플레이어가 닫았을 때에만 초점이 돌아갑니다.
- **미완성 선택은 보드에 보관**하며, 선택적 제어형 `step`으로 `RulesetCombatMenu`에 내려줍니다. 이 조합이 없으면 메뉴가 자체 상태를 유지하며 C3 화면은 이전과 바이트 단위로 동일합니다.
- **보드는 자체 높이의 하한을 유지**하고, 메뉴, 안내 줄, 로그는 각각 자신의 크기를 제한합니다. 진행 중인 전투와 17줄 로그를 둔 채 1366x850 및 375x812에서 측정했습니다. 두 크기 모두 페이지 가로 스크롤이 없고, 토큰이 겹치지 않으며, 보드 전체가 보입니다.
- **검증 완료**: `scripts/regressions/ruleset-combat-screen-client.regression.ts`에서 두 예제 규칙 집합의 칸, 걷기, 경로, 대상, 조준, 문구, "사거리 안에 아무것도 없음" 규칙, 거리 포매터, 네 가지 거부를 검증합니다. `e2e/game-combat-director.e2e.ts`의 네 번째 모드에서는 실제 브라우저로 위치가 있는 Ember Roads 전투를 진행합니다.

## 아키텍처

### 고정 참조

```ts
type RulesetRef = {
  id: string; // bare for an official ruleset, "<owner>/<id>" or "local/<id>" for a community one
  version: number;
  packageId: string | null;
  source?: string; // where a community ruleset came from
  options: Record<string, boolean | number | string>;
};
// chat.metadata.gameRuleset?: RulesetRef   (absent means engine-legacy)
```

`gameExperienceId`처럼 게임 생성 시 한 번 기록합니다. `gameRuleset`은 `ChatMetadata` 인터페이스에 선언하므로 GM 동사 네임스페이스 유도 과정에서 Engine 소유로 인식합니다. 알 수 없는 ID이거나 고정된 `version`이 설치된 정의보다 새로우면 명확한 메시지와 함께 복구 가능한 읽기 전용 상태가 되며, 조용히 재해석하지 않습니다. 설치된 정의가 고정 참조보다 새로운 경우에는 현재 스키마에 대해 시트를 관대하게 읽으므로 허용합니다. 전투 인계 문서의 `RulesetRef`는 `id`를 네 가지 내장 이름으로 제한하지만, 여기서는 커뮤니티 규칙 집합을 위해 문자열로 확장합니다. 이는 위에서 요청한 승인 사항의 일부입니다.

### `ruleset.json`(Capability API 1.20)

패키지는 `contributions.assets.paths`에 `ruleset.json`을 나열하고 `files[]`에서 해시로 고정합니다. `gm-verbs.json`처럼 이 예약된 파일 이름으로 발견합니다. Engine은 선언된 크기가 256 KB를 넘으면 읽기 전에 거부하고, 엄격한 공유 zod 스키마로 검증하며, 사용할 수 없으면 로그 한 줄을 남기고 제외합니다. 이 연결 지점이 없으면 규칙 집합 패키지는 쓸모가 없으므로 1.20을 선언하고, 이전 Engine은 설치를 명확하게 거부합니다.

최상위 구조(초안 파일 참조): `id`, `version`, `name`, `edition`, `license`, `coverage`, `resolution`, `sheet`, `rests`, `gm`.

### 해결 유형

`resolution.kind`는 판별 유니온입니다. 두 종류가 구현되어 있습니다.

- **`dice-sum`**(슬라이스 2): 규칙 집합의 주사위(기본값 1d20)를 굴리고 능력치 수정치, 숙련 단계 보너스, 시트의 자유 보너스를 더하여 DC 이상을 달성합니다. 이점과 불리점, 단일 주사위의 최저·최고 눈에 대한 굴림 유형별 정책을 지원합니다. `5e-2014`에서는 판정과 내성 굴림의 정책이 `none`이며, 이는 의도적으로 `engine-legacy`와 다릅니다. 최초 초안에서는 이 종류를 `d20-sum`이라고 불렀지만, 2d6+능력치 체계가 별도의 종류를 요구하지 않도록 주사위를 매개변수로 바꿨습니다.
- **`dice-pool`**(슬라이스 7b): 시트 자체가 정한 수의 주사위를 굴리고 목표값에 도달한 주사위를 셉니다. 눈의 성공 수 두 배 처리, 폭발, 상쇄, 대실패, 특별 성공, 상황 주사위를 선택적으로 지원합니다. 같은 시트를 사용하되 `dice-sum`에서 굴림에 더하던 값이 여기서는 주사위 개수가 됩니다(§ 슬라이스 7b에서 확정한 것).

두 종류가 공유하는 시트 계산(`abilityModifier`, `proficiency`, `proficiencyTiers`)은 한 번 선언하여 각 유니온 구성원에 펼쳐 넣습니다. 따라서 모든 종류에 교차 검사가 적용되고, 세 번째 종류가 같은 수치에 대한 별도 규칙을 만들 수 없습니다.

해결기는 현재 서비스가 문서화한 모든 불변 조건을 유지합니다. 예외를 던지지 않고, 실행할 수 없는 굴림은 태그를 최소한의 필드만 남겨 다시 쓰며, GM이 만들어 낸 수치는 대체하고, **Logs**(로그)의 기록은 Engine이 작성합니다.

### 시트 스키마 기본 요소

닫힌 집합입니다. `abilities`, `skills`, `saves`(각각 관련 능력치를 선택적으로 지정), 타입이 있는 `fields`(`number`, `text`, `longtext`, `boolean`, `enum`, `dice`), `derived` 값(값 참조에 적용하는 닫힌 연산 집합 `sum`, `stepTable`, `scale`, `min`, `max`), `maxItems`가 있는 타입 지정 열의 `lists`, `live` 상태(`pools`, `tracks`, `text`, `conditions`)가 있습니다. 값 참조는 `const`, `field`, `derived`, `abilityScore`, `abilityMod`, `abilityModFromField`, `skillMod`, `saveMod` 중 정확히 하나만 가진 객체이며 수식 문자열은 없습니다. 편집기와 게임 내 시트는 이 정의를 바탕으로 범용 렌더링합니다. 패키지 클라이언트 코드도 편집기 슬롯도 필요하지 않습니다.

장비는 의도적으로 목록에 넣지 않았습니다. Game Mode가 이미 인벤토리를 소유하기 때문입니다. 시트에는 `attacks`와 직접 입력한 `ac`를 담습니다.

### 저장: 빌드와 실시간 상태

| 부분 | 내용 | 저장 위치 | 스와이프 시 되감기 |
| --- | --- | --- | --- |
| 시작 빌드 | 작성자가 입력한 모든 것 | 카드: `data.extensions.rulesetSheets[rulesetId]`. 페르소나: `personaStats.rulesetSheets[rulesetId]` | 해당 없음 |
| 게임 빌드 | 설정 시 만든 사본. Edit Sheet와 레벨 상승으로 수정 | `chat.metadata.gameCharacterCards[].rulesetSheet` | 아니요. 현재의 `rpgStats`와 같음 |
| 실시간 상태 | 현재 HP, 임시 HP, 남은 슬롯, 생명 주사위, 직업 카운터, 상태 이상, 집중, 탈진, 죽음 내성 굴림 | 카드 이름을 키로 하는 게임 상태 스냅샷 | 예 |

시트 명령은 상대적("3레벨 슬롯 하나 소비")이며 재생성한 턴에서 두 번 소비해서는 안 되므로 실시간 상태는 스냅샷에 속합니다. 전용 열인 `game_state_snapshots.ruleset_live`를 사용하며, 이를 위해 `STORAGE_VERSION`을 올릴 필요는 없었습니다. 턴이 이를 읽고 쓰는 방식은 § 슬라이스 5에서 확정한 것을 참조하세요.

저장되는 각 시트는 `{ v, build }`이며, 직렬화한 크기가 64 KB를 넘으면 거부합니다.

### GM 인터페이스

게임의 규칙 집합을 해석할 수 있으면 턴별 형식 안내(`buildGmFormatReminder`, 시스템 프롬프트는 아님)가 다음 작업을 수행합니다.

1. 내장 기술 판정 문단을 `gm.checkGuidance`와 난도 단계로 대체합니다.
2. `<character_sheets>` 안에 파티원별 간결한 시트 블록을 추가합니다. 능력치 수정치, 훈련된 기술과 내성 굴림, `gm.sheetSummary` 필드, 남은 자원, 기본값에서 벗어난 트랙, 메모, 활성 상태 이상, 요약 목록을 포함합니다.
3. Engine 소유 명령 하나인 `[sheet: who="Name" op="…" …]`를 알려 줍니다. 연산은 `spend`, `restore`(`heal`은 `restore`로 읽음), `damage`, `temp`, `track`, `condition`, `note`, `rest`로 제한합니다. 최초 제안의 `concentrate`는 범용 `note`로 바뀌었습니다.

Engine은 모든 연산을 실시간 시트와 대조하여 검증합니다. 남은 슬롯 없이 시전하려 하면 거부하고 로그에 기록하며, 응답에도 거부 사실을 다시 써 넣고 턴당 한 번 표시합니다. 자원 풀을 음수로 만드는 방식으로 적용하지 않습니다. `sheet`는 예약된 GM 태그 집합에 포함되며, 동사 이름 회귀 검사는 안내에서 학습시킨 태그를 찾습니다. 고정된 규칙 집합이 없으면 프롬프트는 바이트 단위로 동일합니다. `game-ruleset-checks.regression.ts`와 `one-request-dice-prompt.regression.ts`가 이를 고정하고, `pnpm regression:prompt`가 나머지 프롬프트를 다룹니다.

`[skill_check:]`에 선택적 `who=`가 추가됩니다. 생략하면 현재처럼 플레이어를 판정합니다. 내성 굴림은 `skill="Dexterity save"`로 요청하며, 기존 정규화기가 이미 이를 인식합니다.

단일 요청 주사위 자리표시자에는 해석 가능한 이름으로 `PROF`(규칙 집합에 숙련 보너스가 있는 경우), 그리고 ID나 표시 이름으로 지정한 규칙 집합의 기술, 내성 굴림, 능력치가 추가됩니다. 해석할 수 없는 이름은 0으로 취급하지 않고 거부한다는 기존 규칙을 따릅니다.

### 설정, 편집기, 게임 내 UI

- **설정 마법사**: 전투 표현 방식 안이 아닌 옆에 현지화된 **Rules**(규칙) 선택을 둡니다. 기본값은 Marinara 자체 규칙입니다. 설치된 각 규칙 집합은 `coverage.summary`를 표시합니다. 파티원과 페르소나는 선택한 규칙 집합의 시트가 있는지 표시하며, 시트가 없으면 편집기 또는 비어 있는 기본 빌드를 제공합니다. 생성 과정은 권위 있는 능력치를 임의로 만들어 내지 않습니다.
- **설정 공유**(`game-setup-share.ts`): 규칙 집합이 설치되어 있고 호환되면 복원합니다. 그렇지 않으면 Experience 가져오기처럼 이를 알리고 기본 규칙으로 대체합니다.
- **캐릭터 및 페르소나 편집기**: **Stats**(능력치) 아래에 설치된 규칙 집합마다 접을 수 있는 하위 섹션을 하나씩 두고 스키마로 렌더링합니다. 설치되지 않은 규칙 집합의 저장된 시트는 **Remove**(제거) 버튼이 있는 한 줄로 표시합니다.
- **게임 내 시트**(`GameCharacterSheet.tsx`): 게임에 규칙 집합이 있으면 실시간 자원 풀, 휴식 조작, 생명 주사위 소비 기능을 포함한 규칙 집합 시트를 렌더링합니다. v1의 레벨 상승은 수동입니다. 플레이어가 빌드를 수정하면 파생 값을 다시 계산합니다.

### 가져오기와 내보내기

시트를 함께 전달하기 위해 추가할 것은 없습니다. `extensions`와 페르소나 능력치는 이미 모든 가져오기 처리기와 스키마를 통과합니다. 원칙은 **휴면 상태로 보관하고, 절대로 버리지 않기**입니다. 가져오는 쪽에 없는 규칙 집합의 시트는 자신의 키 아래 보관하고, 프롬프트에서 숨기며, 제거 가능한 한 줄로 표시합니다. 가져올 때 크기를 제한하고, 해당 규칙 집합을 처음 설치하여 사용할 때에만 그 스키마로 검증합니다. 이를 버리면 나중에 규칙 집합을 설치하는 사람과 재내보내기 이후 데이터를 받는 모든 사람의 시트가 알림 없이 파괴됩니다.

아직 검증하지 않은 사항: Compatible JSON 및 PNG 내보내기 처리기가 알 수 없는 확장 키를 그대로 두는지 여부입니다. 이 동작을 문서화하기 전에 확인하세요.

## `5e-2014` 시트가 다루는 범위

| 단계 | 의미 | 내용 |
| --- | --- | --- |
| A. Engine이 계산에 사용 | 권위 있는 산술 계산 | 여섯 능력치 점수, 레벨, 숙련 보너스, 기술 숙련 단계(없음, 절반, 숙련, 전문화), 내성 굴림 숙련, 주문 시전 능력치, 주문 내성 DC, 주문 공격 보너스, 수동 지각, 우선권 |
| B. Engine이 수치를 추적 | 장부 처리를 강제하며 이야기 속 판정은 하지 않음 | HP와 임시 HP, 생명 주사위, 1~9레벨 주문 슬롯, Pact Magic 슬롯, 짧은 휴식 또는 긴 휴식으로 회복하는 이름 있는 직업 카운터, 죽음 내성 굴림, 탈진, SRD의 14가지 상태 이상, 집중, 짧은 휴식과 긴 휴식 |
| C. Engine이 저장하고 GM이 읽음 | 구조화된 목록 | 주문(레벨, 준비 여부, 의식, 집중, 메모), 공격, 특성과 특징, 기타 숙련과 언어, 직업, 하위 직업, 종족, 배경, 성향, XP |

v1에서 의도적으로 제외한 항목: 직업 및 하위 직업 표(슬롯 최댓값과 HP는 파생하지 않고 입력), 다중 직업 슬롯 계산, 구조화된 주문 모음, 방어구에서 유도한 AC, 자동 레벨 상승, 적과 NPC 시트, 공격 굴림과 치명타(전투 어댑터), 도구 판정입니다.

주문은 의도적으로 C 단계입니다. 전투 밖에서는 GM이 효과를 판정하고, Engine은 주문이 시트에 있고 슬롯이 실제로 소비됨을 보장합니다. 이후 전투 어댑터가 소규모 지원 주문 목록에 기계적 정의를 부여하면, 그때부터 전투 슬롯은 조우 생성이 아니라 시트에서 가져옵니다.

## 패키지

Marinara-Agents의 `packages/ruleset-5e-2014/`: `manifest.json`(스키마 2, API 1.20, `contributions.assets.paths: ["ruleset.json"]`), `ruleset.json`, `locales/en.json`, `README.md`, `CHANGELOG.md`, SRD 저작자 표시를 포함합니다. 서버 진입점, 클라이언트 진입점, LLM 에이전트는 없습니다. 슬라이스 1에서 `capabilityPackageManifestSchema`가 빈 `entrypoints`를 가진 패키지를 허용함을 확인했으므로 Engine 스키마 변경이나 더미 에이전트가 필요하지 않습니다. Marinara-Agents 카탈로그 검증기는 여전히 모든 등록 패키지에 `entrypoints.agents`를 요구하므로, 슬라이스 6에서 `ruleset` 종류에 대해 이 제한을 완화해야 합니다.

표시 이름은 "5e (SRD 5.1)"입니다. 이름, 설명, 아트워크에 Wizards of the Coast 상표를 사용하지 마세요. SRD 5.1 PDF에서 저작자 표시 문구를 그대로 복사하세요. ID를 먼저 `INCOMPLETE_PACKAGE_IDS`에, 이후 `STAGING_ONLY_PACKAGE_IDS`에 넣으세요.

v1에는 규칙 로어북이 없습니다. 충분한 능력을 갖춘 모델에는 안내 블록과 시트 블록이면 충분하며, 별도 첨부를 원하는 사람을 위한 CC-BY SRD 로어북이 커뮤니티에 이미 있습니다.

## 커뮤니티 규칙 집합 작성과 공유

**작성.** 작성자는 5e 파일에서 시작하여 `ruleset.json` 하나를 만듭니다. Engine이 지원하는 해결 종류를 고르고, 시트와 휴식, GM 안내를 선언합니다. 공유 zod 스키마에서 생성하여 문서와 함께 게시하는 JSON Schema 및 작은 검증 스크립트로 검증합니다. 편집기 UI가 만들어지기 전에도 **Edit Spoilers**(스포일러 편집)에서 시트를 직접 입력하면 판정을 시험하기에 충분합니다.

**한계.** 데이터는 이미 존재하는 종류의 매개변수만 설정할 수 있습니다. 어떤 종류도 표현하지 못하는 규칙(폭발 주사위, 목표 이하를 굴리는 백분율 판정, 성공도, Fate 단계)은 회귀 검증을 포함하여 종류를 추가하는 Engine PR이 필요하며, 규칙 집합 파일로 구현할 수 없습니다. 이것이 스크립트 언어를 두지 않는 대가이며, 작성 문서는 이를 마지막이 아니라 처음에 밝혀야 합니다. 이미 이런 규칙을 구현한 커뮤니티 작성자가 종류를 기여하기에 적합하며, 이들의 기존 사례는 그대로 회귀 검증에 쓸 수 있습니다.

**공유, 세 가지 경로.**

| 경로 | 방법 | 적합한 경우 |
| --- | --- | --- |
| 공식 카탈로그 | Marinara-Agents에 패키지 PR 제출. **Download Agents**(에이전트 다운로드)에서 한 번의 클릭으로 설치 | 널리 플레이되며 라이선스가 명확한 시스템 |
| 사용자 지정 저장소 | 기존 사용자 지정 에이전트 저장소 경로에서 `rulesets/*.json`도 읽음. 사용자는 작성자의 GitHub URL을 한 번 추가하고 미리보기를 검토한 뒤, 이후 업데이트도 같은 방식으로 받음 | 여러 시스템을 제공하는 작성자. 요청자의 저장소는 이미 이런 구조임 |
| 단일 파일 | **Import ruleset**(규칙 집합 가져오기)에서 `ruleset.json` 하나를 받음 | 로컬에서 반복 작업하거나 친구에게 파일을 전달하는 경우 |

모든 커뮤니티 경로는 **Allow custom Agent imports**(사용자 지정 에이전트 가져오기 허용) 뒤에 있습니다. 실행되는 코드는 없지만 `gm.*` 텍스트가 GM 프롬프트에 들어가므로, 가져오기 검토에서 이를 알리고 가져온 에이전트 프롬프트나 로어북과 같은 신뢰 수준으로 규칙 집합을 취급합니다.

**안전한 공유를 위한 규칙.**

- 공식 ID에는 접두사가 없습니다(`5e-2014`). 커뮤니티 ID에는 출처별 네임스페이스를 붙입니다(저장소는 `<owner>/<id>`, 파일은 `local/<id>`). 따라서 두 작성자의 `v20`이 충돌하지 않고 공식 규칙 집합을 가릴 수도 없습니다.
- 정의는 ID와 버전별로 저장합니다. 업데이트는 버전을 추가하며 기존 버전을 덮어쓰지 않습니다. 게임은 고정한 버전을 계속 해석합니다. 같은 버전에 다른 바이트가 들어오면 작성자에게 버전을 올리라는 메시지와 함께 거부합니다.
- 시트는 규칙 집합의 현재 스키마에 대해 관대하게 읽습니다. 알 수 없는 필드는 유지하고, 누락된 필드는 기본값을 사용하며, 범위를 벗어난 값은 편집할 때에만 제한하고 읽을 때는 바꾸지 않습니다. 마이그레이션 스크립트는 없습니다.
- 커뮤니티 `RulesetRef`는 출처 URL을 담습니다. 따라서 공유 설정 파일이나 휴면 시트는 받는 사람에게 규칙 집합이 없다는 사실뿐 아니라 어디에서 왔는지도 알려 줄 수 있습니다.

캐릭터는 독립적으로 이동합니다. 커뮤니티 시트를 포함하여 내보낸 카드는 그 시트를 유지하고, 규칙 집합이 없는 수신자는 이를 휴면 상태로 보관하며, 작성자의 저장소를 추가하는 순간 활성화됩니다.

## 제안: 나머지 카탈로그 기능

상태: 형식, 라우트, Capability API 1.21, 시트 편집기의 선택기는 구현되었습니다(§ 슬라이스 8a에서 확정한 것). 자체 SRD 콘텐츠는 `ruleset-5e-2014` 패키지 0.2.0으로 출시했으며, 전투 연결도 구현되었습니다(§ 전투 연결에서 확정한 것). 크기에 따라 변하는 카탈로그 값, `use` 명령, Refresh from ruleset도 구현되었습니다(§ 슬라이스 8c에서 확정한 것). 이 필요성은 5e 시트를 처음 실제로 사용하면서 드러났습니다. 주문, 공격, 직업 특성을 한 행씩 입력하기는 너무 번거롭고, 커뮤니티 작성자도 자신의 시스템 콘텐츠를 같은 방식으로 배포하고 싶어 할 것입니다.

**선택기.** 시트 편집기는 카탈로그가 공급하는 모든 목록에 **Add from catalog**(카탈로그에서 추가) 버튼을 제공합니다. 이를 누르면 카탈로그가 선언한 필터, 다중 선택, 시트가 이미 보유한 항목 표시가 있는 검색 가능한 선택기가 열립니다. 보유 여부는 선택한 행이 담고 있는 `_catalog` 키에서 읽습니다. 항목은 선택기를 열 때 카탈로그 라우트에서 읽으며, 그 전에는 읽지 않습니다. **Refresh from ruleset**(규칙 집합에서 새로 고침)은 같은 표시를 사용하여 작성자가 변경한 항목의 새 텍스트를 제안합니다(§ 슬라이스 8c에서 확정한 것).

**카탈로그 항목과 전투.** 시트와 카탈로그가 있다고 해서 전투가 규칙 집합을 따르지는 않습니다. 현재 Tactical 및 Classic 전투는 Engine 자체 전투 모델(`CombatSkill`: 사거리, 범위 반경, 슬롯 레벨, 공격 능력치에 대한 위력 배율)로 실행되며, Engine은 규칙 집합 자체 규칙으로 아무것도 해결하지 않습니다. `battle` 블록이 없는 규칙 집합은 전투에서 전혀 읽지 않습니다. 블록이 있으면 전투 연결을 통해 체력, 에너지, 슬롯, 카탈로그에서 선택한 행을 전투에 제공하지만(§ 전투 연결에서 확정한 것), 계산은 여전히 Engine의 것입니다. 규칙에 정확한 해결(성공 시 절반 피해를 받는 내성 굴림, 상위 슬롯 시전, 행동 경제, 어떤 메타매직이 어떤 주문에 적용되는지)은 코드이며, 데이터 파일이 아니라 전투 인계 문서의 규칙 집합별 어댑터(`game-combat-rulesets-implementation.md`, `5e-2014`의 경우 슬라이스 5)에 속합니다. 카탈로그가 담을 수 있는 것은 그런 어댑터에 필요한 사실입니다. 이것이 슬라이스 8a에서 이미 항목에 선택적인 타입 지정 `mechanics` 블록을 제공한 이유입니다. 이 블록에는 사거리, 범위 모양과 크기, 공격 굴림 또는 내성 굴림(시트가 선언한 내성 굴림과 성공 시 효과), 피해 주사위와 유형, 비용 한 단계 증가로 추가되는 내용, 대상, 집중이 들어갑니다. SRD를 한 번만 입력하는 것이 목적입니다. 어댑터가 존재하기 전에도 가능했던 더 작은 단계는 이제 구현되었습니다(§ 전투 연결에서 확정한 것). 규칙 집합이 `battle` 블록으로 참여를 선택하면, 전투 시작 시 시트에서 전투원을 초기화합니다(Engine 자체 최대 체력에 대한 비율, 에너지 풀, 슬롯). 카탈로그 표시가 있는 행은 Engine 기술(칸 단위 사거리, 범위, 슬롯 비용, 원소)이 되고, 이후 체력, 에너지, 슬롯을 다시 기록합니다. 피해 계산은 Engine의 것으로 유지되지만 시트는 전투에 영향을 미치며, 문서와 UI에서도 이를 설명합니다.

**추후 과제였지만 이제 구현된 항목.** 레벨에 따라 증가하는 최댓값(레벨과 같은 Ki 점수, 표에 따른 Rage 사용 횟수)과 시전 도우미(슬롯을 찾는 `[sheet: op="cast" spell="Fireball"]`)가 모두 들어갔습니다(§ 슬라이스 8c에서 확정한 것). 항목 행은 해당 열의 선택적 단계 표를 포함한 값 참조를 담습니다. 편집기는 편집할 때 다시 계산하고 읽을 때는 계산하지 않으며, 도우미는 범용 `use` 명령이 되었습니다.

**형식 변경 없이 적은 비용으로 도울 수 있는 기능**으로 함께 구현할 만한 것은, 이름 목록을 목록에 붙여 넣어 행을 생성하는 기능과 이미 나열한 미결정 사항 1("이 카드에서 시트 제안", 사용자가 검토하고 승인)입니다.

형식이 마련된 뒤 제공할 **`5e-2014` 자체 콘텐츠**: SRD 5.1 주문, 자원 카운터가 포함된 SRD 직업 특성(Second Wind, Action Surge, Rage, Ki, Channel Divinity, Bardic Inspiration, Sorcery Points, Wild Shape, Lay on Hands, Arcane Recovery), 바로 사용할 공격 행 형태의 SRD 무기 표입니다. SRD 5.1은 CC-BY-4.0이므로 패키지에 이미 포함된 저작자 표시와 함께 텍스트를 배포할 수 있습니다. 반드시 권위 있는 기계 판독 가능한 SRD 사본을 바탕으로 만들어야 하며, 기억에 의존하여 입력해서는 안 됩니다.

**슬라이스.** 8a, Engine: 카탈로그 형식, 자산 로더와 라우트, 시트 편집기의 **Add from catalog** 선택기. 5e가 아닌 두 번째 규칙 집합의 회귀 검증을 포함합니다. 구현 완료. 8b, Agents: SRD 카탈로그를 포함한 `ruleset-5e-2014` 0.2.0. 출시 완료. 8c, Engine: 크기에 따라 변하는 카탈로그 값, `use` 명령, Refresh from ruleset. 구현 완료. 커뮤니티 카탈로그를 별도 파일로 제공하는 기능(§ 슬라이스 8a에서 확정한 것에 여기 포함되지 않은 이유가 기록됨)은 별도 슬라이스가 될 것입니다.

## 슬라이스와 완료 증거

각 슬라이스는 `staging` 대상 PR 하나입니다. 작업을 시작할 때 초안 PR을 열고, `CHANGELOG.md`의 `[Unreleased]` 항목, 현지화된 문구, 문서, `[docs-i18n]` 후속 작업, 선택하지 않은 수동 검증 체크박스를 포함합니다. 검증 파일은 `*.regression.ts`이며, `.test.ts`는 트리에 남기지 않습니다.

## 기본안을 포함한 미결정 사항

1. **시트가 없는 동료.** 기본안: 빈 빌드에 수동 입력. 사용자가 검토하고 수락하는 선택적 "이 카드에서 시트 제안" 작업은 이후 추가할 만합니다. 수락은 사용자의 행위이므로 "생성이 권위 있는 능력치를 만들어 내지 않는다"는 원칙과도 일치합니다.
2. **XP 또는 이정표.** 기본안: 시트에 XP를 저장하되 자동으로 지급하지 않으며, 레벨은 손으로 수정합니다.
3. **명령 태그 이름.** `[sheet:]`는 제안입니다. 예약 집합에 포함한다면 어떤 이름이든 가능합니다.
4. **`dice-pool` 구현 주체.** 기본안: 요청자에게 이슈에서 사양을 제시하고, 원한다면 기여하도록 권합니다. 요청자는 작동하는 구현과 시스템 지식을 갖고 있으며, Engine 측은 연결 지점과 검토를 제공합니다.

5. **규칙 집합 위에 적용하는 레이어(예: 5e의 Low Magic).** 규칙 집합이 자체 파일에 포함하여 배포하는 레이어인 L1은 확정되었습니다. § 레이어 L1에서 확정한 것을 참조하세요. 다른 주체가 배포하는 레이어인 L2는 미정으로 남습니다. `appliesTo: { ruleset, minVersion }`을 지정하는 패키지 자산 또는 가져온 파일이며, 커뮤니티 규칙 집합처럼 저장하고 버전을 관리하고 "레이어 누락" 해석 상태를 추가합니다. L1의 형식과 적용 방식을 그대로 재사용합니다. L1이 병합될 때까지 더 설계하지 않습니다.

## 이 문서에서 검증하지 않은 사항

`game-state.storage.ts`와 스냅샷 필드에 저장소 버전 증가가 필요한지 여부, Compatible JSON 및 PNG 내보내기 경로, `GameSetupWizard.tsx`와 Experiences 블록이 `gameExperienceId`를 기록하는 위치, `game-setup-share.ts`, 사용자 지정 에이전트 저장소 경로가 클라이언트에 표시되는 방식과 아카이브 판독기가 추가 최상위 폴더를 허용하는지 여부, 결과를 미리 보는 주사위 풀과 규칙 집합 해결기의 상호작용, `game-combat-ai-design.md`입니다.

> **Game Mode: 선택 가능한 규칙 집합과 규칙 집합 캐릭터 시트(5e부터)**
>
> Marinara-RPG-Extension 작성자의 요청입니다. 현재 d20 전용 판정과 여섯 능력치 시트의 제약을 우회하려고 시스템마다 턴당 에이전트 네다섯 개를 사용해야 합니다. 제안: 규칙 집합은 검증된 데이터(`ruleset.json`, `gm-verbs.json`처럼 예약된 파일 이름을 사용하는 패키지 자산)로서, Engine이 소유하는 닫힌 해결 종류 집합에 매개변수를 제공하고 완전한 캐릭터 시트를 선언합니다. 패키지 코드, 수식 문자열, 추가 모델 호출은 없습니다. 시트는 카드와 페르소나에 시작 빌드로 저장하며 각 게임으로 복사합니다.
>
> 이 제안은 전투 인계 문서의 "내장 어댑터로 이루어진 닫힌 레지스트리"를 해결 종류와 전투 어댑터에 적용되는 것으로 해석하고, 규칙 집합 정의는 데이터로 취급합니다. 이 해석을 받아들일 수 있을까요? 관련 작업을 진행하는 분이 있나요? 자체 제공 범위는 SRD 5.1 기반 `5e-2014`입니다. 전투는 변경하지 않으며 전투 인계 문서의 범위로 남습니다. 전체 계획: `docs/development/game-rulesets-and-sheets-implementation.md`.
