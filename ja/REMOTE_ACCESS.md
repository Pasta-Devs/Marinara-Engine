# リモートアクセス: ログインとIP許可リスト

このガイドでは、スマートフォン、ラップトップ、Dockerコンテナーなど、別のデバイスからMarinara Engineに接続する方法を説明します。主な選択肢はログインです。あわせて、IP許可リスト、ログイン用プロキシ、HTTPS、**Admin Access**(管理者アクセス)、そして「save blocked」というCSRFのメッセージについても取り上げます。ここで扱う設定はほぼすべて、アプリではなくサーバーの`.env`ファイルにあります。

このガイド全体で使う言葉を先に整理します。

- `.env`ファイル: Marinara Engineのフォルダー内、`package.json`と同じ場所にあるテキスト形式の設定ファイルです。
- ループバック: サーバーを実際に動かしているコンピューター自身です。アドレスは`127.0.0.1`または`localhost`です。
- リモートアクセス: サーバーを動かしているコンピューター以外のデバイスからMarinaraを開くことです。

## Marinaraがデフォルトで遮断するもの

データを守るため、インストール直後のMarinaraは、アクセス制御を設定するまで他のデバイスからの接続を拒否します。デフォルトで信頼されるのは、次の3種類のクライアントだけです。

1. ループバック(`127.0.0.1`または`::1`)、つまりサーバーを動かしているコンピューター自身。同じコンピューター上のリバースプロキシやトンネルが中継した訪問者は含まれません。[同じコンピューター上のリバースプロキシとトンネル](#reverse-proxies-and-tunnels-on-the-same-computer)を参照してください。
2. tailnet内のTailscaleデバイス。Tailscaleはプライベートネットワークを作るツールで、アドレスは`100.64.0.0/10`の範囲を使います。
3. 同じホスト上のDockerクライアント。Marinaraは一般的な`172.16.0.0/12`のブリッジ範囲と、コンテナーの正確なデフォルトゲートウェイを認識します。これによりDocker Desktopや独自のアドレスプールにも対応します。

それ以外は、同じWi-Fiにつないだスマートフォンでもインターネット上のクライアントでも、ログインを設定するまで遮断されます。遮断されたデバイスでブラウザーからMarinaraを開くと、暗い色のセットアップページが表示されます。タイトルは**This Marinara Engine install needs a login before remote devices can connect.**です。このページには、サーバーのログに出る1回限りのセットアップコードを入力するフォームがあり、そのデバイスからログインを設定できます。

何もせず、パスワードも設定しなければ、Marinaraはこの3つの信頼済みの経路だけに限定されたままです。これが安全なデフォルトです。

## .envファイルの場所

アクセスに関わる設定はすべて、プロジェクトのルートにある`.env`ファイル、つまり`package.json`と同じ場所に置きます。まだ用意していない場合は、サンプルをコピーします。

```bash
cp .env.example .env
```

`.env`は好きなテキストエディターで開けます。Basic Auth、IP許可リスト、管理者用シークレット、CSRFのオリジンなど、アクセスに関わる設定はほとんどが数秒で反映され、再起動は要りません。ただし`PORT`、`HOST`、HTTPS証明書のパスなど、一部の低レベルな設定は再起動が必要です。

403ではなくタイムアウトになり、他のデバイスからそもそもサーバーに届かないこともあります。その場合、サーバーがローカルのコンピューターだけで待ち受けている可能性があります。すべてのネットワークインターフェイスで待ち受けるように設定します。

```env
HOST=0.0.0.0
```

シェル用の起動スクリプト(`start.bat`、`start.sh`)は`HOST=0.0.0.0`を自動で設定します。`pnpm start`を直接実行した場合は設定されません。

起動方法ごとのデフォルトのバインドアドレスは次のとおりです。

| 起動方法 | `HOST`のデフォルト |
| --- | --- |
| `pnpm start`、`start-local.bat` | `127.0.0.1` |
| `start.sh`、`start.bat`、Windowsインストーラー、`start-termux.sh` | `0.0.0.0` |
| Dockerイメージ | コンテナー内で`0.0.0.0` |
| `docker-compose.yml` | ポートを`127.0.0.1`だけに公開します |

## どの方法を選ぶか

上から順に読み、最初に当てはまったところで止めてください。

1. Tailscale経由だけ、または同じホスト上のDockerコンテナーからだけ接続する場合。何もする必要はありません。すでに動作します。
2. 自宅のWi-Fiにつないだスマートフォン、タブレット、ラップトップからMarinaraに接続したい場合。ログインを設定します(下記の方法1)。
3. Marinaraをインターネットに公開する場合。ログインを設定し、HTTPSを使います。
4. ネットワーク上のログイン用プロキシ(tinyauth、Authelia、Authentikなど)が、すでにすべての訪問者にログインを求めている場合。[ログイン用プロキシ(forward auth)](#login-proxies-forward-auth)を読んでください。

いちばん融通が利くのはログインです。どのIPアドレスからでも使え、デバイスごとの設定も要らず、ブラウザーはサインインしたままになります。

## 方法1: ログイン(推奨)

ログインとは、リモートのデバイスすべてに求めるユーザー名とパスワードです。設定方法は3つあります。

- **Settingsで設定する。** すでにサインイン済みのブラウザーか、Marinaraを動かしているコンピューター(`http://localhost:7860`を開く)で、**Settings → Advanced → Access**を開きます。**Remote login**の下でユーザー名とパスワードを設定します。ログインがまだ存在しないあいだは、DockerホストのブラウザーなどMarinaraが拒否したデバイスでも、同じ場所でサーバーのログにあるセットアップコードを入力できます。
- **セットアップコードで設定する(どのデバイスからでも)。** ログインが未設定でサーバーがループバックの外でも待ち受けているあいだ、サーバーはログに1回限りのセットアップコードを出力します。ログの行は`[login] One-time setup code:`で始まります。Marinaraを動かしているターミナルで探してください。Dockerでは`docker logs <container> 2>&1 | grep "setup code"`を実行します。ログインが存在しないあいだは、拒否の警告がログに出るたびにコードが繰り返されます。次に、任意のデバイスでMarinaraを開きます。デバイスを遮断しているページに、セットアップコード、ユーザー名、パスワードを入力するフォームがあります。コードは`XXXX-XXXX-XXXX-XXXX`のような形式です。大文字小文字、スペース、ダッシュは区別されません。コードは1回しか使えません。再起動やリセットを行うと新しいコードが出力されます。Dockerでは、このページに、データフォルダー(`/app/data/.env`)の`.env`ファイルか、composeファイルの`environment:`リストでログインを設定する方法も表示されます(そのあと`docker compose up -d`を実行します)。ホストにブラウザーがないDockerやNASのインストールでは、この方法を使います。ログインが未設定であることを知らせるバナーは、ローカルの訪問者とサインイン済みのセッションに、画面下部のカードとして表示されます。
- **`.env`で設定する。** 2行追加します。

```env
BASIC_AUTH_USER=alice
BASIC_AUTH_PASS=correct-horse-battery-staple
```

`.env`のログインは、アプリで設定したログインより優先され、変更も`.env`でしか行えません。`.env`を保存します。変更は数秒で反映され、再起動は要りません。

パスワードは強力で、ほかに使い回していないものにしてください。アプリは10文字以上を求めます。ランダムな文字列は次のように生成できます。

```bash
openssl rand -base64 24
```

あとはリモートのデバイスで次の手順を行います。

1. サーバーのアドレス(たとえば`http://192.168.1.50:7860`)を使って、ブラウザーでMarinaraを開きます。
2. サインインページで、ユーザー名とパスワードを入力してサインインします。
3. アプリが読み込まれるはずです。ブラウザーは、サインアウトするまで最長1年間サインインしたままになります。スクリプトやAPIクライアントは、リクエストのたびにユーザー名とパスワードを送ります(Basic Auth)。

パスワードを入力せずに別のデバイスでサインインするには、ペアリングコードを使います。サインイン済みのデバイスで**Settings → Advanced → Access**を開き、**Add a device**を選びます。続いて、新しいデバイスのサインインページでそのコードを入力します。コードは数分間、1回だけ使えます。期限切れのコードには専用のメッセージが表示されるので、新しく作ってください。**Signed-in devices**には、各デバイスがサインイン方法と初めてサインインした日付とともに表示されます。使用中のデバイスを含め、どのデバイスもサインアウトできます。パスワードの変更や削除もできます。その際、Marinaraを動かしているコンピューターで操作している場合か`ADMIN_SECRET`を設定している場合を除き、現在のパスワードを求められます。

パスワードを忘れた場合は、Marinaraを動かしているコンピューターで`pnpm reset-login`を実行します。Dockerでは`docker exec <container> node scripts/reset-login.mjs`を実行します。これでアプリで設定したログインが削除され、すべてのブラウザーがサインアウトされます。サーバーがループバックの外でも待ち受けている場合は、続いて新しいセットアップコードを出力します。このコマンドが動かない場合にかぎり、代わりにデータフォルダーから`.remote-login.json`と`.remote-sessions.json`を削除してください。デフォルトの`/app/data`なら`docker exec <container> rm -f /app/data/.remote-login.json /app/data/.remote-sessions.json`を実行します。`DATA_DIR`を変更している場合は、そのフォルダーを使ってください。`.env`のログインは、`.env`で変更します。

**ブラウザーのないヘッドレスサーバーの場合は?** ヘッドレスサーバーへのネイティブインストールは、ループバックだけで待ち受け、セットアップコードを出力しません。自分のコンピューターで`ssh -L 7860:127.0.0.1:7860 user@server`を実行します。続いてそこで`http://localhost:7860`を開き、**Settings**を使います。

15分以内に10回、異なる間違ったパスワードやコードが入力されると、Marinaraはそのアドレスからのサインインを、15分が過ぎるまで**429 Too Many Requests**で拒否します。それまでに正しいパスワードが入力されれば、回数はリセットされます。ホスト上のリバースプロキシやトンネルが中継した訪問者は1つの回数を共有し、そのうちの誰かがサインインしても回数はリセットされません。サーバーを再起動しても回数はリセットされます。以前にサインインしたことのあるブラウザーは、正しいパスワードを入力すれば引き続き入れるため、ほかの人が入力した間違ったパスワードのせいで、すでに使っているデバイスから締め出されることはありません。サインインページには、あと何分待てばよいかが表示されます。パスワードを忘れた場合、サインインページには**Forgot the password?**というヒントが表示されます。

ブラウザーの入力画面には、デフォルトで**Marinara Engine**と表示されます。この文言は`BASIC_AUTH_REALM`で変更できます。

Basic Authを有効にしても、パスワードを求められないクライアントがあります。

- ループバック(`127.0.0.1`、`::1`)。サーバーを動かしているコンピューター自身では、パスワードは一切不要です。ただし、そのコンピューター上のリバースプロキシやトンネルが中継した訪問者には、引き続きパスワードが必要です。
- `IP_ALLOWLIST`に入っているアドレス。ただし注意してください。許可リストを設定すると、載っていないアドレスはすべて遮断されます(方法2を参照)。
- Tailscale(`100.64.0.0/10`)からの直接の通信。バイパスをオフにしていない場合です。
- Dockerブリッジ/ゲートウェイからの通信。ログイン、許可リスト、`TRUSTED_AUTH_PROXY`のいずれも設定されていないあいだだけです([TailscaleとDockerのバイパス](#tailscale-and-docker-bypass)を参照)。
- `/api/health`のアドレス。稼働監視ツールが動き続けられるようにするためです。アプリを開けない訪問者には`{"status": "ok"}`だけを返し、バージョン、システム、モデルの詳細は、このコンピューター、信頼できるネットワーク、サインイン済みのブラウザーだけに公開します。

重要: Basic Authはパスワードをエンコードするだけで、暗号化はしません。暗号化されていない接続を覗いている相手には読み取れます。Marinaraをインターネットに公開する場合は、Basic AuthとHTTPSを組み合わせてください(後述)。

## 方法2: IP許可リスト

IP許可リストを使うと、指定したアドレスからはパスワードなしで入れます。デバイスのIPアドレスが安定している環境に向いています。アドレスや範囲をカンマ区切りで並べます。

```env
IP_ALLOWLIST=192.168.1.0/24,203.0.113.42
```

例に出てくる`/24`はCIDR表記です。CIDRは、まとまったアドレスの範囲を1つの記述で表す書き方です。たとえば`192.168.1.0/24`は、`192.168.1.0`から`192.168.1.255`までのすべてのアドレスを含みます。`203.0.113.42`のようにスラッシュのないアドレスは、その1台だけに一致します。

IP許可リストの動作は次のとおりです。

- リストに無いアドレスは**403 Forbidden**で拒否します。
- ループバックは常に許可されるので、ローカルからのアクセスを自分で締め出す心配はありません。同じコンピューター上のリバースプロキシやトンネルが中継した訪問者はループバックではないため、許可リストによって遮断されます。プロキシの背後ではBasic Authを使ってください。
- Docker Desktop、OrbStack、rootless Dockerでは、どのデバイスも同じゲートウェイのアドレスからコンテナーに接続するため、許可リストではデバイスを区別できません。これらの環境ではBasic Authを使ってください。
- Tailscaleからの直接の通信も、リストを通らずに入れます。Dockerブリッジ/ゲートウェイからの通信がリストを通らずに入れるのは、ログイン、許可リスト、有効な`TRUSTED_AUTH_PROXY`のいずれも設定されていないあいだだけです([TailscaleとDockerのバイパス](#tailscale-and-docker-bypass)を参照)。
- 不正なエントリーは無視してログに記録します。サーバーが落ちることはありません。
- Basic Authを有効にしても、許可リストは厳格なままです。リストに載ったアドレスはパスワードの入力を省略できます。それ以外のアドレスは**403 Forbidden**で遮断され、ログイン画面も出ません。

許可リストでは、載っているデバイスはパスワードなし、それ以外はパスワードでログイン、という混在の設定はできません。他のデバイスにもパスワードでログインさせたい場合は、`IP_ALLOWLIST`を設定せず、Basic Authだけを使ってください。

リストを消さずに、適用だけを一時的に止めることもできます。新しいIPアドレスから接続して問題を調べるときに便利です。有効化のフラグをfalseにします。

```env
IP_ALLOWLIST_ENABLED=false
```

## プライベートネットワークのバイパス(参考)

いくつかのフラグを使うと、信頼できるプライベートネットワークに対する遮断を解除できます。これは特殊な構成向けです。ログインを使うほうが適切です。フラグとそのリスクについては、[アクセス制御](CONFIGURATION.md#access-control)を参照してください。


<a id="tailscale-and-docker-bypass"></a>

## TailscaleとDockerのバイパス

デフォルトでは、MarinaraはTailscaleネットワーク経由で直接接続したデバイスを信頼します。また、Dockerコンテナー自身のホストも信頼します。ログイン、IP許可リスト、`TRUSTED_AUTH_PROXY`のいずれかを設定すると、Dockerの自動的な信頼は止まり、すべてのデバイスにログインか許可リストへの登録が必要になります。これを変更するフラグについては、[アクセス制御](CONFIGURATION.md#access-control)を参照してください。

## 同じコンピューター上のリバースプロキシとトンネル

nginx、Caddy、Traefik、Cloudflare Tunnel、Tailscale ServeやFunnel、ngrokなど、Marinaraを動かしているコンピューター上のリバースプロキシやトンネルは、ループバックからMarinaraに接続します。Marinaraは、プロキシが付け加える転送用のヘッダーからこれを見分けます。対象は`Forwarded`、`X-Forwarded-For`、`X-Real-IP`、`X-Forwarded-Host`、`X-Forwarded-Proto`、`CF-Connecting-IP`、`True-Client-IP`、Tailscaleの身元を示すヘッダー、`Via`です。MarinaraはHTTP/1.0で届くリクエストも見分けます。ブラウザーはHTTP/1.0を使いませんが、デフォルトのnginxの`proxy_pass`は使うためです。Marinaraは、プロキシがヘッダーを追加しない場合でも、HostがドメインやLANアドレスなど別のコンピューターを指すリクエストを認識します。見分けたリクエストは、実際のとおりリモートからの訪問者として扱います。

- ログインが適用されます([方法1](#option-1-login-recommended)を参照)。ログインがない場合、訪問者にはセットアップページが表示されます。このコンピューターの**Settings**か`.env`でログインを設定してください。
- プロキシが訪問者の本当のアドレスを隠すため、転送されてきた訪問者は`IP_ALLOWLIST`によって遮断されます。
- 特権が必要な操作には管理者用シークレットが必要になり、ループバック専用の機能は使えないままです。

そのコンピューター上で自分のブラウザーから`http://127.0.0.1:7860`または`http://localhost:7860`を開いた場合は、引き続きパスワードは不要です。

Caddy、Traefik、Cloudflare Tunnel、Tailscale、ngrokは、デフォルトで転送用のヘッダーを付け加えます。nginxでは、`location`ブロックに次の行を入れておくことを引き続き推奨します。

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

`socat`や`ssh -R`のように接続をそのまま転送するツールはヘッダーを付け加えないため、その通信はローカルからのものに見えます。Marinaraの公開にはこうしたツールを使わないでください。

プロキシ自体が、転送する前にすべての訪問者にログインを求めている場合は、[ログイン用プロキシ(forward auth)](#login-proxies-forward-auth)を参照してください。

<a id="login-proxies-forward-auth"></a>

## ログイン用プロキシ(forward auth)

[tinyauth](https://tinyauth.app)、[Authelia](https://www.authelia.com)、[Authentik](https://goauthentik.io)、oauth2-proxyなどのforward authプロキシは、リクエストを転送する前にすべての訪問者にログインを求めます。このようなプロキシがMarinaraへ届く唯一の経路であれば、Marinara側の2つ目のログインを省略できます。このようなプロキシがない場合は、設定しないでください。

```env
TRUSTED_AUTH_PROXY=192.168.1.5
```

Marinaraは、その接続元のアドレスから来るリクエストをすべて通します。そのリクエストに対してMarinara自身のログインは求めず、セットアップコードも出力しません。Marinaraは接続そのもののアドレスを確認します。この判断では、`X-Forwarded-For`などの転送用のヘッダーは無視します。プロキシからのリクエストは`IP_ALLOWLIST`も通ります。誰を通すかはプロキシが決めるためです。ローカルとは見なされないので、特権が必要な操作には引き続き管理者用シークレットが必要です。この設定が有効なあいだ、**Settings → Advanced → Access**には**Trusted login proxy: Set**と表示されます。

設定する前に確認してください。

- **プロキシは、すべてのパスでログインを求める必要があります。** `/api/`、WebSocket接続、静的ファイルも含みます。ログインなしでプロキシが通してしまうパスは、誰にでも開かれた状態になります。
- **Marinaraには、プロキシを迂回して到達できないようにします。** Marinaraをプロキシだけが届くアドレスにバインドするか、ファイアウォールでそのポートを塞いでください。Dockerでは、プロキシとMarinaraを同じDockerネットワークに置き、プロキシに固定のアドレスを割り当て、Marinaraのポートは公開しないでください。プロキシがDockerホスト上で動いている場合は、ポートをループバックだけに公開します(`127.0.0.1:7860:7860`)。Docker DesktopとOrbStackでは、公開されたポートに接続するLANのクライアントがすべて、プロキシと同じDockerゲートウェイのアドレスとして見えます。別のデバイスがMarinaraに直接接続できると、プロキシのログインを通らずに入れてしまいます。
- **プロキシ自身のアドレスだけを書きます。** 範囲はプライベートアドレスの内側に収める必要があり、それ以外の範囲はMarinaraが無視します。範囲を指定するたびに警告をログに記録します。範囲に含まれるすべてのデバイスがログインを通らずに入れてしまうためです。
- **公開する名前は、ほかのプロキシと同じように追加します。** ホスト名は`TRUSTED_HOSTS`に、オリジンは`CSRF_TRUSTED_ORIGINS`に入れてください([保存が遮断されるのはなぜですか(CSRF)](#why-is-my-save-blocked-csrf)を参照)。

`TRUSTED_AUTH_PROXY`を設定すると、Marinaraは自動的なDockerの信頼も止めます。プロキシ以外から直接来る訪問者には、Marinaraのログインか、IP許可リストが必要です。また、Marinaraは「まだログインがない」というバナーも表示しません。

プロキシがMarinaraと同じコンピューターで動いている場合は、`TRUSTED_AUTH_PROXY=127.0.0.1`を設定し、プロキシの転送先は`localhost:7860`ではなく`127.0.0.1:7860`にします。`localhost`へ接続するプロキシは`::1`から接続することがあり、これは`127.0.0.1`と一致しません。この設定では、そのコンピューター上のほかのプロキシやトンネルもすべて信頼されます。そのため、ログイン用プロキシがそのコンピューター上で唯一のプロキシである場合にだけ使ってください。プロキシ経由の訪問者に、ローカルのコンピューターと同じアクセスが与えられるわけではありません。

Marinaraが`192.168.1.20:7860`にある場合の、Caddyの例です。

```caddy
marinara.example.com {
  forward_auth tinyauth:3000 {
    uri /api/auth/caddy
  }
  reverse_proxy 192.168.1.20:7860
}
```

Autheliaの場合は、`forward_auth authelia:9091`に`uri /api/authz/forward-auth`を組み合わせます。Authentikは、独自のサインインページもプロキシ経由で配信します。その行は`route`ブロックの中に入れてください。そうすると、Caddyが順序を保ち、outpostのパスがforward auth自体を通らなくなります。

```caddy
marinara.example.com {
  route {
    reverse_proxy /outpost.goauthentik.io/* authentik-server:9000
    forward_auth authentik-server:9000 {
      uri /outpost.goauthentik.io/auth/caddy
    }
    reverse_proxy 192.168.1.20:7860
  }
}
```

Traefikやnginxの場合は、お使いのプロキシのforward authのガイドに従ってください。Marinaraに必要なのは、プロキシのアドレスだけです。

## HTTPSでの公開

HTTPSはTLSを使って通信を暗号化します。TLSは、ふつうの`http`のアドレスを安全な`https`に変える暗号化の仕組みです。完全に信頼できるプライベートネットワークの外から接続できるインストールでは、特にBasic Authを使う場合、必ずHTTPSを使ってください。

追加の方法は2つあります。

1. 内蔵のTLSを使います。証明書と秘密鍵のファイルをサーバーに指定します。

```env
SSL_CERT=/path/to/cert.pem
SSL_KEY=/path/to/key.pem
```

2. リバースプロキシを使います。Marinaraをnginx、Caddy、Traefik、Cloudflare Tunnelの背後に置きます。HTTPSの処理はプロキシが受け持ち、同じコンピューター上のMarinaraへはふつうのHTTPで転送します。先に[同じコンピューター上のリバースプロキシとトンネル](#reverse-proxies-and-tunnels-on-the-same-computer)を読んでください。

`SSL_CERT`と`SSL_KEY`を設定する前に、証明書と鍵を用意しておく必要があります。ローカルで使うなら`mkcert`、公開ドメインなら`certbot`のようなツールで作成できます。ファイルが見つからない、または読み取れない場合、サーバーは起動時に停止し、探したパスをそのまま表示します。

## Admin Accessと特権が必要な操作

特に慎重な扱いが必要な操作があります。データの消去、バックアップの作成とダウンロード、設定プロファイルのインポートとエクスポート、テーマのインストール、Local Modelランタイムのインストールです。これらには、上で選んだアクセス方法とは別に、管理者用シークレットと呼ばれる共有の秘密の文字列が必要です。

ループバックのコンピューターでは、管理者用シークレットなしでもたいてい実行できます。リモートのデバイスから行う場合は、シークレットを設定する必要があります。手順は次のとおりです。

1. `.env`に強力なランダムの値を設定して保存します。数秒で反映され、再起動は要りません。

```env
ADMIN_SECRET=some-long-random-string
```

2. リモートのデバイスでMarinaraを開き、**Settings**(設定)から**Advanced**タブ、さらに**Admin Access**セクションへ進みます。
3. 同じ値を入力欄(プレースホルダーは**ADMIN_SECRET**)に貼り付け、**Save**をクリックします。
4. **Admin secret saved for this browser**というメッセージが表示されるはずです。

管理者用シークレットについて、知っておきたい点がいくつかあります。

- 保存されるのは、その1つのブラウザーの中だけです。デバイス間で同期はしません。特権が必要な操作を行うブラウザーごとに、個別に貼り付ける必要があります。
- 入力欄を空にしたまま**Save**をクリックすると、値を消去して**Admin secret cleared**と表示します。
- サーバーの管理者が`MARINARA_REQUIRE_ADMIN_SECRET_ON_LOOPBACK=true`を設定している場合は、ループバックのコンピューターでもシークレットが必要です。
- これはBasic Authとは別の仕組みで、両方を併用できます。Basic Authはアプリ全体を守り、管理者用シークレットは危険な操作を守ります。

リモートのデバイスで特権が必要な操作に失敗すると、Marinaraは対処法を2つ添えたエラーメッセージを表示します。1つはlocalhost経由でアプリを開く方法、もう1つはサーバーの`.env`に`ADMIN_SECRET`を設定し、同じ値を**Settings** > **Advanced** > **Admin Access**に貼り付ける方法です。

<a id="why-is-my-save-blocked-csrf"></a>

## 保存が遮断されるのはなぜですか(CSRF)

CSRFはcross-site request forgery(クロスサイトリクエストフォージェリ)の略です。同時に開いている別のWebサイトが、許可なく勝手にMarinaraの内容を書き換えるのを防ぐ仕組みです。自動で働くため、オンにするための設定はありません。

自分の保存操作がCSRFで遮断されることもあります。多くは、サーバーがまだ信頼していない公開ドメイン名や、通常とは異なるポート番号でMarinaraに接続したときに起こります。そのときは2つの形で知らせます。

- アプリの上部に赤い帯が出て、このオリジンは信頼されていないため**Saves will silently fail**と警告します。帯には追加すべき`.env`の行がそのまま表示され、**Copy**ボタンも付いています。
- 実際に保存が拒否された場合は、小さなポップアップが表示されます。タイトルは**Save blocked: missing CSRF header**、**Save blocked: cross-site request rejected**、**Save blocked: origin not trusted**のいずれかです。

これを解消するには、接続に使っているアドレスを`.env`の信頼リストに追加します。

```env
CSRF_TRUSTED_ORIGINS=https://chat.example.com,http://203.0.113.10:7831
```

公開ドメインやリバースプロキシのドメインを使う場合は、ホスト名も許可します。

```env
TRUSTED_HOSTS=chat.example.com
```

LAN、Tailscale、IPv4、IPv6のアドレスに直接つなぐ場合、`TRUSTED_HOSTS`は必要ありません。ローカルの`.local`/`.home.arpa`という名前や、ドットを含まないコンピューター名は自動的に受け付けます。`CSRF_TRUSTED_ORIGINS`にすでに載っているホスト名も、そのまま受け付けます。

ループバック、通常のLANのアドレス、Tailscale(`100.64.0.0/10`)、Dockerブリッジ(`172.16.0.0/12`)のオリジンは自動的に信頼します。書き出す必要があるのは、公開されたIPアドレスとドメイン名だけです。変更は数秒で反映され、再起動は要りません。

## ローカルのプロバイダーが遮断される場合について

Marinaraを、たとえば自分のコンピューターで動かしているローカルのAIプロバイダーに接続したとします。このとき「private, loopback, metadata, or reserved IP range」というメッセージとともにリクエストが拒否されることがあります。これはSSRF保護と呼ばれる別の安全機能です。SSRFはserver-side request forgery(サーバーサイドリクエストフォージェリ)の略で、許可しない限りサーバーがプライベートなアドレスを呼び出さないようにします。エラーには`PROVIDER_LOCAL_URLS_ENABLED`のように、設定すべき`.env`の変数名がそのまま示されます。全一覧は[サーバー設定リファレンス](CONFIGURATION.md)を参照してください。

## スマートフォンやタブレットからのアクセス

同じネットワークにあるスマートフォンやタブレットからMarinaraを開く手順は次のとおりです。

1. `.env`に`HOST=0.0.0.0`を設定し、サーバーがすべてのインターフェイスで待ち受けているか確かめます。
2. ログインを設定します(上記の方法1)。スマートフォンからは、遮断されているページで、サーバーのログにあるセットアップコードを使って設定することもできます。
3. サーバーを動かしているコンピューターのローカルIPアドレス(たとえば`192.168.1.50`)を調べます。
4. スマートフォンのブラウザーで`http://192.168.1.50:7860`を開きます。デフォルトのポート番号は`7860`です。
5. ユーザー名とパスワードでサインインします。

ページがまったく開かない場合は、サーバーに届いていない可能性があります。`HOST=0.0.0.0`と`PORT`の値を確認してください。403が返る場合は、サーバーには届いているものの、まだ許可されていない状態です。選んだ方法の設定をもう一度見直してください。

<a id="locked-out-after-updating"></a>

## アップデート後にログインできなくなった場合

新しいバージョンでは、リバースプロキシ、トンネル、Tailscale Serve、Tailscale Funnel経由のアクセスにログインを求めます。古いバージョンでは、こうしたアクセスをパスワードなしで通していました。ログインページ、セットアップページ、または**403**が表示される場合は、これが理由です。

**アップデートに関する注意:** Tailscale Serveや、同じコンピューター上のほかのプロキシを使っていて、パスワードを一度も設定していない場合、アップデート後はほかのデバイスから入れなくなります。同じコンピューター上のプロキシは、ふつうループバックだけで待ち受けるサーバーに接続するため、サーバーはセットアップコードを出力しません。代わりに、Marinaraを動かしているコンピューターでログインを設定してください。

再び入るには:

1. Marinaraを実行しているコンピューターで、`http://localhost:7860`(または自分で設定した`PORT`)を開きます。ローカルでの利用にパスワードは不要です。ヘッドレスサーバーでは、まず自分のコンピューターで`ssh -L 7860:127.0.0.1:7860 user@server`を実行し、そこで`http://localhost:7860`を開きます。Dockerでこれが当てはまるのは、ログインも`IP_ALLOWLIST`も設定していないあいだだけです。そうでない場合は、サーバーのログにあるセットアップコード(`docker logs <container> 2>&1 | grep "setup code"`)を、遮断されているページで入力するか、**Settings → Advanced → Access**で入力するか、まだサインインしているブラウザーを使ってください。
2. **Settings → Advanced → Access**を開き、**Remote login**の下でユーザー名とパスワードを設定します。または、そのコンピューターで`.env`ファイルを開き、`BASIC_AUTH_USER`と`BASIC_AUTH_PASS`を設定します。`IP_ALLOWLIST`を設定している場合は、別のデバイスのアドレスを追加するか、設定を削除してください。リストにないデバイスは、ログインしても**403**になります。
3. 別のデバイスから、そのユーザー名とパスワードでサインインします。

## 検索エンジン

Marinaraは、検索エンジンにページのインデックス登録をしないよう求めます（`X-Robots-Tag: noindex, nofollow`）。これはお使いのインストールを保護するものではなく、すでにインデックス登録されたページを削除するものでもありません。インストールを非公開に保つには、上記のアクセス制御を使用してください。
