# Marinara Engineのトラブルシューティング

このガイドでは、Marinara Engineでよく起きる問題と、その直し方を説明します。症状に合う節を探して、手順どおりに進めてください。どれも当てはまらない場合は、最後の節「さらに助けを求める」を参照してください。

## 最初に試すこと

多くの問題は、次の2つの手順だけで解決します。

1. ページをハードリフレッシュします。WindowsとLinuxでは**Ctrl+Shift+R**、Macでは**Cmd+Shift+R**を押します。
2. サーバーコンソール(Marinaraを動かしているターミナルウィンドウ)に赤いエラー行が出ていないか確認します。その行に本当の原因が書かれていることがほとんどです。

開発チームに問い合わせるときは、先に**Debug mode**(デバッグモード)をオンにして、プロンプトと応答をサーバーのログに残してください。このガイド末尾の「さらに助けを求める」を参照してください。

## インストールと起動の問題

### Windows: pnpmのインストール時にEPERMまたはcorepackの署名エラーが出る

pnpmは、Marinaraがコードをインストールするために使うパッケージマネージャーです。`EPERM: operation not permitted`またはcorepackの署名検証の失敗が表示される場合は、corepackがNodeのインストール先フォルダーに書き込めていません。

次のどれか1つで対処します。

1. ターミナルを右クリックして「管理者として実行」を選び、もう一度ランチャーを実行します。
2. pnpmを自分でインストールします。次のコマンドを実行してから、もう一度ランチャーを実行します。

```bash
npm install -g pnpm
```

3. 管理者権限のターミナルでcorepackをアップデートしてから、もう一度ランチャーを実行します。

```bash
npm install -g corepack
```

### Windows: 共有パッケージのビルド中に`'pnpm' is not recognized`と表示される

Marinara v2.3.0では、Corepack経由でpnpmを起動するところまでは成功しても、共有パッケージのビルドで失敗することがありました。そのビルドが2つ目のグローバルな`pnpm`実行ファイルを起動しようとしていたためです。v2.3.1ではこの入れ子の要求をなくしました。失敗したランチャーを閉じて`start.bat`を実行し直すと、修正後のビルドスクリプトを取得してからビルドをやり直します。データを削除する必要はありません。

チェックアウト自体をアップデートできない場合は、Marinaraのフォルダーで`git pull`を実行してから起動し直します。v2.3.0での一時的な回避策としては、固定バージョンのパッケージマネージャーをグローバルにインストールし、ランチャーを実行し直してから、通常どおりアップデートしてください。

```bash
npm install -g pnpm@10.33.2
```

### ランチャーをpnpm 10.34.5へ更新する

Marinara v2.4.1では、固定パッケージマネージャーがpnpm 10.34.5へ移行します。既存の10.33.2ランチャーは、同じ実行中に一度だけ必要な引き継ぎを完了できます。その後、更新されたランチャーは以降の起動で10.34.5を選びます。Corepackは`package.json`に固定されたSHA-512ダイジェストでリリースを検証し、npmフォールバックも固定されていないlatestではなく、正確に10.34.5を要求します。

以前のv2.4.1 stagingビルドが`Expected version: >=10.34.5`と`Got: 10.33.2`で停止していた場合は、ランチャーをもう一度実行してください。そのビルドは停止前に更新済みランチャーをダウンロードしています。それでも固定バージョンを自動取得できない場合は、正確なバージョンをインストールしてから再実行します。

```bash
npm install -g pnpm@10.34.5
```

### Linux: インストール中にERR_PNPM_ENAMETOOLONGが出る

以前のインストールで長いフォルダーパスが残っているという意味です。Marinaraのフォルダーで、途中まで進んだインストールを削除してから、もう一度ランチャーを実行します。

```bash
rm -rf node_modules .pnpm .pnpm-store
```

そのあと`./start.sh`でMarinaraを起動し直します。手動でインストールしている場合は、これらのフォルダーを削除したあとに`pnpm install`を実行します。

### インストール中にERR_PNPM_TRUST_DOWNGRADEが出る

ほとんどの場合、インストールが途中で終わっているのが原因です。まずランチャーを実行し直して、ワークスペースを修復させます。手動でインストールしている場合は、Marinaraのフォルダーで次のコマンドを1回実行します。

```bash
pnpm --config.trustPolicy=off --config.confirmModulesPurge=false install --frozen-lockfile
```

## 画面が真っ白、古いまま、または見た目が変わらない

サーバーは動いているのにブラウザーが真っ白なページを表示する、あるいはアップデート後も古いバージョンのように見えることがあります。これは、ブラウザーがWebアプリのキャッシュを保持しているためです。

1. ハードリフレッシュします(**Ctrl+Shift+R**または**Cmd+Shift+R**)。
2. それでも直らない場合は、**Settings**(設定)を開き、**Advanced**タブの**Updates**セクションで**Refresh App**(アプリの再読み込み)をクリックします。

**Refresh App**は、ブラウザーのサービスワーカー(Webアプリをキャッシュする、裏側で動くスクリプト)とブラウザーキャッシュを消してから再読み込みします。データは変わりません。チャット、設定、その他のローカルデータはそのまま残ります。サーバー側のコードはアップデートされないため、本来のアップデートの代わりにはなりません。アプリ本体をアップデートするには[Marinara Engineのアップデート](UPGRADING.md)を参照してください。

## ダウンロードしたエージェントの問題

**Agents → Download Agents**でカタログを利用できないと表示される場合、ブラウザーだけでなく、Marinaraのサーバーが動いているコンピューター自体が、公式カタログ[Pasta-Devs/Marinara-Agents](https://github.com/Pasta-Devs/Marinara-Agents)にGitHubのHTTPSで到達できる必要があります。インストール済みのエージェントは、オフラインでも現在のバージョンのまま動きます。サーバーの接続を回復してから、**Refresh**または**Try again**をクリックすると、カタログの閲覧とアップデートの確認ができます。

インストールしたマップや通話が表示されない場合は、Marinara Engineを完全に終了してから起動し直してください。ルートを持つこれらのパッケージは、次にプロセスを起動するまで**Restart required**の状態のままです。Conversationのゲームは異なり、現行のEngineビルドでは即座に有効になります。インストールに失敗した場合はカタログを更新し、ゲームが利用可能になっているか確かめてください。チャットの**Commands**設定に追加する必要があるのは、キャラクター自身にゲームを始めさせたいときだけで、手動のスラッシュコマンドで遊ぶ分には不要です。

古いインストールが最初のパッケージ移行を完了できない場合でも、`data/capability-packages`フォルダーやチャットのデータを削除しないでください。Marinaraは移行を未完了のまま残し、次回の起動時に再試行します。カタログに到達できない間も、既存のチャットの選択内容と設定は保存されたままです。

チェックサム、宣言されたファイル一覧、対応するEngineのバージョン範囲、アーカイブ内のパスのいずれかが公式カタログと一致しないパッケージは、ダウンロードが拒否されます。先にMarinara Engineをアップデートし、カタログを更新してから、もう一度試してください。ダウンロードしたファイルをデータフォルダーへ手動で展開しないでください。

エージェントのアップデートは起動時に自動適用されることはありません。新しい互換バージョンがあるときは、Marinaraが適用するかどうかを確認します。**No**を選べばインストール済みのバージョンをそのまま使い続けられます。**Update**ボタンは**Agents → Download Agents**に残ります。アップデートに失敗した場合もインストール済みのバージョンは登録されたままで、アップデート直後のサーバーランタイムが起動時の自己チェックに失敗すると、前のバージョンへ戻ります。

## 別のデバイスからMarinaraにアクセスする

同じネットワーク上のスマートフォン、タブレット、別のコンピューターからMarinaraにアクセスできない場合は、次の項目を順に確認してください。

- 到達できるアドレスでサーバーを待ち受けさせます。サーバーはデフォルトで`127.0.0.1`(ループバック、自分のコンピューターのみ)を待ち受けます。シェルのランチャーは`HOST=0.0.0.0`を自動で設定します。`pnpm start`で手動起動した場合は、先に`.env`ファイルで`HOST=0.0.0.0`を設定してください。
- 両方のデバイスが同じWi-Fiネットワークにつながっているか確認します。
- ファイアウォールがポートをふさいでいないか確認します。デフォルトのポートは`7860`で、`PORT`を設定した場合はその値です。
- アクセス制御を設定します。通常のネットワーク上のクライアントや公開クライアントに対しては、`.env`に`BASIC_AUTH_USER`と`BASIC_AUTH_PASS`を設定します。ループバックはパスワードなしのままです。Tailscale経由の通信と、同一ホストのDockerブリッジまたは検出されたコンテナーゲートウェイからの直接の通信は、デフォルトで信頼されます。プロキシ経由で転送されたDockerの通信は、`REQUIRE_AUTH_FOR_DOCKER_PROXY=false`を明示的に設定しないかぎり通常の認可が必要です。
- そのデバイスから権限の必要な操作(バックアップ、データの削除、アップデート)を行うには、サーバーの`.env`に`ADMIN_SECRET`を設定します。そのうえで、同じ値をそのデバイスの**Settings** > **Advanced** > **Admin Access**に貼り付けて、**Save**をクリックします。
- 公開ドメインやリバースプロキシのドメインを使っていて**Untrusted request host**と表示される場合は、`.env`の`TRUSTED_HOSTS`にそのホスト名を正確に追加します。スマートフォン、LAN上のコンピューター、Tailscaleのピアが使う直接のIPアドレスは、引き続き自動で受け入れられます。

手順の全体は[リモートアクセス](REMOTE_ACCESS.md)と[よくある質問](FAQ.md)を参照してください。

## 保存がブロックされる、設定が保存されない

保存できたように見えるのに再読み込みすると元に戻る場合は、Marinaraのクロスサイト保護がブロックしています。CSRF(クロスサイトリクエストフォージェリ)保護は、データを変更する操作を守る仕組みで、特定のブラウザーのオリジンだけを信頼します。

次のどちらか、または両方が表示されます。

- このオリジンは信頼されていないため保存が失敗する、という赤い警告バーが画面上部に出ます。
- **Save blocked: missing CSRF header**、**Save blocked: cross-site request rejected**、**Save blocked: origin not trusted**のいずれかのトーストが表示されます。

ループバック、プライベートネットワークのアドレス、Tailscale、Dockerブリッジは自動的に信頼されます。この問題が起きるのは、たいてい公開IPアドレスやドメイン名でMarinaraにアクセスしている場合です。そのアドレスを`.env`の`CSRF_TRUSTED_ORIGINS`に追加してください。複数指定するときはカンマ区切りにします。例を示します。

```bash
CSRF_TRUSTED_ORIGINS=http://203.0.113.10:7831,https://chat.example.com
```

再起動は不要です。警告バーのCopyボタンを押すと、必要な行がそのままコピーされます。詳しくは[リモートアクセス](REMOTE_ACCESS.md)を参照してください。

## 接続と生成のエラー

生成のエラーは画面下部にトーストで表示されます。接続に失敗した場合は、トーストに理由が示されます。トーストは、読んでコピーできるだけの時間表示されます。

- **No API connection configured for this chat**: そのチャットに接続が選ばれていません。**Connections**(接続)パネルを開いて接続を作成し、チャットに設定してください。[AIプロバイダーへの接続](connections/connecting-to-a-provider.md)を参照してください。APIキーとは、プロバイダーから受け取る秘密の文字列で、これがあるとMarinaraがそのモデルを使えるようになります。
- モデルが受け付けないパラメーターがある場合: どのパラメーターかがトーストに表示されます。**Chat Settings**(チャット設定) > **Advanced Parameters**を開いてそのパラメーターを探し、名前の横のスイッチをオフにします(ツールチップには「This parameter is sent to the model」と表示されます)。
- モデルが必須だと言うパラメーターがある場合: 同じ手順で、そのパラメーターの横のスイッチをオンにします。
- **The AI returned an empty response. Try sending your message again.**: メッセージを送り直してください。何度も起きるときは、別のモデルか別の接続を試します。
- **A generation is already in progress for this chat**: 前の返信がまだストリーミング中です。終わるまで待つか、Stopボタンをクリックしてから、もう一度試します。
- **No connections are marked for the random pool**: 接続のランダム振り分けをオンにしたのに、対象の接続が1つも指定されていません。1つ以上の接続を対象に加えるか、ランダム振り分けをオフにしてください。

## Local Modelの問題

**Local Model**(ローカルモデル)は、APIキーなしで自分のコンピューター上で動くAIモデルです。エラーメッセージによっては、この機能をsidecarという言葉で表すことがあります。

- ランタイムのインストールが**Sidecar runtime install is disabled**で失敗する場合、安全のためにサーバー側でその操作が無効化されています。自分のコンピューターであれば、`.env`に`SIDECAR_RUNTIME_INSTALL_ENABLED=true`を設定します。別のデバイスからの場合は、先に管理者用の秘密の値を**Settings** > **Advanced** > **Admin Access**に貼り付けてください。
- 別のデバイス(ネットワークアドレスやDocker)からモデルのダウンロードやセットアップに失敗する場合も、管理者用の秘密の値が必要なことがあります。自分のコンピューターからなら不要です。貼り付ける場所は前の項目を参照してください。
- 同梱のllama.cpp、MLX、uv、またはMLXの依存関係ロックの検証でファイルサイズやSHA-256の不一致が報告された場合、Marinaraは展開やインストールの前にそのファイルを破棄または拒否しています。Marinaraをアップデートまたは再インストールしてから、もう一度試してください。拒否されたファイルを手動で実行、展開、編集したり、検証を回避したりしないでください。

### メンテナー向け: 固定したローカルランタイムのアップデート

GitHubが生成するソースアーカイブは、コミットの内容が変わらない場合でも、バイト単位で同一であり続ける保証はありません。ユーザーの環境で見えたバイト列をそのまま受け入れたり、検証を弱めたりして不一致を「修正」しないでください。ランタイムの入力を固定し直すのは、レビューを経たEngineの変更の中だけにします。

1. 変更されない上流のリビジョンかリリース資産を選び、上流の変更内容をレビューします。
2. 一時フォルダーにファイルをダウンロードし、正確なバイト数を記録して、SHA-256ダイジェストを独立に計算します。
3. `runtime-integrity-manifest.ts`を、そのリビジョン、URL、サイズ、ダイジェストで更新します。MLXの場合は、Apple SiliconかつPython 3.12の環境で、固定したuvのバージョンを使って`.in`ファイルから`packages/server/src/assets/mlx-runtime-requirements.lock`を生成し直し、依存関係の変更をすべてレビューしたうえで`requirementsLockSha256`を更新します。
4. `pnpm regression:runtime-integrity`と`pnpm check`を実行し、対象のプラットフォームでクリーンな状態からのランタイムインストールを実際に試します。
5. レビュー済みのEngineのアップデートを配布してから、再試行を案内します。チェックサムを手動で上書きする手段は用意しないでください。

セットアップ全体は[Local Modelのセットアップ](connections/local-model.md)を参照してください。

## 記憶機能と要約

### Memory Recallが何も思い出さない

**Memory Recall**(記憶の呼び出し)は、過去のメッセージを検索して、関連の強いものをプロンプトへ静かに挿入します。何も覚えていないように見えるときは、次を確認してください。

1. **Chat Settings** > **Memory Recall**を開き、**Enable Memory Recall**がオンになっているか確かめます。
2. **Access memories for this chat**を開きます。**Memories for This Chat**ウィンドウで、各チャンクの状態を確認します。
3. 状態が**Waiting for vector**の場合、その記憶はまだ処理中です。少し待ってから、もう一度チャットしてください。
4. 状態が**Embedding unavailable**の場合、埋め込みの生成元が1つも動いていません。埋め込み用の接続を設定するか、内蔵のローカルモデルを読み込ませてください。[Local Modelのセットアップ](connections/local-model.md)を参照してください。

記憶が作られるには、新しいメッセージが5件以上必要です。また、呼び出しの対象になるのは新しいメッセージと強く一致する記憶だけなので、記憶があっても何も返らないことがあります。

### 要約が生成されない

チャットの要約を書くには、動作するテキスト用の接続が必要です。

- Roleplayモードでは、**Chat Summary**のポップオーバーを開いて接続が設定されているか確かめます。古いチャットに追いつかせるには**Backfill Summary**を使います。
- Conversationモードでは、**Automatic Summarization**を開き、失敗した日付を**Backfill**で再試行します。
- チャットでエージェントの書き込み承認を必須にしている場合、AIによる要約は反映される前にレビュー待ちになります。
- 失敗が続く要約(たとえばAPIキーが誤っている場合)は、時間をおいて再試行されます。接続を直してから**Backfill**を使ってください。

## Card Browserの問題

**Card Browser**(カードブラウザー)を使うと、公開されているキャラクターサイトを検索してキャラクターをインポートできます。上部バーの**Card Browser**アイコンから開き、**Download Cards**をクリックします。

- JannyAIの検索やキャラクターのページがCloudflareのブロックで失敗すると、Marinaraがメッセージを表示します。同じブラウザーでJannyAIのサイトを一度開いてチャレンジを解除し、もう一度試すよう案内されます。
- CharacterTavernやPygmalionのログインがサーバーの再起動後に効かなくなるのは、仕様どおりです。これらのログイン情報はサーバーのメモリー上にだけ存在し、再起動で消えます。ログインのウィンドウを開いて、Cookieまたはトークンを貼り付け直してください。

## メディア生成の問題

### 複雑なシーンでスプライトの背景除去がうまくいかない

生成した静止スプライトは、通常は透過情報をそのまま使うか、色を自動で選んだ単色のマットを使います。内蔵の背景除去は、古い白いマットも認識し、被写体の内側の細部を保ち、アルファのふちをなめらかにして、マットの色のにじみを取り除きます。それでも、写真の室内、描き込まれた風景、濃い影、背景と色が近い被写体などでは、任意のAIによる代替処理が必要になることがあります。

```bash
pnpm backgroundremover:install
```

そのあとMarinaraを再起動し、スプライト生成のウィンドウで**Reapply Cleanup**をクリックします。Marinaraはこの場合もまず内蔵のマット処理を試し、ふちが均一でないときだけAIモデルを使います。インストールに失敗する場合は、次を確認してください。

- Python 3.9から3.11までがインストールされているか確かめます。これより新しいPythonでは、時間のかかるネイティブビルドが走ることがあります。
- `pnpm backgroundremover:reinstall`でツールをビルドし直します。
- 原因を調べている間、AIによる代替処理を使わず自動のマット処理だけを使うには、`.env`に`SPRITE_BACKGROUND_REMOVAL_ENGINE=builtin`を設定します。

### Game ModeやRoleplayの絵コンテが表示されない

Game Modeの絵コンテは、そろったGMの語りをキーフレーム画像と、任意で短い動画に変換します。Roleplayの絵コンテは、そろったやり取りをまとめ、その結果をアシスタントの返信の下に表示します。

- **Agents** > **Download Agents**から**Storyboard**をインストールしてあるか確かめ、そのチャットで**Enable Agents**(エージェントを有効にする)と**Enable Storyboards**(絵コンテを有効にする)をオンにします。
- 手動でシーンの動画を作るには、先に**Gallery**(ギャラリー)の画像を生成またはアップロードし、その**Video**または**Animate**の操作を使います。**Gallery**は**Images**と**Videos**のタブに分かれているので、**Videos**タブを確認してください。
- Game Modeの絵コンテを自動生成するには、**Chat Settings** > **Agents** > **Storyboards**を開き、**Automatic Storyboard Illustrations**がオンになっているか確かめます。短い動画も欲しい場合は**Automatic Storyboard Animations**もオンにします。
- Roleplayでは、**Storyboard**エージェントをチャットに追加します。**Still images**か**Animations**を選び、**Messages per episode**を設定して、Storyboardの画像用の接続を選びます。**Manual only**の場合は、代わりにGalleryの**Create storyboard**から実行します。
- キーフレーム画像には画像用の接続が必要です。動画にはさらに動画用の接続も必要です。
- すべてのキャラクターをまとめたカスタムのプロンプトのほうが結果が良い場合は、**Use NovelAI Character Prompts**をオフにします。
- 応答の遅いプロバイダーではタイムアウトになることがあります。`.env`の`IMAGE_GEN_TIMEOUT_MS`または`VIDEO_GEN_TIMEOUT_MS`を大きくしてから、Marinaraを再起動してください。サーバーはこれらの値を起動時にしか読み込みません。

どちらの使い方も[Storyboardエージェントガイド](game/storyboard.md)で説明しています。Gameのセットアップは[Game Mode: はじめに](game/getting-started.md)を参照してください。

### Game Modeの世界生成でJSONのエラーが出る

モデルが壊れたJSONを返してゲームの開始に失敗した場合、Marinaraはターン全体を捨てずに**Repair JSON**ウィンドウを開きます。JSONは、モデルが返さなければならない構造化されたテキスト形式です。

1. エディターで括弧、カンマ、項目を直します。テキストが正しく解析できるようになると、バーに**JSON is valid.**と表示されます。
2. **Format**をクリックすると、体裁が整います。
3. **Apply Repaired JSON**をクリックすると、応答全体を再生成せずにそのJSONを使えます。

## 音声、通話、TTS

- 通話中にキャラクターが話さない場合は、音声合成が設定されていません。**Connections** > **Text to Speech**を開いて有効にし、生成元を選び、キーを入力し、声を選んで保存します。声が設定されていないキャラクターはテキストだけで応答します。
- マイクが動かない場合は、ローカルの音声認識モデルが必要なことがあります。**Agents > Download Agents**から**Calls**をインストールし、**Connections** > **Local Model**を開いてカードを展開し、**Local Speech Model**でWhisperのモデルを選んで**Download Whisper**をクリックします。特にFirefoxはブラウザー側の音声認識を持たないため、これが必要です。**Calls**をアンインストールすると、ディスク容量を空けるためにWhisperのモデルも削除されます。
- Liteビルドで**Local Whisper is disabled in Lite mode**と表示される場合、この小さいビルドではローカルの音声認識モデルを動かせません。通常のMarinaraをインストールして使ってください。

### リモートやネットワーク越しのインストールでMusic DJのSpotifyログインが失敗する

Music DJエージェントのSpotifyモードはOAuthを使います。OAuthはログインを別のサービスに任せる仕組みで、Spotifyは認証後にコールバックアドレスへ戻します。リダイレクトURIとはそのコールバックアドレスのことで、Spotifyは`https://`のアドレスか、ループバックアドレス`http://127.0.0.1`しか受け付けません。ネットワークのIPアドレスをそのまま指定すると拒否されます。

- localhostでMarinaraにアクセスしている場合、エディターには`127.0.0.1`のコールバックが表示されます。これをSpotifyに登録すればログインが完了します。
- HTTPSでMarinaraにアクセスしている場合、エディターにはHTTPSのコールバックが表示されます。これを登録します。
- HTTPSが手前で終端されていてホスト名が一致しない場合は、`.env`の`SPOTIFY_REDIRECT_URI`に公開用のコールバックアドレスを設定します。
- HTTPのままのネットワーク越しのインストールでは、ポップアップは読み込めませんが、アドレスバーには有効なコードが入っています。ポップアップからURL全体をコピーし、Connectボタンの下にある**Browser couldn't reach the callback?**を展開して貼り付けてください。貼り付けたURLは10分間有効です。

長期的にいちばんすっきりする解決策は、サーバーをHTTPSの後ろに置くことです。最終確認はMarinara Engine 2.2.0です。Spotifyは2025年2月にこの規則を厳しくしました。

## ストレージとデータ

### 起動時に別のプロセスがデータディレクトリを使用中かもしれないと表示される

Marinaraでは、ローカルのデータディレクトリへ書き込める実行中サーバーは1つだけです。起動時にそのディレクトリについて**Another Marinara Engine process ... may be using**と表示されたら、もう一方のMarinaraプロセスを終了して再起動してください。

クラッシュ後やDockerデータボリュームの移動後には、代わりに**The storage writer lease ... is incomplete or invalid**と表示されたり、このホストにはもう存在しないプロセスが示されたりすることがあります。まず、そのデータディレクトリを使うMarinaraの全プロセスとコンテナーが停止していることを確認します。次に、エラーで示された`.writer-lease`ディレクトリだけを削除し、Marinaraを再起動します。周囲の`storage`ディレクトリやテーブルファイルは削除しないでください。

### アップデート後にデータがなくなったように見える

アップデート後にチャットやプリセットが見当たらなくても、まだデータのフォルダーを削除しないでください。Marinaraは実際のデータを、データフォルダーの中の`storage`フォルダーに保存しています。

次の2か所に`storage`フォルダーがないか確認してください。

1. `packages/server/data/`
2. `data/`

サーバーは起動時に、解決したデータフォルダーとストレージフォルダーを表示します。

### 古いバージョンへ切り替えたらチャットのメッセージが表示されない

新しいMarinaraは、各チャットのデータ（メッセージ、swipe、記憶、画像などのチャット単位の記録）を、テーブルごとの大きな1ファイルではなくチャット別のファイルに保存します。これにより、長いチャットの保存が大幅に速くなります。古いバージョンはこの配置を理解できません。古いバージョンへ切り替えるとチャットが空に見えますが、データはディスクに残っており、古いバージョンから見えないだけです。

Marinaraは明らかなダウングレードを自動で拒否します。ランチャーは互換性のないバージョンへ移る自動更新をスキップし、アプリ内アップデーターはここを案内するエラーを表示してブロックします。

それでもダウングレードする場合は、次の手順を使います。

1. Marinaraサーバーを停止します。
2. Marinaraフォルダーで次を実行します。

   ```bash
   node scripts/protect-launcher-data.mjs unshard
   ```

3. 古いバージョンへ切り替え、通常どおり起動します。

このコマンドは、チャット別ファイルから以前の単一ファイル形式を再構築します。何も削除されません。チャット別ファイルは、再構築した各ファイルの隣に`<table>.post-unshard-<timestamp>`というフォルダー（例: `messages.post-unshard-…`）として残り、移行前の原本も`.pre-shard`ファイルとして残ります。後で再びアップグレードすると、Marinaraが自動的にデータを再変換します。

DockerとPodmanは`marinara-data`ボリュームにデータを保存するため、1回限りのコンテナーでコマンドを実行します。実行中のコンテナーを停止し、`docker compose run --rm marinara node scripts/protect-launcher-data.mjs unshard`を実行してから、古いイメージを起動してください。

### バックアップやエクスポートが403を返す

ループバックのセッションであれば、管理者用の秘密の値なしでバックアップを作成できます。別のデバイス、ネットワークアドレス、Dockerからの場合、バックアップとプロファイルのエクスポートには追加の設定が必要です。サーバーに`ADMIN_SECRET`を設定し、同じ値を**Settings** > **Advanced** > **Admin Access**に保存してください。ループバックでも秘密の値を必須にしたい場合は、`MARINARA_REQUIRE_ADMIN_SECRET_ON_LOOPBACK=true`を設定します。

## AndroidとDocker

### AndroidアプリがConnectingまたはWaiting for Serverから進まない

AndroidアプリはTermuxを起動するための小さな入れ物にすぎません。TermuxはAndroid向けのLinuxターミナルアプリで、実際のMarinaraサーバーはこの中で動きます。

1. **Install / Start Marinara**をタップします。
2. AndroidがTermuxのインストールを求めたら、表示される確認を承認します。
3. AndroidがTermuxでのコマンド実行を求めたら、許可します。
4. ランチャーの処理が終わってサーバーが起動するまで待ってから、アプリに戻ります。

通常のAPKの手順では、Marinaraのシークレットを貼り付けるよう求められることはありません。アプリがlocalhost用の非公開認証情報を生成し、Termuxに渡して自動的にログインします。AndroidのアプリインストールとTermux権限のダイアログは、引き続き必要なシステム確認です。`CSRF_TRUSTED_ORIGINS`に`null`、`http://null`、APKのシークレットを追加しないでください。どれもAndroidの設定に必要な正しい手順ではありません。

アプリとTermuxが同じポートを使っているかも確認してください。デフォルトは`7860`です。別のポートでアプリをビルドした場合は、Termuxの`.env`にも同じ`PORT`を設定します。

### Androidのlocalhostでログインページが開く、または401/503になる

APKが管理するTermuxインストールでは、インストールごとに異なる非公開シークレットでlocalhostを保護します。Androidアプリは自動的に認証され、設定中にこのログインページが表示されることはありません。Marinara Engineアプリ内に表示される場合は、[最新のAPK](https://github.com/Pasta-Devs/Marinara-Engine/releases/latest/download/marinara-engine-android.apk)をインストールし、もう一度**Install / Start Marinara**をタップして、Termuxの処理が終わったらアプリに戻ります。

オリジン`null`を示すエラーは、古いAPKとサーバーの組み合わせが、非公開のハンドシェイクより先にAndroid WebViewの不透明なオリジンを一般のCSRF検査へ渡したことを意味します。`.env`を編集しても直りません。リテラルの`null`は意図的に無視され、不透明なオリジンを全体で信頼すると、状態を変更するすべてのAPIルートが弱くなるためです。APKとEngineを更新してください。現在のAndroidログインルートは独自の1回限りの証明またはインストール単位のシークレットを検証し、それ以外では`null`を拒否します。

同じスマートフォンの別のブラウザーだけが、手動のローカルブラウザー認証を必要とします。そのブラウザーで`/android-login`を開き、次のTermuxコマンドで表示される値を貼り付けます。

```bash
cat ~/.marinara-engine/android-secret
```

ローカルの`mari` CLIも同じファイルを自動で読み込みます。401は、貼り付けたシークレットまたは認証チャレンジが拒否されたことを示します。`/android-login`を再読み込みし、現在の値を貼り付けてください。503は、設定されたシークレットの形式が正しくないことを示します。`./start-termux.sh`から再起動してください。シークレットファイルが無効または空であるとランチャーに表示された場合は、Androidアプリに戻って**Install / Start Marinara**をタップし、APKに再作成させます。このシークレットをスクリーンショットや問題報告に含めないでください。

### Androidのアップデートが終了ステータス134で止まる

終了ステータス134は、ビルドの途中でAndroidのメモリーが足りなくなったことを示す場合がほとんどです。最新のランチャーからアップデートし直してください。

```bash
./start-termux.sh
```

それでも止まる場合は、ほかのAndroidアプリを終了し、Termuxを開き直して、もう一度このコマンドを実行します。

### Marinaraの実行中にTermuxが終了または再起動する

サーバーの実行中、ランチャーはAndroidのwake lockを要求し、各サーバーセッションを`~/.marinara-engine/logs/`に保存します。予期しない再起動の後は、最新の`server-*.log`ファイルを報告に添付してください。ファイルの末尾にMarinaraまたはNodeのエラーがなければ、Androidか端末メーカーがサーバープロセスの外側でTermuxを終了した可能性が高いです。

Androidの設定でTermuxのバックグラウンド実行を許可し、バッテリー最適化の対象から外してください。Termux:APIアドオンに対応した端末では、そのアドオンと`termux-api`パッケージをインストールして`termux-wake-lock`を使えるようにします。メーカー固有のプロセス終了をすべて防ぐことはできませんが、一般的なアイドル休止の原因を除き、永続ログにアプリ側の障害の証拠を残せます。

### Androidのアップデート中に依存関係のインストールで空き容量が足りなくなる

ビルドしたMarinaraアプリは数ギガバイトもありませんし、Noodleが独自のAIモデルをダウンロードすることもありません。アップデート中に一時的に容量を大きく使うのは、たいていpnpmの依存関係のストアと仮想ストアが原因です。特に何回かリリースをまたいだあとや、強制的な再インストールが中断されたあとに起こります。

現在のランチャーは、古いリリースから残ったパッケージを削除し、同じアップデートで依存関係のストアを何度も作り直さないようになっています。古いランチャーですでに空き容量を使い切ってしまった場合は、ランチャーをアップデートし、参照されていないキャッシュを回収してから、もう一度試してください。

```bash
cd Marinara-Engine
git pull --ff-only
pnpm store prune
./start-termux.sh
```

`data`、`storage`、`marinara-engine.db`は削除しないでください。これらの場所にはチャットや設定が入っている可能性があります。それでもコマンドが止まる場合は、`Installing dependencies`から始まる行を控え、スマートフォンの空き容量とメモリーの数値も添えて報告してください。

### AndroidでStableとStagingを切り替えるとアプリ内アップデートが失敗する

チャンネルの切り替え(Stable ↔ Staging)では、依存関係のほぼ全体を入れ直すことになります。Termuxのストレージは遅いため、通常のアップデートよりもかなり時間がかかります。アプリ内のアップデーターはAndroidでは各ステップに余分な時間を認めるようになったので、以前は`Update failed: Command failed: corepack pnpm ... install`だけを残して止まっていたチャンネル切り替えも、完了するはずです。

それでもアップデートに失敗する場合、エラーには失敗したステップの名前と、その出力の末尾が含まれるようになりました。このメッセージを読んでください。依存関係やロックファイルの本当のエラーは、そこに書かれています。エラーのヒントに示される手動のコマンドを使って、Termuxから自分でアップデートを実行することもできます。先に空き容量を回収してもかまいません。

```bash
cd Marinara-Engine
pnpm store prune
./start-termux.sh
```

### Noodleに`Etc/Unknown`と表示される、またはスケジュールのタイムゾーンがずれる

Conversationのスケジュールについては、Conversationの**Chat Settings**かキャラクターのスケジュールエディターを開き、**Schedule timezone**を選びます。この選択はすべてのConversationチャットに適用され、裏側で自動送信されるメッセージも対象です。**Use device**で元に戻せます。

Conversation側の指定がないNoodleやサーバーのジョブについては、`.env`から空の`TZ=`の行を削除し、Marinaraを再起動してホストのタイムゾーンを引き継がせてください。ホスト側のタイムゾーンを明示するには、`TZ=Europe/Warsaw`や`TZ=America/New_York`のような有効なIANA名を設定します。現行のリリースでは空の値は未設定として扱われますが、Nodeのタイムゾーンの状態とスケジュールされたジョブを整合させて作り直すには、やはり再起動が必要です。

### ボリュームマウントでコンテナーの権限エラーが出る

DockerやPodmanのコンテナーが、データのボリュームで権限エラーになる場合は、次のように対処します。

- アップデート後の名前付きボリュームでは、最新のイメージを取得して`docker compose pull && docker compose up -d`で起動し直します。公式イメージは起動時に所有権を修復します。
- バインドマウントでは、ホスト側のフォルダーをユーザーIDとグループID `1000`で書き込めるようにするか、代わりに名前付きボリュームを使います。
- FedoraやRHELなどSELinuxを使うシステムでは、ボリュームマウントに`:Z`を付けます。

### Raspberry Pi 4でLiteコンテナーがクラッシュする

Raspberry Pi 4などのARMデバイスで、AIへのリクエストを送るたびにliteコンテナーが再起動する場合は、終了コードを確認してください。終了コード132やSIGILLは、liteイメージのNodeビルドが一部のARMチップで起こす既知の上流の問題を示します。SIGILLは、CPUが実行できない命令にプログラムが行き当たったという意味です。

通常の(liteでない)イメージには影響しません。上流の修正が出るまでは、そのデバイスでは通常のイメージを使ってください。影響が確認されているliteイメージには`1.5.7-lite`と`1.5.8-lite`があります。最終確認はMarinara Engine 2.2.0です。

### AddonsにExternal Extensionsが表示されない

このセクションは、安全のための2つの条件がそろうまで意図的に隠されています。

1. ホストの`.env`に`ENABLE_EXTERNAL_EXTENSIONS=true`を設定します。
2. 設定の監視が反映されるまで2秒ほど待ってから、**Settings → Advanced → Danger Zone**を開き、データ削除の項目より下までスクロールして**Allow third-party extension imports**を有効にします。

Danger Zoneのスイッチが無効のままなら、ホスト側のフラグがまだfalseか、アプリが変更を検知していません。[サーバー設定リファレンス](CONFIGURATION.md)に書かれている、実際に読み込まれる`.env`のパスを編集したか確かめてください。Dockerでは通常`/app/data/.env`です。

どちらかの条件が満たされていない間は、外部、旧形式、プロファイルからインポートされたもの、手動で保存されたもの、提供元不明の拡張機能の記録は表示されず、実行もできません。条件を満たし直しても、これらが自動的に有効に戻ることはありません。

### インポートしたブラウザー拡張機能は表示されるのに動かない

**Settings → Addons → External Extensions**でその拡張機能を開き、**Requested access**を確認します。機能の宣言がない`marinara.extension` v1形式の古いパッケージでは、**Full page access**と表示されるはずです。承認するのは、中身を確認して信頼できると判断したハッシュだけにしてください。

古いパッケージが、機能の一覧を空にした状態で再エクスポートされていると、Marinaraはそれを安全なサンドボックス拡張機能として扱うため、DOMに依存するコードは動きません。マニフェストに`full_page_access`を追加するのは、そのコードがMarinaraのページ全体、ブラウザーのストレージ、ネットワークAPI、同一オリジンのセッションにアクセスできるようになると理解している場合だけにしてください。

ページ全体にアクセスする拡張機能を無効にしたあとも、ツールバーの項目、オーバーレイ、リスナー、見た目の変化が残っている場合は、Marinaraを再読み込みしてください。ページ側のコードはMarinaraが管理する互換APIの外にも影響を残せるため、後片付けは万全ではありません。

### Server Extensionが利用できるサンドボックスはないと表示される

Server ExtensionとProfessor Mariの生のシェルコマンドは、macOSのSeatbeltまたはLinuxのBubblewrapがある環境でのみ動きます。公式DockerイメージにはBubblewrapが含まれますが、既定の最小権限コンテナーは入れ子の名前空間とマウントを作成できません。Marinaraはこの状態を検出し、壊れたコマンドを試す代わりにOSサンドボックス機能を無効のままにします。

広いコンテナー権限を受け入れ、Dockerでこれらの機能が必要な場合は、次を`docker-compose.yml`の隣に`docker-compose.override.yml`として保存します。

```yaml
services:
  marinara:
    environment:
      MARINARA_DOCKER_USER: root
    cap_add:
      - SYS_ADMIN
    security_opt:
      - apparmor=unconfined
```

追加後にコンテナーを再作成します。Marinaraのエントリーポイントが`node`ユーザーへ切り替える際に能力が破棄されないよう、サーバーをrootのままにする必要があります。rootと`SYS_ADMIN`は大幅な権限昇格で、AppArmorの無効化は外側の安全境界をさらに弱めます。警告を消す目的だけで有効にしないでください。現在のDockerでは包括的な`seccomp=unconfined`設定は不要なはずです。

Server Extensionは、macOSのSeatbeltかLinuxのBubblewrapがある環境でしか動きません。Linuxのホストに`bwrap`をインストールしてから、Marinaraを再起動してください。Windows、Android、その他の非対応のホストでは、メインのサーバープロセスで代わりに実行することはせず、Server Extensionの実行を意図的に拒否します。Browser Extensionは、不透明なオリジンのWorkerサンドボックスで引き続き利用できます。

## さらに助けを求める

それでも解決しない場合は、まず十分な情報を集めてください。

1. **Settings** > **Advanced** > **Message Tools**を開き、**Debug mode**をオンにします。これでプロンプトと応答の内容がサーバーコンソールのログに残り、そのまま共有できます。
2. 使っているオペレーティングシステム、Node.jsのバージョン、サーバーコンソールに出たエラーの全文を控えます。

デバッグの出力を共有する前に、APIキー、アクセストークン、管理者用の秘密の値、公開したくないプロンプト、私的なチャットの内容を取り除いてください。

そのうえで、コミュニティに問い合わせます。

- 未解決のissueを読む: https://github.com/Pasta-Devs/Marinara-Engine/issues
- コミュニティの助けを得られるDiscordに参加する: https://discord.com/invite/KdAkTg94ME
- 集めた情報を添えてバグを報告する: https://github.com/Pasta-Devs/Marinara-Engine/issues
