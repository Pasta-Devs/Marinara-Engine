# 任意のエージェントパッケージと機能パッケージ

ステータス: issue #3612として、v2.3.0の開発サイクルで実装済みです。

## 目的

Marinara Engineの基本配布物には、任意のエージェントと機能の実装をコンパイルして同梱してはいけません。新規インストールは、任意のパッケージが1つも入っていない状態から始まります。既存の環境をアップデートした場合は、このパッケージ方式を導入する前から使えていた機能をそのまま維持します。

公式カタログ、パッケージのソース、再現可能なアーティファクト、検証スクリプト、貢献の手順は[Pasta-Devs/Marinara-Agents](https://github.com/Pasta-Devs/Marinara-Agents)にあります。インストールしたアーティファクトは、設定したMarinaraのデータフォルダーの下に置かれるため、アプリのアップデートで上書きされることはありません。

## パッケージのモデル

エージェントパッケージは、宣言的なエージェントを1つ以上提供でき、加えて信頼された実行可能な機能を任意で提供できます:

- ルート、ライフサイクルフック、プロンプトプロバイダー、結果ハンドラー、ストレージのマイグレーションを担うサーバー側のエントリーポイント
- パネル、チャット画面、設定セクション、セットアップの選択肢、実行時の表示を担うクライアント側のエントリーポイント
- 共有のJSONスキーマと、安定したワイヤーコントラクト
- パッケージが所有するアセット、ドキュメント、Professor Mariの知識フラグメント

パッケージは、バージョン管理されたMarinaraの機能APIを対象にします。エンジン内部のプライベートなソースパスをインポートしてはいけません。

クライアント側の機能要素には、Engineが選択しているUIのロケールが`lang`属性と`dir`属性、および
`capabilityProps.localization`オブジェクトを通じて渡されます。パッケージが持つ画面は独自のロケールファイルを保持し、訳がなければパッケージ側の
英語にフォールバックします。Engineはパッケージのプロンプトや、パッケージが定義した機械向けの値を翻訳しません。ロケールが変わったときは既存の
`marinara-capability-props`イベントをそのまま使うので、Engineを再起動しなくてもインストール済みの画面を描画し直せます。

### 配信とキャッシュ

インストール済みパッケージのファイルは、マニフェストに記載されたファイルごとのSHA-256ハッシュから生成した強いバリデーターとともに配信されます。Engineは、読み取るたびに同じ値でバイト列を再検証します。クライアントバンドル(`/api/capability-packages/<id>/client`)とすべてのパッケージアセットは常に再検証されます(`no-cache`と`ETag`)。変更のないファイルは再ダウンロードされず`304 Not Modified`を返し、再公開されたファイルはすぐに取得されます。`immutable`として配信されるものはありません。インストールポリシーでは同じバージョンを異なるバイト列で再公開できるため、パッケージURLはコンテンツアドレスではありません。

Capability API 1.1では、サーバーの有効化コンテキストに汎用のランタイムファサードが追加されます。
パッケージは、プライベートなロガーモジュールや実行時設定のモジュールをインポートしなくても、
実際に適用されているエージェントのデバッグ状態を読み取り、EngineのPinoロガー経由でログを書き出せます。
デバッグモードを明示的に上書きすることもできます。ファサードが公開するのは操作だけで、
Engine内部のオブジェクトそのものは公開しません。

Capability API 1.2では、トランザクションの範囲内で動くチャットとメッセージの操作、チャットのメタデータへの
限定的な書き込み、ロアブックのエントリーが存在するかどうかの読み取り、そして空間スナップショットの互換ストアが
追加されます。パッケージは、データベースハンドルやテーブルオブジェクトを受け取らなくても、Engineの
トランザクションの中でドメインの変更を検証し、所有元のメッセージ、スワイプ、空間スナップショットと
メタデータをまとめて原子的にコミットできます。ロールバックと過去のストレージとの互換性はEngineが担当し、
検証とドメインのポリシーはパッケージが担当します。
同じAPIからは、正規化されたチャットとキャラクターの
レコード、対象になるロアブックのエントリーの選択、JSON風のレスポンスの解析、解決済みの言語モデル呼び出しも
利用できます。接続の認証情報、プロバイダーの実装、データベースハンドル、ストレージオブジェクトは
Engine内部に閉じたままです。

### Capability API 1.7のチャットの分岐

Capability API 1.7では、`CapabilityChatRecord`に正規化された分岐のメタデータが追加されます:

```ts
branch: {
  title: string | null;
  parentChatId: string | null;
  parentMessageId: string | null;
  childMessageId: string | null;
} | null;
```

`title`は、保存されている分岐の名前から前後の空白を取り除いたものです。ルートでは`null`を返します。Engineが
作成したとわかっている分岐では、直接の親チャット、分岐元になったメッセージ、コピーされた子メッセージがわかります。
空の分岐では、メッセージのアンカーがnullになります。従来の形式の分岐、壊れたメタデータ、関係が特定できないまま
インポートされたグループの兄弟チャットでは、系統の項目がnullになります。
Engineは過去の関係を推測しません。
汎用のエクスポートとインポートでは、インストール先ごとにIDが変わるため、親とメッセージのIDを含めません。
親を削除しても、子の系統はそのまま残ります。

### Capability API 1.8のGame Experience

Capability API 1.8では、パッケージが提供するGame Experience、Gameの各ターン用プロンプトコンテキスト、リソースへの書き込みが追加されます。

パッケージは、組み込みGame Modeへの追加機能ではなく、Game Mode全体を提供できます。`game-surface`スロットを宣言し、ゲーム作成時にセットアップウィザードのExperiencesブロックから選択します。選択内容はゲームに記録され、そのゲームが続く限り固定されるため、プレイの途中でExperienceが切り替わることはありません。サーフェスは共通のナレーションの上に独自のHUD、メニュー、戦闘を描画し、置き換える組み込みシステムを宣言します。宣言しなかった機能は組み込みのままなので、Experienceは実際に実装する機能だけを無効にします。任意の`contributions.gameSurface.surfaceClass`では、サーフェスのマウント中にEngineがゲーム領域へ付けるクラスを指定できます。これにより、パッケージのスタイルシートから、独自要素の外側に描画される共通UIも装飾できます。

`prompt-context`権限を持つパッケージは、生成されるGameの各ターンのシステムプロンプトへテキストを追加できます。ライブ状態を所有するパッケージは、プレイヤーが見ている内容とモデルの認識を一致させられます。コントリビューションは置き換える組み込みゲームシステムも宣言でき、その場合Engineはモデルにそのシステムを操作する指示を出さなくなります。コントリビューションはターンごとに収集され、必須ではありません。何も返さないものはスキップされ、例外が発生したものや期限内に完了しないものはログに記録してスキップされます。生成には影響しません。

リソースファサードでは読み取りに加えて書き込みもできるため、パッケージのセットアップフローからプレイヤーのPersonaとそのロアブックを検索または作成できます。ストレージ、検証、識別情報はEngineが保持し、ドメイン内容はパッケージが保持します。

### Capability API 1.10のパッケージアセット

Capability API 1.10では、パッケージ所有の静的アセットを一般的に配信できるようになります。マニフェストは`contributions.assets.paths`を宣言できます。これは、パッケージに含まれる最大256個の画像(`png`/`webp`/`gif`/`jpg`/`jpeg`)とJSONファイルの許可リストです。Engineは、ブラウザータブのアイコンと同じ検証チェーンを通して`/api/capability-packages/<id>/assets/<path>`から配信します。検証内容は、パスの閉じ込め、`files[]`内のハッシュとの一致、受動的なコンテンツタイプの許可リスト、読み取りごとの整合性再検証です。スキーマは能動的な文書タイプ(SVG、HTML、スクリプト)を拒否します。宣言したすべてのパスは`files[]`でハッシュ固定されている必要があり、パッケージ内の`manifest.json`は宣言しても配信できません。`contributions.assets`を宣言するには、`schemaVersion` 2かつ`capabilityApi` 1.10以降のマニフェストが必要です。v1マニフェストでは宣言できません。アセットは常に再検証されます。クライアントバンドルと同じく、マニフェストハッシュに基づく強い`ETag`を持ち、変更のない再検証には本文なしの`304 Not Modified`で応答します。タイルセットが再ダウンロードされるのは、バイト列が実際に変わったときだけです。レスポンスは意図的に`immutable`になりません。同じバージョンを異なるバイト列で再公開できるため、バージョン付きURLもコンテンツアドレスではありません。これにより、`game-surface` Experienceはアートをクライアントバンドルへ埋め込まず、実ファイルとして同梱できます。

違反したマニフェストは、インストール時に次のいずれかで拒否されます。"A declared package asset must be listed in the package file manifest"、"contributions.assets requires schemaVersion 2 and capabilityApi 1.10 or newer"、画像でもJSONでもないパスに対するスキーマの拡張子エラー、または大文字と小文字だけが異なり、大文字と小文字を区別しないファイルシステムでは同じファイルになるアーカイブに対する"Package contains duplicate file" / "Package manifest declares files that collide on case-insensitive filesystems"です。

この用途のため、各Capability要素には固有の識別情報が渡されます。`capabilityProps.packageId`と`capabilityProps.packageVersion`が`localization`とともに届くため、バンドルはアセットURLを`/api/capability-packages/<packageId>/assets/<path>`として構築できます。任意で`?v=<packageVersion>`を付ければ、バージョン更新時に中間キャッシュを無効化できます。インストール済み一覧の再取得や、自身のインポートURLの解析は不要です。

### Capability API 1.11のExperience戦闘インターフェース

Capability API 1.11では、`game-surface`のCapability Propsに戦闘インターフェースが追加されます。`combatActive`は、組み込み戦闘UIが実際にマウントされた瞬間を通知します。GMの物語上のシーン状態である`chatMeta.gameActiveState`は切り替えより遅れ、エンカウンターがないのに"combat"を示す場合がありますが、`combatActive`にはその問題がありません。`combatStyle`は有効なスタイル(`classic`または`tactical`)を示します。`requestCombat()`は、手動のStart Combatボタンと同じ処理でEngineへエンカウンター生成を要求します。ExperienceのUIですでに意図を表しているため、確認ダイアログだけは省かれます。エンカウンターの内容は、引き続きEngineの生成処理が決定します。パッケージが戦闘参加者や戦闘状態を直接渡す方法は意図的にありません。戦闘はEngineが所有します。

`requestCombat()`は同一性が安定し、パッケージ側では通知を表示せず、Experienceが独自のフィードバックを描画するためのコードを返します。成功時は`"started"`、拒否時は`"combat-active"`、`"pending"`(すでに生成中)、`"no-turn"`(GMがまだターンを書いていない)、`"unavailable"`(終了済みセッションまたはリプレイ)です。`combatPending`と`combatError`は生成の進行と失敗を反映するため、生成失敗後にパッケージが`combatActive`を待ち続けることはありません。1.7と1.8のインターフェースと同様に、厳格なゲートがある1.10の`contributions.assets`とは異なり、これらのPropsは宣言した`capabilityApi`に関係なくすべての`game-surface`パッケージへ渡されます。1.11というラベルは導入時期を示します。必要とするパッケージは1.11を宣言し、古いEngineでは明確に拒否されます。

### Capability API 1.12: 所有するExperience向けの空間イベント

Capability API 1.12では、ゲームを所有するExperienceパッケージにも空間Capabilityイベントが送られます。以前は`marinara-capability-server-event`ウィンドウイベントで`hierarchical-maps`だけに送られていた`spatial_transition_committed`、`spatial_transition_rejected`、型なしの`spatial_context_refresh`通知が、チャットの`gameExperienceId`を`packageId`に設定して二重配信されます。ペイロードはイベントごとに異なります。確定イベントは`{ chatId, commandId, currentLocationId, definitionRevision, travel? }`、拒否イベントは移動が起きていないため位置フィールドを含まない`{ chatId, commandId, code?, message? }`、更新通知は`data: null`です。`sendMessage`の`pendingSpatialTransition`引数で移動コマンドを送ったExperienceは、後の状態読み取りから推測せず、ホストが結果を把握した時点で移動を確定または解除できます。1.12ではWorld Mapsにも影響していた欠落を解消しています。生成内でストリーミング前に行う所有者ターンの確定と、単独のREST確定という2つの無通知HTTP経路で拒否された遷移は、以前はイベントを一切生成しませんでした。現在は、`already_applied`以外の`spatial_*`エラーコードという確実な根拠がある場合に限り、どちらも`spatial_transition_rejected`を生成します。成功した確定の応答が失われた可能性があるネットワークエラーなど、結論を出せない失敗では、型なしの`spatial_context_refresh`を送ります。リスナーは推測した結果を採用せず、サーバー状態と同期できます。確定イベントで`travel.mode`が`"step_by_step"`、`complete: false`の場合、移動は継続中です。完了イベントまで保留状態を維持してください。これは1.11と同じソフトなインターフェースで、宣言した`capabilityApi`に関係なくイベントが配信されます。パッケージが必要とする場合だけ1.12を宣言します。

### Capability API 1.13: 一時的なナレーション折りたたみ

Capability API 1.13では、`game-surface`パッケージが`setExperienceChrome`へ渡すChrome宣言に`requestsCollapsedNarration`が追加されます。このフラグがtrueの間、Game Modeのナレーションボックスは細いハンドルまで折りたたまれ、Experienceはカットシーンや全画面の演出に画面を広く使えます。

これは要求であり、設定ではありません。プレイヤー自身の折りたたみ設定は書き換えられず、Experienceが現在のサーフェスである間だけフラグが有効です。フラグを外すか現在のサーフェスでなくなると、ボックスはプレイヤーが選んだ状態へ戻ります。これが「終了後に必ず再び開く」という保証であり、パッケージから折りたたみを永続化する方法は意図的にありません。

Engineの安全規則は要求より優先されます。プレイヤーのテキスト入力が画面に表示されている間は、まだセグメントがないシーン開始直後も含め、ボックスが強制的に開きます。セグメント進行コントロールが有効な間も同様です。このコントロールだけがターンを終える手段であり、パッケージが隠せるとプレイヤーを永久に進行不能にできてしまいます。保留中のシーン分析、生成、戦闘生成の再試行がある場合、ハンドルは注意インジケーターを表示し続けます。要求中にプレイヤーが手動でボックスを開いた場合、要求が解除されるまで開いたままです。1.11と1.12と同様に、これはソフトなインターフェースです。宣言した`capabilityApi`に関係なくフィールドが適用されます。1.13というラベルは導入時期を示すため、必要とするパッケージは1.13を宣言します。

### Capability API 1.14: トラッカー画面とエージェントのライフサイクル

Capability API 1.14では、クライアントのエントリーポイントを持ち、有効かつ稼働中のRoleplayエージェントパッケージ向けに、`contributions.slots`へ2つの値を追加します。

- `roleplay-tracker`はRoleplay HUDにパッケージの`toolbar`ビューをマウントします。Propsには`chatId`、`chatMode`、`mobileCompact`、ホストの`toolbarButtonClass`、`onRerunTracker`、`trackerRetryBusy`、`lockMode`、`onToggleLockMode`があります。コールバックは任意なので、存在を確認してから使ってください。
- `tracker-panel`は既存のTracker Panel内にパッケージの`tracker`ビューをマウントし、`chatId`、`chatMode`、`detached`を渡します。別のパネルを開かず、ホストの画面を再利用してください。両方のスロットには通常の識別情報とローカライズのPropsも渡されます。

プロンプトコンテキストの提供は引き続き`api.registerPromptContext`で登録し、`prompt-context`権限が必要です。要求に`targetCharacterIds`、`personaId`、`placedAgentTypes`(互換性のため任意)が追加されます。`placedAgentTypes`はプリセットが配置済みのエージェントデータセクションを示し、コンテキストの重複を防げます。ホストは各提供元のパッケージ識別情報を`packageBlocks`に保持し、パッケージのテキストを対応するエージェントセクションへ配置します。閲覧者別のテキストを返す場合は、指定された対象キャラクターIDを尊重してください。

サーバーのエントリーポイントは`api.registerService("agent-runtime:<package-id>", service)`で独自の後処理ライフサイクルサービスも登録できます。`agent-runtime`権限が必要で、他のパッケージIDへの登録は拒否されます。任意のフックは次のとおりです。

```ts
const cleanup = api.registerService(`agent-runtime:${packageId}`, {
  prepareContext({ agent, context }) {
    // Return small, JSON-serializable context for this agent, or nothing.
    return { chatId: context.chatId };
  },
  finalizeResult({ agent, context, preparedContext, result }) {
    // Validate or enrich the result before the host publishes/applies it.
    return result;
  },
});
// Return cleanup from activate(), or include it in the activation cleanup.
```

`prepareContext`は後処理の前に実行され、null以外の結果はそのエージェントに限定され、シリアライズしたランタイムコンテキストとしてプロンプトに含まれます。`finalizeResult`はその値と生成結果を受け取り、`AgentResult`を返します。生成と手動再試行では、最終処理が終わるまで結果の公開を待ちます。非同期フックの期限は各2秒です。準備失敗はログに記録して省略しますが、最終処理の失敗は未検証の出力を適用せず、結果自体を失敗にします。これらは短いホストライフサイクルフックであり、追加の遅いモデル呼び出しを行う場所ではありません。

これらの追加に、フィールドごとの1.14ゲートはありません。任意のPropsを検出して古いEngineで機能を縮退させることはできますが、スロット、配置、ライフサイクル動作が必須なら、v2マニフェストで`capabilityApi: { major: 1, minor: 14 }`を宣言し、古いEngineがインストールを明確に拒否できるようにしてください。

### Capability API 1.15: 現在の埋め込み設定

`api.runtime.resolveEmbeddings()`は、パッケージの現在のエージェント接続設定を使う、新しい`Promise<CapabilityEmbeddingHost>`を返します。埋め込み処理を開始するときに呼んでください。`api.runtime.embeddings`をキャッシュすると、有効化時のスナップショットなので、再有効化しない限り接続変更に追従しません。

```ts
const embeddings = await api.runtime.resolveEmbeddings();
const vectors = await embeddings.embed(texts, signal);
// Store/compare embeddings.spaceId with persisted vectors; do not mix embedding spaces.
```

返されたホストは`spaceId`、`label`、`embed(texts, signal?)`を持ちます。設定された埋め込みソースを使い、利用できないか設定の解決が失敗した場合は組み込みのローカルMiniLMへフォールバックします。`embed`は`null`を返すことがあります。空のバッチ、128テキスト超、合計200,000文字超は拒否されます。新しいホストが既存ベクトルを再埋め込みすることはないので、保存済みベクトルと比較する前に`spaceId`の変更へ対応する必要があります。

現在のEngineでは宣言APIバージョンに関係なく公開されます。接続変更への追従が必須ならAPI 1.15を宣言してください。古いEngineも意図的にサポートするパッケージは、`typeof api.runtime.resolveEmbeddings === "function"`を調べ、有効化時の設定に固定される制約を受け入れて`api.runtime.embeddings`へフォールバックできます。

### Capability API 1.16: パッケージ宣言のGame Master動詞

Capability API 1.16では、Experienceパッケージが少数の名前付きGame Masterアクション(動詞)を限定リストとして宣言できます。EngineはそれをGMの形式リマインダーに描画し、完成したナレーションから読み取り、パッケージに代わって実行します。これらの処理でパッケージのサーバーコードは一切動かないため、`agents`と`client`のエントリーポイントだけを持つ`game-surface` Experienceでも、GMの文章から世界を変更できます。

スキーマ、予約名とキーの所有規則、テーブルの読み取り、プロンプト描画、実行処理まで、インターフェース全体が稼働しています。テーブルを同梱し`chat-write`を持つパッケージでは、結び付けられたチャットのGameの各ターンで動詞がGMリマインダーに表示され、GMが使うと実行されます。パッケージに結び付いていないチャットや、テーブルを宣言しないパッケージでは動詞を一切解決せず、ターンはこの機能以前とバイト単位で同一です。

テーブルは`gm-verbs.json`として宣言し、ほかのアセット同様に`contributions.assets.paths`へ記載して`files[]`でハッシュ固定します。この予約ファイル名による検出は新しい規約です。従来のパッケージ処理では`entrypoints`、アイコンパス、アセットパスは宣言した名前で読み、形状から見つけるファイルはありませんでした。このアセット経路には2つの注意点があります。`files[]`だけに同梱し`contributions.assets.paths`から省いたファイルは、インストールとカタログビルドの両方で何も起きず、診断なしで動詞を持たないパッケージになります。また、アセット経路に特権アクセス検査はなく、宣言したファイルは`/api/capability-packages/<id>/assets/gm-verbs.json`で保護なしに配信されるため、機密情報は絶対に入れないでください。1.11〜1.13同様のソフトなインターフェースです。古いEngineは普通のJSONアセットとして無視するため、インストール範囲を狭めずに同梱できます。動詞の実行が必須の場合だけ`capabilityApi` 1.16を宣言してください。宣言すると、それより古いすべてのEngineへのインストールが拒否されます。

文書は`{ "schemaVersion": 1, "verbs": [ … ] }`で、1〜16個の動詞を持ちます。各動詞は厳密で、未知のキーを余分なものとして黙認せず拒否します。一方、`schemaVersion`と`verbs`と並ぶ未知のフィールドは、意図的に2つの場面で扱いが異なります。Engineの読み取りでは削除するため、新しいEngine向けのテーブルでも理解できる動詞は得られます。作成ツールが検証する共有文書スキーマでは厳密に拒否します。したがってスキーマ検証は実行時のEngineより厳しく、作成時に望ましい方向の差です。

```json
{
  "schemaVersion": 1,
  "verbs": [
    {
      "name": "weather",
      "description": "Set the sky when the weather visibly changes.",
      "effect": "state",
      "metadataKey": "pixelforgeWeather",
      "args": [
        { "name": "word", "type": "string", "enum": ["fair", "overcast", "rain", "storm", "snow"] },
        { "name": "intensity", "type": "string", "enum": ["light", "heavy"], "optional": true }
      ]
    }
  ]
}
```

動詞名は`[a-z][a-z0-9_]*`で最大32文字、Engine自身のGM角括弧タグは使えません。リマインダーの`[Note:`と`[Book:`は大文字で、解析正規表現は大小文字を区別しないため、小文字の`note`でも日誌タグを隠してしまいます。そのため検査では大小文字を同一視します。予約集合はGMとパーティーのリマインダーの全分岐が描画するタグ、および完成したターンから読み取る5つの解析器から導きます。クライアントのタグ解析器とナレーションフォーマッター、サーバーのセグメントエディター、サイドカーのシーン解析器、生成ルートの台詞書き直し処理です。その語彙はリマインダーより広く、台詞の`main`、`side`、`extra`、`action`、`thought`、`whisper`や、ナレーションフォーマッターだけが読むQTEの`qte_bonus` / `qte_result`も含みます。最後の組が固定検査の価値を示します。`whisper`動詞があると、保存前に台詞の`[whisper:Tam]`が切り取られ、その行は二度と台詞と認識されなくなります。抽出器を含め回帰検証で固定しています。独自の名前を提供する解析器(タグ解析器の`party-chat` / `party-turn`、フォーマッターのQTE組)はその名前を提供し続ける必要があり、走査から密かに抜けたソースは予約集合を狭めずビルドを失敗させます。独自名を持たない残り3つも、新しいタグを最初に導入した場合を捕捉するため走査します。ただし完全性は保証しません。対象外ファイルに追加されたタグや、抽出器が読めない形のタグは見逃すため、新しい解析器が現れたら集合を広げます。`action`、`state`、`status`、`note`も組み込みタグなので、普通の動詞名の拒否は多くの場合スペルミスではなくこの規則です。`description`は角括弧も改行も含まない1〜200文字の1行で、リマインダーの`COMMANDS:`ブロックへそのまま描画します。改行はCRとLFだけでなく、ブロックを読む処理にとって行末となる`U+0085`、`U+2028`、`U+2029`も含みます。C0制御文字とDELも、特にタブは行を終えずにブロックの形を変えるため拒否します。ただしマクロ処理まで素通りするわけではありません。リマインダー全体を送信前にマクロ展開するので、説明内の`{{…}}`は文字として表示されず展開され、`{{setvar::…}}`のようにチャット変数を書き込むものも対象です。`chat-write`がすでに許す範囲を超えませんが、誤って使いやすいため、意図しないマクロ括弧は説明に入れないでください。各動詞は最大6個の`{ name, type, enum?, maxLength?, optional? }`引数を取り、引数名は最大32文字の`[a-z][a-zA-Z0-9_]*`です。角括弧タグではなくJSONキーなので、大文字禁止の動詞名より意図的に広い構文です。`enum`は文字列引数だけに許され、重複のない1〜16値です。重複は集合に情報を足さず、テーブル内のほかの重複と同様に拒否します。enumのない文字列には`maxLength`(1〜500)が必須です。実行器の限定解析には独自の上限がなく、自由文が無制限だとナレーション全体が入りかねないためです。enum自体が値を制限するので、`enum`と`maxLength`の併記は拒否します。ペイロードは平坦な1行JSONです。入れ子の`}`はタグの一致を途中で終えます。メッセージ内で各動詞名は1回だけ解析され、繰り返しても適用は1回です。

これらを説明文に書く必要はありません。解析済みテーブルから、構文を示すペイロード、説明、コピーできる例1つの順でリマインダー行を生成します。

```
- [weather:{"word":"fair|overcast|rain|storm|snow","intensity"?:"light|heavy"}] — Set the sky when the weather visibly changes. Example: [weather:{"word":"fair"}]
```

語彙を教えるのは構文表示です。全引数を宣言順に並べ、任意のものはJSON文字列の外で`"name"?:`と示し、enumは全候補、enumなしの文字列は上限、数値と真偽値は引用符なしで示します。検証器は数値の`"3"`を変換せず拒否するためです。例は具体的な1件でenum値を1つしか見せられず、語彙を教えるものではありません。`{"word":"fair"}`だけを見せるとGMは"sunny"と書き、知らされていない値を検証器が拒否します。この拒否は表に見えません。タグは検証成功時ではなく名前の一致時に除去され、文章はきれいでも世界は変わらないためです。同じ解析済みテーブルから両方を生成することで食い違いも防ぎます。値を説明文で定義しなくなったので、検証器が拒否する値を説明で約束することはありません。200文字は引数の言い直しではなく、いつ使うかに使ってください。

縮退は動詞ごとです。新しい`effect`、表現できない形、予約名や他パッケージのキーなど、Engineが使えない動詞だけをログ付きで除き、理解できる動詞は実行します。カタログ項目への`parseCapabilityCatalogWithCompat`と同じ規則です。拒否された動詞は静かに失敗するため、宣言した動詞が出ない場合はログを読んでください。未知の`schemaVersion`、空の`verbs`配列、オブジェクトでない値など文書全体が使用不能なら、空のテーブルとログ1行になります。また、読み取り前に宣言された`files[].bytes`が64 KBを超えていれば拒否します。`files[]`は最大100 MBを許し、ほかに読み取り前の上限がないためです。どの失敗でもターンはそのまま維持されます。

`metadataKey`を宣言する動詞は**状態動詞**で、引数全体をチャットのメタデータ行のそのキーに書き込み、パッケージは既存のPropsで変更を受け取ります。`metadataKey`のない動詞は**イベント動詞**で、永続書き込み、キュー、再生、受領確認のないライブの機能クライアントイベントとして送ります。イベント動詞に`metadataKey`は許されず、書かないキーを占有できません。状態動詞では必須です。

選ぶ前に両者の違いを理解してください。状態の書き込みは永続し、元に戻りません。ターンのスワイプ切り替え、編集、削除でも値は残り、最後に表示したスワイプではなく最後に生成したスワイプが勝つため、文章と世界が食い違っても調整するものはありません。イベントは記憶を持たず、1フレームの同期配信だけです。ターンの中断、ストリーミング中のタブ閉鎖・再読み込み、初回マウント前の配信、別チャットへの切り替え、パッケージ独自の読み込み待ちの間には、通知なしに失われます。再配信はありません。その代わり、巻き戻しで復元する場所にパッケージが効果を保持すれば、物語と一緒に戻せます。巻き戻らないチャットメタデータ行では不可能です。どちらにも痕跡を残さない損失は、ライブ状態に適用したイベントが次の保存フラッシュ前の強制再読み込みで失われる場合です。

そのため、両方とも相対的な意味を意図的に拒否します。状態動詞は絶対値の上書きなので「金を5追加」は構造上表せません。相対イベント動詞も規則として拒否します。ターン再生成は新しいスワイプ番号を作り、以前の印を引き継がず、生成のたびに相対効果が累積するからです。`chatId:messageId:swipeIndex`での重複排除は、この経路でそもそも起きない再配信を防ぐだけで、実際に起きる再生成は防げません。2回適用しても安全にするのは台帳ではなく絶対値です。相対的な語彙は、メッセージごとの絶対値に変換した場合だけ使えます。

両方を持つターンでは、非同期の状態再取得が届く前に同期イベントがパッケージへ届きます。イベントハンドラーは同じターンの状態動詞の結果を読み、新しい値だと期待してはいけません。

拒否の非対称性も仕様です。Engineは引数名、型、enumへの所属、文字列上限という形だけを検証し、意味はパッケージが担当します。チャットごとに世界を生成する場合、NPC名は宣言時に列挙できません。状態動詞はパッケージが受け取る時点でメタデータが確定しており、パッケージの拒否は助言にすぎません。イベント動詞ではEngine側に確定したものがなく、同じ拒否が拘束力を持ち、未知の名前を実際に拒否できます。

状態動詞の`metadataKey`は3つの規則で宣言元パッケージに属する必要があります。パッケージIDをキャメルケースに正規化した接頭辞(`hierarchical-maps` → `hierarchicalMaps`)で始まり、空でない接尾辞を大文字境界で続けて他パッケージの名前空間への侵入を防ぎ、正規化IDがEngine所有のメタデータ名前空間そのもの、またはその大文字境界での拡張であってはいけません。名前空間一覧は`ChatMetadata`の全トップレベルキー、Engineのキー定数、宣言ではなくインデックスシグネチャ内に存在するキーから導きます。最後には`encounterActive`、`internalAssistant`、`imageGenConnectionId`など、最初の2ソースでは見えない未宣言キーが含まれます。この第3群を読むには7つのソースが必要です。`patchMetadata`/`updateMetadata`の引数オブジェクト、ほぼ同頻度で使うアップデーターコールバックの戻り値、`patchMetadata`を通らないクライアントの`useUpdateChatMetadata()`と`onMetadataChange`、そのフックも通らない直接の`PATCH /chats/:id/metadata`(Game画面が戦闘・シーン・ナレーションのキーを書く方式)、`chatMetadata.key`と`chat.metadata.key`のプロパティ読み取り、Engineで最も多く`scenario`などを唯一検出できる`parseChatMetadata(…)`の結果からの読み取り、そして関数境界をまたいでのみ使うキーを収めた、チャット設定プロファイル向けの手動メタデータキー一覧です。

これらは抽出器も含め回帰検証で固定します。走査対象外は意図的に2つあります。変数やヘルパーの戻り値を渡す書き込み(`patchMetadata(id, hydratedMeta)`やメタデータルートの同形式)のキーは静的走査で読めません。現在20か所あり、その数を固定しているため、21か所目は人が読むまでビルドに失敗します。ヘルパー内部でパラメーターから読む処理も関数間解析が必要で、走査できません。`spatialContext`はこのリポジトリではなくAgentsリポジトリから配信される`hierarchical-maps`のクライアントが書き、こちらではヘルパーとファイル内解析で読みます。この2つ目の穴を手動一覧が埋めるため、7ソースの1つは自動導出ではありません。見落としがないと主張せず、盲点を明示しています。一覧の`persona`は現在どのソースも出力しない、手動追加の最低限の予約です。3つ目の規則は意図的にパッケージ全体を拒否します。`conversation-calls`は`conversationCalls`へ正規化され、`conversationCalls` + `Enabled`が既存Engineキーなので、自身のID下でも所有できません。`noodle`と`background`も同様で、後者は`background`自体がEngineのメタデータキーです。これらもキーを所有しないイベント動詞は宣言できます。キーが平坦なトップレベルなのは、既存のパッケージの調整処理がその形を読むためです。

パッケージが宣言したモデルコマンドは、そのパッケージが`chat-write`を宣言し、インストール済みで準備完了の場合にのみ実行されます。この権限は、メッセージ、チャットのメタデータ、roleplayイベント、空間スナップショットを含むパッケージの永続化API経由の書き込みも制御します。`chat-read`はチャット、メッセージ、ゲーム状態、空間スナップショットの読み取りを制御します。永続化トランザクションやチャットロックの内部でも同じ検査が適用され、書き込み権限が読み取り権限を暗黙に与えることはありません。エンジン自身の永続化呼び出しは引き続き信頼されます。

インストール後の**Download Agents**(エージェントのダウンロード)の詳細画面には、インストール済みバージョンが宣言した権限が表示されます。カタログ側のバージョンが異なる権限を要求する場合は、分けて表示します。コードのインストールや更新には、そのバージョンとチェックサムに厳密に結び付いた既存の承認が引き続き必要です。モデルコマンドが毎ターン個別の承認を求めることはありません。

これらはAPIの検査であり、JavaScriptのサンドボックスではありません。ネットワーク、ストレージ、UIの権限はアクセスの宣言です。パッケージのブラウザー側・サーバー側コードは信頼されたコードとして扱われ、ホスト環境にアクセスできます。信頼できるパッケージだけをインストールしてください。ファイルを配信できるかではなく準備完了かを検査するため、更新後に`restart-required`となったパッケージのコマンドは、エンジンの再起動まで解決されなくなります。

### Capability API 1.17: 最初のターンより前にExperienceを準備

`game-surface`パッケージは、スキーマバージョン2とCapability API 1.17で`contributions.gameSurface.prepareBeforeStart: true`を宣言できます。Engineはゲームが準備済みになると、**Start Game**(ゲームを開始)を有効にする前にそのサーフェスをマウントします。従来のゲームと、このフラグを持たないパッケージの起動手順は変わりません。

この機能を有効にしたメインサーフェスには、次の2つのプロパティが追加されます。

- `startup: boolean`は、プレイヤーが**Continue**(続ける)でEngineの導入を終えるまでtrueのままです。その間はワールドのシミュレーションとプレイヤーの操作を一時停止してください。
- `setStartupReady(context: string | null): void`は準備状態を報告します。読み込み中、保存中、または障害からの復旧中は`null`を送信してください。実際のワールドが永続保存され、使用可能になってから文字列を送信します。空文字列なら追加コンテキストなしで開始できます。

ホストは、準備完了を示す文字列を受け取るまで、**Start Game**、ウィジェット準備の確認、最初のターンの再試行をブロックします。ブロック中も、パッケージ独自の読み込み画面とエラー・再試行画面は表示されます。準備ができると、パッケージは通常のEngine導入画面の背後に隠れます。**Continue**で通常のサーフェスが開き、その際に再マウントされる場合があります。ワールドの準備を冪等にし、再生成せずに保存済み状態を復元してください。導入を完了したゲームに戻った場合、起動時の準備は繰り返されません。

開始コンテキストの上限は**8,000文字**です。無効または長すぎるコンテキストは起動をブロックしたままエラーを表示します。ホストがワールドの事実を切り詰めることはありません。準備済みの開始地点と、実際にそこにいるキャラクターを簡潔に説明してください。Engineは、このテキストをソース`game_start`として最初のターンの既存の`generationGuide`に追加し、実在するワールドに基づいて冒頭を生成します。後続ターン用のコンテキストが登録されるわけではありません。後続ターンには、通常のパッケージのプロンプトへの寄与やターン生成コンテキストを引き続き使用してください。

準備完了のコールバックは、マウントされたチャット、ゲーム、パッケージに属します。別のスコープから遅れて届いたコールバックは無視されます。モジュールやランタイムに障害が起きた場合、ワールドのコンテキストがない状態を成功とみなさず、起動をブロックします。再読み込み後は、保存済みワールドに基づいて準備完了を報告する必要があります。サーバー側のプロンプトコンテキスト提供処理は引き続き読み取り専用で、短い制限時間が適用されます。ワールド生成や長時間の起動待ち処理には使用しないでください。

### Capability API 1.19: パッケージが提供するツール

Capability API 1.16では、パッケージがモデルに何かを_言わせて_、それに応じて処理できました。このバージョンでは、モデルが何かを_呼び出せます_。新しい`tools`権限を持つパッケージは、サーバーのエントリーポイントで名前付きツールを登録します。Engineはすべてのチャットの各ターンで組み込みツールと一緒に提示し、パッケージのJSON Schemaで呼び出しを検証して、引数をハンドラーに渡します。

```ts
export async function activate({ api }) {
  api.registerTool({
    name: "set_time",
    description: "Move the world clock forward or back.",
    parameters: {
      type: "object",
      properties: {
        action: { type: "string", enum: ["advance", "rewind"] },
        minutes: { type: "integer", minimum: 0 },
      },
      required: ["action", "minutes"],
      additionalProperties: false,
    },
    handler: async (args, { chatId }) => {
      const clock = await moveClock(chatId, args.action, args.minutes);
      return { time: clock.label };
    },
  });
}
```

応答形式ではなくツール呼び出しを使うのは意図的です。応答形式は返信全体を占めるため、語りをJSONオブジェクトのフィールドに入れる必要があり、ストリーミングできません。ツール呼び出しは本文と並行して届き、モデルは通常どおりターンを書けます。パッケージが受け取るのはプロバイダーによって制約された引数であり、完成した語りから解析して取り出す必要はありません。スキーマによる制約と、モデルに守るよう依頼する規約との違いです。

列挙値でこの違いが明確になります。世界に12か所の場所があるなら、その12個の名前をスキーマに含められます。13番目の名前はハンドラーに届く前に拒否されます。Engineの既存の引数検証は有効な値を示すため、モデルは呼び出しを修正できます。ハンドラーの戻り値はツールの結果としてモデルに渡されます。

ツールを作成する前に、次のルールを確認してください。

- 名前は`<packageId>_<name>`となり、`-`は`_`に置き換わります。`world-clock`の`set_time`は`world_clock_set_time`としてモデルに届きます。別のパッケージが使用中の名前は拒否されます。組み込みツールと有効なカスタムツールは競合する名前を保持し、パッケージの定義は省略されます。完全な名前は**64文字**までです。定義と実行の両方で、組み込み、カスタム、パッケージの順に優先されます。
- パッケージが有効な間、ツールは常に追加されます。組み込みツールのようなチャットごとの追加スイッチはありません。権限の宣言と登録が決定になります。選択したプロバイダーはネイティブのツール呼び出しに対応している必要があります。
- パラメータースキーマは登録時にコピーしてコンパイルします。Engineがコンパイルできない場合、ターンの途中ではなく、開発時に確認できる有効化の段階で失敗します。
- ハンドラーが例外を投げると、呼び出しは失敗として報告され、ログに記録されます。例外のメッセージは転送されません。**10秒**経っても完了しなければ、ターンは待機を終了します。ハンドラー自体は動き続けますが、ターンを止め続けることはありません。
- 結果は最大**64 KiB**にシリアライズできる必要があります。大きすぎる結果やシリアライズできない結果は、会話の領域を奪う代わりに呼び出しを失敗させます。説明と結果は信頼されたパッケージの内容です。チャット固有のデータを読み書きする前に`chatId`を確認してください。
- 各定義は毎ターンのプロバイダーリクエストにシリアライズされ、コンテキスト調整でも計上されます。上限は**パッケージごとに16ツール**、**全パッケージで64ツール**、説明は**512文字**、パラメータースキーマは**8 KiB**です。超過すると例外が発生し、有効化に失敗します。自分の名前を再登録すると、そのツールを置き換え、枠を追加で消費しません。
- 有効化の終了後、そのコンテキストは機能しなくなります。保存した`api`から後のコールバックで`registerTool`を呼んでも拒否されます。終了したランタイムはツールを登録したり、再有効化後のツールを置き換えたりできません。
- パッケージの無効化、更新、削除でツールは解放されます。応答できるパッケージがないツールはモデルに提示されません。クリーンアップを待つ前にツールを削除し、各クリーンアップコールバックには8秒の期限を設けます。

これらの期限が制限するのは非同期の待機だけです。パッケージはサーバープロセス内で信頼されたコードとして実行されます。イベントループをブロックする同期処理はタイマーで中断できません。強制的なキャンセルには別のワーカーやプロセスが必要ですが、このAPIはその分離を提供しません。

`api.registerTool`はこのEngineバージョン以降でのみ利用できます。必要なパッケージは`capabilityApi` 1.19を宣言する必要があり、古いバージョンへのインストールは拒否されます。

## Decision文とDecisionモデル

ユーザーの**Decision model**(Decisionモデル)は、最近のチャットについてyes/noや選択式の文に答えます。概要と設定方法は[Decisionモデル](../connections/decision-models.md)を参照してください。

パッケージに同梱するエージェントのプロンプトテンプレートでも、ユーザーのカスタムエージェントと同じく`{{#if decision:"..."}}`と`{{#if decision_choice:"..." == "..."}}`を使えます。Engineはテンプレートから文を探し、エージェント実行前(後処理エージェントでは返信後)に質問し、答えを使って展開します。Capability APIのバージョンには関係しません。構文と言い回しは[条件付きプロンプト](../prompts/conditional-prompts.md#asking-the-decision-model)、エージェントの各フェーズでの扱いは[カスタムエージェントの作成](../agents/custom-agents.md#decision-statements-in-the-agents-prompt)を参照してください。

パッケージのランタイムコードからDecisionモデルを直接呼ぶ方法はまだありません。専用のCapability APIメソッドとバージョン更新が必要です。

Decisionモデルを持たないユーザーでも動くよう、すべての利用箇所を設計してください。答えのない文はnoとみなすため、`{{else}}`側、または何も出さない動作を妥当な既定にします。Jevを必須にせず、一般のDecisionモデル向けに書いてください。ローカルチャットモデルやほかの対応バックエンドも同じ構文を使いますが、答えは異なる場合があります。特定のスコア、リクエスト数、キャッシュ済みの答えに依存する前に、[しきい値](../connections/decision-models.md#thresholds)と[制限とコスト](../prompts/conditional-prompts.md#limits-and-cost)を読んでください。

### Game Mode Experience開発者への補足

通常の敵の行動はEngineの戦闘自身が決めます。GM側のボス以外の全敵には、スキルとクラスに基づく役割(bruiser、bulwark、skirmisher、marksman、spellcaster、supporter、controller)、明示指定がなければレベルに基づく熟練度(novice、trained、veteran、master)、reckless、cautious、opportunistic、protectiveなどの気質が割り当てられます。beastsとmonstrositiesは常にmindlessです。Engineはモデルを呼ばずシードから選び、ゲームの難易度がその類型どおりに動く一貫性を変えます。GMがモデル呼び出しで指揮するのは、作り込まれたボスだけです。[Game Modeの戦闘AI](game-combat-ai-design.md)を参照してください。

戦闘は今後も改善予定です。戦闘処理にDecisionモデルを組み込む前に、標準Engineの戦闘が必要な動作をすでに備えていないか確認してください。敵に特定の性格が必要なら、まず対応する熟練度と気質を与えます。敵の各ターンでDecisionを行うとモデル処理と制限時間が増え、ホスト型バックエンドならネットワーク要求と料金も増えます。ユーザーが設定していないかもしれないモデルの答えに戦闘が依存するため、答えがない場合の妥当なフォールバックも必要になります。

## 信頼性とインストール

公式カタログは、HTTPSで取得する、スキーマ検証済みでバージョン管理されたJSONドキュメントです。各リリースの項目には、変わることのないアーティファクトのURL、SHA-256のダイジェスト、バイトサイズ、エンジンとの互換性、権限、そして実行時に再起動が必要かどうかが含まれます。

サーバーの起動時、公式パッケージが1つ以上インストールされていれば、ホストはカタログを1回だけ取得します。そこから、動作中のEngineと機能APIに対応する新しいバージョンだけを選び、通常のインストールパイプラインで検証したうえで、パッケージのランタイムが有効になる前にインストールします。失敗はパッケージ単位で切り離されます。カタログに接続できないときや検証に失敗したときも、既存のファイルとレジストリーの状態は引き続き使えます。サーバーランタイムの準備に失敗した場合は、前のバージョンへ戻すロールバックの経路を使います。

インストーラーが満たすべき条件は次のとおりです:

1. ループバックまたは管理者の権限を必須にすること
2. HTTPS、ダウンロードの上限、タイムアウトを強制すること
3. 展開の前に、カタログの信頼性とアーティファクトのSHA-256を検証すること
4. 絶対パス、パスの遡り、リンク、デバイスファイル、宣言されていないファイルを拒否すること
5. マニフェストとエンジンの互換性を検証すること
6. 同じ階層にある一時フォルダーへ展開すること
7. 検証が成功したあとにだけ、原子的に有効化すること
8. 新しいランタイムが正常に起動するまで、前のバージョンを保持すること
9. 失敗したら有効化をロールバックすること
10. インストール、アップデート、アンインストールのスクリプトを絶対に実行しないこと

公式カタログで有効になるのは、ファーストパーティーの信頼された実行可能パッケージだけです。将来サードパーティーの流れを受け入れる場合は、信頼性の設計を別途、明示的に行う必要があります。

## 実行時と再起動の動作

インストール済みパッケージのレジストリーはサーバーが管理し、インストール済みの機能をクライアントへ公開します。宣言的なモジュールと再読み込みできるモジュールは、すぐに有効になります。有効化のあと、UIはカタログ、エージェント、モードの機能、アクティブなチャットのクエリーを無効化します。

マニフェストが`restartRequired`を宣言できるのは、そのエントリーポイントをホストが安全に再読み込みできない場合だけです。再起動なしで有効化に成功したときは`Agent installed. It is ready to use.`と表示します。再起動が必要なときは`Agent installed. Restart Marinara Engine to finish setup.`と表示します。

ターン制ゲームのパッケージは、再起動なしで読み込み直せます。インストールするとサーバー側のエンジンと手動のスラッシュコマンドによる起動手段がすぐに登録され、アンインストールするとEngineを再起動しなくてもランタイムが切り離されます。チャットごとの**Conversation Commands**(Conversationのコマンド)設定が制御するのは、キャラクターがパッケージの隠しコマンドを出せるかどうかだけで、自分で入力するスラッシュコマンドの起動手段は制限しません。現在の公式のターン制ゲームのマニフェストは、Engine 2.xとの互換性のために、従来どおりの保守的な再起動マーカーを残しています。Engine 3.xは`turn-game`という種類を認識し、安全な再起動なしの有効化を行い、パッケージをアクティブかつ利用可能な状態として返します。

## 互換性のための移行

アップデート後の初回起動時には、次のように動作します:

- カスタムエージェントには手を加えません
- そのインストール環境で見えていた従来の組み込みエージェントは、すべてインストール済みとして記録します
- マップ、Conversationの通話、Conversationのゲームは、これまでと同じように使えます
- チャットごとの既存の設定、スナップショット、ゲームの状態、通話履歴、エージェントの記憶はそのまま残ります
- 移行処理は何度実行しても同じ結果になり、従来の利用可否の情報がすべて確実に保存されてから完了を記録します

従来のパッケージのアーティファクトは、移行元として公式カタログから引き続き入手できます。新規インストールでは、実際にインストールするまで表示も有効化もされません。

## アンインストール

アンインストールすると、アクティブなチャットの選択からパッケージが外れ、そのエージェントの設定とダウンロード済みの実行ファイルが削除され、必要な場合は再起動時にランタイムが切り離されます。過去のチャット、メッセージ、マップのスナップショット、通話の要約、終了したゲームの記録は引き続き読めるので、パッケージを削除しても作ったものが失われることはありません。過去のドメインデータそのものを消す操作は、明示的に行う別の操作です。

アンインストールには必ず確認が入ります。影響を受けるチャットは、履歴を壊すことなく通常の基本画面に戻ります。

## カタログの画面

**Agents**(エージェント)パネルには、Card Browserの`Download Cards`と同じ位置づけの`Download Agents`という操作があります。これを開くと全画面のレスポンシブなライブラリーが表示され、検索、パッケージの種類、互換性の情報、インストールとアップデートの状態、権限、必要な容量、ドキュメント、アンインストールの操作を利用できます。

デスクトップでは、一覧の横に詳細の領域を並べます。モバイルでは1枚のパネルにまとめ、戻る操作を明示し、指で押せる大きさの操作を用意します。空、オフライン、非対応、ダウンロード破損、インストール中断、アップデート、ロールバック、再起動が必要という各状態は、いずれも正式な状態として扱います。

## 分離完了の判定基準

分離が完了したと言えるのは、次の条件がすべて満たされたときだけです。本番用のクライアントとサーバーの基本バンドルにパッケージの実装が含まれていないこと、新規インストールではパッケージをダウンロードしないと有効化できないこと、アップデートしたインストール環境では引き続き利用できること、そしてパッケージのインストール、アップデート、アンインストールが、デスクトップ、モバイル、Termux互換のファイルシステムで問題なく通ることです。

### Capability API 1.30: 負傷トラック、判定への消費、トラックで戦う戦闘

ルールセットの`live.tracks`項目に`levels`と`kinds`を宣言すると、範囲付き整数ではなく負傷トラックになります。各マスに名前とペナルティがある縦列に印を付けます。`levels`は良い状態から悪い状態の順に1〜16段階で、各段階は`label`と整数の`penalty`です。`kinds`は受けられる負傷を1〜6種類定め、それぞれ`id`、短い`label`、異なる`severity`を持ちます。両者は組で、印を置く場所がないため`levels`なしの`kinds`は拒否されます。`resolution.penaltyFrom`は全ロールに適用するペナルティのトラックを指定します。`dice-pool`では`pool.min`を下回らない範囲でダイスを減らし、`dice-sum`では固定修正値となります。

この段階で追加した残りの機能も1.30に含まれ、どれか1つでも同梱するパッケージは1.30を宣言します。

- `combat.health`はプールの代わりに負傷トラックを指定できます。その場合`combat.damageKinds`が各ダメージ種別の印を指定します。`default`、任意の`byType`マップ、`marks`からなり、`marks`は命中1撃で1マスの`per-blow`、またはダメージロールの値を負傷段階として数える`per-point`です。負傷トラックでは`damageKinds`が必須、プールでは禁止です。
- `resolution.spend`(`dice-pool`だけ)は、判定に消費できるプール、1回の支払額、得るものが`successes`か`dice`か、1ロールの上限`perCheck`を定めます。
- カタログ項目の`mechanics.check`は、キャラクターが実際に選んだものが判定に与える効果を定めます。`reroll`(`upTo`と`once`または`until`)、`dice`、`successes`、`threshold`があり、これもプール方式専用です。

```json
{
  "capabilityApi": { "major": 1, "minor": 30 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

負傷トラックの長さは段階数なので、`min`は0、`max`は`levels.length`です。異なる値のファイルは黙って修正せず拒否します。`resolution.penaltyFrom`が指す先は負傷トラックでなければなりません。普通のトラックには適用するペナルティがないためです。

1.20〜1.28と同じ理由でソフトなインターフェースではありません。`levels`、`kinds`、`penaltyFrom`、`damageKinds`、`resolution.spend`、`mechanics.check`を読めないEngineはルールセットファイル全体を拒否します。インストールは検証済みの`ruleset.json`のバイト列を読み、古い宣言のパッケージを拒否します。トラックが普通の数値、体力がプールで、判定への消費を宣言しないルールセットには変化がありません。

### Capability API 1.29: ルールセットの戦闘で1ターンにできること

`combat`ブロックと戦闘が読むカタログ項目に、5つの任意機能を追加します。

- 1撃は最初のダメージに加え、最大3つの追加ダメージを持てます。カタログ項目の`mechanics.plus`とクリーチャー行動の`damage.plus`は、それぞれ`{ dice?, flat?, type?, save?: { save,
difficulty?, onSuccess: "none" | "half" } }`です。独立してロールし種別を持ち、クリティカルで個別に倍増し、対象が個別にセーヴします。それでも集中維持と倒れる判定は1撃全体につき各1回です。
- `combat.attacks[].strikes`は、そのリストの行動枠1回の消費で得る攻撃数を表す値参照です。残りはターン終了まで保持され、残りがある間はそのリストの全行で行動枠を消費しません。
- `mechanics.free`は行動枠を消費せず、`mechanics.gives`はこのターンだけ枠を返し(受け取る側の上限まで)、`mechanics.standard`は所持者が別の枠で名前付きの標準行動を買えるようにします。`gives`か`standard`を宣言する`utility`項目は、除外せず選択肢に表示します。
- 新しい項目種別`rider`とクリーチャー独自の`riders`は、ターンまたはラウンド内の最初の条件を満たす命中にダメージ効果を加えます。常時効果で、メニューには出ません。
- 限定された状態効果の一覧に`own-saves-advantage`、`own-saves-disadvantage`、`resist-all`、`cannot-target-source`、`cannot-approach-source`が加わります。状態は対象のセーヴを`saves`で限定し、`whileSourceInSight`で付与者が見える間だけ有効にし、`endsWhenSourceDown`で付与者が倒れると終了できます。

```json
{
  "capabilityApi": { "major": 1, "minor": 29 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

1.20〜1.28と同じ理由でソフトなインターフェースではありません。これらのキーを読めないEngineは、ルールセット全体、またはキーを持つカタログファイル全体を拒否します。そのためインストールは`ruleset.json`と宣言されたすべての`catalogs/<id>.json`の検証済みバイト列を読み、古い宣言ならどちらも拒否します。権限は不要で、何も宣言しないルールセットは変わりません。

### Capability API 1.28: 盤面上のルールセット戦闘

ルールセットの`combat`ブロックは、戦場の1マスに相当する独自距離を`distance: { label, perCell }`で指定でき、それによって初めて戦闘が位置を持てます。加えて、`ranged`は通常射程を超えた射撃や敵が隣接する場合の射撃コスト、`cover`は攻撃の判定先となる防御への遮蔽の加算、`opportunity`は離れる相手への攻撃に使う行動枠を定めます。攻撃リストは`reach`と`range`を自身の列から読むか、全行共通の値で指定できます。クリーチャー行動の`range`は数値だけでなく`{ "normal": 30, "long": 120 }`でも指定できます。

```json
{
  "capabilityApi": { "major": 1, "minor": 28 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

`distance`なしで`ranged`、`cover`、`opportunity`、武器の間合いまたは射程を宣言したルールセットはインポート時に拒否されます。測るためのマスがなければ意味がないためです。盤面はタクティカル戦闘自身の生成器、地形、配置を使い、この段階で別の戦場モデルや権限を追加しません。

1.20〜1.27と同じ理由でソフトなインターフェースではありません。これらのキーを読めないEngineはルールセット全体、または射程が組になったクリーチャーを含むカタログ全体を拒否します。そのためインストールは`ruleset.json`と宣言されたすべての`catalogs/<id>.json`の検証済みバイト列を読み、古い宣言ならどちらも拒否します。距離を宣言しないルールセットは変わりません。

### Capability API 1.27: ルールセットのクリーチャー図鑑

ルールセットのカタログは`"holds": "creatures"`を宣言し、シートの行の代わりにクリーチャーの能力データを持てます。`combat`ブロックが宣言する数値で記述します。体力は固定値または開戦時に振るダイスで、防御、イニシアチブ修正値、シートIDによる能力値とセーヴ修正値、抵抗・弱点・無効化するダメージ種別、決して受けない状態、脅威段階、GMへ見せる特徴を指定します。行動は命中、セーヴ要求、状態付与、回数制限、再充填ロール、1つの行動枠でブロック内の他の行動を順に解決するもの、自身の特殊ポイントで買うものに対応します。

```json
{
  "capabilityApi": { "major": 1, "minor": 27 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json", "catalogs/beasts.json"] } }
}
```

クリーチャーのカタログは`feeds`を宣言せず、シート編集の選択画面にも出ません。読むのはシートではなく戦闘です。戦闘ディレクターの`ruleset`スタイルが、インストール済みルールセットの`combat`と図鑑をそのまま使うため、独自のCapability APIレベルは不要です。

1.20〜1.26と同じ理由でソフトなインターフェースではありません。`holds`や項目の`creature`を読めないEngineはルールセット全体、またはそれを含むカタログ全体を拒否します。そのためインストールは`ruleset.json`と宣言されたすべての`catalogs/<id>.json`の検証済みバイト列を読み、古い宣言ならどちらも拒否します。権限は不要で、図鑑のないルールセットは変わりません。

### Capability API 1.26: ルールセットの戦闘

API 1.26は、ロール、対象、行動枠、攻撃・能力一覧、状態、精神集中、HPゼロ時、ダメージ種別、敵の強さを定義する `combat` を追加します。カタログの `mechanics` は対象、必中、状態、一時ポイント、シートに基づく連動、行動枠の消費を記述できます。

```json
{
  "capabilityApi": { "major": 1, "minor": 26 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

戦闘ディレクターが有効で`combat`を宣言するゲームは、戦闘画面でこのブロックに従って戦います。持たないルールセットは従来どおり、`battle`ブロックまたはプレイヤーのClassicかTacticalの設定を使います。

1.20〜1.25と同じ理由でソフトなインターフェースではありません。`combat`や新しい`mechanics`キーを読めないEngineはルールセット全体、またはそれを含むカタログ全体を拒否します。そのためインストールは`ruleset.json`と宣言されたすべての`catalogs/<id>.json`の検証済みバイト列を読み、古い宣言ならどちらも拒否します。権限は不要で、どちらも持たないルールセットは変わりません。

### Capability API 1.25: レイヤーと世界指示

ルールセットは、トップレベルの任意の`layers`配列で、Low magicやHard winterなどの名前付きバリエーションを宣言できます。プレイヤーがゲーム作成時に有効にし、そのゲームの固定情報として全期間保持します。同じリリースでは、基本の`gm`ブロックに任意の`worldGuidance`文字列も追加されます。世界生成はセットアップ時に一度読み、舞台をパーティーが使うルールに合わせます。

```json
{
  "capabilityApi": { "major": 1, "minor": 25 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

レイヤーの効果は限定され、すべて絞り込みか追記です。ルールセットの指示の後に案内を加え、enumフィールドから値を取り除き、同じ判定種別の難易度表へ置き換え、シート編集の選択画面からカタログ項目を隠します。新しい項目は追加しないため、どのレイヤーを選んでもシートは読み取れます。パッケージコードも追加のモデル呼び出しもありません。ルールセット作者以外が配布するレイヤーは今後の追加機能です。

1.20〜1.24と同じ理由でソフトなインターフェースではありません。`layers`か`gm.worldGuidance`を知らないEngineはルールセット全体を拒否するため、インストールは`ruleset.json`の検証済みバイト列を読み、古い宣言ならどちらも拒否します。権限は不要で、どちらも持たないルールセットは変わりません。

### Capability API 1.24: ダイスプール

`resolution` は `"dice-sum"` の代わりに `"kind": "dice-pool"` を指定できます。シート値をダイス数とし、しきい値以上の出目を数えます。セットは成功数2倍、爆発、相殺、大失敗、卓越した成功、GMの状況修正範囲を定義できます。

```json
{
  "capabilityApi": { "major": 1, "minor": 24 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

シートは同じで、合計への修正値がダイス数になります。新しいシート要素、編集スロット、パッケージコードはありません。検証済み `ruleset.json` の `dice-pool` はAPI 1.24以上が必要です。`dice-sum` だけの旧Engineは全体を拒否するためです。権限追加や合計式セットへの変更はありません。

### Capability API 1.23: カタログ値の連動

`scaled` は、1行の自身の数値列を最大4個までセットに管理させます。既存の値参照と任意の段階表を使い、レベル依存のリソースや能力値依存の回数を表現します。新しい算術演算は加えません。

```json
{
  "capabilityApi": { "major": 1, "minor": 23 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json", "catalogs/spells.json"] } }
}
```

値を計算するのはシート編集時だけで、読み取り時ではありません。そのためライブ状態、Game Masterのプロンプトブロック、戦闘への橋渡しは、いずれも保存された数値を読み続けます。

連動する行は`ruleset.json`内にも`catalogs/<id>.json`アセットにも置けます。マニフェストは両ファイルをアセットとして宣言しますが内部のキーを示せないため、インストールは両方の検証済みバイト列を読み、1.23より古い宣言の`scaled`を拒否します。1.21の`catalogs`、1.22の`battle`と同じ方式です。古いEngineの厳密なスキーマでもファイル全体が拒否されます。権限は不要で、連動する行のないカタログを持つルールセットは変わりません。

`[sheet: op="use" name="..."]` は `mechanics.cost` と、その項目が作った全行プールの1回分を支払います。既存カタログを読むため追加宣言は不要です。

### Capability API 1.22: battleブロック

任意の `battle` はHP、任意のMP、呪文スロットプールと、カタログ行を `CombatSkill` にする一覧を指定します。終了後はプレイヤー用ボタンと同じシート操作で値を書き戻します。

```json
{
  "capabilityApi": { "major": 1, "minor": 22 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

これはEngine戦闘へのデータ接続で、卓上ルールの完全なアダプターではありません。内蔵計算は `attackRoll`、`save`、`concentration`、`perCostStep` を読みません。正確なシステム別戦闘は別途アダプター接続で扱います。`coverage.combat` は独立した意味を保ち、この接続では読みません。検証済み `ruleset.json` の `battle` はAPI 1.22以上が必要で、`catalogs` の1.21制限と同じ扱いです。権限追加や、ブロックのないセットへの変更はありません。

### Capability API 1.21: カタログ

カタログは、シート選択画面に呪文、クラス能力、装備の候補を提供します。ヘッダーは `ruleset.json` の `catalogs` に置き、項目はインラインまたは予約リソースにします。

```json
{
  "capabilityApi": { "major": 1, "minor": 21 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json", "catalogs/spells.json"] } },
  "files": [
    { "path": "ruleset.json", "sha256": "<sha256>", "bytes": 25767 },
    { "path": "catalogs/spells.json", "sha256": "<sha256>", "bytes": 418204 }
  ]
}
```

`catalogs/<id>.json` はそのカタログIDと一致させ、別のカタログを参照できません。`files[]` のハッシュと、宣言元の `ruleset.json` が必要です。宣言サイズ1 MB超は読み込み前に拒否します。両形式とも同じシートに対して検証し、1セット12カタログ、1カタログ2000項目までです。

クライアントは選択画面を開いてから `GET /api/capability-packages/rulesets/catalog?rulesetId=&catalogId=&version=` で読み込みます。インストール済み一覧には件数だけを含めます。カタログ本文はプロンプトに自動挿入せず、GMには `gm.sheetSummary` が選んだ情報だけを渡します。リソースと検証済みファイル内の `catalogs` はAPI 1.21が必要です。古い厳密なスキーマはファイル全体を拒否するためです。権限は不要です。

### Capability API 1.20: Game Modeルールセット

ルールセットは検証済みデータです。Engineが対応する判定方式、定義済み要素のシート、休息、GM指示を提供します。予約リソース `ruleset.json` は `gm-verbs.json` と同様、`contributions.assets.paths` と `files[]` のハッシュで登録します。

```json
{
  "schemaVersion": 2,
  "capabilityApi": { "major": 1, "minor": 20 },
  "id": "ruleset-5e-2014",
  "kind": ["ruleset"],
  "permissions": [],
  "entrypoints": {},
  "contributions": { "assets": { "paths": ["ruleset.json"] } },
  "files": [{ "path": "ruleset.json", "sha256": "<sha256 of the file>", "bytes": 25767 }]
}
```

例は関連項目だけを示します。`name`、`version`、`description`、`engine`、`builtAgainst` は引き続き必須です。権限、エージェント、クライアントやサーバーの入口は不要です。`ruleset` 種別と `ruleset.json` は相互に必須です。コードや文字列式は実行されず、新しい判定方式にはEngineの変更が必要です。形式と5e例は [`game-rulesets-and-sheets-implementation.md`](game-rulesets-and-sheets-implementation.md)にあります。

マニフェストはAPI 1.20を宣言する必要があり、古いEngineはインストールを拒否します。256 KBを超える宣言サイズは読み込み前に拒否し、インストール済みハッシュを再確認して厳密な `packages/shared/src/schemas/ruleset.schema.ts` で検証します。無効なファイルは除外し、パッケージと最初のいくつかの`path: message` エラーを1件のログに出します。ID重複はパッケージID順で先のものを採用し、後をログ付きで除外します。`engine-legacy` と `traditional` は予約されています。

選択は `chat.metadata.gameRuleset` に一度保存します。固定情報がなければ従来のルールです。パッケージがないか定義が古ければ利用不可となり、別のルールで代用しません。セットIDと提供パッケージの両方を確認するため、同じIDの別パッケージがゲームを引き継ぐことはありません。

### Capability API 1.18: Gameウィザード内でのExperience設定

`game-surface`パッケージは、スキーマバージョン2とCapability API 1.18で`contributions.gameSurface.setup`を宣言できます。Engineは、**Party**(パーティー)、目標、モデル、ロアブックを含む通常の7つの設定ステップを維持します。Experiencesを選べるのは新規ゲームだけです。既存ゲームの設定を開き直した場合、そのExperienceとパッケージ設定は保持されます。この宣言がないパッケージは、従来の設定ダイアログを引き続き使用します。

```json
{
  "setup": {
    "seed": { "key": "seed", "label": "World seed" },
    "config": { "generate": true, "packWanted": true },
    "requires": { "enableCustomWidgets": false }
  }
}
```

3つのフィールドはすべて任意です。宣言されたシードは、選択したExperienceの下に**Randomize**(ランダム化)ボタンとともに表示されます。入力が空、または有限の数値でない場合、**Start**(開始)がブロックされます。ホストは数値シードと宣言された定数を`experienceConfig`に書き込みます。`config`にはシードのキーを含められません。定数はシリアライズ後に8,000文字以内に収まる必要があります。シードのラベルはパッケージ作者が用意する表示テキストです。省略するとEngineのローカライズ済みラベルを使用します。

宣言されたウィジェット要件がデフォルトを設定するのは、プレイヤーがそのコントロールを変更するまでです。Experienceをオフにすると通常のデフォルトに戻りますが、プレイヤーが明示的に選んだ値は変わりません。コントロールにはExperienceの想定が説明され、編集可能なままです。これらのExperiencesでは空間マップの設定コントロールが非表示になり、別のマップ下書き、テンプレート、ビルダーは起動しません。

**Lorebooks**(ロアブック)ステップでは、未接続のブック内のものも含め、有効なエントリーを個別に最大100件選べます。無効なブック、エントリー、チャットの除外指定は尊重されます。これらのIDは`GameSetupConfig.activeLorebookEntryIds`で渡されます。`/game/setup`では、追加の強制エントリーとして確率判定を省略しますが、通常のトークン上限は維持します。グローバル、キャラクターに紐づくもの、接続済みのロアは、引き続き通常のスキャンに参加します。パッケージも設定から同じ選択済みIDを読み取り、独自のワールド生成リクエストに使用できます。

設定ファイルのインポートでは、インストール済みで互換性のあるExperienceとその有効な数値シードを復元しますが、任意のパッケージ設定は破棄します。定数は現在のマニフェストから改めて取得します。既存ゲームでは、理由を説明したうえでExperienceのインポートをスキップします。作成時のスナップショットには、設定の要約用にExperience名とシードを保持します。

最初のターンより前にワールドを準備する必要がある場合は、既存の起動準備完了の宣言を独立して使用してください。パッケージの最低要件としてAPI 1.18を宣言します。古いホストはこの設定宣言を解釈できません。

### Capability API 1.34: ルールセット自身の形式で記述するクリーチャー

図鑑のクリーチャーは、ルールセット自身の形式のキャラクターシート`sheet`を持てます。必要な部分だけのシートでも構いません。戦闘は仲間とまったく同じ方法で構築するため、体力、防御、セーヴ、イニシアチブ、速度、リストの能力はルールセット自身の宣言から決まり、自身のプールから支払います。この場合シートと並んで`health`、`defense`、`initiativeModifier`、`speed`、`abilities`、`saves`を指定せず、独自のブロック行動も持てません。

```json
{
  "capabilityApi": { "major": 1, "minor": 34 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json", "catalogs/creatures.json"] } }
}
```

ゲートは1.27と同じく、ルールセットとインストール内のすべてのカタログファイルのバイト列を読みます。クリーチャーのシート行は、そのリストへ供給するカタログの項目を`_catalog: "<catalog>/<entry>"`で指定できます。Engineは図鑑とともにそのカタログも戦闘用に読み込みます。1.20〜1.33と同じ理由でソフトなインターフェースではありません。キーを読めないEngineは厳密なカタログファイル全体を拒否するため、同梱するパッケージは1.34を宣言します。権限は不要です。

### Capability API 1.33: リアクションが待つ瞬間

カタログ項目の`mechanics.reaction`は`true`だけでなくオブジェクトにできます。`on`はEngineが検出する瞬間、`at`は選んだ行動を向ける相手、`cancels`は受付中に保留している効果を完全に取り消すかを指定します。

```json
{
  "capabilityApi": { "major": 1, "minor": 33 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json", "catalogs/spells.json"] } }
}
```

`on`は所持者に効果が当たる前の`aimed`、または被害を受けたあとの`harmed`で、いずれかを指定すると対応する受付メニューに出ます。`at`はその瞬間を引き起こした相手を自動指定する`source`か、項目本来の対象を保つ`chosen`です。すでに起きたことは取り消せないため、`cancel`できるのは`aimed`だけです。取り消した行動のコストは、誰かに尋ねる前に支払い済みなので消費されたままです。

`"reaction": true`のままの項目は、自分のターンで使わないと指定するだけで、選択肢として提供するには不十分です。どのメニューにも出ず、新しいバージョンも必要ありません。1.20〜1.32と同じ理由でソフトなインターフェースではありません。オブジェクトを読めないEngineは厳密なカタログファイル全体を拒否するため、同梱するパッケージは1.33を宣言します。権限は不要です。

### Capability API 1.32: 独自に攻撃数を制限する武器

攻撃ソースは自身のリストの真偽値列`strikesCappedBy`を宣言できます。その列が有効な行は、リストの`strikes`が何回でも1回の攻撃だけを得ます。そのため、ターンに1回撃つ武器は1発のまま、リストのほかの武器はシートどおりの回数を振れます。SRD 5.1のLoading特性の「通常の攻撃回数に関係なく、アクション、ボーナスアクション、リアクションで射撃する際に撃てる弾薬は1つだけ」という規則のために存在します。

```json
{
  "capabilityApi": { "major": 1, "minor": 32 },
  "kind": ["ruleset"],
  "contributions": { "assets": { "paths": ["ruleset.json"] } }
}
```

`strikes`の併記が必要で、なければ拒否します。1消費で1回のリストなら、もともと全行が1回に制限されているためです。1.20〜1.31と同じ理由でソフトなインターフェースではありません。キーを読めないEngineはルールセット全体を拒否するため、同梱するパッケージは1.32を宣言します。権限は不要です。

### Capability API 1.31: ホストの生成サービスとの統合

サーバーパッケージは`api.runtime.integrations`で現在のEngineのLLM、画像、動画サービスを使えます。マニフェストにCapability API 1.31を宣言し、有効化時に統合ホストの利用可否を確認してください。古いEngineは有効化前に新しいAPI要件を拒否します。プロバイダー操作には`network`、メディアの保存、一時配置、削除には`storage`権限が必要です。

- `llm.createProvider(...)`はカスタム要求パラメーターやヘッダーを含め、Engineのプロバイダーファクトリーと同じ接続設定を受け付けます。返すプロバイダーは`chat`、`chatComplete`、`embed`、`maxContextValue`、`maxTokensOverrideValue`をサポートし、認証情報のプロパティは公開しません。
- `llm.localSidecar()`は同じファサードでホストのローカルサイドカープロバイダーを返します。
- `llm.withFallback(...)`は同じパッケージホストで作ったプロバイダーを包み、Engineの受付制御、フォールバック通知、プロバイダー選択動作を維持します。
- `images.generate(...)`と`videos.generate(...)`はキャンセル、要求ログ、ネットワーク検査、メディアキューを含むEngineの実装を使います。呼び出し元の`signal`とUIの`debugMode`があれば転送してください。
- `images.save`、`images.remove`、`images.stage`、`images.sweepStaged`はギャラリーの安全な書き込みと一時ファイルのライフサイクルを再利用します。`videos.save`と`videos.remove`は動画の保存経路を再利用します。`images.resolveNovelAiRequestSize`はホストのNovelAIサイズ正規化を使います。動画時間と公開参照アップロードの正規化も、`videos.resolveDuration`と`videos.resolveReferenceUpload`で利用できます。

共有の要求・結果型は`@marinara-engine/shared`からエクスポートされます。パッケージ固有のプロンプト構築と処理の調整はパッケージに置き、プロバイダーI/OにはEngineのサービス実装をコピーせず、これらのホスト入口を呼んでください。純粋なヘルパーや型は引き続きバンドルできます。
