# ルールセット作成者ガイド

自分の卓上ゲームシステム用のGame Modeルールセットを設計するときは、リファレンスページを開く前にこのページを使ってください。ルールセットの各部分のつながり、特に重要な選択、そして大きく異なる16のシステムを変換して学んだことを説明します。キーごとのリファレンスは[Game Modeのルールセットを作成する](../extending/writing-rulesets.md)から始まり、以下の各節にも、その内容を詳しく説明するページへのリンクがあります。

ルールセットは、システムの仕組みをMarinara Engineに伝える一つのJSONファイル(または複数ファイルのパッケージ)です。Engineはそれに従ってすべての判定を振り、シートの変更をすべて適用し、戦闘全体を独自のルールで進めることもできます。ルールセットにコードは含まれないため、Engineがすでに知っている仕組みの空所を埋めて設計します。Engineが知らない仕組みには、Engineへの機能要望が必要です。

以下の各キーには、そのキーが追加されたCapability APIのマイナーバージョンを記載しています。そのキーを使うパッケージは、そのマイナーバージョン以降を宣言します([バージョン管理、テスト、公開](#versioning-testing-and-publishing)を参照)。

次の二つの用語は混同しやすいものです。

- **ClassicとTactical**は_戦闘スタイル_です。前列と後列のあるメニュー式の戦闘と、盤面上の戦闘を指します。ルールセットの有無にかかわらず、どのゲームもいずれかを使います。
- **Marinara独自のルール**は、ルールセットのないゲームが使うものです。ルールセットはこれを置き換えます。

## ルールセットの構成

ルールセットは最大512 KBの一つのJSONファイルで、インポート時に全体を検証します。より大きいルールセットは、カタログを分割してパッケージにまとめます。まず使うダイスに最も近い例をコピーしてください。

- [`ember-roads.json`](../examples/rulesets/ember-roads.json): 2d6に能力値を加えます。
- [`gravewatch.json`](../examples/rulesets/gravewatch.json): d10のプールです。
- Marinara-Agentsにある完全な[5e (SRD 5.1)パッケージ](https://github.com/Pasta-Devs/Marinara-Agents/tree/staging/packages/ruleset-5e-2014)。

`$schema`の行でエディターに[JSON Schema](../extending/ruleset.schema.json)を指定すると、自動補完と誤字の検査が使えます。

| キー | 内容 | リファレンス |
| --- | --- | --- |
| `schemaVersion`, `id`, `version`, `name`, `edition`, `license` | 識別情報です。`version`は変更を公開するたびに増やす整数です | [ルールセットの作成](../extending/writing-rulesets.md) |
| `coverage` | ルールセットが扱うもの(判定、戦闘など)と、ウィザードに表示する一行の要約です | [ルールセットの作成](../extending/writing-rulesets.md) |
| `resolution` | 五つの方式のいずれかによる判定の振り方と、結果帯、消費、振り直しです | [判定](../extending/ruleset-checks.md) |
| `sheet` | 能力値、スキル、フィールド、リスト、現在値を持つプール、トラック、ステート、負傷トラック、ペナルティ、移行です | [シート](../extending/ruleset-sheets.md) |
| `party`, `clocks` | 共有パーティーシート(クルー、船、ストーリーポイント)と進行クロックです | [シート](../extending/ruleset-sheets.md) |
| `rests` | 各休息が回復・解除するものです | [シート](../extending/ruleset-sheets.md) |
| `gm`, `gmReference` | Game Master向けの文章、キャラクターごとの要約、相手の操作主体、最大16,000文字のルールリファレンスです | [シート](../extending/ruleset-sheets.md) |
| `catalogs` | 既製のエントリー(呪文、タレント、クリーチャー)です。それぞれ任意の`mechanics`ブロックを持てます | [カタログ](../extending/ruleset-catalogs.md)、[仕組み](../extending/ruleset-mechanics.md)、[ビルダー](../extending/ruleset-character-builder.md) |
| `items` | カテゴリー、武器、鎧、弾薬、戦利品、お金、初期装備、市場です | [アイテム](../extending/ruleset-items.md) |
| `battle` | シートの数値をMarinara独自のClassicとTacticalの戦闘へ貸し出します | [戦闘](../extending/ruleset-combat.md) |
| `combat` | ベスティアリ、盤面、リアクション、対抗判定を使い、独自のルールで戦闘全体を進めます | [戦闘](../extending/ruleset-combat.md) |
| `layers` | プレイヤーが一つのゲームでオンにするバリエーションです(Low magic、Hard winter) | [レイヤーと翻訳](../extending/ruleset-layers-and-translations.md) |

**ID。** ルールセットのIDは、小文字、数字、単独のハイフンで構成します(`ember-roads`)。シート内のIDは、英字で始まり、小文字、数字、アンダースコアで構成します(`grit_max`)。保存済みのキャラクター、カタログを借用するほかのルールセット、ExperienceのオーバーレイがすべてIDを参照するため、公開後はIDを変えないでください。

**プロンプトに安全に入れられる文章。** モデルに届くもの(名前、ラベル、Game Master向けの文章)はすべて一行にし、角括弧と`{{`や`}}`を使わないでください。

**パッケージ。** 一つのファイルには大きすぎるルールセットは、`<id>.ruleset.json`として配布します。マニフェストに加えて、`ruleset.json`、各2 MBまでの`catalogs/<id>.json`ファイルを最大12個、翻訳を最大40個含み、すべてbase64で保存します。zipは拒否されます。Pixelforgeなどのルールセットエディターがこのファイルを作成します。マニフェストは、ルールセットに必要なCapability APIのマイナーバージョンを宣言します。

**ルールセットの登録先。** インポートしたファイルは`local/<id>`、GitHubリポジトリー由来のものは`<owner>/<id>`となり、公式カタログ由来のものは元のIDをそのまま使います。二人の作者がそれぞれ`v20`を公開しても競合しません。

## 判定、ダイス、シート

最初の、そして最も重要な選択は`resolution.kind`です。ほかのすべては、この指定に従って読み取られます。Game Masterはスキルと難易度を指定するだけです。Engineがダイスを振り、シートに基づいて計算し、結果をモデルへ伝えるため、モデルに計算を求める文章をGame Master向けに書かないでください。

| 方式 | 振り方 | 適したシステム |
| --- | --- | --- |
| `dice-sum` | ダイスを振り、シートの数値を加えて、難易度以上を目指します。独自の出目、オープンエンドの連鎖、エクスプローディングダイスに対応します | d20方式のゲーム、2d6に能力値を加える方式、Fate(出目−1/0/+1の4dF)、Rolemaster |
| `dice-pool` | シートに応じた個数のダイスを振り、目標に届いたものを数えます。目標はシートから読むことも、判定ごとに指定することもでき、以上と以下のどちらにも対応します | World of Darkness、Exalted、Shadowrun系、Lasers & Feelings |
| `dice-highest` | プールを振って最大の出目を読むか、上位いくつかの出目を合計します。ダイスがゼロ個のときのルールと、二つ目の「dark」のダイスセットに対応します | Blades in the DarkなどのForged in the Dark系ゲーム、Trophy Dark |
| `roll-against` | シートの数値以下(または以上)を出すように振ります | Call of Cthulhu、GURPS、BRP、オールドスクールのX-in-6 |
| `symbol-pool` | ナラティブダイスを組み立てて格上げし、対立するシンボルを相殺します | Genesysなど |

続いて、システムに必要なものを加えます。すべて[ルールセットの判定](../extending/ruleset-checks.md)で説明しています。

- **結果帯**(`resolution.outcomes`、1.135): マージンか合計に応じた、二つから八つのラベル付き結果です。成功度、「代償付きの成功」、ハードやイクストリームの成功などを表します。各帯は、卓上での意味をGame Masterに伝える一行を持てます。変換したシステム全体で、最も広く必要とされた機能でした。
- **独自の方法で振る判定**(`resolution.overrides`、1.140): 一部のスキルで異なるダイスを使います。たとえば、d20方式のゲームで盗賊のスキルにd100、Open Doorsにd6を使う場合です。
- **ロールを変える消費**(`resolution.spend`)と無料の振り直し(`resolution.reroll`): 成功を得るための意志力、幸運、ヒーローポイントなどです。`perCheck`で一回のロールに使える量を制限するため、プールが満杯でも確実な結果を買うことはできません。
- **ロールを変えるチャーム**: キャラクターが選んだカタログのエントリーに`mechanics.check`を置き、そのエントリー自身のコストを支払います。

**判定がまだできないこと。** 対抗プール(二人のロールを比較するもの)と、OpenD6のようなワイルドダイを含む合計プールです。どちらもEngine内の新しい判定方式が必要です。システムがいずれかを必要とする場合は、計算過程を示したロール例をいくつか添え、Engineリポジトリーに機能要望を開いてください。その例がテストになります。

**シート**([ルールセットのシート](../extending/ruleset-sheets.md))は、能力値、スキル、フィールド、リスト、派生値に加えて、Engineがプレイ中に変える現在の状態を保持します。

- **プール**: ヒットポイント、意志力、モート、呪文スロットなどです。シートコマンドと休息で消費・回復します。
- **トラック**: ストレス、Ruin、XPなどです。満杯になったときのトリガーを持ちます。
- **負傷トラック**: 一つの数値ではなく、名前付きの段階や番号付きの枠で体力を表し、ロールへのペナルティを持ちます。
- **ライブステート**: 形態、構え、アニマなどです。維持されている間、ロールを変えられます。
- **パーティーシートとクロック**: クルー、船、共有ストーリーポイントと、4、6、8区画の進行クロックです。

Game Masterは、Engineが自動的に教えるシートコマンドを通じて、ルールセット独自のIDでシートを変更します。そのため、`gm.sheetGuidance`でコマンドを説明する必要はありません。恒久的な成長(XP、新しいドット、レベルアップ)にはカタログのシートコマンドを使います。[ルールセットのカタログ](../extending/ruleset-catalogs.md)を参照してください。

**キャラクターの作成。** [キャラクタービルダー](../extending/ruleset-character-builder.md)は、定義したステップに従ってプレイヤーを案内します。出自とクラス、評価値(ロール、購入、割り当て)、習熟、呪文、装備、初期通貨を扱い、ルールへの適合を検査し、共有パーティーの作成にも対応します。カタログは`from`(1.220)で、インストール済みの別のルールセットのカタログを借用できます。そのため、5eのバリエーションは、SRDのクリーチャーや呪文をコピーせずに再利用できます。

**Game Master向けの文章。** `gm.checkGuidance`と`gm.sheetGuidance`(各1,500文字)は毎ターン送られるため、簡潔にしてください。`gm.worldGuidance`は世界の作成時に一度だけ読まれます(「火薬はない」「魔法は珍しい」など)。`gmReference`は、固定のシステムプロンプト内に、より詳しいルールを最大16,000文字保持します。`gm.sheetSummary`は、モデルにキャラクターごとに見せる内容を選び、そこに含まれるものはすべて毎ターンのトークンを消費します。ルールブックの文章をコピーせず、すべて自分の言葉で書いてください。

## 戦闘

ルールセットが戦闘に関わる深さは三段階あります。浅い段階から始め、後で深くできます。戦闘がシステムの個性をどれだけ担うかで選んでください。

| 深さ | 書くもの | 戦闘で起こること | 適した用途 |
| --- | --- | --- | --- |
| なし | `battle`も`combat`も書きません | Marinara独自のClassicかTacticalの戦闘が、自ら戦闘参加者を作ります。シートは変わりません | 戦闘を物語として扱うナラティブ系システム(Fate、Blades、Trophy) |
| シートを貸し出す | `battle`ブロックです。体力プール、任意のエネルギープール、呪文スロット、最大8個のスキルリストを指定します | 計算とダイスはMarinaraのものですが、体力はシートと同じバーの割合から始まり、結果はシートへ書き戻されます | 結果を後に残したい軽量なシステム |
| 独自のルール | `combat`ブロックです | 独自のダイスで、すべての攻撃、セーヴ、対抗判定を解決します。相手はベスティアリか脅威尺度から選ばれ、消費は発生するたびにすべてシートへ書き込まれます | 詳細な戦術システム(5e、Pathfinder、Storyteller、Genesys) |

**`combat`ブロック**は、Engineが持つ三つの方式のいずれかをパラメーターで設定します。`attack-vs-defense`(防御値に対してダイスを振る方式)、`dice-pool`(独自のプールで成功数を数える方式)、`symbol-pool`(消費を伴うナラティブダイス、1.382)です。基本となるのは、`health`(減っていくプール、印を付ける負傷トラック、または満たしていく通常のトラック、1.383)、`defense`、`initiative`、`attackRoll`、行動の`economy`、そして`attacks`と`abilities`になるリストです。小規模なブロックなら、完全なものでも約25行です。[ルールセットの戦闘](../extending/ruleset-combat.md#combat-a-fight-your-own-rules-resolve)のEmber Roadsのブロックが、よいひな形になります。

基本に加え、システムに必要なものを追加してください。

- **状態**: 限定された一覧から効果を選びます(防御、攻撃ロール、セーヴ、対抗判定、速度、最大体力、与えるダメージと受けるダメージ)。
- **セーヴ**、集中、瀕死のルール、**ウィンドウ**で待機するリアクションです(エントリーは`used`、`aimed`、`hit`、`harmed`、`falls`、`turn-start`を待てます)。
- 掴み、突き飛ばし、振りほどきのための**対抗判定**です。
- **クリーチャー**: 戦闘が読み取るベスティアリのカタログで、ステータスブロック、アクション、感覚、呪文発動を持ちます。**脅威尺度**を使うとGame Masterが一戦用の相手を作れ、`combat.threat.budget`(1.803)は難易度ごとの経験値予算に合わせて遭遇を作ります。
- カタログのエントリーの**仕組み**: 範囲の形、持続するゾーン、壁、召喚、治療、感覚です。[ルールセットのエントリーの仕組み](../extending/ruleset-mechanics.md)を参照してください。

**ClassicかTacticalか。** 独自の戦闘に盤面が付くのは、`combat`が`distance`(`label`、`perCell`)を宣言し、シートかクリーチャーが移動量を指定する場合だけです。それらがなければ、Tacticalのゲームでも、頭の中で状況を描いて独自のルールを使います。ルールが位置に依存する場合(範囲、リーチ、挟撃)は、`"styles": ["tactical"]`(1.379)を指定して、そのルールセットを使うすべてのゲームに盤面を付けてください。

**クリーチャーの画像**はルールとは別です。[クリーチャーパック](../extending/writing-creature-packs.md)(`.creatures.json`、Pixelforgeで作るのが最も簡単です)が、クリーチャーのIDを照合してベスティアリをTacticalの盤面に描きます。画像のないものはトークンのままです。

**既知の制限**は[未対応のもの](../extending/ruleset-combat.md#not-yet)にあります。変換で特によく問題になったのは、対抗する防御ロール(DodgeとFight Back、ParryとBlock)、命中部位、陣営単位のイニシアチブ、リアクションへのリアクションでした。Game Masterが、Engineの戦闘に合わせてそれらを語ります。

## 戦闘AI: 思考、性格、相手の操作主体

Engineは、ほかの誰も操作しないすべての相手とAIの仲間を操作し、ターンごとのモデル呼び出しは行いません。特定のルールセットに依存せず、5eに加えて、Storyteller、Exalted、オールドスクール、Call of Cthulhu、GURPS、Genesysの変換でもテストしました。以下のキーがなくても動きますが、指定するとクリーチャーらしい戦い方になります。すべて[ルールセットのエントリーの仕組み](../extending/ruleset-mechanics.md)にあり、設計は[Game Modeの戦闘AI](game-combat-ai.md)にあります。

| キー | 制御するもの | API |
| --- | --- | --- |
| クリーチャーの`mind`、または能力値に対応する`combat.minds`の段階 | どれだけ考えるかです。`mindless`、`instinct`、`cunning`、`tactical`、`genius`があります。野獣はデフォルトで本能に従い、人造と粘体は思考を持ちません | 1.761 |
| `behavior.temperament` | 戦い方です。reckless、cautious、opportunistic、protective、supportive、disciplined、cowardly、patient、methodical、coordinatedがあります | 1.763 |
| 物語でのみ指定する性格 | `fanatical`(決して戦意を失わない)、`arrogant`(力を出し惜しみし、伝説的な存在で劣勢になると空へ上がる)、`territorial`、`cruel`、`honourable`(パーティーに**Surrender**(降参)を提示する)、`hungry`(獲物を引きずって連れ去る)です。ランダムに割り当てられることはありません | 1.778から1.784 |
| `behavior.role` | bruiser、bulwark、skirmisher、marksman、spellcaster、supporter、controller、`solo`(1.776)です。指定がなければ能力に基づいて割り当てられます | 1.763 |
| `behavior.targets`, `opens`, `pack`, `ambush` | 標的の優先順位、初手、群れの戦術、隠れて待ち伏せすることです | 1.763 |
| `behavior.shifts` | 体力が半分未満になる、味方が倒れる、リーダーが倒れる、追い詰められるといった状況で変わる性格です | 1.779 |
| `combat.morale` | 敵がいつ、どのように戦意を判定するか(2d6で評価値以下を出すか、セーヴを振る)と、誰が降伏するかです | 1.762, 1.775 |
| `gm.opposition: "game-master"` | Game Masterが、Engineの合法な選択肢から選んですべての相手を操作し、失敗時はEngineが代わります | 1.774 |

`behavior`は、`combat`ブロック全体、クリーチャーの種類、個々のステータスブロックに置け、それぞれ前の指定を上書きします。SRDの例では、狼は`{"targets": ["wounded"], "pack": true}`、ゴブリンは`{"temperament": "cowardly", "targets": ["weakest"]}`、グールは`{"ambush": true}`です。

**盤面での戦闘でAIに必要なのは**、`combat.distance`、移動量(`combat.economy.movement`またはクリーチャーの`speed`)、遠隔攻撃と武器の行の`range`、そして範囲に効果を与えるものすべての`area`です。射程がなければ、ピストルも手の届く距離でしか使えません。範囲がなければ、AIは散開しません。

**ナラティブ系システム。** デフォルトではEngineが通常の敵を、Game Masterがボスを操作します。相手との対立をダメージではなく物語で扱うシステム(Fate、Blades、Trophy、Lasers & Feelings)では、`gm.opposition: "game-master"`によって、モデルがすべての相手をその人物らしく操作できます。これは、プレイヤーが設定時に「GM directs bosses」(GMがボスを指揮)をオンにした場合だけ有効です。その設定が、戦闘中のモデル呼び出しへの同意になるためです。

**combatブロックがなくても**、ClassicとTacticalの戦闘には士気があります。ボスでも思考を持たない者でもない各敵には、思考と性格に基づく2から12の評価値が付き、考える敵は降伏することもあります。遭遇の作成者は、陣営の`leader`を指定できます。

**パーティーの性格。** ゲーム開始時に、各パーティーメンバーの**Description**(説明)から性格が決まり、セッション終了時の振り返りで物語上の理由がある場合だけ変わります。AIの仲間はその性格に従って戦います。ルールセットで設定するものではありませんが、Game Master向けの文章でそれを踏まえることはできます。

## レイヤー、オーバーレイ、移行

ルールセットをフォークせずに変更する仕組みは三つあります。プレイヤーが選ぶバリエーションにはレイヤー、一つの冒険に属する内容にはオーバーレイ、シートの形を変えるときは移行を使ってください。

**レイヤー**(`layers`、最大12個)は、**New Game**(新しいゲーム)ウィザードで切り替えるもので、そのゲームが続く間は固定されます。レイヤーができるのは、選択肢を絞ることと文章の追加だけで、ルールの追加はできません。

- Game Masterへの指示を追加します(`gm.guidance`、`gm.worldGuidance`、レイヤーごとに4,000文字)。
- 列挙型フィールドから値を取り除き、難易度の段階を置き換え、宣言済みのフィルターでカタログのエントリーを隠します。
- 通貨を取り除き(1.64)、市場の売り手を取り除き、アイテムを非売品にし、戦利品表を差し替えます(1.813)。
- ほかのレイヤーとの`conflicts`を宣言します。

レイヤーは、フィールド、値、スキル、プール、休息、売り手、戦利品表を追加できず、判定方式の変更も、戦闘の数値の変更もできません。レイヤーが取り除いたものも、キャラクターは保持します。SRDの**Low magic**(低魔法)レイヤーがよい見本です。呪文は5レベルまでに制限し、アンコモンより上のアイテムは出現頻度を下げて通常は非売品にし、高魔法のクリーチャーをランダム遭遇から除き、世界についての指示でGame Masterに魔法が珍しい理由を説明するよう求めます。ほかの作者もこれをコピーできます。ほかの人のルールセット向けに書くレイヤーには、まだ対応していません。

**オーバーレイ**(1.355)を使うと、Experienceがオンの間、そのマップパックからルールセットへクリーチャー、状態、シートの状態、アイテム、トラック(1.367)を追加できます。冒険に固有のモンスターと戦利品は、基本のルールセットではなくオーバーレイに入れてください。既存のIDを再利用するか、適合しないオーバーレイは全体が破棄されます。これもIDを変えないほうがよい理由です。リファレンス: [ルールセットのオーバーレイ](optional-agent-packages.md#capability-api-1355-ruleset-overlays)。

**移行**(`sheet.migrations`、1.77)は、フィールドの名前を変える、一つのレベルをクラスごとのレベルへ分ける、プールを分割するといったときに、保存済みのキャラクターをどう移すかを指定します。項目の追加には移行は不要ですが、シートの形が変わったら`sheet.version`を上げてください。リファレンス: [レイヤー、翻訳、移行](../extending/ruleset-layers-and-translations.md)。

## 翻訳

ルールセットは英語で書き、ほかの各言語は独立した翻訳ファイルとして配布してください(1.811)。翻訳は表示専用です。ルール、シートコマンド、Game Masterに伝えるものはすべて英語のままなので、翻訳によってゲームが壊れることはありません。

翻訳では、英語の文字列を一語一句そのままキーに使います。

```json
{
  "_meta": { "locale": "ru", "direction": "ltr" },
  "package": { "name": "5e (SRD 5.1)" },
  "ruleset": { "Prone": "Лежащий", "Fire Bolt": "Огненный снаряд", "Goblin": "Гоблин" }
}
```

- 言語コードはEngineのものと一致させます(`ru`、`pt-BR`、`zh-Hans`)。文字列がないか空の場合は英語で表示し、`pt-BR`はまず`pt`にフォールバックします。
- **共有するパッケージファイルでは**、`locales/<language>.json`に置きます。各8 MBまでで、最大40個です。インポート時にはEngineの現在の言語だけを保持します。切り替えるには、言語を変えて再インポートしてください。
- **公式カタログでは**、言語ごとに独立したパック`<id>-<version>.<language>.json`とし、カタログのエントリーの`locales`に、URL、sha256、サイズ、翻訳したストアの名前と説明を載せます。Engineは現在の言語のパックだけをダウンロードし、言語が変わると入れ替えます。SRDの全11言語を一つのファイルにまとめると、ダウンロードが7 MBから34 MBへ増えたため、パックを分けています。
- 翻訳の修正に新しい`version`は不要です。

SRDパッケージはこの方法で11言語を配布しており、参考にできる見本です。リファレンス: [翻訳](../extending/ruleset-layers-and-translations.md#translations)。

## 5e (SRD 5.1)パッケージ: 大規模な例

Marinara-Agentsの[ruleset-5e-2014パッケージ](https://github.com/Pasta-Devs/Marinara-Agents/tree/staging/packages/ruleset-5e-2014)は、このページの機能をほぼすべて使っています。キーの実際の使い方を見たいときは参照してください。参考になる点は次のとおりです。

- **構成**: `ruleset.json`と、`catalogs/`内のカタログごとのファイル(クリーチャー、呪文、魔法のアイテムなど)を、`.ruleset.json`パッケージにまとめます。READMEとMODELING.mdで、各ルールをどのようにモデル化したかを説明しています。
- **ライセンス**: `license`の下にCC BY 4.0の帰属表示と、提携関係がない旨の一文を置き、商標登録された製品名をどこにも使っていません。
- **完全な戦闘**: d20の`attack-vs-defense`ブロックに、アクション、ボーナスアクション、リアクションの行動枠、集中、ShieldやCounterspellなどのリアクション、盤面、思考と性格を持つ完全なベスティアリ、遭遇予算があります。
- **ビルダー**: 種族、クラス、ロールか購入による評価値、習熟、呪文、初期装備です。
- **レイヤー**(Low magic)と、オンデマンドのパックとして配布する**11の翻訳**です。
- **変わらないID**: ほかのルールセットがクリーチャーや呪文を借用するため、IDは決して変わりません。
- **回帰テスト**は、変更のたびに独立したCIジョブとして実行します。

システムがd20のバリエーションなら、カタログをコピーする代わりに`from`(1.220)で借用することを検討してください。

## 類似システムの設計: 変換から学んだこと

コミュニティのコレクションから、ルールの軽い物語ゲームからRolemasterまで、16のシステムをこの形式へ変換しました。最大の教訓は、ここでのルールセットは提案ではなく、強制されるものだということです。Engineがすべての判定を振り、シートの変更をすべて適用するため、「GMが処理する」として残したものは、実際に未処理になります。Engineが担うものとGame Masterが語るものを早い段階で決めてください。

| システムの系統 | 例 | 判定方式 | 実現に役立ったキー | Game Masterに委ねたもの |
| --- | --- | --- | --- | --- |
| 詳細なd20とd% | 5e、Pathfinder 2e、Rolemaster | `dice-sum` | 成功度の結果帯、Rolemaster用の`openEnded`と`unmodified`、大きな表用の`gmReference` | Pathfinderの重複しないボーナスの種類、結果帯では扱えないRolemasterのクリティカル表 |
| オールドスクール | OSE | `dice-sum` | 盗賊のスキル(d100)とX-in-6(d6)用の`resolution.overrides`、2d6の士気 | 陣営単位のイニシアチブ(個人単位としてプレイ) |
| ロールアンダー | Call of Cthulhu 7e、GURPS Lite | `roll-against` | `against`、ボーナスとペナルティの`tens`ダイス、クリティカルの出目、ハードとイクストリームの結果帯 | 対抗するDodge、Fight Back、Parry、GURPSの命中部位 |
| Storytellerのプール | V20、W20、Exalted 3e、Exalted WoD | `dice-pool` | ペナルティ付きの負傷トラック、ライブステート(形態、アニマ)、1の出目で相殺しないための上書き、プール式の`combat`ブロック | エントリーとして書かれていない範囲効果のDisciplinesとGifts |
| Forged in the Dark | Blades in the Dark、Trophy Dark | `dice-highest` | `keep`、`zeroDice`、`dark`のダイスセット、結果帯(6 / 4から5 / 1から3)、`onFull`を持つトラック、クロック、クルー用のパーティーシート | `gm.opposition: "game-master"`による戦闘 |
| 構えによるプール | Lasers & Feelings、独自のゲーム | `dice-pool` | シートから読む`target`、`stances`(以下か以上)、完全一致の`exact`、船用のパーティーシート | 物語としての戦闘 |
| Fate | Fate Core | `dice-sum` | 4dF用の独自の出目、引き分けとスタイリッシュな成功の結果帯 | 物語としての発動と強制、物語としての戦闘 |
| ナラティブダイス | Genesys | `symbol-pool` | `symbols.spends`を持つ`combat.kind: "symbol-pool"`、吸収、満たしていくWoundsトラック上の体力 | 戦闘外の判定での消費 |

**変換から得た実践的な助言:**

1. **ダイス、シート、Game Master向けの文章の順に始めてください。** カタログや戦闘を加える前に、一つの判定を正しく振れるようにしてください。
2. **システムに結果帯がある箇所にはすべて使ってください。** 各帯の`text`は、卓上で何が起こるかをモデルに伝えます。ナラティブ系システムの要はそこにあります。
3. **中途半端なcombatブロックより、書かないほうを選んでください。** ナラティブ系システムは、ルールを半分だけモデル化したcombatブロックより、Marinara独自の戦闘(またはGame Masterによる相手の操作)のほうがうまく遊べます。
4. **戦闘を書く場合は、盤面の基本を指定してください**: `distance`、移動量、遠隔武器の射程、少なくとも一つの範囲攻撃です。AIでテストした変換はすべて、このいずれかが欠けており、戦闘が停滞するか、位置取りがまったく使われませんでした。
5. **移動量が距離の尺度に合うか確認してください。** 一マス2メートルの場合、速度2のクリーチャーは丘を登れず、戦闘が停滞しました。
6. **出典を書き残してください。** ルールセットごとにメモファイルを用意し、元の各ルールと変換方法を列挙してください。特に、食い違う解釈から一つを選んだ箇所を記録します。レビュー担当者が最初に求めるものです。
7. **Engineに本当にない仕組みは**、`gmReference`でGame Masterに委ね、計算過程を示した例を添えて機能要望を出してください。このページの多くの機能(結果帯、`dice-highest`、`roll-against`、シンボル式の戦闘、クロック、パーティーシート)は、変換で必要になったために実現しました。

## バージョン管理、テスト、公開

**重要なバージョン番号は二つです。** ルールセットの`version`は、変更を公開するたびに増やす整数です。インストールしたバージョンが書き換えられることはなく、すべてのゲームは作成時の正確なバージョンに結び付いたままなので、進行中のキャンペーンの計算方式は変わりません。**Capability API**のバージョンは、ファイルに必要なEngineの機能を示します。パッケージのマニフェストは`schemaVersion: 2`と`capabilityApi: { "major": 1, "minor": N }`を宣言します。Nは使っているキーのうち最も高いマイナーバージョンなので、古いEngineにそのルールセットが提示されることはありません。公式カタログのルールセットには1.374以降が必要です。通常のファイルをインポートする場合は、読み込むEngine自身が検証するため、宣言は不要です。

**草案作成の繰り返し。** 編集し、`version`を上げ、インポートし、新しいゲームを始めます。内容の異なる同じバージョンのインポートは拒否されます。旧バージョンは、ルールセットを削除するまでインストールされたままです。シートの形が変わったら`sheet.version`を上げ、値を移す場合は移行を書いてください。

**テスト。**

- `$schema`の行を使い、入力中にエディターが誤字や型の間違いを検出できるようにしてください。
- インポートしてください。**Settings → Advanced → Danger Zone → Allow custom Agent imports**(設定 → 詳細設定 → 危険な操作 → カスタムエージェントのインポートを許可)をオンにし、**Agents → Import agents → Game Mode ruleset**(エージェント → エージェントをインポート → Game Modeのルールセット)を使います。確認画面は何かを保存する前に、存在しないものを指す名前も含め、すべての問題をそのパスとともに列挙します。
- 宣言した各方式の判定をいくつか試し、上書き、消費、各結果帯も確認してください。ログには実際の計算が表示されます。
- `combat`ブロックがある場合は、ClassicとTacticalの両方で、AIの仲間とともに、各思考を持つクリーチャーと戦ってください。停滞(誰も誰にも届かない)、範囲による味方への誤射、最善のアクションを決して使わない敵に注意してください。
- 各レイヤーをオンとオフにし、翻訳を配布する場合はEngineの言語も切り替えてください。
- Experienceがルールセットにオーバーレイを適用する場合は、`POST /api/game/experience/check`が適合しない箇所を報告します。
- システムを知らないプレイテスターに、ビルダーでキャラクターを作ってもらってください。

**公開。** 簡単な順に五つの方法があります(詳細は[ルールセットの共有](../extending/writing-rulesets.md#sharing-your-ruleset)を参照)。

1. `.json`ファイルを送ります。
2. カタログと翻訳を含む`.ruleset.json`パッケージを送ります。
3. 公開GitHubリポジトリーの`rulesets/`に置きます(最大32ファイル)。ユーザーがリポジトリーをカスタムソースとして追加すると、ルールセットは作者のGitHub名の下に登録されます。
4. `ruleset-5e-2014`と同じ構成にして、[Marinara-Agents](https://github.com/Pasta-Devs/Marinara-Agents)へのプルリクエストで公式カタログに提案します。広く遊ばれていて、ライセンスが明確なシステムが対象です。
5. マップパックがルールセットへ冒険の内容をオーバーレイするExperienceを配布します。

**ライセンス。** 共有する権利のあるルールの文章だけを公開してください。多くのシステムはオープンライセンスの参照文書を持ちます。そのSPDX IDと必要な帰属表示を`license`の下に入れてください。ルールセットに主に必要なのは名前と数値なので、Game Master向けの文章はすべて自分の言葉で書いてください。

### 共有前の確認

- [ ] IDが確定しており、IDの規則に従っています。
- [ ] `license`にSPDX IDと帰属表示があり、商標登録された名前を無断で使っていません。
- [ ] すべての判定方式、上書き、消費、結果帯を、ゲーム内で少なくとも一度は振りました。
- [ ] `gm.checkGuidance`と`gm.sheetGuidance`は短く、モデルに計算を求めず、自分の言葉で書いています。
- [ ] ルールセットが許可する各スタイルで戦闘を試したか、`combat.styles`で制限しています。
- [ ] パッケージのマニフェストが、正しいCapability APIのマイナーバージョンを宣言しています。
- [ ] ほかの誰かが持つ最新のファイルより`version`を上げています。
- [ ] メモファイルで、元の各ルールをどのように変換したかを説明しています。
