# オプションのマルチプレイヤー

実装の追跡: [#6790](https://github.com/Pasta-Devs/Marinara-Engine/issues/6790)。この文書は実装の境界と必要な検証を記録します。マルチプレイヤーが利用可能であることや、特定のプラットフォームがテストに合格したことを表明するものではありません。

<a id="smallest-architecture"></a>

## 最小限のアーキテクチャ

1つのホストが新しい共有チャット、保存されたゲーム状態、AI接続を所有します。ホストは人間とAIの構成を選び、参加者数やカード数に固定上限はありません。Conversation、Roleplay、Gameは既存のモードを維持します。招待によって過去の非公開チャット履歴が共有されることはありません。

通信には、小さなJSONアクションと上限付きロングポーリングを扱う専用HTTPSリスナーを使います。Fastify、Node HTTPS、Zodは導入済みです。WebRTCならシグナリング、ICE/TURN設定、モバイルのホストタブの存続期間への対応が増え、WebSocketなら別のサーバー依存関係とストリーミングパーサーが必要です。非公開の共有チャットはそれらを追加せずHTTPSを再利用します。ルームの通信方式はこれ1つです。リスナーはルーム操作だけを登録し、通常のEngine APIは登録しません。中央リレーを介さずゲストからホストへ直接接続します。招待によって相手のファイル、ライブラリー、設定、認証情報、無関係なチャットへアクセスできるわけではありません。通常のEngine管理ポートは非公開にし、招待には専用のルームポートだけを含めます。

ゲスト自身の信頼できるEngineがホストへ接続します。TLSの証明書チェーンとホスト名の検証に加え、招待でホスト証明書のフィンガープリントを固定します。パスワードやペルソナを送る前に、この結び付きを確認してください。リダイレクトを追跡したり、HTTPへ切り替えたり、証明書検証を無効にしたり、ルーターの転送を自動設定したりはしません。ホストが既存のTLS機能でHTTPSアドレスと証明書を設定します。

ゲスト画面は信頼できる同梱コードで、オリジンが不透明なサンドボックス内で動作します。ネットワーク、ダウンロード、画面遷移、ストレージ、ネイティブブリッジ、管理用フックはありません。認証済みMessageChannelが検証済みのルーム表示データと少数の明示的なアクション型だけを渡します。親画面がローカルの表示設定を提供し、参加者はスタイル、アセット、コード、取得先URL、任意のAPI呼び出しを提供できません。相手のテキストはテキストとして表示します。既存の高機能チャットレンダラーはこの境界の外です。Androidラッパーは各フレームへネイティブブリッジを挿入するため、ブリッジのないコンテキストを実装して実機で検証するまでゲストとして利用できません。

<a id="trust-boundaries"></a>

## 信頼境界

| 境界 | 保護方法 |
| --- | --- |
| ローカル管理者からルームコントローラー | 既存のBasic Auth、CSRF、ホスト検証、ネイティブのローカル認証を維持します。 |
| ゲストEngineから相手のリスナー | HTTPS、フィンガープリントの固定、専用パスワード、承認、期限付きランダムセッション、上限付きリクエスト。 |
| 相手から信頼できるゲスト | 両受信側の厳密なバージョン付きスキーマ、テキストのみの表示、不透明なサンドボックス、制限的なCSP。 |
| 参加者からチャット・ゲーム状態 | 認証済みセッションから身元と所有権を決め、相手が指定したロール、ルート、生成要求は受け入れません。 |
| ルームから生成・ツール | ホストが管理する操作の対応付け、既存の生成ロック、明示的なルーム用コマンド・ツール規則、Gameの準備完了待ち。 |
| 共有状態から履歴 | 公開可能なフィールドを明示的に許可し、認証情報、デバッグプロンプト、思考、非公開メモ、無関係なライブラリー、隠されたGM状態を除外します。 |

認証済みの参加者も信頼対象ではありません。プロンプト本文はそのまま保ち、権限はプロンプトのエスケープやモデルへの安全な行動の依頼ではなくコードで強制します。ホストと設定されたAIプロバイダーは共有内容を読めます。直接接続なので、ホストには接続するEngineのIPアドレスも伝わります。それ以外のゲストのライブラリーやデバイスのデータはプロトコルに含まれません。あらゆるブラウザー・OSの欠陥からの保護を保証するものではありません。

<a id="activation-and-lifetime"></a>

## 有効化と存続期間

`MULTIPLAYER_ENABLED=true`は再起動が必要な前提条件です。未設定、false、不正な値ではマルチプレイヤーは無効です。Settingsでも別途有効化が必要で、どちらの設定だけでも通信は始まりません。ホストと参加にはそれぞれ明示的な操作が必要です。再起動でライブのルームは復元しません。Stop、Kick、Leaveは該当する認証情報を取り消し、その後の操作や遅延配信を防ぎます。

どちらかの条件がオフなら、セッション走査、証明書利用可否の確認、ホスト・ゲストのポーリング、自律的なルームジョブはありません。サーバーはフラグを読み、クライアントは1回の利用可否確認をキャッシュします。Settingsでの明示的な操作では更新できます。無効なAPIへの直接リクエストも拒否します。保存済みセッションの整理は有効化まで延期し、通信は再開しません。

<a id="proof-before-enabling-the-feature"></a>

## 有効化前に必要な検証

- 対応するゲスト環境で、悪意ある相手のテキストが実行、アセット取得、画面遷移、ダウンロード、ローカルAPIへのアクセス、ネイティブブリッジの呼び出しを行えないこと。
- 無効な条件、未認証の参加、所有権、非公開状態の表示、通信量制限、権限取り消しが、不許可の操作を確実に拒否すること。
- 1つのホスト調整機構で既存の生成、コマンド、自律動作を再利用し、コマンドごとの互換性と制限を公開すること。
- Gameの2人がともに提出または明示的にパスしてから1ラウンドだけ進み、再試行、切断、キャンセル、再起動で状態が二重適用されないこと。
- デスクトップとモバイルで既存の設定、ドロワー、サイドバー、入力欄を操作し、Leave/Stopと復旧操作が明確なこと。実機検証の不足を記録すること。

未完成の段階は無効のままにします。#6790を完了とするには、3つのモードすべてと安全境界が必要です。

<a id="command-and-feature-compatibility"></a>

## コマンドと機能の互換性

ルーム操作は認証済みホストの調整機構を通ります。表はその境界を示し、相手の環境で任意のコマンドを実行する許可ではありません。拒否理由は入力欄に表示され、ゲストが実行することはありません。

| 機能 | 呼び出し元と実行 | 共有結果とラウンドの規則 |
| --- | --- | --- |
| 人間のメッセージ、`/send` | 承認済み参加者。ホストが発言者付きのユーザーメッセージを作ります。`/send`は自動返信を抑止します。 | 公開テキスト。Conversation/Roleplayは受理した投稿と生成を直列化し、処理中の送信者は下書きを保持します。Gameの投稿はラウンド収集を通ります。 |
| `/roll`、`/r`、`/dice` | 承認済み参加者。既存の上限付きEngineダイスパーサーとロール処理をホストで実行します。 | 発言者付きテキスト結果。Gameのロールはラウンド終了までそのプレイヤーの提出済み行動です。 |
| 生成、`/trigger` | 承認済み参加者。永続化されたホスト生成の排他的な実行権と既存の生成ロックを使います。 | フィルター済みの確定したAI描写。Gameは独立したトリガーを拒否し、準備完了だけがラウンド処理を起動します。 |
| その他のスラッシュコマンド | ルーム権限を監査して明示的に追加するまで利用不可。 | systemロールの挿入、なりすまし、非公開チャットの移動・編集、ギャラリー操作、デバイス操作、任意のローカルコマンド実行は不可。 |
| グループ返信 | ホストが選んだ承認済みAI構成と既存の順次・Smart・手動生成。 | AIの身元は人間のペルソナスナップショットと区別します。`{{user}}`は確認済みホストのペルソナで、最後に話したゲストではありません。 |
| Conversationのスケジュールと自律動作 | 既存のサーバースケジューラー、候補・意図ロジック、クールダウンと混雑時の待機。同じルーム実行権で処理します。 | ゲスト側スケジューラーはありません。停止・一時停止中のルームとGameはタイマー生成しません。人間の画面または承認済み参加者が45秒間確認できないと自律動作を休止します。 |
| Conversationの`schedule_update`、`memory`、`react` | ルーム規則に従う既存のEngineハンドラー。 | スケジュール・記憶の変更はルーム内だけです。リアクションはこのチャットを対象にし、独自画像を含めません。グローバルなキャラクター記憶や在席状態は更新しません。 |
| Roleplayのメモ、リマインダー、ロール、ささやき | 既存のコマンド解析とホストハンドラー。承認済み参加者IDで宛先を決めます。 | 非公開メモは非公開のままです。ささやきは宛先のフィルター済みスナップショットにだけ表示されますが、保存データはホストが所有します。ルームのエージェントは、その出力を参加者全員が見るため、ささやきを一切読みません。 |
| チャット間のシーンとブラウザーリマインダー | 通常は関連する非公開チャットを作成・開くか、ブラウザーローカルのタイマーを使うため制限します。 | シーンは共有履歴に描写し、自律メッセージにはホストが調整するConversationスケジュールを使います。受信コマンドは非公開チャットやローカルリマインダーを作りません。 |
| ロアブックと記憶 | ホストが確認した添付・ルーム所有のブックとルーム内の会話記憶。 | プロンプト文脈のみで、ライブラリーの書き出しではありません。暗黙のグローバルブック、関連する非公開チャット、グローバルなカード記憶を除外します。 |
| Engineのトラッカー、ダイス、状態、要約、変数 | モデルのプロンプトだけでなく、実際のツール・エージェント実行部で明示的な許可リストを適用します。 | 安全な公開フィールドだけを表示し、エージェントの生出力、隠された思考、デバッグプロンプト、GMの非公開フィールドは渡しません。Gameの効果はラウンド実行権に従います。 |
| Gameの行動、選択、判定、インベントリー、シート | ホストによる設定・開始と既存の生成。決定的なターン後効果は1回だけ確定します。 | 人間の行動の所有者は認証済み参加者から決めます。選択は下書きを埋めるだけで、提出の準備完了を迂回しません。 |
| メディア、カスタム・パッケージツール、Game Experiences、デバイス連携 | ルーム生成では利用不可。 | 相手のファイル、画像、音声、動画、リモートスタイル、ダウンロード、ネイティブコマンド、パッケージ提供のゲストUIはありません。別の安全性対応が必要です。 |

初期の共有Gameは、同期された描写・行動の流れです。クライアント専用の戦術・ミニゲーム画面、独自のGame Experiences、シーン・メディア表示はゲスト機能として案内しません。標準のGame設定を再利用し、それらの選択肢を明示的に制限します。互換性の不足を埋めるためにホスト提供のレンダラーを読み込むことはありません。

<a id="recovery-and-limits"></a>

## 復旧と上限

各認証済み参加者には永続化した単調増加のアクション番号と、上限付き操作受領記録があります。再試行は前の結果を返し、記録が128件のキャッシュから外れても再送は古いものとして扱います。プレイヤーが後でペルソナを変えてもメッセージ内のスナップショットは変わりません。宛先指定のささやきや判定のため、人間とAIのペルソナ名は一意に判別できる必要があります。

表示名とペルソナ名は公開情報なので、席の所有者を証明するものにはなりません。退出したプレイヤーや応答しなくなったプレイヤーが元の席に戻れるのは、そのプレイヤーのEngineがその席の非公開の再参加キーを提示した場合だけです。再参加キーとは、最初にそのプレイヤーを席に着かせた承認で発行されたセッショントークンで、新しい参加リクエストにbearerとして付けて再送されます。キーがなければ、同じ名前を使ったリクエストは名前の競合となり、その席のセッションには手が加えられません。どちらのEngineも、キーをメモリー上にだけ保持します。ゲストのEngineが再起動した場合は、そのプレイヤーが同じペルソナを再び使えるようになる前に、ホストが古い席を削除します。

Gameのペルソナ変更は次のラウンド境界で適用します。既存のシート、現在値、インベントリー所有権、トラッカーのプライバシーキーは安定した参加者IDに従い、過去のメッセージは元の発言者を保ちます。その境界までにNPCが希望名を使った場合、元のペルソナを維持して名前の競合を表示します。ホストのパス、削除、一時停止、再開は同じ履歴に翻訳済みイベントを残します。

Gameは必要な参加者、提出の各リビジョン、一意の処理実行権を既存のチャットメタデータに保存します。提出の収集と発言者付きメッセージの確定は既存のメタデータキューを経てストレージトランザクションで行います。プロバイダー処理はその外です。Stopは信頼できる操作のシグナルをキャンセルし、遅れて到着する書き込みも有効な実行権との一致を必要とします。中断ターンを自動再試行しません。明示的な再開は確定済み効果を繰り返さず次の収集境界へ進みます。設定失敗時はロビーに留まり、明示的な確認・再開始を待ちます。

人間・AIの人数に固定上限はありません。プロトコルバージョン1では、アクションは16 KiB、スナップショットは256 KiBかつ直近100メッセージ、テキストメッセージは8,000文字までです。承認待ちキュー、リスナーソケット、リクエスト、ロングポーリング、セッション、パスワード導出、生成処理に上限があります。セッションごとに相手へのポーリング1つ、ゲストEngineごとにコネクターのポーリング1つが動きます。圧縮やリダイレクトは受け入れません。パスワード・トークンはURLや共有スナップショットに含めません。

大人数のルームはホストの資源、通信速度、モデルの文脈量に依存します。更新を収めるために構成メンバーを黙って削除しません。共有更新が通信量の上限を超えると、ゲストは最後の有効な状態を保持し、退出できます。ホストは管理を続けて共有データを減らし、ポーリングを復旧できます。

<a id="verification-record"></a>

## 検証記録

自動検証は使い捨てストレージ、ローカルのテストCA、模擬モデルプロバイダーを使います。ユーザーの証明書、データ、設定済みAI接続は変更しません。

- `multiplayer-peer-security.regression.ts`: HTTPデータ開示前のTLSチェーン・ホスト名・フィンガープリント確認、不正・過大・リダイレクト応答、キャンセル。
- `multiplayer-peer-server-security.regression.ts`: ルーム専用ルート、本文・ヘッダー・出力・頻度・同時処理数の制限、リスナーの即時停止。
- `multiplayer-seat-key-security.regression.ts`: 名前のコピーや誤った再参加キーでは席もそのささやきも取得できないこと、キーの所持者が同じ席に戻ること、キーがほかの参加者や保存済みチャットデータに渡らないこと。
- `multiplayer-room.regression.ts`: 2つのEngine、承認、所有権、履歴フィルター、権限取り消し・再送、生成の直列化、2人のGameラウンド・復旧。
- `multiplayer-session-flows.regression.ts`: HTTPS上の2つのEngine、実際の生成・Gameランタイム、模擬プロバイダー、完全なConversation・Roleplay・Gameラウンド。
- `multiplayer-generation-policy.regression.ts`と`generation-output.regression.ts`: 実行部の制限、非公開ライブラリー除外、プロンプト内の身元、共有生成ロック、完了の意味。
- `multiplayer-autonomy-security.regression.ts`: 既存スケジューラー再利用、ルーム活動の時計、単一の制御権、Stopの競合。
- `multiplayer-game-runtime.regression.ts`: Game設定・開始・導入、決定的なターン効果、古い書き込み、設定中断。
- `multiplayer-game-persona.regression.ts`と`multiplayer-game-projection.regression.ts`: ペルソナ所有権移行、競合復旧、閲覧者フィルター、上限付き公開トラッカー。
- `e2e/multiplayer-guest-isolation.e2e.ts`: デスクトップChromium、モバイルChromium、モバイルWebKitで、本番ゲストバンドルに敵対的テキストとローカル・ネットワーク・ネイティブアクセスの試行を与える検証。
- 設定と操作の重点ブラウザーテストは、承認警告、Players、Gameロビー、タッチ配置、ライト・ダーク、下書き・再試行を扱います。

マージ前に最終候補で`pnpm check`、関連Node回帰テスト、`pnpm regression:prompt`、`pnpm smoke:ui`、重点ブラウザーマトリックスを再実行してください。実際の結果とリビジョンをPRに記録し、CodeRabbitと重点的なセキュリティレビューを終え、対応する実機を検証します。ブラウザーエミュレーションは実際のiPhone・iPadのホーム画面やAndroidの証明ではありません。Androidネイティブラッパーのゲスト機能は無効のままです。実機の結果は記録されるまで未確認です。ビューポートのプリセットから対応を推測しないでください。

ゲストは従来型IIFEとしてビルドします。不透明なオリジンからESモジュールを読み込むと、CORSを緩和する必要があるためです。本番・開発の起動時に固定されたローカルのゲストアセットをビルドします。開発サーバーの稼働中にゲストソースを編集したら、`node packages/client/scripts/build-multiplayer-guest.mjs`を実行し、ゲスト画面を再読み込みしてください。ランチャーの完全性確認には両方の隔離アセットが含まれます。
