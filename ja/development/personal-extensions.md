# Personal Extensionのアーキテクチャ

Personal Extensions(個人用拡張機能)は、デフォルトで無効になっており、ハッシュによる承認を受けたコードだけが、隔離された2つの実行環境で動きます。デフォルトで使える拡張機能は、Professor Mariが作成した下書きだけです。それ以外の入手元はすべてExternal Extensions(外部拡張機能)にあたり、運用者が開く独立した2つのゲートが必要になります。

## セキュリティ不変条件

次の性質は常に成り立たせてください。

1. 新規作成とインポートは、必ず無効かつ未承認の下書きを生成します。
2. 承認には、現在のコンテンツハッシュ(`sha256:`)と完全に一致する値と、コードを実行することへの明示的な同意が必要です。ページ全体へのアクセスには、さらにもう1つ別の明示的な同意が必要です。
3. 実行対象のコードが変わると、拡張機能は無効になり、`approvedHash`は消去されます。
4. ロールバックで戻るのは、無効状態の下書きです。
5. バックアップとプロファイルのインポートでは、承認と有効状態が消去されます。
6. Professor Mariは下書きの作成と更新はできますが、承認したり有効にしたりする操作は一切持ちません。
7. `professor_mari`以外の入手元はすべて外部として扱います。`external`、`local`、`legacy`、`profile_import`、および`legacy`へ正規化された未知の値も含みます。
8. 外部のレコードは、`ENABLE_EXTERNAL_EXTENSIONS=true`であり、かつ永続化されたDanger Zoneのオプトインもtrueである場合を除いて、管理用の応答にもランタイムの応答にも現れません。
9. どちらか一方のゲートを閉じると、保存済みの外部レコードは無効になり、動作中のサーバープロセスは停止します。Browserランタイム側は、ポーリングによって動作中のブラウザーワーカーを取り除きます。
10. サンドボックス化されたBrowserのコードが、Marinaraのドキュメント上で実行されることはありません。別枠のページランタイムを使えるのは、`full_page_access`をハッシュ完全一致で承認された外部のBrowser Extensionだけです。Serverのコードは、Marinaraのサーバープロセス内では実行されません。
11. URLからのインストーラー、リモートのカタログ、自動アップデーターはいずれも存在しません。
12. ホストへのコントリビューションは、検証済みの素朴なディスクリプターです。拡張機能のマークアップ、スタイル、URL、コンポーネント、コールバックがMarinaraのReactツリーへ渡ることはありません。
13. コントリビューションの登録、有効化、イベント、更新、削除は、有効な拡張機能の承認済みコンテンツハッシュと完全に一致していることが前提です。
14. Browser側のコンテキストスナップショットには、基本状態としてアクティブなチャットのIDとキャラクターのIDだけが入ります。`read_active_characters`と`read_active_persona`の権限を追加すると、そのチャットでアクティブなレコードに限って、上限つきで許可リストにある項目が加わります。メッセージ、ライブラリー全体、宣言されていない項目、メタデータ、アプリへのアクセスが公開されることはありません。
15. 要求する権限は実行対象のハッシュに含まれます。権限が変わると拡張機能は無効になり、ハッシュ完全一致の承認をやり直す必要があります。
16. `full_page_access`は外部の拡張機能専用で、External Extensionの2つのゲートが両方とも必要です。Professor Mariの下書きでは決して使えません。これはサンドボックス化を保証するものではなく、明示的に信頼を与えるモードです。

ゲートはルートとランタイムのサービスで強制します。操作用の表示を隠すことはセキュリティ境界にはなりません。手動で追加されたもの、復元されたもの、レガシーなもの、正規の経路以外で入った外部レコードは、どちらかのゲートが閉じているあいだ、見えず実行もできない状態を保つ必要があります。

## 保存とポリシー

`installed_extensions`のファイルテーブルには、メタデータ、実行対象のコード、`contentHash`、`approvedHash`、入手元、および過去10件までの実行対象コードのリビジョンを保存します。拡張機能ごとの非公開設定には、`extension-storage:`を接頭辞に持つ`app_settings`のキーを使います。Danger Zoneのオプトインは`external-extensions-enabled`です。

起動時には`preparePersonalExtensionTrust`が動きます。ハッシュを持たないレガシーな行は残しますが、無効かつ未承認にします。保存されたハッシュが実行対象の項目と一致しなくなった行も、無効にしたうえでフィンガープリントを取り直します。

`personal-extension-policy.service.ts`は、`.env`側の現在のゲートと、永続化された利用者のオプトインを組み合わせます。`personal-extension-storage.service.ts`は、Professor Mari以外のレコードをすべて無効にできます。`.env`のウォッチャーはおよそ2秒以内にポリシーを再適用し、ゲートが閉じたときにはサーバーランタイムへコードの停止を要求します。

## API

管理用のインターフェイスは`/api/personal-extensions`の下にあります。

- `GET /policy`は、両方のゲートの状態とサーバーサンドボックスが使えるかどうかを返します。
- `PATCH /policy/external`は、Danger Zoneのオプトインを変更します。`.env`側のゲートが開いていない場合、`true`への変更は拒否します。
- `GET /`は、Professor Mariの下書きを一覧します。外部の下書きが含まれるのは、両方のゲートが開いているときだけです。
- `POST /`は、External Extensionをインポートします。両方のゲートが開いていなければ拒否します。
- `PATCH /:id`は、下書きの編集または無効化を行います。
- `POST /:id/approve`は、現在のハッシュと完全に一致する内容を承認し、外部側のゲートを適用します。対応するOSサンドボックスがない場合、Serverの承認は拒否します。
- `POST /:id/rollback`は、無効状態の過去のリビジョンへ戻します。
- `DELETE /:id`は、拡張機能と非公開設定を削除します。

承認済みのBrowserランタイムのメタデータは`GET /runtime/client`から読み取ります。サンドボックス化されたコードは`GET /:id/sandbox.html?hash=...`が配信します。ページ全体で動くコードとCSSは、`GET /:id/page-runtime.js?hash=...`と`GET /:id/page-style.css?hash=...`が配信します。いずれのエンドポイントでも、ハッシュが完全に一致し、有効かつ承認済みで、ポリシー上も許可されている必要があります。ページ用のエンドポイントではさらに、入手元が外部であることと`full_page_access`が必要です。

## サンドボックス化されたBrowserランタイム

`PersonalExtensionInjector.tsx`は、`sandbox="allow-scripts"`を指定し`allow-same-origin`を付けない非表示のiframeを作ります。このiframeはオリジンが不透明になるため、MarinaraのDOM、クッキー、ストレージ、同一オリジンのAPIには一切アクセスできません。

サンドボックスの応答は、通常のページのポリシーを狭いCSPに差し替えます。デフォルトのリソース取得なし、通信なし、フォームなし、オブジェクトなし、ナビゲーション権限なしです。拡張機能のCSSは非表示のiframeの内側にとどまります。JavaScriptは、信頼されたiframeのブートストラップが作る専用のWorker内で動きます。多層防御として、ネットワーク関連のグローバルと入れ子のWorkerを作るグローバルは取り除いてあります。

ワーカーが受け取れるものは次に限られます。

- 名前空間つきのログ出力
- 親側が仲介する拡張機能ごとの非公開ストレージ
- 管理されたタイマー
- クリーンアップの登録
- `marinara.context`経由の読み取り専用のアクティブなチャットIDとキャラクターの識別子
- 別途承認された機能を通してのみ得られる、アクティブなキャラクターカードと選択中のペルソナの限定的な項目
- `marinara.ui.showWindow(...)`による制約つきのiframeウィンドウ
- `marinara.ui.registerContribution(...)`による信頼されたホスト側のコントリビューション枠

Browser Extension APIのバージョン5では、`marinara.context.get()`と`marinara.context.subscribe(listener)`が追加されています。不変のスナップショットの形は次のとおりです。

```ts
{
  chatId: string | null;
  characterId: string | null;
  characterIds: readonly string[];
  personaId: string | null;
  characters: readonly PersonalExtensionCharacterSnapshot[];
  persona: PersonalExtensionPersonaSnapshot | null;
}
```

クライアントは`useChatStore`からスナップショットを導き、アクティブなチャット、そのキャラクターの一覧、選択中のペルソナが変わったときに送信します。IDは空でない文字列で、最大256文字です。キャラクターの一覧は重複を除いたうえで最大256件に制限されます。iframeがコンテキストの更新を受け付けるのは、送信元が親であり、かつ`contentHash`が拡張機能のリビジョンと完全に一致するときだけです。そのうえでWorkerがペイロードを正規化し、あらためて凍結します。拡張機能の起動時は最初のホスト側スナップショットを待ちますが、1秒でコンテキストをnullとして進むフォールバックがあるため、橋渡しが失敗してもWorkerが延々と止まったままになることはありません。

`characterId`は単一キャラクターのチャット向けの補助であり、グループチャットでは`null`のままです。アクティブな参加者はすべて`characterIds`に入ります。`personaId`が得られるのは`read_active_persona`があるときだけです。アクティブなチャットがない場合、`chatId`、`characterId`、`personaId`、`persona`は`null`になり、`characterIds`と`characters`は空になります。これらの識別子は、拡張機能ごとの非公開ストレージのキーとして安全に使えます。

`read_active_characters`があると、`characters`にはアクティブなカードの`id`、`name`、`description`、`personality`、`scenario`、`firstMessage`、`exampleDialogue`、`creator`、`characterVersion`、`tags`、`backstory`、`appearance`、`aboutMe`、`conversationDisplayName`だけが入ります。`read_active_persona`があると、`persona`には`id`、`name`、`description`、`personality`、`scenario`、`backstory`、`appearance`、`tags`、`aboutMe`、`conversationDisplayName`だけが入ります。サーバーはどちらもアクティブなチャットから導き、項目ごとと全体の両方に上限をかけます。クライアントから渡されたレコードIDを、参照範囲の根拠として受け入れることはありません。

要求する機能は拡張機能のペイロードで宣言し、リビジョンごとに保存し、Settingsと承認ウィンドウに表示し、実行対象のハッシュにも含めます。ホストはまずIDだけのスナップショットを送り、そのあとで承認済みの拡張機能ごとの仲介役を通して内容を補います。Workerは独自に、宣言されていないレコードを捨て、IDが`characterIds`にないキャラクターのレコードを拒否し、ペイロードにあらためて上限をかけ、結果を凍結します。

`marinara.ui.showWindow({ title, elements, onEvent, onClose })`は、`update({ title?, elements? })`と`close()`を持つハンドルを返します。ワーカーが送るのはディスクリプターだけで、要素はすべて信頼されたiframeのブートストラップがDOM APIと`textContent`で組み立てます(`innerHTML`は使いません)。ホストは、ウィンドウが開いているあいだだけ通常は非表示のサンドボックスiframeを表示し、閉じるときにまた隠します。

`marinara.ui.registerContribution({ id, kind, label, description?, icon?, surface?, position?, elements?, onActivate?, onEvent? })`は、`update(patch)`と`remove()`を持つ凍結されたハンドルを返します。次の信頼済みホストの配置場所をサポートします。

- `button`: 既定では上部バーのコンパクトな操作ボタン、または`chats`、`bots`、`characters`、`personas`、`lorebooks`、`presets`、`connections`、`agents`、`settings`の各画面にホストが描画する操作ボタンです。
- `menu-item`: Extensionsメニュー内の操作として表示します
- `panel`: Marinaraの信頼されたExtensionsサイドパネルを開く項目です

サイドパネルのボタンは`position: "header"`、`"before-content"`、`"after-content"`を受け付けます。上部バーのボタンでは`position`を省略します。アイコンはMarinaraのLucideアイコンカタログの、長さなどを制限したケバブケース名です。未対応の名前はパズルアイコンにフォールバックします。

パネルの要素には、制約つきウィンドウと同じ宣言的な語彙を使います。`heading`、`text`、`pre`、`button`、`input`、`select`、`toggle`、`slider`、`color`、`spacer`です。操作できるコントロールには一意のIDが必要です。パネルのボタンは`onEvent`へ`{ contributionId, elementId, values }`を送ります。`values`には各コントロールの現在の文字列値が入ります。`onActivate`は、コントリビューションを開いたり呼び出したりしたときに、拡張機能のWorker内で実行されます。状態が変わったあとにラベル、説明、アイコン、パネルの要素を差し替えたい場合は、`handle.update(...)`を呼び出します。

クライアントは各記述子をランタイムストアに追加する前に独立して検証します。コントリビューションの種類、画面、位置、コントロール、ID、選択肢リスト、アイコン名の構文、テキスト長、パネルの総テキスト量、要素数、拡張ごとのコントリビューション数を検証し、上限を設けます。Reactは拡張のテキストをテキストとして描画します。拡張が制御するHTML、CSS、URL、Reactコンポーネント、ホストコールバックは受け付けません。ワーカーが停止した場合、ハッシュが変わった場合、承認済みランタイム応答から消えた場合には、ホストがすべてのコントリビューションを削除します。イベントは、同じ拡張IDとコンテンツハッシュで登録されたワーカーだけに送られます。

DOMを操作する補助機能、MarinaraのAPIの呼び出し、親側のイベントへのアクセス、任意のネットワーク通信はいずれもありません。iframeはメッセージを検証し、流量を制限します。ハートビートの監視機構が、応答しないワーカーや無限ループに陥ったワーカーを終了させます。

## ページ全体の互換ランタイム

設定項目の多いツールや複数の手順をたどる作業でも、推奨する方法はコントリビューションのプロトコルのままです。複雑な拡張機能でも、パネルの要素を段階的に差し替え、自身の状態を拡張機能ごとの非公開ストレージに持たせられます。

ホスト側のセレクターでボタンを挿入する、Reactの内部構造をたどる、任意のオーバーレイを書き込む、同一オリジンの`/api`ルートを呼び出す。こうした作りの既存のレガシーパッケージは、安全なランタイムではそのままでは動きません。コントリビューションのディスクリプターと、範囲を絞った仲介役の機能へ移植することをおすすめします。

互換性の都合でどうしてもホストのページが必要な場合、External Extensionは`full_page_access`を要求できます。`PersonalExtensionInjector.tsx`は、承認されたそのリビジョンを、同一オリジンのscript要素と任意のスタイルシートとして読み込みます。コードはasync関数の中で実行され、識別、ログ出力、非公開ストレージ、管理されたタイマー、クリーンアップの登録を備えた小さな互換用の`marinara`オブジェクトを受け取ります。ページのグローバル変数はそのまま使えますが、それこそがここで要求している権限です。

ページ側のローダーは、コードを呼び出す前に`id`、名前、コンテンツハッシュをランタイムのメタデータと照合します。サーバーはスクリプトとスタイルシートの要求ごとに、ハッシュの完全一致、有効状態、入手元が外部であること、権限、2つのゲートのポリシーを別途検証します。ゲートを閉じるとレコードは無効になり、ランタイムのポーリングが挿入されたノードを取り除き、可能な範囲でクリーンアップを行います。ただし、完全な信頼で動いたページ側のコードがすでに引き起こした副作用まで取り消すことはできません。そのため画面上の案内では、再読み込みが必要になる場合があると警告します。

`kind: "marinara.extension"`を持ち、`capabilities`が明示されていないレガシーなインポートには、`full_page_access`が割り当てられます。新しい形式の書き出しでは、空の配列であってもcapabilitiesの項目を必ず書き出すため、安全なパッケージが再インポートで分類し直されることはありません。

## Serverランタイム

Server側のコードは、プロセス内でimportするのではなく、独立したNodeプロセスで実行します。Nodeの権限モデルにより、ファイルシステム、ネットワーク、子プロセス、ワーカー、ネイティブアドオン、WASI、インスペクターの機能は拒否されます。子プロセスはさらに、次のいずれかの内側で動きます。

- macOSのSeatbelt
- LinuxのBubblewrap(PID、ネットワーク、IPC、マウントの各名前空間を分離)

サンドボックスに渡されるのは、最小限の環境変数、小さなV8ヒープ、アプリのファイルなし、サーバーの秘密情報なし、そして専用の一時フォルダー内にある行区切りで上限つきのプロトコル用ファイルです。使えるのはログ出力、拡張機能ごとの非公開ストレージ、管理されたタイマー、クリーンアップの登録だけです。メッセージ数の割り当てと専用のハートビートファイルにより、プロトコルの大量送信と無限ループを抑え込みます。

Nodeの権限と`node:vm`は多層防御の1つであって、セキュリティ境界そのものではありません。OS側の独立したサンドボックスは必須です。Windows、Android、`bwrap`のないLinux、そのほか対応していないプラットフォームでは、Server Extensionsを有効にできません。

## 検証

次を実行します。

```bash
pnpm check
pnpm regression:extensions-security
pnpm regression:professor-mari-shell-sandbox
pnpm smoke:ui
```

セキュリティの回帰テストでは、2段階のゲート、ハッシュ完全一致による無効化、不透明オリジンのワーカーの形、上限つきでハッシュに紐づくコンテキストスナップショット、ホストへのコントリビューションの検証とクリーンアップ、ページ全体のルーティングと同意が外部の拡張機能に限られること、レガシーパッケージの分類、環境変数の除去、ファイルシステムとネットワークの拒否、非公開ストレージ、サンドボックスが使えないときにフェイルクローズすることを、いずれも証明する必要があります。
